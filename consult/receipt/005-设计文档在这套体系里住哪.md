## 一 · 👤 **O166：补充 ⑧ 设计类**（Q1）

### 1.1 专业实践依据

参考 [videojs/decisions/README.md](https://raw.githubusercontent.com/videojs/v10/561a2f2778f7eba93cee13f256719a12fec8f3a4/internal/decisions/README.md)：

**Decision docs（决策文档）**：
- 记录**单个具体选择**（one specific choice）
- 短小（通常一页）
- 状态永远是 `decided`

**Design docs（设计文档）**：
- 规定**架构/功能/子系统**（architecture, feature, subsystem）
- 前瞻性、通常更长
- 状态：`draft` → `decided` → `implemented` → `superseded`
- **关键关系**：**一个设计文档常常产生多个决策文档**

### 1.2 裁定内容

**新增 ⑧ 设计类**：
- **定义**：架构/功能/子系统的技术规约
- **载体**：`package-info.java`（包内）+ 生成索引 `DESIGN_INDEX.md` + 跨包设计文档
- **状态**：草案 → 裁定 → 实现 → 作废
- **与 ③ 关系**：⑧ 设计生成 ③ 决策（一个设计可能产生多个裁定）

## 五 · 👤 **O172：跨包设计容器**（Q5）

### 5.1 问题

- 草案说"在顶层策略文档里手工登记一行"
- 但顶层策略文档 = 规定**文档体系规则**本身
- ⇒ 跨包设计**本体**没有家

### 5.2 专业实践依据

**Java 项目标准实践**（调研结论）：
- 根 package-info.java = 项目概述 + 顶层架构 + 跨包设计
- 子包 package-info.java = 具体模块职责
- docs/ = 长篇架构文档（可选）

**优势**：
- ✅ 跨包设计在代码里（跟着代码动，编译即同步）
- ✅ 生成器自动抽到 DESIGN_INDEX.md
- ✅ 符合 Java 惯例
- ✅ 统一真相源（所有设计都在 package-info.java）

**劣势**：
- ⚠️ 根 package-info 可能较长（30 个包 + 36 条跨包设计）
- ⚠️ 不适合"特别详细的跨包设计"（需要图/表/长篇说明）

### 5.3 裁定

**跨包设计分两层**：

#### 5.3.1 简洁版（必须）

**载体**：`src/main/java/com/dddgn/alice/package-info.java`（**根 package-info.java**）

**内容**：
- 一行一条（设计名称 + 涉及包 + 一句话说明 + 决策编号）
- 36 条跨包设计的简洁列表

**类标**：⑧ 设计

**维护**：🔴 手写（你审核）

**格式**：
```java
/**
 * Alice —— Minecraft Forge 1.20.1 服务端权威 AI 玩家模组
 *
 * <h2>项目架构</h2>
 * <p>见 README.md</p>
 *
 * <h2>跨包设计</h2>
 * <ul>
 *   <li><b>事件总线</b>（event ← listener, core）：
 *       全局事件分发机制，支持异步监听器。O123</li>
 *   <li><b>区域授权</b>（region/authz ← job, action）：
 *       统一授权检查入口。O456</li>
 *   <li>...（36 条）</li>
 * </ul>
 * <p>详细架构说明见 {@code docs/CROSS_PACKAGE_DESIGN.md}</p>
 *
 * <h2>包结构</h2>
 * <ul>
 *   <li>{@link com.dddgn.alice.action} —— 执行面</li>
 *   <li>{@link com.dddgn.alice.job} —— 作业层</li>
 *   <li>...</li>
 * </ul>
 */
package com.dddgn.alice;
```

#### 5.3.2 详细版（可选）

**载体**：`docs/CROSS_PACKAGE_DESIGN.md`

**内容**：
- 长篇架构说明
- 架构图/时序图
- 详细设计决策

**类标**：⑧ 设计

**维护**：🟡 手写（按需创建）

**格式**：
```markdown
## 事件总线架构

**涉及包**：`event`, `listener`, `core`  
**主责包**：`event`  
**决策编号**：O123

### 设计说明

[长篇架构描述]

### 架构图

[图片或 ASCII 图]

### 相关决策

- O123：事件总线选型
- O124：监听器注册时机
```

#### 5.3.3 登记表

**载体**：顶层策略文档（`DOC_REFACTOR_DRAFT.md`）

**内容**：手工登记表，记录"这个设计跨了哪些包"

**格式**：
```markdown
| # | 设计名称 | 涉及包 | 主责包 | 决策编号 | 设计文档位置 |
|---|---------|--------|--------|---------|-------------|
| 1 | 事件总线 | event, listener, core | event | O123 | 根 package-info §跨包设计 |
| 2 | 区域授权 | region/authz, job, action | region/authz | O456 | 根 package-info §跨包设计 |
| ... | ... | ... | ... | ... | ... |
```

**门禁**：
- 登记表 vs 根 package-info 一致性
- 涉及的包必须真实存在
- 主责包必须有 package-info.java

### 9.2 查阅路径

| 场景 | 路径 | 用时 |
|------|------|------|
| 看跨包设计 | DESIGN_INDEX → 项目级设计 → 根 package-info | ≤2 次点击 |
| 看包设计 | DESIGN_INDEX → 搜索包名 → package-info | ≤2 次点击 |
| 看统计 | DESIGN_INDEX → 底部统计 | ≤1 次点击 |
| 找设计关联的决策 | DESIGN_INDEX → 模块设计 → 相关决策 | ≤2 次点击 |

### 9.3 生成规则

**生成器**：`tools/check-design-index.sh`（增强版）

**抽取逻辑**：
1. 抽取根 package-info.java 的跨包设计清单
2. 遍历所有 package-info.java
3. 每个包抽取：
   - 首段摘要（第一个 `<p>` 标签内容）
   - 子包列表（扫描子目录）
   - 相关决策（抽取 O### 编号）
4. 生成统计
5. 逐字节比对（门禁）

### 9.4 门禁检查

**check-design-index.sh 增强项**：

| 检查项 | 失败 = 红 |

| ✅ 登记表中的"涉及包"真实存在 | ⛔ |
| ✅ 登记表中的"主责包"有 package-info.java | ⛔ |
| ✅ 核心 14 件必须有 package-info | ⛔ |
| ✅ 子包有 package-info 的，父包也必须有 | ⛔ |
| ✅ 生成 DESIGN_INDEX.md | ⛔ |

## §1 对「LLM 决策层任务队列提案」的评价

### 1.1 提案是什么（摘要，**引用原文要点，不作抽象**）

| # | 提案要点（`DECISION_LAYER_DESIGN.md §7.1`） |
|---|---|
| 1 | **LLM 维护一个任务队列**，含三段：**当前任务** / **后续任务列** / **最终任务目标（最终状态）** |
| 2 | **最终态是持久目标**：决定做完一堆任务后 bot 最后应处于什么状态 —— 可以是**待机**，可以是**一直持续砍树**，**由玩家决定** |
| 3 | **实际做过哪些任务、什么顺序，要落文件** ⇒ 让 LLM **不遗忘已经做了什么** |
| 4 | 场景（砍树原例）：斧子耐久没了 ⇒ LLM **向队列插入"获取工具"任务** ⇒ **先问玩家**是否允许去指定容器取 ⇒ …… 直到**达到终态**或**终态不可达 ⇒ 待机** |
| 5 | 作者提出的关键问题：**LLM 到底在什么时候被触发做一次队列管理？** 以及**玩家交互怎么设计** |

### 1.2 ✅ 做得对的地方（6 条）

| # | 好在哪 |
|---|---|
| **1** | ⭐ **`TaskSpec` 不接受自由文本** —— 这是"表单是唯一真值"的具体落地，且**加了硬规则**：`precondition` 或 `successCriterion` 不可判定 ⇒ **不许入队**（原文："否则队列就是给循环发牌照"） |
| **2** | ⭐ **`REACH_STATE` / `MAINTAIN` 两型分开** —— 「一直在砍树」和「走到某处」**不是一类东西**；这个区分是整份提案**最关键的一刀** |
| **3** | ⭐ **触发点显式化 + "任务正常推进时零调用"** —— 直接回答了作者的关键问题，且给了一个**可测判据**（"`MAINTAIN` 稳态可以几小时不叫它"） |
| **4** | ⭐ **§9「队列不得绕过」权限** —— **队列是数据，不是授权**（这条很关键） |
| **5** | ⭐ **§12「与既有决定的关系（不得冲突）」** —— 防止它长成**第七个"到处是红线"** |
| **6** | **§13「明确不做」+ §14「可先做的临时缺口」** —— 有边界，且能**先拿走近乎无风险的那部分** |

### 1.3 ⚠️ 隐藏坑一：**"能保证"被放在了错误的位置**

**⇒ 原文（`DECISION_LAYER_FINAL_FORM.md:137`）：**

> **§7 三条防乱派/防空转的机制（**这是"能保证"的全部来源**）**

**⇒ ⚠️ 但表里那四条机制（准入校验 / 进展契约 / 循环检测 / 陈旧复验）**全部是"事后刹车"。**

**⇒ 而作者的项目口径是（`survey` 累积）：**

```
「一次长作业自主闭环，全程不需人插手」
```

**⇒ 刹车能保证什么、不能保证什么：**

| | 刹车能保证 | 刹车不能保证 |
|---|---|---|
| **不循环** | ✅ | |
| **不空转** | ✅ | |
| **能完成任务** | ❌ | ⚠️ **它只能"诚实地失败 + 待机"** |

**⇒ ⭐ 所以：**

> **§7 保证的是「**不会坏**」，不是「**能成功**」。**
> **"能成功"的保证在别处 —— 在**每个 `TaskSpec` 的 `successCriterion` 真的可判定**上。**

**⇒ 而这一条**已经被项目自己证明很难**（`D-345/D-346`）：**

> `32` 的追取上限**比它自己的作用域还小**（`MineJob` 作用域半径 = `SCAN_RADIUS 24` ⇒ 直径 **48 > 32**）
> ⇒ **自己挖出来的产物被自己的上限永久退休**（`retire reason=too_far`）
> ⇒ `gained < minedCount` ⇒ **FAILED `product_not_collected`**
> **⇒ 这是一个"纸面上可判定、在**世界里**却判不定"的例子。**

**⇒ 勘测侧建议（未拍板）：**

| 建议 | 内容 |
|---|---|
| **a** | `§7` 标题改成「**不会失控**的全部来源」（而非"能保证"） |
| **b** | **另立一节**："能保证闭环"的全部来源 = **每个 `successCriterion` 必须有一条"世界事实对账"路径**（像 `WorldModLedger.dropStale` 那样的方法） |

### 1.4 ⚠️ 隐藏坑二：**"队列陈旧"的对策只覆盖条目级，不覆盖终态级**

**⇒ 原文（`§7.4`）：**

> **队列陈旧**（世界变了，队列还按旧的走）⇒ 每条目执行前**重验前置条件**

**⇒ ⚠️ "重验 `precondition`"只解决**条目级**陈旧，不解决**终态级**陈旧。**

**⇒ 举例（用砍树原例）：**

```
终态 = MAINTAIN（一直砍这片林）
    ↓
玩家中途把这片林砍光 / 改了区域
    ↓
⚠️ 每个条目的 precondition 依然成立（"取工具"和"林里有没有树"无关）
    ↓
⇒ 队列会一直跑，但终态其实已经不可达
```

**⇒ 提案**其实有对策**（"终态不可达 ⇒ 待机"），但关键是**"终态不可达"怎么判定**。**

**⇒ 这是一个**新的可判定性问题**，而且比条目级难：**

| 层 | "可达"的判据 | 现状 |
|---|---|---|
| **条目级** | `precondition` 可判定 | ✅ 提案已解决 |
| ⚠️ **终态级 `REACH_STATE`** | "还能不能到" | ✅ **可复用寻路结论**（`UNREACHABLE`） |
| ⚠️ **终态级 `MAINTAIN`** | ⭐ **"不变量还能不能维持"** | ❌ **今天没有判据** |

**⇒ 勘测侧建议（未拍板）：**

> **`§5` 触发点应加一条：**"终态不可达"要成为一个**能被检测的事实**，而不是靠 LLM 判断。**
> **且分两型：`REACH_STATE` 用寻路结论（现成）；`MAINTAIN` 用**不变量检查**（要新做）。**

### 1.5 ⚠️ 隐藏坑三：**"问玩家"的链条没有上限**

**⇒ 看作者原例的链条：**

```
斧子坏 → 问：能去容器取吗？
   ├─ 不允许 → 结束队列 → 待机
   └─ 允许 → 去取
        └─ 取不到 → 再问：能搜索材料自制吗？
             ├─ 不允许 → 待机
             └─ 允许 → LLM 自行编排（材料获取 / 制作）
                  └─ ⚠️ 做不出来 → ？（提案未写这一层）
```

**⇒ `§7.3-D` 有 `escalationCount`（升级计数），但**没有说"升到顶之后怎么办"**。**

**⇒ 勘测侧建议（未拍板）：**

> **升级链必须有**终点**：`escalationCount >= N` ⇒ **强制 `END_QUEUE` + 待机 + 如实登记原因**。**
> **⇒ 对齐 `PermissionGate` 那条既有原则：「绝不让'没批准'变成'卡死'」。**

### 1.6 对作者三问的勘测侧看法（**非裁定**）

| # | 作者的问 | 勘测侧看法 | 理由 |
|---|---|---|---|
| **1** | 先做单目标+两条链，还是先做通用队列框架？ | ⭐ **先做单目标 + 两条链** | `D-345/D-346` 刚证明：**一个"看起来简单"的 `successCriterion`（收集产物）就藏着一个真缺陷**。**通用框架会把这类缺陷的排查面放大 N 倍** |
| **2** | 按不变量类别设默认策略（而非每次问）？ | ✅ **同意** | 这就是 `PermissionGate` 现成的形状（能力名 → 四档 + `always` 持久化） |
| **3** | 终态两型是否区分？ | ⭐ **必须区分** | `REACH_STATE` 有终点，`MAINTAIN` **没有"完成"这个概念**；混在一起会让"完成了没有"这个判据失效 |

### 1.7 §1 小结

> **这份提案的**结构**是对的。**
> **⚠️ 但它把"能保证"押在了**刹车**上，而项目这两天的经历证明：**
> **真正咬人的不是"跑不停"，是"**纸面上可判定、世界里判不定**"。**
> **⇒ 所以它缺一节：**每个 `successCriterion` 的"世界事实对账"路径。****

## §2 对「后面的高级任务能否靠这几天的经验加速」的答复

### 2.1 作者的问题（原文收档）

> 「这个项目一开始，我只是根据已知信息和设想来推进的这个项目，我会让主工作流做，有问题就修，
> 乱七八糟地搞了半天项目，**现在我才摸出来大模型的上限**，放着不管，只让大模型做出一个一个的功能，
> **方向偏的太严重了**，感觉这几天工作一直是在**重定义、细化、修复**，
> 你说后面我们要做的很多高级任务，**能够靠这几天的经验来加速研发吗**」

### 2.2 ⭐ 先回答：**能，但加速的不是"写得更快"，是"少走回头路"**

**⇒ 作者说的"重定义、细化、修复"，本质是同一件事：**

| 作者说的 | 真实做的事 |
|---|---|
| **重定义** | 发现**两个不同的东西共用一个词**（可回收性 / 安全 / 保护区） |
| **细化** | 把一个模糊概念拆成**可判定的形状**（`TaskSpec` 的 `successCriterion`） |
| **修复** | 发现"**纸面上可判定、世界里判不定**"（`D-345/D-346` 的追取上限） |

**⇒ ⭐ 三者有一个共同点：**

> **它们都在补**「可判定性」。**
> **⇒ 而项目的验收口径「一次长作业自主闭环，全程不需人插手」，**唯一的要求就是可判定**。**

**⇒ 所以"能不能加速"取决于：**

> **这两天的经验，有没有变成**能复用的判据**？**
> **还是只是"这次修好了"？**

### 2.3 ✅ 已经变成可复用的（会持续省时间）

| 模式 | 已固化在哪 |
|---|---|
| **先红后绿** | 已是惯例（`D-345` → `D-346` 就是这么走的） |
| **反向对照**（拆掉消费者 ⇒ 判据必须变红） | 已是习惯（多处这么写） |
| ⭐ **词的红线**（一个词管两件事 ⇒ 必然误伤） | **作者这两天自己发现的**，但**尚未固化成检查项** |
| ⚠️ **"纸面可判定 ≠ 世界可判定"** | ⚠️ **刚出现第一次**（`D-345/346`），**尚未变成纪律** |

### 2.4 ⚠️ 还没变成的（下次还会咬）

**⇒ 最关键的一条：**

> **「这个东西叫什么」和「这个东西是什么」没分开。**
> **⇒ 这两天的重定义，**一半是命名问题，一半是真设计问题**，而**它们混在一起处理**。**

| 事 | 是命名问题 | 是真设计问题 |
|---|---|---|
| 可回收性一词四义 | ✅ 命名 | — |
| 保护区是父类 | ✅ 命名 | — |
| **安全区必须显式注册** | — | ✅ **设计**（不能从几何推断） |
| **提权 = 搭和挖** | — | ✅ **设计**（靠黑名单控风险） |
| **斜向上升缺一格** | — | ✅ **设计**（动作集完备性） |

**⇒ ⚠️ 混在一起的代价：**

> **命名问题**很便宜**（改词、加注释），但它消耗的**讨论时间**和真设计问题一样多。**
> **⇒ 这两天的"累"，很大一部分是**在命名问题上花了设计问题的时间**。**

### 2.5 ⭐ 所以答复分三层

#### 第一层：**能 —— 如果每个高级任务开工前先问三个问题**

**⇒ 勘测侧建议把这三个问题固化成**开工前置检查**（成本极低）：**

```
① 这次涉及的概念，有没有和别的东西共用一个词？      （词的红线）
② 这条任务的"成功"，能不能用世界事实对账？          （可判定性）
③ 它要用的每个动作/权限，今天的信封里有没有？        （形状完备性）
```

**⇒ 每一个都对应项目**已经踩过的坑**：**

| 问题 | 对应踩过的坑 |
|---|---|
| ① | 可回收性 / 安全 / 保护区（**两次**） |
| ② | `D-345/D-346`（追取上限 < 作用域直径） |
| ③ | 斜向上升缺一格（`D-336` 才补） |

#### 第二层：**不能 —— 如果任务是"新领域"**

**⇒ 因为这几天的经验，全部来自**一个领域**：**

> **"bot 在一个已知世界里，做一件有明确终点的事"（砍树、挖矿、走路）。**

**⇒ 而作者说的高级任务（AE 操作、工作站、魔法仪式）**不是这个形状**：**

| | 砍树 / 挖矿 | AE / 工作站 |
|---|---|---|
| **目标** | **世界里的一个状态** | ⚠️ **一个菜单里的一个槽位** |
| **成功判据** | 产物进背包 | ⚠️ **配方跑完 + 产物对** |
| **世界事实** | 方块、掉落物 | ⚠️ **菜单内容、容器内容、流体** |

**⇒ ⭐ 所以那类任务的"可判定性"要**重新建立**，这几天的**结论**不能直接搬。**

#### 第三层：⭐ **但有一件事能搬，而且是最值钱的**

**⇒ 这两天反复做的其实是一件事：**

> **把一个"人脑里清楚、代码里模糊"的东西，变成**一个能红的判据**。**

**⇒ 这个方法**与领域无关** —— 它就是能带走的东西。**

**⇒ 而它的具体形态，已经用出来了：**

```
"我感觉这里有风险"  →  "造一个夹具，让它在现状下必须红"
                    →  "修到它绿" + "拆掉消费者，让它再红"
```

**⇒ 这套东西在 AE 任务上一样能用：**

> **"bot 能不能正确写样板" ⇒ 造一个样板，让它在现状下必须失败。**

### 2.6 ⚠️ 对「方向偏得太严重」的诊断（勘测侧看法）

**⇒ 诊断对，但**结论可以更准**。**

**⇒ 偏的不是"方向"，是"**没有验收判据的方向**"。**

**⇒ 证据：这几天的每一次重定义，都不是因为"功能做错了"，是因为：**

> **"这个功能做完了没有"——答不上来。**

**⇒ 而一旦有了判据（`D-347` 运行账那种），"方向偏"就**自动被兜住** —— 因为偏了它会红。**

**⇒ ⭐ 所以：**

> **不需要"先想清楚整个方向再做"。**
> **需要的是"**每个功能都有一条能红的判据**"。**
> **⇒ 有了这个，方向会自己收敛 —— 因为偏的方向**跑不出绿的判据**。**

### 2.7 §2 小结

> **这两天的"重定义 / 细化 / 修复"**不是浪费**，但它的价值**不在"修好了什么"**，在于：**
>
> **作者从"让大模型做功能"，开始问"**这个功能做完了没有，谁能证明**"。**
>
> **⇒ 第二个问题一旦开始问，**加速就自动发生了** —— 因为它砍掉了"做了一半又重做"的那部分。**
>
> **⇒ 至于"能不能靠这几天经验加速高级任务"：**
> **判据层的方法能带走（大头）；领域层的结论带不走（AE/工作站要重来一遍）。**
> **⇒ 所以真正该投资的，是把**方法**固化成**开工前置检查**，而不是指望"这次学到的结论"能复用。**

## 1. ⭐ 设想一：视觉作为**只读语义标注器**

### 1.1 用户原话（逐字）

> 「其实使用 **API 原生的识图通道**，让项目也兼容**限制的视觉识别**也是个方案，**
>  不是一个基础功能**，但是很有意义，现在项目**没办法结构化识别一个复杂结构，他甚至认不出来建筑**，
>  但是**在需要的时候**让 bot 的 LLM **做一次视觉识别**，就能获取很多信息并加以利用，
>  我让 bot **看看我修的建筑**，bot 就真正的**能给建筑给出评价**，
>  或者在野外**遇到某些遗迹或者特殊结构**，即使**扫描方块从知识库得不到结果**，也能**报告给玩家**。」

### 1.2 ⚠️ 必须先切开：**这不是 C 路线**

`docs/INTERACTION_LAYERS_COMPARISON.md` 里的三条路线（A 接口直写 / B 菜单协议 / C 视觉识别）
讨论的是**交互方式**。用户这条**不是 C 路线**，差别是结构性的：

| | C 路线（如外部报道的纯视觉 agent） | ⭐ 用户这条 |
|---|---|---|
| 视觉的角色 | **唯一的输入**（所有信息从像素来） | **补充的输入**（结构化事实仍在） |
| 谁在用 | 整个 agent 主循环 | **某一个时刻的某一次调用** |
| 频率 | 每帧/每秒 | ⭐ **按需、低频** |
| 失败后果 | 什么都做不了 | ⭐ **退回原有能力**（没视觉照样跑） |

**⇒ 准确命名：「带外视觉 / 按需观察」。**

### 1.3 项目今天的感知边界（**已核实**）

| 感知方式 | 能回答什么 | 边界 |
|---|---|---|
| `InterfaceScanner` / `GridDiscovery.scan(menu)` | "这个菜单里有什么" | 只能到**容器/槽位**层级 |
| `MineCandidateSource` / `TreeScanner` | "附近有没有我要找的目标" | **只认注册过的方块/标签** |
| `MineMenuCheckTask`（菜单构建） | 扫 25³ 立方体 | **只找它被要求找的东西** |
| `decision/MachineMap.java`（生成 `docs/MACHINE_MAP.csv`，**59 行**） | "这个方块属于哪类工作站" | ⭐ **表驱动，只认登记过的** |

**⇒ 结论：项目的感知是「按目标查表」，不是「理解场景」。**

**⇒ 用户举的三个例子，全都落在同一个缺口：**

| 例子 | 今天会怎样 |
|---|---|
| "看看我修的建筑" | ⛔ **无解** —— 没有"建筑"概念，扫出来就是一堆方块坐标 |
| "野外遇到遗迹" | ⚠️ **能扫到方块，但不知道那是什么**（组合不在知识库里） |
| "特殊/复杂结构" | ⛔ 同上 —— `MachineMap` 只认登记过的机器 |

**⇒ 三个共同点**：
> **全是「语义缺失」，不是「数据缺失」。**
> 方块 id 有、坐标有 —— **缺的是"这一堆方块意味着什么"。**

### 1.4 ⭐ 所以视觉的价值是「给数据加一层意义」

```
今天： 一堆方块坐标  →  （知识库查不到）  →  ⛔ 结论：未知
                            ↓ 加一次视觉调用
        一张截图      →  "这是一座中式庭院"  →  ✅ 可以做评价 / 报告 / 记录
```

**⇒ 视觉在这里的角色是「语义标注器」，不是「导航仪」。**

### 1.5 ⚠️ 由此推出的一条硬边界

> **它只读，不写。视觉结果只进「汇报」和「对话」，不进「执行路径」。**

**⇒ 理由（三条，缺一不可）**：

| 理由 | 说明 |
|---|---|
| **像素不可验证** | "到底是石头还是阴影？" —— 无法用代码断言 |
| **"没看到" ≠ "不存在"** | 有遮挡、有渲染距离、有雾 ⇒ **bot 可能因为"那边看着是路"而走进断崖** |
| **看错了的后果不对称** | 评价说错了 ⇒ 无害；据此行动 ⇒ 可能致命 |

**⇒ 而且这条边界**让这个功能**几乎不需要新的授权讨论** —— 见 §1.6。

### 1.6 ⭐ 它天然落在 `survey/16` 的「**对话线**」上

`survey/16` §6 把 AI 的两条线分开：**对话线**（无需授权）/ **决策线**（走信封）。

| 用例 | 属于哪条线 |
|---|---|
| "看看我的建筑并给评价" | ⭐ **100% 对话线** |
| "遇到遗迹，报告给玩家" | ⭐ **也是对话线**（报告 ≠ 行动） |
| "看到遗迹就自己去探索" | ⚠️ **必须走决策线**（信封 + 请示） |

**⇒ 与 `survey/16` §5.3 那条同构**：

| | 同一条纪律 |
|---|---|
| 恶作剧 | **提出来**，不直接做 |
| 视觉识别 | **看出来并说出来**，不直接据此行动 |

### 1.7 ⚠️ 三个未解问题（**登记，不判断**）

| # | 问题 | 为什么重要 |
|---|---|---|
| **a** | **谁来截图、截哪一刻** | 见 §2（这是实现形态问题，已由用户选定方向） |
| **b** | **成本边界** | 一次视觉识别远贵于一次文本决策（**图像 token**）⇒ ⭐ **它必须明确"按需"，而不是"顺便"**。⚠️ **判据：如果它会被"每 N tick 自动调一次"，那它就已经是 C 路线了（只是慢一点）** |
| **c** | **评价要不要留存** | "一次性事件"还是"可追溯记忆"？⚠️ **项目的 `WorldModLedger` 记的是"我改了什么"，不是"我看到了什么"** ⇒ 若要留存需新路径 |

### 1.8 🚩 证伪点

1. **若视觉结果被允许进入执行路径**（"我看到那边有个箱子，去开它"）⇒ 本报告 §1.5 的整个安全论证失效。
   **判据：`GoalAction` 的动作集里，是否会新增一个由视觉驱动的新动作。**
2. **若"复杂结构识别"能靠纯方块扫描 + 表驱动解决**（例如给 `MachineMap` 加结构定义）⇒ 视觉的价值大幅下降。
   **⚠️ 对"机器/工作站"成立（`MachineMap` 已有 59 行）；对"建筑/遗迹"不成立（**无边界、无标准、玩家自建**）。**

## 2. ⭐ 设想二：**bot 视角渲染（照相客户端）**

### 2.1 用户原话（含一次勘测员的自我更正）

> 「我**不是说渲染 bot**，我是说像玩家一样，**在 bot 的眼睛的地方当一个摄像机**，
>  从他的眼睛**按次数渲染世界**，这个有多麻烦」
>
> 随后用户裁定：
> > 「我感觉还是**借用玩家客户端做一次渲染**比较合适，这个功能**就登个记**吧」

> **⚠️ 勘测员更正**：第一次回答时**答歪了**（回答的是"渲染 bot 这个实体"，那个确实是零成本）。
> 用户要的是**从 bot 的位置渲染世界**，是完全不同的一件事。**本节按更正后的口径。**

### 2.2 为什么它比"渲染一个实体"麻烦得多（**架构层原因**）

MC 的渲染**硬绑在客户端**，有四个前提：

| 前提 | 含义 |
|---|---|
| **需要 GL 上下文** | ⛔ **专服没有 OpenGL** |
| **需要 `ClientLevel`** | 渲染读的是客户端那份世界副本，不是 `ServerLevel` |
| ⭐ **`Camera` 是客户端单例** | **同一时刻只有一个相机** ⇒ "按次数渲染"本质是"把这一帧借给 bot" |
| **需要渲染线程** | 客户端渲染线程与 tick 线程分离 |

**⇒ 前两条已经判了"服务端渲染"的死刑；后两条决定了实现形态。**

### 2.3 ⭐ 用户选定的形态：**借用玩家客户端**

```
  MC 服务端（跑 Alice mod）
       ↑
       │ ① 真玩家客户端登在服上（玩家就在旁边）
       │ ② 服务端请求："从 bot#3 的位置，朝东，渲一帧"
       │ ③ 客户端移相机 → 渲一帧 → 读 framebuffer → 发回
       └ ④ 服务端拿到图 → 转给 LLM
```

| 优点 | 说明 |
|---|---|
| ⭐ **不需要新进程、不需要第二个账号** | 用玩家现成的客户端 |
| ⭐ **正好覆盖最想要的用例** | "陪玩家看建筑" —— **玩家本来就在场** |
| ⭐ **有额外的陪伴感** | "bot 借用你的眼睛看"这件事本身就是互动 |

| 代价 / 约束 | 说明 |
|---|---|
| ⚠️ **玩家必须在场** | 玩家离线 ⇒ 拍不了 |
| ⚠️ **相机是共享的** | 若不做离屏 framebuffer，渲染期间**玩家画面会闪一下** |
| ⚠️ 需要**新的 C2S 包** | ⚠️ 会动 `AliceNetwork.PROTOCOL_VERSION = "1"` ⇒ **协议不一致时拒连** |

### 2.4 ⚠️ 一个必须一起钉死的设计前提：**一双眼睛还是 N 双眼睛**

| | 共享的眼睛（一个渲染源） | 每个 bot 一副 |
|---|---|---|
| 成本 | ⭐ **O(1)，与 bot 数量无关** | ⛔ **N 倍** |
| 后果 | 排队即可 | ⛔ **立刻撞上 `survey/10` 的多 bot 灾难**（N 个 bot 分一个 50ms tick） |

**⇒ 建议：**共享**。而"借用玩家客户端"天然就是共享的（只有一个客户端、一个相机）。**

### 2.5 三种"装眼睛的位置"对比（**供将来选**，非本报告主张）

| 位置 | 可行性 | 备注 |
|---|---|---|
| ⭐ **玩家客户端代理** | ✅ **用户已选定** | 玩家必须在场；需要新 C2S 包 |
| 独立无头/最小化客户端 | ⚠️ 可行但更重 | 玩家不在也能拍；⚠️ 多一个进程 + 账号 + 断线处理；⚠️ **`Camera` 单例 ⇒ 多 bot 要排队** |
| 服务端"软渲染" | ⛔ **不是渲染** | 服务端拿方块数据自绘 = **方块点阵**（无光照/无实体/无天空）⇒ **给不出"建筑评价"那种结果** |

### 2.6 🚩 证伪点

1. **若 MC Forge 已有"离屏渲染到 framebuffer"的成熟现成做法** ⇒ 玩家画面不闪、成本更低。
   **⚠️ 本报告未核实**（这是这个方案成本的最大不确定性）。
2. **若 `PROTOCOL_VERSION` 的变更成本被证明不可接受** ⇒ 那"借用玩家客户端"这条就要重新选形态。
3. **若渲染出的画面**质量**不足以支持"建筑评价"**（渲染距离、FOV、雾）⇒ 用例本身要重新定义。
   ⚠️ **这条只能实测。**

## 3. ⭐ 设想三：**带成本的回收性道具**（用户称之为"外挂"）

### 3.1 用户原话（逐字）

> 「不管怎么想，特别是整合包，**很多情况连玩家都做不到百分百存活**，现在**也不可能继续收紧风险管理策略**，
>  会让 bot 越来越束手束脚，我希望能给 bot 加一点'**外挂**'，我现在只举一个例子，
>  经验丰富的玩家会做**延时传送装置**，也就是玩家只要**低血量或者触发复活图腾，就自动传送回家**，
>  我想给模组加一些类似的**简单实现物品**，给 bot 一个**护身符**，能保证**死亡前传送回安全地点**，
>  当然**不是免费的功能**，可能**受游戏进度影响，材料成本之类的**，这是一类想法，
>  我们可以**从其他机制来提高 bot 回收性，但这种回收性要花费成本**，可以给 bot **定制一些物品**」

### 3.2 这个方向的本质：**换一个维度解决问题**

**⇒ 与 `survey/15` §4.4 登记的那条机制对得上**（"加守卫 → 守卫互相打架 → 为不误杀而设保守 ⇒ 覆盖面变小"）：

| | 收紧策略（今天在做） | ⭐ 加外挂（用户的想法） |
|---|---|---|
| 手段 | **减少 bot 能做的事** | **增加 bot 能承受的事** |
| 自由度 | ↓ 递减 | ↑ 递增 |
| 代价 | **无成本，所以会被滥用** | ⭐ **有成本，所以会自我约束** |
| 玩家感受 | "它越来越笨" | ⭐ **"它值得我为它投资"** |

**⇒ ⭐ 关键洞察：「要花成本」这个设计本身就是**正确性保证** ——**
**它把"放宽策略"的责任，从"我们拍脑袋决定"变成"**玩家用资源投票**"。**
**⇒ 这正是 `survey/16` §4（授权不继承玩家）的正确延伸**：
**不是"我们给 bot 更多权限"，是"**玩家决定给 bot 多少装备**"。**

### 3.3 ⚠️ 但用户举的这个例子，形态要改一处（**这是本节最重要的一条**）

「**死亡前传送回安全地点**」——**"死亡前"这个瞬间可能不存在。**

| 死因 | 从能死到死，有多少窗口 |
|---|---|
| 掉进岩浆 / 虚空 | **几 tick 或瞬间** |
| 摔死 | **落地那一 tick 结算** |
| 苦力怕贴身炸 | **一次结算**（可能满血秒） |
| 被一群怪围殴 | **几秒**（这个有窗口） |

**⇒ 所以"死亡前传送"不是一个可以可靠实现的判据。**

**⇒ ⭐ 建议改成：「死亡后回来」。**

| | 用户原设想 | ⭐ 建议形态 |
|---|---|---|
| 触发 | "死亡前"（**可能不存在**） | **死亡事件**（**一定存在，且是确定事实**） |
| 做什么 | 传送回家 | **在安全点复活** + 可选保留/找回装备 |
| 可靠性 | ⚠️ 可能来不及 | ✅ **一定生效** |

**⇒ 而"死亡"在项目里**已经有现成痕迹**（**已核实**）：**

```java
// BotManager.java:1568-1584
/** 假人死亡:打印死亡原因(死亡反馈) → 直接清除(暂时策略,后续可改为重生)。 */
@SubscribeEvent
public static void onLivingDeath(LivingDeathEvent event) {
    ...
    event.setCanceled(true); // 阻止原版死亡流程(掉落物/死亡动画),直接消失
    remove(bot);
}
```

**⇒ 注意它的注释：「暂时策略，**后续可改为重生**」。**
**⇒ 也就是说，"复活"这条路项目已经预留过了。**

> **⇒ ⭐ 用户想解决的核心痛点其实是「死了之后进度归零」**
> —— 而这**正是外部报道里那个 141 小时测试崩溃的同一件事**（见 §4）。

### 3.4 五条具体建议（**按性价比排序**，均为勘测建议、非裁定）

#### ⭐ 建议 1：**复活锚点 / 绑定护符**（用户那个想法的可靠版）

| 项 | 设计 |
|---|---|
| 效果 | 死亡时**在绑定位置复活**（而非默认出生点），可选**保留部分背包** |
| 成本 | 按进度：需要较稀有的材料（**早期拿不到**） |
| 玩家视角 | ⭐ "我给它投资了，它就不会因为一次意外全毁" |
| 为什么最值得 | ⭐ **它不改变 bot 的行为策略，只改变失败的代价** |

**⇒ 最干净的一条：放宽的是「敢做」，不是「能做」。**

#### ⭐ 建议 2：**召回符**（玩家主动，不是 bot 主动）

| 项 | 设计 |
|---|---|
| 效果 | **玩家**可以随时把 bot 召回身边（或召回到某点） |
| 成本 | 廉价，但**有冷却** |
| 为什么值得 | ⭐ **它把"救援"从 bot 的自动行为，变成玩家的交互** |

**⇒ 它不增加 bot 的自主权，但给了玩家一份掌控感** ⇒ 符合 `survey/16` §4（玩家权限最大）。
**⇒ 而且它天然是个"陪伴行为"**（"我把你叫回来"）。

#### 建议 3：**一次性保命**（血盾 / 紧急脱离）

| 项 | 设计 |
|---|---|
| 效果 | 低血量或受致命伤时，**自动触发一次短距脱离**（不是传送回家，是"闪开几格"） |
| 成本 | **消耗品** |
| ⚠️ 诚实边界 | **它救不了掉进虚空、救不了一次性秒杀** ⇒ **宣传成"多一次机会"，不是"保命"** |

#### 建议 4：**任务保险**（可能比物品更值）

| 项 | 设计 |
|---|---|
| 效果 | 任务失败时，**消耗资源自动重跑一次**（而不是把终态交给 LLM 重新决策） |
| 成本 | 每次失败消耗 |
| 为什么值得 | ⭐ **它直接放宽任务策略**：因为"失败"不再等于"白干" |

**⇒ 它和 `survey/16` §2 那个断点（失败事实传不到决策层）正好对上：**
**如果失败是可承受的，"看见失败"的紧迫性就下降了。**

#### 建议 5：**临时权限凭证**（机制，不是物品）

| 项 | 设计 |
|---|---|
| 效果 | 花资源购买**一次性的"危险动作授权"**（例如"允许本任务挖 32 格通道"） |
| 成本 | 按量计费 |
| 为什么值得 | ⭐ **把"放宽 D-076"从"全局改规则"变成"玩家按次购买"** |

**⇒ 最激进，但也最符合用户目标：不是"给 bot 加外挂"，是"让玩家可以为 bot 买外挂"。**

### 3.5 ⚠️ 一条设计原则（本节最重要的一句）

**"外挂"这个词有个陷阱：它可能让 bot 变成"不需要聪明的富二代"。**

| 风险 | 说明 |
|---|---|
| **玩家用资源把缺点全买了** | 那 bot 的**策略能力永远不会被逼着变好** |
| **它会掩盖真问题** | 例：`survey/16` §7 那个"一直在走但挖不动" ⇒ **有了复活，就更没人去查它为什么不挖了** |

**⇒ 设计原则：**

> ⭐ **外挂只能降低「失败的代价」，不能降低「失败的概率」。**

| ✅ 符合 | ❌ 不符合 |
|---|---|
| 复活锚点（死了能回来） | "自动绕开所有危险地形" |
| 任务保险（失败能重跑） | "自动选择最优目标" |
| 召回符（玩家叫得回） | "自动远离一切敌人" |

**⇒ 判据**：
> **如果这个物品让 bot 更"能扛" ⇒ 做；如果它让 bot 更"不会错" ⇒ 危险。**

**⚠️ 为什么这条重要**：`survey/15` §2 已经划过一次范围（"AI 自动设计产线"划出项目）。
**"自动规避"和"自动设计"是同一种病：把本该由能力解决的问题，交给一个规则表。**

### 3.6 🚩 证伪点

1. **若"死亡前传送"其实有可靠的触发点**（例如原版图腾触发的 Forge 事件在服务端可见）
   ⇒ 那 §3.3 的更正不必要。**⚠️ 本报告未核实该事件的可用性。**
2. **若玩家普遍把"能花钱买平安"视为破坏游戏体验**（付费/spend 就能规避风险）
   ⇒ 这条方向本身要重新权衡。⚠️ **这是口味问题，不是技术问题，勘测员不替玩家定。**
3. ⭐ **若"外挂"被用在"掩盖失败"而不是"承受失败"上** ⇒ §3.5 的原则就被违反了。
   **⇒ 判据：这个物品是否让某类失败**从报告里消失了**。**

### 4.2 ⭐ 对本项目最有价值的三条观察

**(a) 它自己总结出了「可回收性」原则**

> 模型自述：**"永远随身携带关键物品；永远不要再把它们存放在没有防备的箱子里。"**

| | GPT-6 Astra | Alice |
|---|---|---|
| 得出方式 | ⭐ **惨痛经验 + 自我总结**（死了、丢光了、才说出来） | ⭐ **事前写进代码的硬约束**（`MovementSpec` 构造器抛异常校验） |
| 谁保证下次不犯 | **它自己的记忆/上下文**（不保证） | **确定性层**（模型弱/不在，约束照在） |

**⇒ 这是 `survey/15` §1.3（"可回收性 = 底座/许可证"）的活证据。**

**(b) 它的自责命中"决策延迟 = 死亡"**

> 模型自责：**"我们上一个工具的使用愚蠢地结束了，15 秒的思考害死了我们。"**

| | 它的处境 | Alice |
|---|---|---|
| 决策周期 | **一次思考 = 15 秒** | 跨 tick，25 s 超时 + 看门狗 |
| 谁兜底 | **只有模型自己** | ⭐ **维生系统独立于决策层**（`SurvivalSystem.tick` 每 tick 跑，**不等 LLM**） |

**⇒ 这是 `survey/10` / `survey/16` 那条架构选择的**价值证据**。**

**(c) ⭐ "忙碌 ≠ 进展"——它给了 `survey/16` §7 一个更有说服力的说法**

> 报道：被苦力怕炸后，它**"spent the next several hours doing essentially nothing but farming potatoes"**
> （接下来几个小时除了种土豆什么也没干），Twitch 观众开始**催它快点**。

**⇒ 这是"任务丢失后退化到最低风险的重复动作"这一失效模式的真实样本。**

**⇒ 对照 `survey/16` §7 标记的那条**（`NO_PROGRESS` 检测的是「站着不动」而非「白忙一场」）：
- **从外部看**：它在忙
- **从结果看**：它什么都没得到
- ⭐ **这和"种了几小时土豆"是同一类症状**

**⇒ ⭐ 而且它给了一条更准的判据**：
**"种土豆"之所以被观众看出来，是因为观众有'这对通关没帮助'的常识。**
**⇒ 而在项目里，`progressSummary()` 的数字变化本身就能表达这件事：**
**`failed` 在涨、`mined` 不动 ⇒ 这就是"它在种土豆"。**

**⚠️ 而这个判断纯靠两个计数器的差，不需要任何智能。**

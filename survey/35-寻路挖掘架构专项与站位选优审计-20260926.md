## §4 ⭐⭐⭐ 站位选优审计（本文核心，全部实查）

### 4.1 发现①：**鱼骨其实已经在用"固定流程"了**（但只是参数装出来的）

- ✅ `FishboneJob:231`：`private static final MiningProfile CELL_PROFILE = MiningProfile.STANDABLE_ONLY.withPlacementApproach();`
  ⇒ `standableOnly = true` ⇒ `MiningPlanner.plan` 走**只调 `planDirect`（模式 A）**的分支，**不进模式 B / 兜底**。
- ✅ 代码注释逐字（`FishboneJob:484-486`）：
  「站位只用**现成可站**的格：**鱼骨的站位永远在身后一格** ⇒ 不需要规划器自己挖隧道
  （`STANDABLE_ONLY` = 计划 §5 方案 A 的"每格 1 次、距离恒 1 格"）」
- ✅ ⭐ **追簇也走同一档**（`FishboneJob:1120-1122` 用 `cellProfile()`）——
  矿是"暴露面"（邻接 `dugCells`）⇒ 站位也在刚挖完那一格，**1 格距离**。
- ⚠️ **但"固定流程"只体现在参数上**：`CURRENT` 失败后**仍然**走 `selectBest` → `exactTopK`
  （即**整套站位枚举照样会跑**）。

### 4.2 发现②：**模式 B（唯一昂贵的那部分）只有一个生产消费者**

`TUNNEL_ALLOWED`（唯一能进模式 B / 兜底的 profile）的全仓消费者：

| 位置 | 性质 |
|---|---|
| `MineJob:553-555` | ⭐ **真挖矿作业 —— 唯一生产消费者** |
| `BotManager:2157` | `/alice mine`；同行注释逐字自述「`D-119`：`/alice mine` 是**开发/测试入口**」 |
| `task/ClearGuardCheckTask` · `FluidMineCheckTask` · `MineRegressionTask` 等 | 全部是夹具 |

⇒ ⭐ **模式 B = 只有"挖埋藏矿"一个场景需要它。**

### 4.3 发现③：成本结构（`MiningPlanner` 631 行）

| 成员 | 行数 | 做的事 | 成本 | 消费者 |
|---|---|---|---|---|
| `planDirect`（模式 A 入口，`:218`） | 78 | CURRENT 快路径 → 枚举 → 排序 | | **鱼骨 / 伐木 / 收集 / `MineJob` 全都要过它** |
| `selectBest`（`:375`） | 31 | 现成站位选择 | | |
| `exactTopK`（`:482`） | 92 | ⭐ top-K 各自**全预算 A\***（`k = exactTopK() = 4`，可扩张至 `exactTopKMax = 10`） | 贵 | |
| `planTunnel`（`:296`） | 24 | | | **只有 `MineJob`** |
| `selectBestApproach`（`:406`） | 76 | 固定几何集，**每个候选一次全预算 A\*** | ⭐ 2.4 s（截断前） | **只有 `MineJob`** |
| `planEnterTarget`（`:320`） | 55 | 以目标格为终点破坏进入 | **1 次搜索**（便宜） | **只有 `MineJob`** |

- `StandingPointSelector.generateCandidates`（`:47-57`）：`(2·ceil(reach)+1)² × 3` + 下方深度。
  `reach ≈ 4.5` ⇒ **13×13×3 = 507 格**，**每格一次 LOS 校验**，且 ⚠️ **无短路**（三重循环跑完才 `return`）。
- ✅ 真机实测（`MiningPlanner:48-64` 注释逐字）：`candidates=13 planned=13` ⇒ 一次规划 ≈ 13 × 185 ms
  ≈ **2.4 s 卡在服务端 tick 线程**（≈0.4 TPS，持续 57.6 s）。`D-367` 另测单次 `MiningPlanner` ≈ **28 ms**。
- ✅ `MAX_APPROACH_PLANS = 3`（`:54`）是**临时止血**，注释逐字给的**回收条件** =
  「出现一次「前 3 个候选全失败、但更多候选能成功」的实测反例」⇒ 届时正确做法是
  **"把穷举摊到多个 tick"**，**不是把上限调大**。

  「**病灶** = 13 次搜索**每次都烧满 200 ms**；**廉价搜索** = 找到路的普遍 0–2 ms」

### 4.4 Baritone 的对比（✅ 本轮实拉源码核过）

Baritone `MineProcess.updateGoal()` 的全部：

```java
Goal goal = new GoalComposite(locs2.stream()
        .map(loc -> coalesce(loc, locs2, context)).toArray(Goal[]::new));
return new PathingCommand(goal, PathingCommandType.REVALIDATE_GOAL_AND_PATH);
```

- `coalesce` 只做一件事：**根据地形的局部事实决定"该把脚/头放进哪一格"**
  （`GoalTwoBlocks` / `GoalBlock` / `GoalThreeBlocks`），**产出一个 Goal**。
  至于"有没有站得住的地方、要挖掉几块"——**全交给 A\* 在搜索中自然发现**
  （`CalculationContext` 把破坏成本内嵌进边权）。
- ⭐ `GoalThreeBlocks` 是 `MineProcess` 的**私有内部类**（`extends GoalTwoBlocks`），
  `heuristic()` 还做了定制（y 差 ≤ −1 映射成 0 = "到了下面就算到了"）
  ⇒ **Baritone 的 Goal 是开放抽象，挖矿自己就地定义。**
- 而且 `rescan()` 在 `Baritone.getExecutor()` **独立线程**里跑。

> ⭐ **⇒ 一句话**：**Alice 的站位选优 = "站在外面枚举 507 格 + 排序 + top-K 各跑一次全预算 A\*"；
> Baritone = "把目标包成 Goal，让搜索器自己找站位"。这不是算法优劣，是架构路线。**

### 4.5 诊断：**模式划分是对的，粒度错了**

`MiningPlanner` 现在把**三种性质完全不同的问题**塞进一个类：

| | 问题 | 机制 | 本质 |
|---|---|---|---|
| **(a)** | "这格我现在能不能挖到" | `CURRENT` 快路径，一行 LOS（`:221-241`） | 局部判据 |
| **(b)** | "附近有没有现成站位" | 模式 A，507 格枚举 + top-K 精算 | **几何 + 成本** |
| **(c)** | ⭐ **"怎么挖过去"** | 模式 B / 兜底（破坏式 A\*） | ⭐ **寻路问题** |

- ⚠️ **根因：`(c)` 被放在挖掘层** ⇒ 所有"路径类"需求都得在这里**重新实现一遍**：
  预算（`WALK_BUDGET` / `MAX_APPROACH_PLANS` / `SearchTickBudget`）·
  摊 tick（**没做，只能截断**）· 优先级（`selectBestApproach:409` 用**直线距离**排序）·
  判据（`inconclusive` / `SEARCH_INCOMPLETE`）。
- ⭐ **这就是"噼里啪啦一大堆"的来源。** Baritone 用一句 `PathingCommand(goal, …)` 全部继承内核。

### 4.6 ⚠️ 公道话：**站位选优不是失误，是 `D-076` 红线的代价**

它买到了三件 Baritone 没有的东西：

1. **`MiningProfile.approach`**：**逐请求**授权（Baritone 是全局 `allowBreak` 开关）；
2. **LOS 硬前提**（`D-066`"看得到但打不到不算能挖"；Baritone 的 `MovementBreak` 不管这个）；
3. **精确 top-K 成本排名**（`Dijkstra` 成本场，`StandingCostEstimator`）。

⇒ **问题不在它重，在它跟"追簇"这种动态目标天生不合。**

### 4.7 追簇复杂度爆炸的**根因（一句话）**

> **追簇时"站位"是连续变化的（矿脉一层层往里长），而站位选优是"为单个静态目标设计的重武器"。**

每格新暴露的矿都要重跑那套 507 格枚举 + top-K 全预算 A\*。追簇 = 几十上百次重跑
⇒ 于是**不得不**加：额度（`oreBudgetPerUnit` 16→32）· "够不着不许永久否"（`chasePending`）·
游走段（`CHASE_APPROACH`，因为站后一格看不见第二层）· 补路（`withPlacement`/`A14`）……
**每一个都是"重武器太贵"的补偿**（`FishboneJob` 里"追簇"注释 **32 处**）。

反观 Baritone：`rescan()` 把新矿格塞进 `knownOreLocations` → **重算 Goal**。**零新增行为。**

⭐ **这与 `K2`（`Goal` 族只有 2 种）是同一件事的两面。** 缺口清单写 `GoalAdjacent` 缺失导致
"挖矿站位搜索各自重写一遍"—— **其实 `K2` 不只是"补个 Goal 类型"，它是解开追簇复杂度爆炸的那把钥匙。**

## §6 ⭐⭐⭐ 「到底啥任务用这个系统更有优势」（回答 N8）

### 6.1 地基：`D-066` 给了答案

- 📋 `D-066`（`AI_DECISIONS.md:1082`）**用户原话逐字**：
  「**可挖掘面真正参与选优不是作为参照评分，而是这个站位能挖掘的前提条件**」
- ✅ 该条语义逐字：「**视线 = 过滤（能不能挖）；距离/高度 = 排序（在能挖的站位里选哪个）**」
- ⭐ **所以站位选优回答的是「哪些站位能挖到这个目标」** = **LOS + 触及距离的联合判据，纯几何问题**。
- ⭐⭐ **`A*` 结构上回答不了这个问题**：它回答的是"能不能**站**到那一格"。
  Baritone 的 `MovementBreak` 是"**边走边挖**"，压根不问"我站这里能不能挖到那个目标"。
  ⇒ **这就是 Alice 站位选优 vs Baritone 的真正分界线**，不是"算法优劣"。

### 6.2 判定表

| ③ | **存在 ≥2 个有意义的接近方案且成本差异大** | 多方块可进入（埋藏矿） | 只有一个方向可行 |

1. ⭐ **应该退化，但现在的退化方向错了**：现在是"**换一批站位候选、再花一遍大钱**"；

5. ⭐ **超预算 ≠ 失败**（独立的一刀）：`MAX_APPROACH_PLANS` 截断与 `enter_target_over_budget`

## §8 「模式 B 冗余 + 模式 A 适配基地任务」的核对（回答 N9）

### 8.1 ✅ 判对：**模式 B 架构上是冗余的**

- B（`planTunnel:296` → `selectBestApproach:406`）= "在目标周围**固定几何集**里挑站位，
  然后各跑一次**全预算破坏式 A\***"。
- ⭐ 而 Baritone 用 **`coalesce` 决定脚/头进哪一格 → 一个 Goal → 一次 A\*** 完成同一件事（§4.4）。
  ⇒ **B 是把"寻路问题"搬到挖掘层又实现了一遍** —— 它绕开了内核的 Goal 抽象。
- ⭐ **B 的排序还很粗**：`selectBestApproach:409-410` 用 `GoalFoot(foot).heuristic(startFoot)` = **直线距离**排序；
  而 A 用的是 `StandingCostEstimator` 的 **Dijkstra 成本场**。⇒ B = "挖到直线最近的，然后希望"。

### 8.2 ⚠️ **必须修正的一处**：`成本特别大` 这个数 🟡 **已经过期**

| | 候选生成 | 排序依据 | ⭐ **精确 A\* 次数** | LOS 门 |
|---|---|---|---|---|
| **模式 A**（`planDirect`→`selectBest`→`exactTopK`） | `generateCandidates` **507 格**（全枚举，无短路） | ⭐ **Dijkstra 成本场**（1 次） | ⭐ `MiningTuning.exactTopK = 4`，可扩张至 `exactTopKMax = 10`（`MiningTuning:64-65`） | ✅ **有**（`isValidStandingPoint` 要求 `los.isClear()`） |
| **模式 B**（`selectBestApproach`） | 固定 **13 格** | 直线距离 | `MAX_APPROACH_PLANS = 3`（**已截断**） | ❌ **无** |

- 🟡 那个 **2.4 s** 是 **B 截断前**（13 候选 × 185 ms）的实测。
  **截断后 B 只跑 3 次精确 A\*，而 A 跑 4–10 次** ⇒ **"B 比 A 贵"今天已不成立**。
- ⚠️ **但** B 真正的浪费在另一处，而且更严重（见 8.3）。

### 8.3 ⭐⭐ 本轮新发现：**模式 B 没有 LOS 门**（A 有）

- **A**：`generateCandidates` → `isValidStandingPoint`（`StandingPointSelector:71-79`）**先要求 `los.isClear()`**
  ⇒ **根本不会为"站那儿也摸不到目标"的位置花钱**（`D-066` 的原意）。
- **B**：`selectBestApproach:455-460` **只挑成本最小的已到达路径，LOS 只存不算**：

```java
best = StandingPointEvaluator.of(foot, cost, cost,
        LineOfSightChecker.checkFromEye(level, StandingPointSelector.eyeAt(foot), target));
```

⚠️ **没有 `if (!los.isClear()) continue;`**。

- ⇒ 后果：`MiningPlan.visibility` 可能是 **false**，而
  **`MiningPlan.isExecutable()`（= `path.reached() && visibility.isClear()`）全仓只被日志用**
  （✅ 实查：仅 `MineTask:930`）⇒ **不构成任何门**。
- ⇒ ⭐ **所以 B 的实际形态是**：
  **「挖过去 → 到那儿才发现摸不到 → 运行期报 `LINE_OF_SIGHT_BLOCKED`」**
  （`MineBlockRunner:288-290`，`retryable=true`）→ `MineTask:409-411` `tryClearLineOfSight()`
  → `tryReplan`（最多 2 次）⇒ **先付挖路钱，再付清障钱，最后付重算钱。**
  A 永远不会：**A 在花钱之前就把这条路掐了。**
- ⇒ ⭐ **一句话**：**A 的贵在"枚举"，B 的贵在"事后"；A 的贵可以优化，B 的贵是设计漏的。**

### 8.4 ✅ 判对但需精修：**模式 A 的优势描述**

- ⚠️ N9 说"**不考虑能否到达所在格**" —— **不精确**：A **确实考虑可达性**
  （`exactTopK` 对候选逐个规划路径）。
- ✅ 但**精神完全对**，精确表述是**顺序**：
  > ⭐ **A 先用"可触及性"筛（便宜、纯几何），再用"可达性"排（贵、搜索）；
  > Baritone 只有"可达性"这一半，可触及性交给运行时。**
- ⭐ 这就是 `A*` **结构上给不出**的那一半（§6.1）。
  ⇒ **A 不是"更重的 Baritone"，是"多了一层 Baritone 没有的前置过滤"。**

### 8.5 ✅ 判对：**基地任务确实是 A 的主场**（含一条关键连接）

- ⭐ 理由干净：**基地任务 = 目标暴露 + 不需要为接近而挖 = A 的价值 − B 的成本**。
- ⚠️ **但要加条件**：站在机器旁边 1 格时，**`CURRENT` 快路径一行 LOS 就够**（`planDirect:221-241`）。
  A 的整套机器**只在"候选 ≥2 且接近成本差异大"时才赚回成本** —— 也就是
  **拥挤的基地**：管道、线缆、机器各个面、高低不一的地板、墙。
- ⭐⭐ **一条关键连接（本轮新发现，直接承接"工作站 / 槽位"设计）**：
  ✅ `LineOfSightChecker.samples`（`:60-72`）= **`target.getCenter()` + 6 个面心**
  （`(x+e, y+.5, z+.5)` = −X 面 … 六面各一）
  ⇒ **`successfulSample` 这个 `Vec3` 天然编码了"摸到的是哪个面"**。
  ⇒ ⭐ **机器槽位交互（进料面 / 出料面 / 正面对）需要的原语，这套 LOS 采样里已经有了** ——
  只是**没被暴露成 `Direction`**（`LineOfSightResult` 只有 `isClear`/`firstBlocker`/`successfulSample`）。
  ⚠️ **这是优化项不是缺口**：数据在，命名不在。

### 8.6 ⚠️ 一条必须说清的边界：**鱼骨根本不走 B**

- ✅ 实查：`FishboneJob:231` ⇒ `standableOnly=true` ⇒ `MiningPlanner:186` **A 一失败就 return**
  ⇒ **B 与兜底对鱼骨是不存在的代码**。
- ⇒ N9 的「**用于挖掘深矿成本过高**」要分开读：
  - **鱼骨（深矿长巷）** ⇒ **压根不用 B**，不受它影响；
  - **`MineJob`（单颗埋藏矿）** ⇒ 这才是 B 的**唯一**生产消费者。

### 8.7 ⭐⭐⭐ 综合结论（⚠️ 勘测侧观点）

> **把 A 留下、把 B 交出去。**

- ✅ **留 A**：它回答的是 `A*` 结构上回答不了的问题（"哪些站位能摸到目标"），
  而且它的**形状是对的**（先便宜地筛、再贵地排、只对有意义的做精确）。
  基地任务 / 机器交互 / 单暴露目标 **正是它的主场**，且随整合包拥挤程度**收益上升**。
- ⭐ **把 B 交给内核（Goal 化）**：B 做的本来就是 `GoalAdjacent` / `GoalGetToBlock` + 一次 A\* 的活；
  它现在自己实现，**代价是**：直线排序（粗）· 无 LOS 门（事后才发现）· 6 次搜索上限 ·
  以及**"授权载体"和"候选集"两个职责糊在一起**（§7.4 第 4 条）。
- ⚠️ **顺序建议**（省力优先，**不是**推倒重来）：见 `§9` 第三桶。

    ⇒ ⭐ **id 不变、顺序单独一处**，改顺序只改一行。

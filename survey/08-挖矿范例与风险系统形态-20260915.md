## 3. ★ 短线 → 长线 = 把「到达」从 5 格放大到 60 格

### 3.1 现状：三种挖掘模式**全部**假定"目标在够得着范围内"

| 模式 | 语义 | 依据 |
|---|---|---|
| `DIRECT` | 站在目标旁边（视线可达）直接挖 | `MiningPlanner.planDirect` |
| `TUNNEL` | 掏一段短通道过去 | `MiningPlanner.planTunnel`（`StandingPointSelector.tunnelCandidates`） |
| `ENTER` | 以目标格为终点，破入 | `MiningPlanner.planEnterTarget` |

**三者的深度上限来自同一处**：

```java
// StandingPointSelector.java:110（tunnelCandidates）
int maxDepth = (int) Math.floor(reach + 1.54D);     // reach = bot.getBlockReach() ≈ 4.5 ⇒ 6
// StandingPointSelector.java:56（generateCandidates 的正下方候选）
int belowDepth = Math.max(1 + BELOW_LEVELS, (int) Math.floor(reach + 1.54D));
```

⇒ **向下最多 5~6 格。全部是"微观到达"。**

| 场景 | 现状 |
|---|---|
| 地表矿石、洞穴壁上的矿 | ✅ 能挖 |
| 树干、脚边方块 | ✅ 能挖 |
| **深埋矿（Y=-59，头顶数十格石头）** | ❌ **任何模式都做不到** → `found_but_unminable` |
| 60 格外的另一个矿区 | ❌ **没有"走过去"的规划概念** |

**正面评价**：`found_but_unminable` 是一个**诚实的失败码**（系统没在骗人）。⇒ 这个缺口是**可观测**的，不是静默失败。

### 3.2 宏观到达确实不存在（复算）

全仓搜 `yLevel` / `targetY` / `descend` / `竖井` / `shaft` 在**规划层**：**无任何"下到某一 Y 层"的概念**。

**但写入原语已经存在**：

```java
// action/WriteReason.java:27
DESCEND_FOOT(Policy.EXPLICIT_TARGET, Action.BREAK, "向下挖掘"),
```

⇒ **工具在手边，但没人拿它规划一条下行的路。**

### 3.3 ★ 为什么"哪哪都接不上"：长度变了之后，所有缺口同时出现

| 长度从 5 格 → 60 格 | 冒出什么 |
|---|---|
| 要走几百 tick | → **中途会发生事**（G2：长作业中段静音） |
| 要挖穿石头 | → **要预算/授权**（`DESCEND_FOOT` 在，无人规划） |
| 挖到下层，坑壁是石头 | → **回不来怎么办**（= D-024 可回收性） |
| 半路背包满 / 镐子快坏 | → **失败归因**（G3：缺镐被说成"没矿"） |
| 从哪下？ | → **作业区**（审计排第一的承重件） |

⇒ **不是模块缺了，是这一段的入口被整个跳过了。**
**短线任务是"在你身边挖"，长线任务是"去某个地方挖" —— 你去不了那个地方，所以后面的全接不上。**

**这解释了审计为什么把"作业区抽象 + 进入作业区"排在承重件第一位**：对短线任务，"作业区"是个没用的概念（目标就在身边）；对长线任务，它是第一件事。

### 3.4 ★ 但短线的形状**已经存在**（不要重造）

```java
// job/mine/MineJob.java:135-170（tick 主体）
return switch (phase) {
    case SELECT -> select();
    case MINE -> mine();
    case COLLECT -> collectPhase();
    case DONE -> finish(Task.Status.DONE);
};
```

`SELECT → MINE → COLLECT → 循环` + `spec.quota()` 定额 + `attempted` 去重 + `progressSummary()`。

⇒ **"自动搜索附近目标 → 选一个 → 挖 → 收集 → 下一个 → 直到定额"这个形状，代码里已经有了。**
用户描述的目标形态**不是新设计，是给一个已有的循环补一个维度**（"下去"）。

### 3.5 远距离寻路：**不需要分层，需要"粗目标"**

**Alice 现状（复算）**：

| 项 | 值 | 位置 |
|---|---|---|
| 搜索预算 | `DEFAULT_MAX_NODES = 20_000` / `DEFAULT_MAX_MILLIS = 3_000` | `CorePathPlanner.java:14-15` |
| 状态区分 | `SEARCH_LIMIT` ≠ `UNREACHABLE` ≠ `GOAL_NOT_LOADED`，另有 `PARTIAL` | `PlanningStatus` |
| 执行侧滚动重规划 | `MAX_TICKS_PER_SEGMENT = 100` / `MAX_RESYNCS = 5` | `PathSession.java:39,45` |
| 前缀走完继续重规划 | K-1：`partial_prefix_done` → `replans++` | `PathRetryRunner.java:130-137` |

**Baritone 的做法**（§5.7 审计已记述）：**不做分层抽象**，做**滚动重规划**（每次只算一段，走到那儿再算下一段）。**远距离是"重复"出来的。**

**真正的差别在一处**：

| | 目标形态 | 后果 |
|---|---|---|
| Baritone | **粗**（`GoalXZ`："到 X,Z 附近就行"） | 不需要最终那一格在加载范围内 ⇒ 可以朝看不见的地方走 |
| Alice | **精**（`GoalFoot`：精确到某一格） | 必须已加载 ⇒ 超过区块半径直接 `GOAL_NOT_LOADED` |

**而"必须已加载"是硬约束**：

```java
// MovementContext.java:46（注释）
// 用 hasChunkAt（等价于 getChunk(..., FULL, false)）绝不加载区块
// MovementContext.java:50
public boolean chunkLoaded(BlockPos pos) { return level.hasChunkAt(pos); }
// AStarMovementSearch.java:52-53
if (!context.chunkLoaded(goal.goalFoot())) return PathPlan.failure(PlanningStatus.GOAL_NOT_LOADED, ...);
```

⇒ **用户提出的"先粗寻路、到达范围内再精准寻路"方向正确，但实现它不是造分层规划器 —— 是"把 goal 变粗"。**
滚动重规划的骨架**已经在跑**（`PathRetryRunner` + `PathSession` 分段），只是没人给它一个粗目标。

⚠️ **附带一个鸡生蛋**：`MineCandidateSource` 的"矿物透视"是在**服务端扫立方体**，但它**只能看到已加载的地方**。要看到远处的矿得先跑过去，要跑过去得先知道目标在哪。**这个结必须由外部信息解开**（玩家给区域 / 给 Y 层 / 给坐标）—— 这是"作业区"排第一的**深层原因**：它不只是"选个地方"，它是**打破这个循环的唯一入口**。

## 4. ★ 通道挖掘：两堵墙，不是一个能力缺口

### 4.1 第一堵墙 = **授权层**（挡在门口）

**D-076 寻路红线（现行表述）**：

> **寻路请求默认纯通行；破坏/放置只能由上层任务显式授权，并受预算闸门约束。**
> 1. **默认**：`PathRequest.of`（`TRAVERSE/DIAGONAL/ASCEND/DESCEND`）—— 不允许破坏、放置或特殊垂直移动；
> 4. **禁止**：寻路器自行挖穿地形；把 `SEARCH_LIMIT` 当作授权（D-004）；**把不可达当作"那就挖过去"**。

**而"边走边挖"的机制已经存在**：

```java
// PathRequest.java:43 —— 已存在，未被挖掘到达使用
public static PathRequest withWorldModification(String botId, BlockPos startFoot, BlockPos goalFoot,
                                                 String requester) {
    return new PathRequest(botId, startFoot, new GoalFoot(goalFoot),
            Set.of(TRAVERSE, DIAGONAL, ASCEND, DESCEND, PILLAR, FALL,
                   BREAK_AND_TRAVERSE, BREAK_AND_ENTER, PLACE_STEP_AND_TRAVERSE),
            SearchBudget.UNLIMITED, requester);     // ← 无限搜索预算（挖开了路就多了）
}
```

**它有活着的生产使用者** —— `WritePolicyMatrix` 的 **P-03 行**：

```
Row("P-03", Zone.EXTERNAL, Task.GATHERING, Obligation.REASON_DEFAULT,
    Set.of(MovementGrant.OF, MovementGrant.PURE_TRAVERSAL,
           MovementGrant.WITH_WORLD_MODIFICATION, MovementGrant.CLIMB_APPROACH),
    with(WORLD_MOD_REASONS, WriteReason.LINE_OF_SIGHT),
    "task/CollectDropsTask.java:254,360",
    "掉落物收集需调用方**显式** allowWorldModification（D-076）")
```

⇒ **「边走边挖」在 Alice 里已经实现、已经授权、已经在生产里跑 —— 只是授予了「捡掉落物」，没授予「挖掘到达」。**

**`MiningPlanner` 反面证据**（`PathRequest.miningApproach` 刻意禁用三种）：

```java
// PathRequest.java:59-66
Set.of(TRAVERSE, DIAGONAL, ASCEND, DESCEND,
       BREAK_AND_TRAVERSE, BREAK_AND_ENTER, PLACE_STEP_AND_TRAVERSE)
// ← 刻意不含 PILLAR / FALL / DOWNWARD（D-067 ㉘："避免挖矿时先搭柱子/跳下来"）
```

⇒ **它允许"挖穿"（`BREAK_AND_*`），但**不允许**"向下"（`DOWNWARD`）与"上升"（`PILLAR`）。** 挖竖井需要的恰好是被禁的那两个。

**为什么不能直接加一行**：D-076 第 4 条明令禁止"把不可达当作'那就挖过去'"，而这条禁令**有理由** ——
`withWorldModification` 今天能带出的 `PATH_ACCESS`（清障）是**瞬时承诺**（挖掉再还原）；**挖一条 60 格竖井是完全不同的承诺。**

### 4.2 第二堵墙 = **可回收性要求层**（放开授权后立刻撞上）

这三种走法在评估器里的判定（`RecoverabilityEvaluator.java:31-32`）：

```java
case PILLAR -> LOCAL_STEP
// "上升本身合法，但回程需要'拆掉自己放的方块'的授权与预算，规划期没验证 ⇒ 不给回程保证"
case BREAK_AND_TRAVERSE, BREAK_AND_ENTER, DOWNWARD -> LOCAL_STEP
// "破坏了地形且不恢复（账本只保证我方放置，不保证地形复原）"
```

而门槛表这边（`RecoverabilityPolicy.requiredFor`）：

```java
case FALL -> RecoverabilityLevel.PATH_REVERSIBLE;
default -> RecoverabilityLevel.LOCAL_STEP;        // ← 其余全部停在最低档
```

⇒ **能力和要求都躺在最低档，所以它们能通过 —— 能通过不是因为安全，是因为"没人要求它们更多"。**

**这一句就是"保证能回去的能力缺在哪"的答案**：

> **缺的位置在「要求端」。评估器已经诚实地说"这几种走法没有回程保证"，但门槛表没有据此拒绝它们。**

⚠️ **顺序纪律（硬性，违反会崩规划器）** —— `RecoverabilityPolicy` javadoc：

> 必须**先**让评估器能产出真实等级、**后**才抬 required。否则 `LOCAL_STEP < required` ⇒ **现有合法边也会抛**。

⇒ **不能先抬 required。** 必须**先有能产出 `SAFE_EXIT_REQUIRED` 的东西**（见 §5.4）。

### 4.3 「修建通道」语义**还在**，但按用户裁定**不可复用**

### 4.4 ★ 三种「承诺」—— 用户直觉的正确形式化

用户提出"通道挖掘"与"施工通道"是**两种行为**（一种只保证到达，一种要保证重复通行）。
**更准确的分界不是"能不能重复通行"，而是「世界被改了之后要不要还原」** —— 而 Alice 里**已经是三种**：

| 行为 | 对世界的改动 | 残留策略 | 现状 |
|---|---|---|---|
| **清障** `PATH_ACCESS` | 挖掉挡路的 | **要还原**（账本记账 + `RestoreScopeTask` 拆回） | ✅ 完整实现 |
| **通道挖掘** | 挖一条通路 | **不还原**，且**必须能自己走回来** | ❌ 只有 5~6 格微通道 |
| **修路** `RoadBuildTask` | 建持久结构 | **要保留**（这就是产物本身） | ⚠️ 已实现但不可复用 |

**三者是"同一个动作（在世界里开路）的三种残留承诺"** —— 而 `WritePolicyMatrix` 的 `Obligation` 字段（`TEMP` / `REASON_DEFAULT` / …）**就是表达承诺的地方**。

**这顺带解开一个结**：用户的可回收性（D-024 / D-151–153，两根轴已闭合）——
- 修路**不需要**它（路本身就是回来的方式）
- 清障**不需要**它（要还原）
- **它天生是给通道挖掘准备的** —— 而通道挖掘还没做

⇒ **它今天看起来像个没有消费者的孤岛，是因为它等的那个人还没出生。**

## 5. ★ 风险管控系统的形态：一把已有的尺子 + 一个空着的插槽

> **权威来源**：`docs/RISK_SYSTEM_DESIGN_DRAFT.md`（2026-09-10，主线已入库）。
> 本节**不重复**它，只做三件事：① 核实现状；② 把"能不能回去"翻译成它的语言；③ 指出缺的那一环。

### 5.1 它是「一张价格表 + 一把尺子」，**不是一个开关**

**草案 §1.1 原话**：

> **别把"风险"做成一个全局的总开关，要把风险做成"每条路上的价格标签"。**

**§1.3 论证了为什么不能做全局开关**（两条都硬）：

1. 同一片岩浆洞里**有的边安全、有的边致命**。因"附近有岩浆"全局切保守 ⇒ **在最需要能力的地方把能力关掉**（爬出洞可能正需要 parkour，而低风险模式恰好禁了 parkour）。
2. **模式翻转非单调**：降级 → 路径变长/无解 → 乱走 → 进入新风险 → 再降级 ⇒ **会抖**。

⇒ **用户最初构想里的"检测到风险 → 自动开启低风险模式"这半句需要改写**：不是切模式，是**给那几条边加价/加门槛**。

### 5.2 四件零件的现状（**逐件复算**）

| 零件 | 回答什么 | 符号 | 现状 |
|---|---|---|---|
| **① 度量单位** | "这一步提供了多少保证？" | `RecoverabilityLevel`（`LOCAL_STEP` / `PATH_REVERSIBLE` / `SAFE_EXIT_REQUIRED` / `EMERGENCY_EXIT_REQUIRED`） | ✅ 四级已定义 |
| **② 门槛表** | "这种走法**至少**要多少？" | `RecoverabilityPolicy.requiredFor` | ✅ 在工作 |
| **③ 评估器** | "这条边**实际**提供多少？" | `RecoverabilityEvaluator.evaluate`（逐边规则表 = 唯一裁决点） | ✅ **有真读者** |
| **④ 定价** | "贵不贵？" | 权重项（`f = g + h + r·w`） | ⚠️ 部分 |

**② 与 ③ 的关系**：`MovementSpec` 构造时**当场比较，不够就抛异常**（不是静默降级）。

```java
// RecoverabilityEvaluator javadoc
// "评估器说'这条边提供了什么保证'，策略表说'这种 Movement 要求什么保证'；
//  MovementSpec 构造时比较两者，不够就抛异常（不是静默降级 —— 规划期就该炸）"
```

**③ 有真读者的证据**（出现次数，排除定义文件本身）：

| 等级 | 出现次数 | 判定 |
|---|---|---|
| `LOCAL_STEP` | **35** | ✅ 有真读者 |
| `PATH_REVERSIBLE` | **41** | ✅ 有真读者 |
| `SAFE_EXIT_REQUIRED` | **2** | ❌ **无产出者**（仅在注释里） |
| `EMERGENCY_EXIT_REQUIRED` | **2** | ❌ **无产出者**（仅在注释里） |

⇒ **这不是死抽象。** 它是 **Alice 与 Baritone 差异①的落地处**，且**真的在拒东西**（`RecoverabilityPolicy` javadoc：FALL 是"本表唯一能真的拒东西的一条"，此前是 `0<0` 恒假）。

### 5.3 权力结构（用户问的"维生 vs 风险的边界"的答案在此）

草案 **§5.5**：

| 通道 | 角色 |
|---|---|
| **规划期准入 / 执行期事前** | 做**过滤 + 定价**，**不宣称否决权** |
| **`SurvivalSystem.shouldInterrupt`** | 维生**唯一且绝对的嘴**（硬否决在这里） |

> **预算是情报，不是否决。否决只有一处。**

**§1.2 的三句口诀**：

1. **风险系统是闸门**（决定要不要走）；
2. **维生系统是否决权**（决定还能不能继续走）；
3. **谁否决，都得说清"那该去哪"** —— 否则两方都保守，Bot 就原地不动。

⇒ **这就是风险系统的形态边界**：它**不否决**，它**过滤 + 定价 + 提供情报**（§3.4 反过度保护：拒绝必须产出机器可读的理由集，无解时**升级 LLM** —— 这正是 Alice 与 Baritone 的**真正分野**）。

### 5.4 ★ 缺的那一环：**反向可达性（逃生集）搜索** —— 全仓 0 命中

草案 **§3.2「进入时保守，逃离时激进」**：

> **大白话**：先算清"哪些地方我还能跑掉"，然后只在能跑掉的范围内小心走。跑的时候允许用全力。
> **工程含义**：以已知安全点为种子，用**激进包络**做**反向**可达性搜索得到"逃生集"；
> 正向搜索**只在逃生集内**用**保守包络**展开。
> **已有对应物**：`RecoverabilityLevel.SAFE_EXIT_REQUIRED` / `EMERGENCY_EXIT_REQUIRED` 的字面语义就是这条。

**复算**：全仓搜 `escapeSet` / `retreat` / `reverseReachab` / `逃生集` / `反向可达` → **0 命中**。

⇒ **这一环一点没做。而它就是"保证能回去"的实现形式**：

1. **倒着算**：从"我知道能活的地方"出发，**允许挖、允许搭**（怎么方便怎么来），算出**哪些格子还回得去** = 逃生集；
2. **正着走**：只在逃生集里走，且用**保守**手段（不许乱挖乱搭）。

**⇒ "能不能回去"不再是出发前的额外检查，而是搜索的结构本身 —— 你挖穿的每一格，事先已被证明在逃生集里。**

**⇒ 那两个"死值"不是废料，是给通道挖掘预留的插槽。它们空着，是因为"产出者"（反向逃生集搜索）还没出生。**

### 5.5 「风险管控系统的形态」一句话答案

> **风险管控系统 = 一个「随请求冻结的画像」+ 一张「逐边门槛表」+ 一个「逐边评估器」+ 一个「定价函数」
> + 两个搜索方向（反向算逃生集 / 正向只走逃生集内）+ 唯一一处否决（维生）。**

**运行时机三次**（草案 §5.1）：**规划期准入** / **执行期事前** / **执行期事后**。

| 时机 | 现状 |
|---|---|
| ① 规划期准入 | ⚠️ 有，`SurfaceMovementProvider` 内联（**无统一入口**，每个新守卫都要改 provider） |
| ② 执行期事前 | ⚠️ **最薄**：`PathSession.currentTargetStillValid`/`futureTargetBlocked` 判的是"**世界变了吗**"，**不含即死危害** |
| ③ 执行期事后 | ✅ `SurvivalSystem` |

⇒ **它看起来"几乎空白"，不是没建 —— 是「建了度量单位和门槛表，但没有给通道挖掘用的产出者，也没有随任务变的画像」。前半截有，后半截空。**

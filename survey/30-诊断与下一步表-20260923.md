## §0 一句话

> **卡住的原因不是"能力不够"或"方法不对"，是「方法太贵」。**
> 项目已有的纪律（判据 / 反向对照 / 门禁先红后绿 / 五档验证等级）是它**最强的资产**；
> 问题是**执行一次这种纪律的成本高到一个数量级**，于是好方法只能用得起在少数地方。
> ⇒ **要的是把方法的成本降一个数量级，不是加新方法。**

**⚠️ 勘测侧不主张"危机感"**：本文的所有建议都是**建设性**的，且**没有一条要求新能力**。

## §2 结论：需要新方法吗 → **不需要**

项目已有的是**高质量纪律**（判据必须能红 / 反向对照 / 门禁先红后绿 / 五档验证等级 /
`JobKindContract` 那种"产不出门禁就作废"的尺子）。外面同类项目连"编译成功 ≠ 客户端可用"都不写。

**问题不是方法不够，是方法的单位成本太高。** 高到只能用在高价值切片上（`Z1` 那种），
而 `lumber_job`、假绿夹具这类地方就一直烂着——**不是因为不重要，是因为"修它们要付一次完整代价"。**

> ⇒ **要的是把方法的成本降一个数量级。**

## §3 ⭐ 办法：把「优先级队列」换成「下一步表」（可满足性，不是排序）

### 3.1 队列为什么会乱（**已发生，不是假设**）

- `OPEN_ITEMS_LEDGER §11` 本身就是队列，**已被重排多次**（各节编号变动在 git 里）。
- `Z1 → Z2 → Z3` 那条链**不是优先级，是依赖** —— Z2 必须等 Z1，这不是判断。
- ⭐ **最要命的一条**：**优先级排序永远选不出最高杠杆的那件事。**
  例：`lumber_job` 幂等性（见 §4-1）是一个**没有任何前置条件、却能解锁大量东西**的小活；
  但它**不在关键路径上** ⇒ 在任何"优先级排序"里它都会排在 `Z2`/`Z3` 后面，永远轮不到。
  **排序会隐藏的，正是这种信息。**

### 3.2 换形状：Makefile，不是 TODO list

| | TODO list | **下一步表** |
|---|---|---|
| 顺序来自 | **判断** | **依赖求值** |
| 能否重排 | 能（所以会被重排） | **不能**（没有可重排的东西） |
| "下一步做什么" | 讨论结果 | **算出来的** |

**每一行五个字段（全部是"事实"，不是"判断"）**：

| 字段 | 内容 | 为什么它是事实 |
|---|---|---|
| `goal` | 一句话 | — |
| `precondition` | **能被某个现成工具求值**的前置条件 | 可当场求值 ⇒ 不会重排 |
| `scope` | 允许碰什么（见 §3.3） | 可计算 ⇒ 不会重排 |
| `exit` | **必须指名一个真实存在的门禁步**（先红后绿） | 名字存在性可查 ⇒ 不会重排 |
| `unblocks` | 它能解锁谁 | 可由依赖图推出 ⇒ 不会重排 |

**求值规则**：

```
ready = { 行 | precondition 求值为真 }
       − { 行 | scope 与在飞的行相交 }        ← 这就是"互相干扰"的可计算形式
next  = ready 中 unblocks 最多的（平手取 cost 最小）
```

### 3.3 ⭐ 范围限制的具象化：**项目已经发明过一次，只是只用在测试上**

`D-332` 的自测档位：

```
文档改动 →  只跑文档类门禁
单功能   →  single:<步名>
单模块   →  module:<模块名>
收口     →  CORE / 全量
```

**这是一套现成的"范围语言"**，今天只用在**测试**上。推广到**改动**上就是 scope 三件：

1. **允许改的包/文件集合**（`task/`？`pathing/core/`？只 `survey/`？）
2. **允许花的预算**（CORE 步数 / 会话数 / 客户端轮次）
3. **红线：不许碰什么**（`D-076` 授权面 / 换档逻辑 / `PROTOCOL_VERSION` …）

⇒ 于是"两项会不会互相干扰"**变成可计算的：冲突 ⟺ scope 相交**。
⇒ 用户问的"把范围限制具象化"，答案就是**这三件 + 一行相交判断**。

### 3.4 ⭐ 怎么保证"这一步就是现在最该做的"—— 用主工作流自己那把尺子

`survey/28` 的判据：**「产不出门禁 ⇒ 就是旧规划员改名」**。
所以这张表**必须自带门禁**，照 `JobKindContract` + `check-job-kind-contracts.sh` 的模子：

| 门禁规则 | 红了说明什么 |
|---|---|
| `precondition` 必须能被**现成工具**求值 | 它不是前置条件，是愿望 |
| `exit` 必须指向**真实存在的**门禁步（名字查得到） | 它不可验证 |
| 在飞的行**不许 scope 相交** | 两项互改同一处 ⇒ 干扰 |
| 声称的 `unblocks` 那些行**必须真的存在** | 依赖图已漂 |

**关键**：这张表**不发明新的真相源**，它 **join 现成的** ——
台账有条目、电池有步名、`check-all.sh` 有门禁名、`job/JobKindContract` 有契约表。
⇒ 它的"事实性"**从项目已有的四个生成视图那套纪律继承**（`survey/12 §3`：单一出处 / 产出勿手改 / **双向防漂移** / **解析不到就响亮失败**）。

### 3.5 "看一眼就知道" = 一条命令

```
$ tools/next-step.sh
next: fix-lumber-idempotency
why:  precondition ✓（无前置）
      scope: job/lumber/ + 电池 1 步
      unblocks: core-cache（D-352）⇒ CORE 260s → <30s
      conflict: 无
```

若 `ready` 有多项 ⇒ **全列出 + 打印选取规则** ⇒ "为什么是它"永远可见、可审计。**可审计，就不会乱。**

⚠️ **最小可用版本**：五列 + **一条**门禁规则（`exit` 必须指向真实存在的步）。跑起来、证明能红，再加其余。
否则这张表会变成第 350 条决策。

## §4 ⭐ 若要动，先动这三件（**候选，不是指令**）

> 选取口径：**① 无前置条件 ② 能直接变成判据 ③ 降低"方法的单位成本"**。

### 4.1 杠杆一（乘法级）：把 CORE 的反馈时间从分钟级打到秒级

**现状**（`docs/HANDOVER.md §1` 原文 + `tools/headless-battery.sh` 头注释复核）：
`D-352` 的 CORE 结果缓存**只写 PASS** ⇒ **只要 CORE 不是全绿就永不命中** ⇒ 每轮真跑 ≈ **4–5 min**。
而 `lumber_job` 是 CORE 唯一红项 ⇒ **永久不命中**。

**两条路（可并行论证，建议先做风险低的那条）**：

**路线 A（低风险，保真）—— 修 `lumber_job` 的三个症状**
已知三个症状（`HANDOVER` 原文）：`no_reachable_candidate` + `trunk_too_tall` + **`idempotent=false`**。
⭐ **其中 `idempotent=false` 已定位到一个高置信度的根因（勘测侧当场对比代码）**：

| | `MineTask` | `LumberJob` |
|---|---|---|
| 终态闩锁 | **有** —— `private Status terminalStatus;` + `return terminalStatus;`（注释逐字 **"D-175：终态幂等"**） | ⚠️ **查不到** —— 只有 `private String terminalReason`（字符串），**无终态状态闩锁** |

⇒ `RegressionBatteryTask:731-743` 对终态步任务**补 tick 两次**并断言 `idempotent=`，
**这正是 `D-175` 给 `MineTask` 加那个闩锁要防的事**。
⇒ **可试的最小修复：把 `MineTask` 的终态闩锁同样加给 `LumberJob`。**
⚠️ **待实测**：勘测侧只做了 grep 对比，**没跑过** ⇒ 先写判据（`single:lumber_job` 期望 `idempotent=true`）。
⚠️ 另两个症状（候选不可达 / 树干过高）是**功能性问题**，与闩锁无关，要单独查。

**路线 B（高收益，但需先验一个前提）—— 把缓存粒度从"整轮"降到"逐步"**
- 收益：一个红项不再使其余 40 步的缓存失效 ⇒ **直接拿到乘法级收益，且不需要等 `lumber_job` 修好**。
- ⚠️ **必须先验的前提**：**步与步之间是否真的独立**（`headless-battery.sh` 每轮从 `world-pristine` 重置世界，
  但若某步的结果依赖前序步骤写过的世界状态，逐步缓存就会**造成假绿**）。
- ⇒ **验证方法**：同一提交跑一次全量、再跑一次逐步缓存，**逐条判决必须完全一致**（`D-201` 附注一的"逐步 diff"纪律现成）。

⭐ **两条路都值得**：A 是"修一个真缺陷"，B 是"改一处基础设施"。**B 的收益更大，A 的风险更低。**

### 4.2 杠杆二：修假绿夹具（**假绿比红贵**）

- 已知：`restore_underfoot_safety` **是假绿**（`resetInventory` 把镐清掉了）；`HANDOVER` 已点名"几何重做"。
- ⭐ **为什么这条优先级高**：**红告诉你哪里坏了；假绿告诉你"哪里都没坏"，而其实坏了。**
  用户感到的"原地打转"，有一半来自这里。
- **建议的最小纪律**（项目已有，只是没全域执行）：
  **每条判据必须先用"反向对照"证明它能红**（`D-268⑤` 两次教训已经写明）。
  ⇒ 可武器化：**"证明它能红"这一步做成夹具自带的断言/门禁**，而不是靠人记得做。

### 4.3 杠杆三：把已有结论"武器化"（**零新设计，只把散文变成会红的东西**）

项目里有一批**已经想清楚但没有判据**的结论。把它们变成门禁，成本远低于新功能：

| # | 结论（已定） | 可武器化成的门禁 |
|---|---|---|
| 1 | ⭐ **底线不许进配置面**（`survey/12` 的"玩家开关几乎什么都控制不到" + 用户本轮裁定取消三档） | 断言 `RiskSwitches.KNOWN`（及其后继）**不含**底线类；底线类不出现在命令/配置面 |
| 2 | **必选 vs 可选守卫的分界**（用户本轮裁定；`D-333` 未完成的那一半） | 断言"必选"集合**不出现**在任何玩家可写入口 |
| 3 | **`TaskSpec` 的 `successCriterion` 必须有世界事实对账**（已落地 `JobKindContract`） | ✅ 已有，可作**其余武器的模板** |
| 4 | **`GoalNearXZ.around` 只许出现在允许层**（已落地 `check-far-goal-usage.sh`） | ✅ 已有，同上 |

⇒ **③④ 已经证明"武器化"这件事在项目里能做成。** ① ② 是同一形状的追加。

## 1.【要做】进度叙述：原料已就绪，而且**已经在快照里了**

### 1.1 事实

`Job` 接口**把进度叙述定成了契约**：

```java
// job/Job.java:24
/** 人类可读进度（终态与定期健康输出用），如 `logs 4/8 trees 1/3`。 */
String progressSummary();
```

两个真实实现（**是本项目仅有的两个生产 Job**）：

| Job | 输出 | 语义 |
|---|---|---|
| `LumberJob.java:243` | `"trees 3/8 logs 12/40 cleared=5"` | 产出型计数器 |
| `MineJob.java:185` | `"mined 2/8 failed=3"` | 产出型计数器（**连失败数都有**） |

**⭐ 而且它已经通过快照送进决策层了**：

```java
// DecisionSnapshot.java:139
node.addProperty("progress", current instanceof Job job ? job.progressSummary() : "");
// → 快照的 tree[0].progress
```

**⇒ 结论：进度叙述**不需要新写、不需要新抽象、不需要新协议**。它已经写好了、已经在快照里了。**

### 1.2 那"要做"的是什么

**⚠️ 只差一件事：读它的时机。**

| 层 | 今天 | 结果 |
|---|---|---|
| 决策层**主动问** | `DecisionSnapshot.build()` 时读 | ✅ 但**只有决策被触发时才发生** |
| 推送 | —— | ❌ **任务开始响一次、结束响一次，中间没有** |

**⇒ 缺的不是数据，是「有人定期看一眼」。** 这正是用户问的"ai 知不知道事情做到哪了"的准确答案。

### 1.3 ⚠️ 诚实标注：这里有一条**未闭合**的推断

**本报告没有确认** `Job.progressSummary()` 被读的**频率**在 `MineJob` 长循环里是否够用。
`LumberJob` 的一棵树是几十秒级，`MineJob` 的一个目标也可能是秒级
⇒ **阈值定多少，本报告不给建议**（那需要实测，见 §12 不虑）。

## 2.【要做】失败的**逐次**事实传不到决策层 —— 一个**具体**的断点

### 2.1 事实（已核实到行）

`MineJob` 的主循环是 `select() → mine() → select()`：

```java
// MineJob.java:256-283
private Task.Status mine() {
    Task.Status status = miner.tick();
    if (status == Task.Status.RUNNING) return RUNNING;
    ...
    if (status == DONE) minedCount++;
    else attemptFailures.add(new AttemptFailure(mined, reason));   // ← 只进内存列表
    ...
    finishedMinerNode = TaskNode.finished("MineTask", ..., miner, status);  // ← 快照会读它
    miner = null;
    phase = Phase.SELECT;
    return RUNNING;
}
```

**⚠️ 断点在这里**：`finishedMinerNode` **只被赋值，从来没有被重置**（全文件 `grep "finishedMinerNode = null"` **零命中**）。

```java
// MineJob.java:154-158  —— subTasks()，快照树的数据源
if (miner != null) { children.add(TaskNode.leaf("MineTask", ..., "cleared=" + miner.clearedBlocks(), "")); }
else if (finishedMinerNode != null) { children.add(finishedMinerNode); }   // ← 唯一读者
```

**⇒ 于是选择阶段（`miner == null`）快照里显示的是「上一个目标失败」，
而如果已经切到新目标（`miner != null`），`finishedMinerNode` 虽然还在，
但 `subTasks()` 走的是**第一条分支**（只给 `cleared=`），**失败事实就消失了**。

**⇒ 净效果**：`attemptFailures` 这个"试过几个、失败几次、为什么"的**完整事实**，
**只活在 `progressSummary()` 的那一行文本里**（`failed=3`），**没有结构化地进快照**。

### 2.2 为什么这条是【要做】

它是**用户原始问题的直接答案**：ai 想知道"我做到哪了、做得好不好"，
而"**试了 3 个目标全失败**"和"**刚选中第 4 个目标**"，在快照里**看起来可能一样**。

**⇒ 而且要改的地方极小**：`finishedMinerNode` 的**生命周期**（何时清）
—— **不是新字段、不是新协议、不是新抽象。**

### 2.3 🚩 证伪点

**若 `finishedMinerNode` 的"永不清空"是刻意的**（例如为了让"最后一次失败"一直可见）
⇒ 那"新目标在上面盖住了它"就是**渲染顺序问题**，不是生命周期问题。
**⚠️ 本报告无法分辨**（需要看设计意图或历史提交）。**⇒ 只标记，不断言。**

## 3.【要清】「驱动者」这个概念

### 3.1 用户原话（逐字）

> 「假如说我部署了一个**桌面级的 ai**……然后这个 ai 想要**通过我们的项目的接口，代替 LLM 层**，
>  在游戏里和玩家交互」

用户随后**当场修正**：
> 「**不对，有一点我纠正，不一定是完全替代 LLM，可能是其他兼容层**」

### 3.2 这条修正在架构上的含义

「替代 LLM」和「其他兼容层」是**两种不同的东西**：

| | 替代 LLM | ⭐ 兼容层（用户修正后） |
|---|---|---|
| 隐含 | 换一个更强的模型接到同一个位置 | **同一道缝，多个驱动者并存/切换** |
| 需要 | 只改配置（`LlmConfig.url`） | **需要"驱动者"这个概念** |
| 风险 | 单点替换，行为不透明 | 需要身份、需要审计、需要降级 |

**⇒ 本报告采用修正后的口径：这不是"换模型"，是"多驱动者 + 身份分层"。**

### 3.3 为什么必须"先想清楚"而不是"边做边想"

今天决策缝的形状**已经收敛**（细节见 §8），但**没有"驱动者"这个标识**：

```
今天日志： [Goal] decision_request trigger=... mode=... model=...
                                                      ↑ 只有模型名，没有"谁在驱动"
```

**⇒ 若将来同时有本地 LLM 和桌面 AI，出了问题分不清是谁干的。**
**⇒ 这不是"现在要改"，是"现在要知道将来必须有一个名字"。**

### 3.4 🚩 证伪点

**若最终只有一个驱动者**（用户自己那台桌面 AI，不再用云 LLM）
⇒ 「驱动者」这个概念**就是多余的抽象**，加了反而是负担。
**⇒ 所以这条是【要清】而不是【要做】——先想清楚，别先动手。**

## 4.【要清】授权：桌面 AI **不继承玩家的权限**

### 4.1 项目已拍板的红线（引用，非本报告新提）

| 红线 | 出处 |
|---|---|
| **授权信封 per-bot** | `survey/05` 拍板，用户 2026-09-16 重申 |
| **LLM 只能"请求"，不能"批准"** | `PermissionGate` 类注释（S3 请示层 / D-140） |
| **提权粒度 = 绑定「完成一个具体任务目标」为止** | `survey/05` |
| **有最高权限壁垒，无法决定的事直接失败** | 用户裁定 |

### 4.2 正确形态（一句话）

> **桌面 AI 是「一个比 LLM 更宽、但比玩家更窄的主体」。**
> 它能**发起**任务、能**请求**提权，但**批准权永远只属于玩家或配置默认值**。

**⇒ 桌面 AI 继承的是「信封」，不是「玩家身份」。**

### 4.3 ⚠️ 这条【要清】的理由

用户愿景里有一句很容易被误读的话：
> 「ai 想要……**在游戏里和玩家交互**」

**"和玩家交互" ≠ "以玩家身份行事"。** 若把这两件事混起来，
桌面 AI 一旦拿到玩家身份，`PermissionGate` 的整套设计（超时=拒绝、审计留档）
**会在一瞬间失效** —— 因为它会变成"自己问自己"。

**⇒ 这是整份报告里唯一一条"想错了会伤到根"的东西。**

### 4.4 🚩 证伪点

**若桌面 AI 就是玩家本人授权的唯一入口**（例如玩家不在游戏里，只通过桌面 AI 操作）
⇒ 那"请求 vs 批准"的分离在体验上会变成"自己跟自己对话"。
**⚠️ 这是真实的设计张力，不是可以忽略的边界情况。** 留待需要时再决。

## 5.【要清】陪伴性 = **触发源 + 提议动作**，不是权限

### 5.1 用户举的三个例子，落在**三个不同的层**

用户原话：
> 「bot 应该能够**主动跟随玩家**，**主动保护玩家**，甚至**对玩家做恶作剧**」

| 例子 | 它需要什么 | 撞规则了吗 |
|---|---|---|
| **主动跟随** | ⭐ 一个"关怀触发" | ❌ **没撞**：`FollowTask` **已有**（`follow on/off`，D-062 已迁新内核，保持 2 格、24 格失效） |
| **主动保护** | 跨 bot 感知 + 一个主动触发源（玩家受害） | ⚠️ 撞**"谁决定"**（触发源只有四类） |
| **恶作剧** | ⭐ **改世界 / 动玩家物品** | ⛔ 撞红线：`WorldModLedger` + 信封 + `PickupGate`（`FOREIGN` 默认 **ASK**） |

**⇒ 关键观察：三件里只有第三件真的是"规则 vs 陪伴"的冲突。**
**前两件根本不是规则问题，是"没有触发源"的问题** —— 而这类**最便宜、最不触红线**。

### 5.2 今天触发集合是什么（`GoalDirector`，已核实）

| 触发 | 来源 |
|---|---|
| `terminal:` | `BotSession.complete` 末尾 |
| `survival:` | 维生中断 |
| `event:` | 工具见底 / 卡住 / 掉血 / 可回收性失败（**4 类，见 §7**） |
| `idle:` | 空闲（`idleDecisionEnabled` **默认关**） |
| `operator:` | 玩家 `/alice instruct` |
| `manual:` | 夹具/玩家手动 |

**⇒ 陪伴需要的触发，全都不在这个表里**：
`player_moved_away:` / `player_hurt:` / `player_idle:` / `player_speaks:`。

**⭐ 而且这四个触发全都不需要放宽任何规则**，并且**自动继承既有的节流 + 单飞 + 看门狗**。

### 5.3 "恶作剧"该怎么办：**从"危险动作"改归为"一种请示的措辞"**

这是本轮讨论里**最有复用价值的一条判断**：

> **不要问"bot 能不能有恶意"，要问"bot 能不能提出一个玩家可能不喜欢的提案"。**

一旦这么换，它立刻变成**项目已有的东西**：

```
   AI 自己起的念头（"我想把他脚下的方块拆了"）
                ↓
      ⭐ 必须落成一个提议，不是动作
                ↓
      PermissionGate.request(capability, reason, options, defaultOption, timeoutTicks)
                ↓                                    ← 已有！
   玩家点"允许" ⇒ 做；不点 ⇒ 超时=拒绝
```

**为什么这个映射是对的**（三条，都可核实）：

| 理由 | 依据 |
|---|---|
| 恶作剧的**陪伴价值几乎全在"提议"那一刻**，不在"执行"那一刻 | 玩家看到"Alice 想把你脚下的方块挖掉（可撤销）。允许/拒绝"——**这个卡片本身就是陪伴感** |
| **拒绝权**正是让恶作剧变好玩的关键 | 朋友之间的恶作剧之所以不伤人，是因为存在"我可以让他停"的默契 |
| `PermissionGate` **已经支持任意 capability + 任意 options** | `request(bot, capability, reason, options, defaultOption, timeoutTicks)` —— 今天的用例是 `fetch_tool_materials`，加一个 `capability="prank"` **不需要改架构** |

### 5.4 ⚠️ 但"提议"这个**动作**今天不存在（这是与 §10 的交汇点）

`GoalAction` 的动作集（已核实，`VOCABULARY` 与 `parse()` 一致）：

```
start_job / stop_current / craft / maintain_tool / report_status / no_op
```

**⇒ 没有 `propose`。** 所以"AI 自发提议"**无处落脚** —— 这不是加配置能解决的，
而是**动决策层契约**（`GoalAction` 加新成员 + `VOCABULARY` 加一节）。

**⇒ 本条列【要清】而非【要做】**：先想清楚"提议是不是一等动作"，再决定要不要加。

### 5.5 🚩 证伪点

1. **若"提议"被实现成"让 LLM 直接调 `PermissionGate`"** ⇒ 那就绕过了 `GoalAction`
   的白名单校验（"未知动作一律拒绝"），**决策层的安全边界会开一个洞**。
2. **若玩家不在线** ⇒ `ASK` 的语义是**超时=拒绝** ⇒ 恶作剧永远得不到回应。
   **⚠️ 这正好是 `survey/05` 已经拍板的"玩家离线 ⇒ 前置资源进队列"的另一个面**，需要一起想。

## 6.【要清】两条线必须分开：**对话线** vs **决策线**

### 6.1 用户的愿景实际上是**两句不同的话，共用一个词**

| | 对话能力 | 决策能力 |
|---|---|---|
| 想做什么 | 像普通大模型一样聊天、答攻略、给建议 | 决定 bot 下一步做什么目标 |
| 今天的接口 | ❌ **不存在** | ✅ 存在（决策缝） |
| 桌面 AI 接管哪个 | **要新开** | **直接接缝** |

**⇒ 「桌面 AI 代替 LLM 层」实际上要接两根线，不是一根。**

### 6.2 为什么必须分开（理由是**项目自己已经拍板过的**）

用户 `survey/05` 的裁定：
> **「NL 只生成草稿，表单是唯一真值」**

**⇒ 如果把「聊天」和「发布任务」挤在同一条线上，就退回了"说一句就自由发挥"的老问题。**

### 6.3 建议形态

| 线 | 授权 | 说明 |
|---|---|---|
| **对话线** | ✅ **无需授权** | 只说话，不碰世界。玩家问攻略、闲聊——**桌面 AI 的主场** |
| **决策线** | ⚠️ **走信封** | 能提议，不能批准 |

**⇒ 两条线的信任级不同，但可以是同一个 AI、同一个声音。**
（"同一个声音、两个身份" —— 见 §12.3 的边界说明。）

### 6.4 🚩 证伪点

**若"聊天"被认为是决策层的一部分**（即：AI 在聊天里说的话被解析成任务）
⇒ 那就违反了 `05` 的拍板。**⇒ 判据：聊天的输出永远只进聊天，不进 `GoalAction.parse`。**

## 7.【要标】`NO_PROGRESS` 判据把"脚位在动"当成"有进度"

### 7.1 事实（已核实到行）

```java
// EventThresholds.java:253-255
int window = NO_PROGRESS_WINDOW_TICKS;                       // 默认 0 = 关
String progress = window <= 0 ? null : progressFingerprint(bot);   // ← ⭐ 短路，零成本
```

```java
// EventThresholds.java:286-299  —— 进度指纹
String job = BotManager.currentTaskProgressSummary(bot);
BlockPos foot = MovementHelper.footCell(...);
return task + "|" + job + "|" + foot.toShortString() + "|" + inventoryFingerprint(bot);
```

**⇒ 三个信号用 `|` 串成一个字符串比"整体是否相等" ⇒ 任何一项变了就算"有进度"。**

项目自己的注释也写明了这是**刻意的**：
> **"走路中的任务不会误报（脚位在变），真停滞的才会。"**

### 7.2 代价（这条是"标"，不是"判"）

**⇒ 一个"一直在走、但砍不动/挖不动"的 bot，永远不触发 `NO_PROGRESS`。**

而这**不是假想场景**，它是 `MineJob` 主循环的形状（§2）：
`select() → 走过去（脚位在变）→ 走不到 ⇒ 失败 → select() 下一个 → 再走过去……`

**⇒ `mined 0/8 failed=7` 的 bot，脚位一直在动，`NO_PROGRESS` 一声不吭。**

### 7.3 ⚠️ 本报告**只标记三条**，不判断、不建议

| # | 标记 | 为什么不能断言 |
|---|---|---|
| a | `NO_PROGRESS` 检测的是「**站着不动**」，不是「**白忙一场**」 | 这是**判据语义**问题，不是 bug —— 取决于设计想检测哪个 |
| b | `attempted` 集合（`withoutAttempted`）让同一目标不会重复试 ⇒ **候选耗尽后会自然终态** | 所以"不至于永远转"；**但"转多久才停"没人知道** |
| c | `maxTicks` 默认 `3600`（**3 分钟**）耗尽前，**决策层完全不知道** | 需要确认 `MineJob` 有没有内建"连续失败 N 次就放弃" |

**⚠️ 这三条本来是要"核实/审查"的，按用户指示留给主工作流。**

### 7.4 一处**勘测员自我更正**（按"只增不改"，记在这里）

**本报告 §7 的前身（同一轮对话里的口头结论）曾说**：
> "把那个指纹从只报警改成节流上报，进度感知就白送了"

**⇒ 这句是错的。** 核实后：
- `progressFingerprint()` 在 `window <= 0` 时**根本不执行** ⇒ **不是"白送"，是"半白送"**（实现现成，引擎短路）
- 而且**不该复用它做进度推送**：它是为"卡住检测"设计的（重、含背包哈希、每格 `ForgeRegistries.ITEMS.getKey()`）
- ⭐ **该用的是 `job.progressSummary()`**（轻、语义化、`Job` 契约保证）—— 见 §1

**⇒ 教训（本目录第四次同类"结论要自验"记录）**：
**"某段代码已经写好了 ⇒ 改一行就能用"是一个必须核实到执行路径的断言。**

## 8.【留口】决策缝的**替换点**在哪 —— **一行**

### 8.1 现状（已核实）

```
触发（终态/维生/事件/空闲） → 节流三闸 → fire() → LlmClient.askAsync(system, prompt)
                                                        ↑ ⭐ 唯一的外部调用
                                              pollResult() → GoalAction.parse(json, bot, menu, directed)
                                                              ↑ ⭐ 唯一解释处（白名单在这里）
                                              execute() → 只走既定入口
                                                  start_job → BotManager.assignJob(JobRequest)
                                                  stop_current → BotManager.stopTask
```

### 8.2 可替换性评估

| 层 | 换驱动者时要动吗 | 核实依据 |
|---|---|---|
| 触发与节流 | ❌ 不动 | `maybeTrigger` 与 provider 无关 |
| **请求发出** | ⭐ **唯一要换的** | `LlmClient.java:64 askAsync(systemPrompt, userPrompt)` → `Reply(ok, text, error, latencyMs)` |
| **解析与白名单** | ⛔ **绝不能换** | `GoalAction.parse` 未知动作 ⇒ `Refused`；菜单外 id ⇒ 拒绝 |
| **执行入口** | ⛔ **绝不能换** | `BotManager.assignJob`（J-6 后所有 `assign*` 都走它） |
| 请示 | ❌ 不动 | `PermissionGate`：超时=拒绝，LLM 无权批准 |

**⇒ 结论**：**"替代 LLM 层"在工程上的准确说法 = 把 `LlmClient` 换成一个 `DecisionProvider`。**
下游一个字都不用动。

### 8.3 三个具体缝（供将来参考，**现在不要动**）

| 缝 | 现状 | 备注 |
|---|---|---|
| **① 请求层** | `LlmClient.askAsync(system, prompt) → CompletableFuture<Reply>` | 换掉它就是换驱动者 |
| **② 协议层** | `POST {url}` + `{model, messages[]}` → `choices[0].message.content`（**OpenAI 兼容**） | ⭐ 好处：**任何能说 OpenAI 协议的东西都能当驱动者**（桌面 AI 起一个本地兼容端点即可） |
| **③ 配置层** | `LlmConfig`（`config/alice-llm.json`，**全局单例**） | ⚠️ 多驱动者时这里会撞（一个 url / 一个 key） |

### 8.4 ⚠️ 一个**要点明的**（不是问题，是特征）

`LlmConfig` **不只被 `GoalDirector` 读**：`EventThresholds` 也读它
（`grep` 结果：`GoalDirector` / `LlmClient` / `EventThresholds`）。

**⇒ 换驱动者前要确认 `EventThresholds` 读的是哪个字段。** 这是【留口】清单里唯一需要留意的点。

### 8.5 🚩 证伪点

**若 `LlmClient` 里藏了决策语义**（自己拼 prompt / 改菜单）⇒ "换掉它就行"不成立。
**目前看没有**：`systemPrompt` 由 `GoalDirector` 传入；`maxReplyChars` 截断在 `GoalDirector` 侧；
`LlmClient` 只管 HTTP + 解析 `choices[0]`。**⚠️ 但 `sendWithPathMatrix`（三条路径尝试）是 `LlmClient` 内部逻辑**，
换驱动者后需要确认它是"重试策略"还是"语义"，**本报告未判定**。

## 9.【留口】触发集合是**可扩的**（加触发不破契约）

### 9.1 事实

`GoalDirector` 的触发入口是**一组公开静态方法**，各自映射到一个 `trigger` 字符串：

```java
GoalDirector.onTaskTerminal(bot, kind, terminalReason) → "terminal:…"
GoalDirector.onEvent(bot, summary)                      → "event:…"
GoalDirector.onSurvivalInterrupt(bot, reason)           → "survival:…"
GoalDirector.tick(bot)                                  → "idle(…)"（默认关）
```

**⇒ 加一类触发 = 加一个 `onXxx` + 一个字符串前缀。**
**所有触发共用同一道节流闸（`minIntervalTicks` / `maxRequestsPerMinute` / 单飞 / 看门狗）**
⇒ **新触发自动继承全部安全护栏。**

### 9.2 ⚠️ 但有一条**已知的硬约束**（不是问题，是需知的）

**节流配额是全局共享的**：`maxRequestsPerMinute = 6`（默认）。

**⇒ 加"进度推送"这类高频触发，会与决策请求抢同一个配额。**
**⇒ 【留口】的含义**：将来加触发时，**判据不是"这个触发有没有用"，而是"它值不值得花 1/6 的分钟配额"。**

### 9.3 🚩 证伪点

**若将来需要"进度摘要"以高于 6 次/分的频率上报** ⇒ 那它**不该走 `GoalDirector`**
（决策层的配额），而应该走**独立的输出通道**（见 §10）。
**⚠️ 这个分叉点本报告不判定，只标出它的存在。**

## 10.【留口】AI **独立于决策的说话出口**（今天**完全没有**）

### 10.1 事实

**AI 今天只有三种"话"，全都是决策的副产品**：

| # | 话 | 触发条件 | 问题 |
|---|---|---|---|
| 1 | `report_status(note)` | **要等一次决策触发** | 不能主动说 |
| 2 | `PermissionGate` 请示卡片 | 请示时 | 走玩家 `SimpleChannel`（见 §11） |
| 3 | `GoalDirector.tell()` | 超时/失败 | 系统消息，不是 AI 说的 |

**⇒ 没有"AI 想说一句，就说一句"的路。**

### 10.2 项目自己的立场（引用，非本报告新提）

```java
// BotEventLog.java 类注释
"为什么是环而不是推送：LLM 不该每 tick 收到东西（成本 + 噪声）。
 确定性层把事件按类型塞进定长环，汇报时读它、阈值触发时读它。"
```

**⇒ 这个立场是对的**（防止噪声 + 防止烧钱）。**推论**：
"主动说话"**不能靠提高推送频率实现**，只能靠**新增一条低频、单向、独立于决策的输出通道**。

### 10.3 为什么列【留口】而不是【要做】

**因为它今天完全不存在，且不需要现在存在。**
【留口】的具体含义只有一条：

> **将来设计它时，它必须与 `GoalDirector` 的节流配额解耦**（§9.3），
> 否则"AI 主动说句话"会挤掉"AI 做决策"的额度。

**⚠️ 这条的代价**：新增 S2C 消息会动 `PROTOCOL_VERSION = "1"`（`AliceNetwork`）
⇒ **协议版本不一致时拒连**。这是【留口】必须记住的代价，**但不需要现在决定。**

### 10.4 🚩 证伪点

**若"主动说话"可以复用既有的 `TargetPacket` 式广播**（无新包）
⇒ 那协议变更的代价就不存在。**⚠️ 未核实。**

## 11.【留口】+【要清】请示通道对**非游戏内主体**是否可见

### 11.1 已核实的三条出口

| 出口 | 实现 | 到达谁 |
|---|---|---|
| ① 客户端卡片 | `PermissionNoticePacket`（S2C，`SimpleChannel`） | **装了 mod 的玩家客户端** |
| ② 聊天可点击按钮 | `broadcastChatRequest` + `ClickEvent.runCommand` | **游戏内玩家** |
| ③ 命令 | `PermissionGate.answer(server, id, option, scope, ...)` | **任何人只要能发命令** |

### 11.2 ⚠️ 这条为什么重要（**整套愿景的硬闸**）

**桌面 AI 不是玩家 ⇒ 它既收不到卡片，也不在游戏里看聊天。**

⇒ **如果桌面 AI 看不到请示，它就永远停在 `ASK = 拒绝`**（`PermissionGate` 的默认档）。
⇒ **§5.3 的"恶作剧即提议"、§6 的"两条线"，全都依赖这条通道。**

### 11.3 ⚠️ 本报告**未核实**的一点（诚实标注）

**出口 ③（`answer`）是 `public static`，理论上可从任意 Java 代码调用**——
但它今天**只被命令入口调用**。

**⇒ "能不能有一条非游戏内的答复路径"这个问题，本报告没有答案。**
**⚠️ 按用户指示，这属于"留给主工作流"的审查范围。**

### 11.4 【留口】的具体含义

**不需要现在加通道。** 只需要知道：

> **将来接桌面 AI 时，"请示的出口"是第一个要验证的地方**，
> 而不是"决策请求能不能发出去"（那个缝已经在 §8 核实过了）。

## 12.【不虑】现在**明确不用管**的四件（写下来是为了防止它们变成前提）

### 12.1 桌面 AI 的**延迟预算**

| 问题 | 为什么现在不管 |
|---|---|
| "桌面 AI 要跑在同一台机器上才够快吗" | **需要 RTT 实测**，今天**零数据**。而且决策层已经有 25 s 超时 + 看门狗兜底 ⇒ **不影响现有功能** |

**⚠️ 不虑 ≠ 不存在**：它**将来会成为**一个约束条件（决策层是"先观察后动作"的离散控制回路，
1 tick 延迟是固有属性 —— 这是项目已在 `D-038` 讨论过的）。

### 12.2 多驱动者**并发**

| 问题 | 为什么现在不管 |
|---|---|
| 两个驱动者同时想控制一个 bot 怎么办 | `GoalDirector` 已经是 **single-flight**（`state.pending != null` ⇒ `"busy:已有一个请求在飞"`）⇒ **今天就不会并发**；真要做多驱动者时再说 |

### 12.3 "AI 自己设计产线"

**已在 `survey/15` §2 明确划出项目范围**（用户定性"另一个项目的野心"）。
**⇒ 本报告不重复讨论，只做一个交叉引用。**

### 12.4 ⚠️ 一条**必须一起记住的边界**（不是"不虑"，是"别搞混"）

**桌面 AI 的"自由"与游戏内 bot 的"约束"不矛盾，因为它们是同一个声音的两个身份**：

| | 为什么自由 / 为什么受限 |
|---|---|
| **游戏外的伙伴**（陪你聊天、有自己想法） | 自由来自**"没有身体"** —— 说话不改变世界 |
| **游戏内的执行体**（要请示才能拆方块） | 约束来自**"有身体"** —— 改世界有代价 |

> **⇒ 不是"机甲 vs 束缚"，是"有身体就必须有可控性"。**

**⇒ 这条不是本报告的推论，是对用户自己那句话（"被困在执行规则当一个乖乖的 bot 的束缚里"）的重新表述。**
用户对约束的感受是**真实的**，但它的根**不在规则太多**，而在**"AI 的想法今天看不见"** ——
而"看得见"正是 §5.3 和 §10 要解决的事。

## 1. ⚠️ Baritone 的单开线程**不能照抄**：世界的权威性不同

### 1.1 Alice 的搜索是**同步主线程**，因为它**直接读权威世界**

```java
// CorePathPlanner.java javadoc（原文）
// "同步主线程执行：采集实时世界 → Movement-aware A* → PathPlan。
//  本类不含执行逻辑，也不修改世界；执行交给 R4 的 PathSession。"
```

而搜索确实**直接读 `ServerLevel`**：

| 读点 | 位置 |
|---|---|
| `chunkLoaded(pos)` → `level.hasChunkAt(pos)` | `MovementContext.java:50-51` |
| 方块状态 / 流体状态 | `SurfaceMovementProvider` / `MovementHelper`（全文多处） |

### 1.2 ⭐ 为什么"Baritone 能开线程"在 Alice 不成立

| | Baritone | Alice |
|---|---|---|
| 形态 | **客户端 mod** | **服务端 mod（假人）** |
| 它读的世界 | **客户端的 world 副本** | **权威 `ServerLevel`** |
| 读脏了/读旧了 | **无所谓**（客户端本来就滞后、且会被重同步） | **会按错误的世界做决策** |

⇒ **把搜索搬到 worker 线程 = 并发读一个正在被主线程修改的世界。**

| 风险 | 说明 |
|---|---|
| **① 撕裂读** | 主线程每 tick 改方块，worker 读到**不一致的中间状态** |
| **② ⚠️ 触发区块加载** | 读到未加载区块会**同步加载/生成**（`AStarMovementSearch:45-51` 注释明说这是它被硬拒的理由）—— 那**在主线程外不安全** |
| **③ 非线程安全** | MC 的服务端 chunk 系统**不是**为并发访问设计的 |

**⇒ "对齐 Baritone 开线程"在 Alice 里不是同一个动作 —— 它要额外付一笔 Baritone 不用付的代价。**

**✅ 好消息**：异步搜索的**必要前提已经有一半** —— `MovementContext.java:46` 的注释自述
「用 `hasChunkAt`（等价于 `getChunk(..., FULL, **false**)`）**绝不加载区块**」。
⇒ **"绝不加载区块"这条纪律本身就是"允许在别处读"的前提。**

## 2. ★★ 多 bot 的灾难：**N 个 bot 分一个 50ms tick**

### 2.1 今天的调度是**串行**的

```java
// BotManager.onServerTick（TickEvent.Phase.END，主线程）—— BotManager:951 / 964
for (BotSession session : BOTS.values()) {
    session.bot().syncPlayerChunkTicket();
    checkEntityTickProgress(session);
    HazardState hazard = SurvivalSystem.tick(session.bot());
    session.tick(hazard);              // ← 每个 bot 的规划/搜索在这里同步阻塞
    PermissionGate.tick(session.bot());
    MenuLifecycle.tick(session.bot());
    EventThresholds.tick(session.bot());
    GoalDirector.tick(session.bot());
}
```

**⇒ 所有 bot 在同一个 tick 内依次跑完，谁在中间阻塞，后面的全等。**

### 2.2 ⚠️ 所以"灾难"今天是**必然**的，不需要等线程

**量级推算**（⚠️ 非实测）：一个 bot 的逃生预检最多 `PRECHECK_MAX_MILLIS = 20ms`（`SurvivalSystem:180`），
而逃生真正的规划用 `UNLIMITED`（`survey/09` 补遗 A）。设一个 bot 吃 **40ms**：

| bot 数 | 后果 |
|---|---|
| 1 | 它自己这一 tick 迟 40ms，**没别人受害** |
| 5 | **另外 4 个 bot 这一 tick 全被挤掉** |

**⚠️ 而"被挤掉"不是"变慢"，是「这个 tick 什么都没做」** —— 它们的任务推进、维生判决、
输入设置**全部延后一 tick**。

### 2.3 ★ 对正在危险中的 bot，"漏一 tick"= 死

| 情形 | 漏一 tick 的后果 |
|---|---|
| 淡水里溺水 | 少一 tick 上浮 ⇒ 空气继续掉 |
| 岩浆里 | 少一 tick 中断/逃生 ⇒ **直接被烧** |
| 悬空下落中 | 少一 tick 输入 ⇒ 落点错位 |

**⇒ 这是级联的**：

```
A 的规划拖慢 tick
  → B 的维生判决延后
    → B 死
      → B 的死亡处理（清除/账本对账/persist）又要时间
        → C 更晚
```

**⇒ 真实的多 bot 灾难形态：不是「互相堵塞」，是「一个 bot 的重活，把其他所有人的生存时钟一起拖慢」。**

### 2.4 ⚠️ 而"漏 tick"这件事**本身**已有前科

`BotManager:1104` 附近有一条 D-176 的记载：会话在跑但 bot 实体整 tick 没被 tick ⇒ **物理冻结**，
`segmentTicks=121 entityTicksInSegment=0`，表现为"**任务在跑、bot 一格不动**，且**没有任何报错**"。
⇒ **"一个 tick 没做事"是一种已经在项目里造成过真实故障的失败模式。**
（当时的对策是"实体 tick 看门狗"，`checkEntityTickProgress`。）

## 3. 为什么"一 bot 一线程"是错的

| # | 理由 |
|---|---|
| **① 无界资源** | 线程数随 bot 数增长（N bots × 每 bot 可能有多个并发搜索）⇒ 内存 + 上下文切换 |
| **② 并发读权威世界** | §1.2 的三条风险 × N |
| **③ ⭐ 它没解决根问题** | **真正稀缺的资源是主线程的 50ms，不是 CPU 核数。** 把搜索搬走**不减少它对世界的依赖** —— 结果的**"应用"（执行、写世界、读最终状态）仍然必须在主线程** |
| **④ 优先级无法表达** | N 个**对等**线程里，"正在淹死的那个 bot 的搜索"**没法抢占**"闲逛寻路的搜索" |

**⇒ 线程数不是解法，它是把同一个瓶颈换了个地方排队。**

## 4. ⭐ 正确形状：三层，从里到外

### 4.1 (a) 最内层：**先别做规划**

**逃生根本不需要图搜索。**

`survey/09` §8 的**原路返回** —— 把"搜一张图"变成"**读一个列表**"：

| | 今天 | 原路返回 |
|---|---|---|
| 逃生选落点 | 17³ 扫描 + 一次**无界**规划 | **读一个环形缓冲，O(1)** |
| 线程需求 | 有 | **零** |

**⇒ 这是同一个模式，项目里已经出现过两次：**

| 场景 | 不该做的事 | 因为事实已经在那儿 |
|---|---|---|
| 流体危险 | 不该**模拟**流向 | **服务器已经在算**（`getFluidState` 免费读） |
| 逃生路径 | 不该**搜索**路径 | **你刚走过**（轨迹就是路径） |

> **⇒ 如果 design 层面修好了，"要不要开线程"这个问题会自己消失一半。**

### 4.2 (b) 中层：真要异步时，形状是「**有界池 + 可取消 + 优先级 + deadline**」

| 要素 | 要求 | 现成锚点 |
|---|---|---|
| **池大小固定 M** | 与 **bot 数解耦**（M ≈ 1~2），而不是每 bot 一个 | — |
| **可取消** | bot 已脱险 ⇒ 那次搜索是垃圾，**立即丢** | ✅ `SearchBudget.cancelled`（`BooleanSupplier` 字段**已存在**） |
| **优先级** | **逃生搜索抢占闲逛寻路** | ⚠️ 无 |
| **deadline 而非 budget** | "必须在 N tick 内给出**够好的**答案"，而不是"跑够 3000ms" | ⚠️ 今天只有 `maxMillis` 预算语义 |
| **应用在主线程** | 结果只做"收结果"，执行仍在本 tick | ✅ 架构已经是这样（`PathSession` 是执行层） |
| **读世界约束** | 只读已加载区块 + 容忍陈旧读 + **绝不触发加载** | ✅ `hasChunkAt`/`chunkLoaded` 已经保证"绝不加载" |

### 4.3 (c) ⭐⭐ 项目**已经有这个形状的完整模板**

`LlmClient.askAsync` + `GoalDirector` 的 `pending` —— **这就是"异步 + single-flight + 看门狗"的完整实现**：

| 要素 | 已有实现 | 位置 |
|---|---|---|
| **不在主线程等** | `CompletableFuture`，javadoc 明写「**绝不在主线程上等**」 | `LlmClient.java:24,64` |
| **专用线程池** | `Executors.newCachedThreadPool` + 命名 + `setDaemon(true)` | `LlmClient.java:39-43` |
| **single-flight** | `if (state.pending != null) return;`（已有请求在飞就跳过） | `GoalDirector.java:69`（`State.pending`） |
| **节流** | `minIntervalTicks` | `GoalDirector` |
| **看门狗** | 有 | `GoalDirector` |
| **主线程只收结果** | `GoalDirector.tick()` = "收结果 + 空闲触发" | `BotManager:980` |
| **失败如实** | `ok=false` + 一行可 grep 日志 | `LlmClient` javadoc |

**⇒ "把搜索做成异步"不是新架构 —— 是把已经在 LLM 那条路上验证过的形状，搬到搜索上。**

**⭐ 而且 `LlmClient` 的线程池注释里留着一条**硬**教训，正是用户担心的情景的"单 bot 版本"且已踩过并解决**：

> 「① 必须**多线程**（缓存池）——一个卡住的调用不能把整条管道堵死；
> ② **绝不能**把它同时交给 `HttpClient` 当内部 executor —— 否则 `send()` 占住唯一线程、
> HttpClient 的内部任务排不进来 ⇒ **死锁**：请求发不出去，超时也永不触发
> （实测现象：日志停在 `llm_dns` 之后整整 5 分钟没有任何一行）。」

⇒ **"一个卡住的东西不能把管道堵死"与"一个 bot 的搜索不能把 tick 堵死"是同一个命题** ——
**项目在 LLM 那条路上已经解过一次了。**

### 4.4 ⚠️ 一处**已登记的债**

风险草案（`RISK_SYSTEM_DESIGN_DRAFT.md` §9）明说：

> **约束提醒**：`PathingStats.snapshotAndReset()` 是**清空式**的。将来若要在**异步线程**规划，
> 这个设计**会丢数据**。目前是同步主线程（`CorePathPlanner` javadoc 明说），**先记着这个约束**。

**⇒ 这是"将来要异步"的第一个已知破坏点，主线已经记着了。**

## 5. ⭐ 多 bot 调度的根解：给 **tick 做预算**

### 5.1 事实：全仓**没有任何 tick 级预算**

| 搜索 | 命中共 |
|---|---|
| `tickBudget` / `budgetPerTick` / `timeBudgetPerTick` / `tickMillis` | **0** |

⇒ **今天没有任何东西在计量"这一 tick 总共花了多少"。**

### 5.2 正确的做法

**每 tick 只允许 K 个 bot 做昂贵工作**（预算分摊 / 轮转），而不是"每个 bot 都能跑一次无界搜索"。

- 需要**紧急工作的 bot 优先**（维生判决 / 逃生）
- 非紧急的（闲逛寻路、候选扫描）**可以延后到下一 tick**
- **延后要有账**：今天延后了几次、谁延后的 ⇒ **可归因**（否则会变成"某 bot 有时不工作"的幽灵 bug）

### 5.3 ⭐ 它和 `WriteBudget` 是**同一个思想**

| 资源 | 已有的计量 | 缺的计量 |
|---|---|---|
| **世界写入** | ✅ `WriteBudget`（每作用域 **64 破坏 / 32 放置 / 32 容器写**） | — |
| **权限** | ✅ `PermissionGate` + `survey/05` 的**授权信封**（**per-bot**） | — |
| **算力（tick）** | ❌ **无** | **本文的核心建议** |

> **资源要计量、要有限额、要可归因。**

**★ 用户的直觉早已对过**：`survey/05` 定的「**授权信封 per-bot**」（"不同 bot 可能在同时执行不同任务"）
正是这个思想在**权限**上的版本；**缺的是它在「算力」上的版本**。

## 6. 建议的顺序（各条独立可采纳/否决）

### 6.1 止血（小、立刻可做）

| # | 做什么 | 依据 | 代价 |
|---|---|---|---|
| **A1** | **给逃生请求有界预算**（别用 `UNLIMITED`） | `survey/09` 补遗 A.5#1 | 小 |

### 6.2 根治（让问题不发生）

| # | 做什么 | 依据 | 代价 |
|---|---|---|---|
| **B1** ⭐ | **原路返回** —— 让逃生不搜索 | `survey/09` §8 | 小（环形缓冲 + 候选格来源替换） |
| **B2** | **tick 预算分摊**（每 tick 只让 K 个 bot 做重活） | §5 | 中（需先有"昂贵工作"的分类 + 可归因的延后计数） |

### 6.3 结构性（多 bot 真上线前）

| # | 做什么 | 依据 | 代价 |
|---|---|---|---|
| **C1** | **异步搜索**（固定池 + 优先级 + 可取消 + deadline） | §4.2；**模板已有** = `LlmClient` + `GoalDirector` | 大 |
| **C2** | **`PathingStats` 改非清空式**（或按 bot 分桶） | §4.4（已登记的债） | 小~中 |
| **C3** | **多 bot 调度验收** | `MULTI_BOT_INTERFACE_RESERVATION.md` 已记录身份边界，行为改造**延期** | 大 |

### 6.4 ⚠️ 一条顺序提醒

**C1（异步）应当排在 B1/B2 之后。** 理由：

> **在"逃生不需要搜索"之前做异步搜索，是在给一个本可以消失的问题建基础设施。**

## §2 车万女仆的任务抽象形状（**证据**）

### 2.1 ⭐ `IMaidTask`（本体 `api/task/IMaidTask.java`）

**⇒ 任务抽象的核心是这四样：**

```java
ResourceLocation getUid();                                  // 任务 ID
ItemStack getIcon();                                        // 图标
List<Pair<Integer, BehaviorControl<?>>> createBrainTasks();  // ⭐ 任务 = 一组 brain behavior
MenuProvider getTaskConfigGuiProvider(EntityMaid maid);      // ⭐ 自带配置 GUI
```

**⇒ 以及一组**开关**（勘测侧认为这个形状值得注意）：**

| 开关 | 作用 |
|---|---|
| `isEnable(maid)` | 任务是否可用 |
| `enableLookAndRandomWalk(maid)` | 是否禁用"四处张望/随机走动"（专心工作时关掉） |
| `enablePanic(maid)` | 是否禁用慌乱 AI（攻击/灭火时关掉） |
| `enableEating(maid)` | 是否禁用吃饭 AI |
| `workPointTask(maid)` | 是否为"有工作点的任务"（钓鱼要坐垫/船） |

**⇒ ⚠️ 勘测侧看法：这个"开关族"的形状，与项目 `D-333`（守卫线：必须开启的 vs 可开关的）**是同一类东西**。**
**⇒ 车万女仆的解法是：**每个任务自己声明**这些开关的默认值，而不是全局统一。**

### 2.2 本体任务清单（**证据**，约 30 个）

`TaskNormalFarm` / `TaskGrass` / `TaskFishing` / `TaskTorch` / `TaskHoney` / `TaskShears` /
`TaskFeedAnimal` / `TaskFeedOwner` / `TaskSugarCane` / `TaskMelon` / `TaskCocoa` / `TaskSnow` /
`TaskMilk` / `TaskExtinguishing` / `TaskBoardGames` / `TaskAttack` / `TaskBowAttack` / …

**⇒ ⭐ 全是地表作业**（种、收、割、钓、插火把、剪羊毛、喂动物）。

### 2.3 ⭐⭐ 锚点机制（**证据**，作者设想的第二种是现成的）

**⇒ `IMaidFindTargetTask` 的默认值：**

```java
default int maxOutDistance()       { return 10; }   // 离锚最远 10 格
default int minReScheduleDistance(){ return 3;  }   // 靠近到 3 格就重新调度
default int moveDistance()         { return 10; }
```

**⇒ 锚点是谁？看 `FindTargetMoveBehavior`（证据，原文逻辑）：**

```java
LivingEntity owner = maid.getOwner();
if (finalTarget.distSqr(ownerPos) > task.maxOutDistance() * task.maxOutDistance()) {
    // ⚠️ 目标离主人太远 ⇒ 不奔目标
    //    改成"朝目标方向走一段，但走完仍不超 maxOutDistance"
    //    且候选落点要再检查一次 distSqr(ownerPos) < maxOutDistance²
}
```

**⇒ ⭐ 结论：**

| | 车万女仆 |
|---|---|
| **锚点** | **玩家**（`maid.getOwner()`） |
| **半径** | **10 格** |
| **固定锚点** | ❌ **没有**（它的前提是主人一定在场） |

**⇒ ⚠️ 所以作者设想的"两种锚点"中，第二种是**现成且验证过的**，第一种（固定锚点）是**车万女仆没有的原创补充**。**

## §3 ⭐⭐ 挖矿为什么缺席（**本轮最重要的推断**）

### 3.1 证据：附属模组里有一个**空壳**的挖矿任务

**⇒ `zxy19/maid_useful_task` 的 `task/MaidMineTask.java`（证据，全文）：**

```java
public class MaidMineTask implements IMaidBlockDestroyTask {
    @Override
    public boolean shouldDestroyBlock(EntityMaid maid, BlockPos pos) {
        return false;        // ← 空实现
    }
    @Override
    public boolean mayDestroy(EntityMaid maid, BlockPos pos) {
        return false;        // ← 空实现
    }
}
```

**⇒ ⚠️ 这不是"没人做挖矿"，而是"有人建了文件、写了空壳、然后停住了"。**

### 3.2 ⭐ 证据：垂直搜索范围**写死为常量**

**⇒ 本体 `IMaidTask.java`：**

```java
/**
 * 垂直搜索范围
 */
int VERTICAL_SEARCH_RANGE = 4;
```

### 3.3 ⭐ 勘测侧推断：三条前提在挖矿上全部不成立

| 车万女仆的架构前提 | 挖矿的要求 |
|---|---|
| 目标在**地表**，垂直范围 **4** | 目标在**地下 30~60 格** |
| 主人**必须在场**（锚点 = 玩家） | 需要**自主下矿**（锚点不成立） |
| 目标**天然可见 / 可走** | 目标**不可见、不可走、要开路** |

**⇒ ⭐ 勘测侧结论：**

> **挖矿不是"没人写"，是车万女仆的**整体架构前提**套不进去。**
> **⇒ 那个空壳 `MaidMineTask` 很可能是"写到一半发现套不进去就停了"。**

**⇒ ⚠️ 这条推断是**勘测侧判断**，不是源码明说；但它能同时解释"为什么有文件"和"为什么是空的"。**

### 3.4 证据：它的"挖掘"形状（供砍树用）

**⇒ `IMaidBlockDestroyTask`（附属）：**

| 方法 | 形状 |
|---|---|
| `reachDistance()` | **7** |
| `toDestroyFromStanding(maid, targetPos, standPos)` | ⭐ **从站位点向目标光线投射**，沿途只收 `mayDestroy` 的方块 |
| `getTryDestroyBlockListBesidesStart(startPos, standPos, maid)` | ⭐ **BFS 收集"相连的可挖方块"**（26 邻域） |

**⇒ ⭐ 勘测侧推断：这个形状是"**站在能站的地方，把挡路的挖掉**"，**
**⇒ 而**不是**"规划一条通道往下走"。**

**⇒ 这与项目自己的发现吻合：`survey/24` 里"斜下不在候选集"的问题，在车万女仆这边**同样不存在解决方案**（因为它根本不面对这个问题）。**

## §4 对「一套任务 + 两种锚点」的评价

### 4.1 ⭐ 作者的定性（**本轮重点**）

**⇒ 作者原话：**

> 「**固定锚点实际上可能不适合真实世界挖矿**，两种锚点模式是**为一套任务准备的**，
> 但实际上**两种锚点模式都可能有各自的用处**」

**⇒ 勘测侧此前把它理解成"二选一"，**理解偏了**。正确的形状是：**

```
一套任务（不定工作区 + 自动搜索附近目标）
    ├─ 锚点取值一：固定锚点
    └─ 锚点取值二：玩家锚点
```

**⇒ ⭐ 勘测侧看法：这个区分的价值在于 ——**

| 写法 | 代价 |
|---|---|
| 写成两个任务 | ⚠️ 两份代码、两套判据、同步维护 |
| **一套任务 + 锚点参数** | ✅ 一套判据；换锚点 = 换参数 |

**⇒ 且这与项目 `D-356`（作业区/意图过滤层）的形状一致：**
**⇒ 锚点 = **作业区的来源**，不是作业区本身。**

### 4.2 ⚠️ 勘测侧的一条警告（**已因作者补充而降级**）

**⇒ 警告原文**：车万女仆的"玩家为锚 + 半径 10"能工作，是因为**草和树到处都是**。
**⇒ 而自然挖矿场景下，玩家站位附近十几格内很可能**一格矿都没有**，bot 会大部分时间"找不到目标"。**

**⇒ ⚠️ 降级说明（作者补充后）：**

> **不是"半径 10 太小"，而是"半径 10 只适合**目标持续存在**的场景"。**
> **⇒ 自然挖矿 = 不适合；凝矿兰场景 = 可能正合适（见 §6）。**

## §6 ⭐⭐ 凝矿兰：这套任务的第一个真正落点（**作者提出**）

### 6.1 作者原话（**原样收档**）

> 「甚至在整合包里，**固定锚点模式可以结合植物魔法的凝矿兰使用**，实现简单，**自动采集**，
> 这套任务确实有**很高的应用前景**」

### 6.2 ⭐ 为什么这条重要（勘测侧推断）

**⇒ 回到 §3.3 的结论：这套任务架构在自然挖矿上**不成立**，因为"附近没有矿"。**

**⇒ 凝矿兰把这个前提直接消掉：**

```
凝矿兰：把石头变成矿（持续产出）
    ↓
矿在锚点附近**持续生成**
    ↓
⇒ "附近没有矿"这个假设**不再成立**
    ↓
⇒ ⭐ 车万女仆那套架构的前提**被重新满足了**
```

**⇒ ⭐ 勘测侧结论：**

> **固定锚点 + 凝矿兰 = 让"不定工作区挖矿任务"落在一个**它的架构天然支持**的场景里。**
> **⇒ 这就是"实现简单 + 自动采集"的真正原因 ——**难的部分（深层搜索）根本不在这个场景里**。**

### 6.3 为什么勘测侧认为它适合当**第一个验证场景**

| 条件 | 是否满足 |
|---|---|
| 目标在锚点附近 | ✅ 持续生成 |
| 不需要深层搜索 | ✅ |
| 不需要 LLM 决策 | ✅ 纯机械 |
| 不需要玩家在场 | ✅ 固定锚点 |
| 有真实需求 | ✅ 整合包自动采集 |

**⇒ ⚠️ 它比"陪伴挖矿"更适合当第一个场景，因为它**没有外部依赖**（不需要玩家在场、不需要矿洞）。**

### 6.4 ✅ 凝矿兰机制（**已查证**，来源 mcmod 官方条目 + Botania 源码树）

**⇒ 数据表：**

| 项 | 值 |
|---|---|
| **工作范围** | ⭐ **11 × 7 × 11 长方体**（水平以花为中心 ±5；垂直以花 + 其下方方块为中心 **±3**） |
| **产出速度** | ⭐ **每 5 s（100 tick）随机替换一块石头为矿石** |
| **媒介** | 石头 / **深板岩**（深板岩提高稀有矿概率） |
| **魔力消耗** | 内部缓存 **17500 mana，每次生成消耗 17500** ⇒ **生成一次 = 耗空一次** |
| **开关** | 含红石根 ⇒ **可用红石信号控制是否工作** |
| **矿石选择** | 来自矿物词典（兼容 MEK 锇、AE 赛特斯石英等） |

**⇒ 1.20.1 实测概率（mcmod 原文）：**

| 媒介 | 分布 |
|---|---|
| **石头** | 煤 57.5% / 铁 25% / 红石 6.5% / 铜 6% / 金 2.3% / **钻石 0.8%** |
| **深板岩** | 深层铁 25% / 深层青金石 17.5% / 深层红石 15% / 深层金 12.5% / **深层钻石 10%** |

### 6.5 ⭐ 机制查证后，对三个问题的回答（**勘测侧结论**）

| # | 问题 | ✅ 查证结论 |
|---|---|---|
| **1** | **产物会累积吗？** | ⭐ **会，而且会"堵死"** —— 范围是 **11×7×11 的有限体积**，石头被换完就没了；⚠️ **不挖走矿石 ⇒ 矿石占住位置 ⇒ 产量趋近 0**。⇒ **bot 必须持续清空**。**这才是"自动采集"的真实意义：不是"收集产物"，是"保持兰继续工作"** |
| **2** | **它消耗什么？** | ⚠️ **魔力，而且很凶** —— 每次生成消耗 **17500**（= 全部缓存）⇒ **产能完全由供魔速度决定，不是由花决定**。⇒ 这**不是"偶尔补给"**，是"**必须有稳定魔力供给系统**" ⇒ 场景前提 = **玩家已进入植物魔法中后期（已建好产魔设施）** |
| **3** | **产出速度 vs bot 挖速** | ⚠️ **严重不匹配** —— 兰：**每 5 s 1 块**；bot：挖一块约 **0.5~1 s**（含寻路）⇒ **bot 比兰快 5~10 倍** ⇒ **bot 大部分时间在"等"** |

### 6.6 ⭐⭐ 结论修正（**查证后**）

**⇒ §6.3 的判断**部分修正**：**

| | 修正 |
|---|---|
| ✅ **仍然成立** | 矿在锚点附近持续生成 ⇒ **不需要深层搜索** ⇒ 车万女仆那套架构适用 |
| ⚠️ **新增前提** | **需要玩家已建好魔力供给**（17500/个，消耗很大） |
| ⚠️ **形态修正** | ⭐ **不是"持续挖矿任务"，是「低频轮询 + 定时清空」** |

**⇒ ⭐ 但它能验证的东西比原先预想的**更窄、也更干净**：**

> **它验证的是「不定工作区 + 固定锚点 + 自动搜索附近目标」这套任务形态本身，**
> **而完全不涉及「深层搜索 / 通道挖掘 / 资源管理」——**
> **因为产出由别人（玩家 + 兰）负责，bot 只负责"看到就挖"。**
>
> **⇒ 这恰恰是它适合当**第一个验证场景**的原因：它把所有难的东西都排除掉了。**

### 6.7 ⚠️ 一个勘测侧发现的用法（**推断，未验证**）

**⇒ 深板岩版深层钻石概率 10%，石头版钻石仅 0.8% ⇒ 相差约 12 倍。**

**⇒ 整合包玩家会主动用深板岩铺底来优化产出 —— 而**清空频率**正是 bot 的价值所在**（人懒得每 5 秒去清一次，bot 可以）。**

**⇒ ⚠️ 这是勘测侧推断，**未在任何真实整合包验证**，不得当结论。**

## §8 收档：作者原话（**不作抽象**）

> 「嘶，我觉得跟随玩家不是一种特殊任务，应该做成**一套任务**，也就是车万女仆式的任务，
> 不定工作区的自动搜索附近目标的任务，之前车万女仆模组自己和他的附属模组做了很多实现，除了挖矿」

> 「你先去查一下吧，**区域锚点可以设吧，一种是固定锚点，一种是玩家为锚点**」

> 「首先，**固定锚点实际上可能不适合真实世界挖矿**，两种锚点模式是**为一套任务准备的**，

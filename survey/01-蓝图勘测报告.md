## §1 三条产品线

来源：`AI_PLAYER_DESIGN.md` §1.1

| # | 产品线 | 内容 | 对应阶段 |
|---|---|---|---|
| 1 | **通用玩家助手** | 采集、战斗、跟随、安全区、巡逻、返航等跨整合包常见任务 | A → B |
| 2 | **无 AE 自动合成阶段** | 执行玩家**定义的**流水线搬运与生产订单；**不**自动猜测或搭建流水线 | C → D |
| 3 | **AE 自动化阶段** | 通过 AE2 适配器完成网络观察、存取、样板编写与管理 | C → F |

**LLM 的边界**（原文）：

> 「LLM 用于理解目标、选择已注册工具与处理异常；它**不能替代**移动、库存事务、机器语义适配器或服务端验收。」

### 1.1 差异化支柱（对抗的竞品）

来源：`AI_PLAYER_DESIGN.md` §1.2 / §1.3

| 竞品 | 原文指出的致命短板 |
|---|---|
| Voyager / Mindcraft（协议 bot） | 感知走协议（慢）、任务逐格指挥（低效）、看不见模组 GUI |
| mc_aiplayer / numen（游戏内模组） | 执行层漏洞多（站位/搜索/拾取）、任务写死、点不了 GUI |
| Cradle（视觉 GUI） | 慢、脆、无 MC 模组 grounding 数据 |

四条支柱：

1. **目标级智能 + 确定性执行**（LLM 管目标/约束/候选/异常，执行器管动作/资源/权限/验收）
2. **服务端语义接口**（不依赖视觉点击 GUI，走 capability + 模组 API + 适配器）
3. **玩家/整合包可注入规则**（预设 / `PackProfile` / `WorldProfile` / `TaskPolicy`）
4. **本地知识优先**（教程精炼为版本化指导手册，外部 RAG 按需）

### 1.2 明确不做的事（原文 §1.4）

- ❌ 不做"视觉点击 GUI"路线
- ❌ 不追求让模型从原始世界数据自主推理一切
- ❌ 不逐格指挥挖掘/建造

| **B** 通用助手闭环 | 挖矿/木材、动物食物、作物/野生食物、跟随、停留/返航、巡逻、保护、钓鱼 | 🔨 **伐木 J1–J5 在做** |

**关键约束（原文）**：

> 「阶段并非严格串行……但**共享移动、库存事务、权限与结果契约必须作为主线先稳定**。」

### 2.1 蓝图自列的"可实现性判断"

| 判定 | 内容 |
|---|---|
| **确切可实现** | 标签化采集/攻击/拾取/安全区；标准 capability 只读快照；明确端点的模拟插入/提取；玩家定义流水线下按 contract 投料等待收产物；固定版本的 AE2/Mekanism 专用适配器；版本化指导手册；LLM 选目标/路线 + 执行层验收反馈 |
| **可实现但成本高** | 复杂地形长期跟随/战斗保护/巡逻；通用树木作物采集；任意机器工艺归一化；AE 样板自动编写与正确放置；多路线生产规划 |
| **不应承诺为通用能力** | 仅靠 capability 自动理解任意复杂机器槽位；仅靠教程生成安全写操作；自动理解并搭建任意玩家流水线；不经玩家规则处理所有魔改配方；让 LLM 逐步控制移动/战斗来弥补执行器缺失；「接入新模组无需代码或配置即可端到端工作」 |

> 这段"**不应承诺**"清单价值很高：它是**产品对外口径的护栏**。
> 建议长期留在活文档里（不只在归档区）。

## §3 C0–C5 兼容分级（框架本身很有价值）

来源：`PRODUCT_ARCHITECTURE_ROADMAP.md` §4

| 等级 | 能力 | 主要机制 | 典型范围 |
|---|---|---|---|
| **C0** 识别 | ID、标签、方块/实体/物品存在 | Registry / Tag | 大部分模组内容 |
| **C1** 只读观察 | 库存、能量、流体、状态摘要 | Forge/模组 capability、BlockEntity | 暴露稳定接口的机器 |
| **C2** 通用受限操作 | 经模拟校验的插入/提取、普通实体交互 | 标准 capability / 原版 API | 语义明确的简单端点 |
| **C3** 配置驱动语义 | 玩家/整合包定义槽位、端点、配方、完成条件 | `PackProfile` / `WorldProfile` | 手搓期流水线 |
| **C4** 模组原生适配 | 工作模式、专有化学品、AE 样板/网络拓扑 | **版本化代码适配器** | Mekanism、AE2 等目标模组 |
| **C5** 端到端技能 | 经客户端/服务器验收的完整任务 | 编排器 + 适配器 + 知识包 | 指定版本和场景 |

原文的重要修正：

> 「标准 capability 能提高 C1 覆盖率，但**不能自动提供 C3/C4 的语义**。
> 教程/RAG 可以帮助 LLM 选择工具，却**不能替代执行层适配器**。」

以及升级/降级纪律：

> 「适配器**不能通过反射或内部 API 静默跨版本运行**。版本不匹配时应降级到已证明的兼容级别，**通常是 C0/C1，只读报告**而不是尝试写操作。」

> **勘测评价**：C0–C5 是一套**可直接对外声明**的兼容性语言（避免"支持模组 X"这种笼统承诺）。
> 它与 `README.md` §5「未知模组能力默认只读」一致，但比它更完整。
> **建议：C0–C5 升级为活文档**（现在只在归档区）。

## §4 勘测结论

### 4.1 ✅ 主线方向正确，且它在**唯一的关键路径**上

蓝图 §1.1 原文：

> 「**最大共享前置是移动与站位可靠性。** 跟随、战斗、采集、巡逻和搬运都不能各自复制一套寻路补丁；它们应消费同一组经场景验证的移动能力，并显式声明可用能力……

> 未验证能力必须拒绝，不可由 LLM 指令绕过。」

**三条产品线全部依赖移动/站位/内核。** 当前主线（Baritone 兼容内核 + 挖掘 + 伐木 Job）**正是这条关键路径**。
→ **主线没有走偏**，这是我作为勘测员要确认的第一件事。

### 4.2 ⚠️ 蓝图的后半段卡在一个**非技术**前置上

蓝图 §10「需要用户逐步拍板的问题」第一条：

> 「**首个目标整合包及优先模组/版本是什么**；Mekanism、AE2 之外还有哪些必须首发支持？」

**这不是小事**：

| 阶段 | 为什么依赖它 |
|---|---|
| **D** ProcessContract | 固定输入/催化剂/概率产出/容器返回的**真值**来自具体模组 |
| **E** 适配包排序 | 完全按"目标整合包里的优先模组"排 |
| **F** AE2 | 必须锁定**固定版本** API |

> **勘测判断**：这是整个项目**最大的未知数**，比任何技术问题都大。
> 而且它有特殊性——**没有技术门槛，却会被无限推迟**（永远不会"到时候再说"就自动解决）。
> 同时它**反过来校准前面**：若目标科技整合包已定，阶段 B 的"通用助手"范围就该收窄
> （蓝图 §1.1 自己警告「不把所有功能塞入一个生存助手」）。

### 4.3 🌉 最该修的下一座桥：**Policy Gate（授权闸门）**

蓝图 §2.2 自标：

> 「**策略与计划验证层**——这是现有设计**需要显式补出的层**。」

即**蓝图作者本人已登记此处缺一层**。依赖它的阶段：

| 阶段 | 原文要求 |
|---|---|
| **C** | 「物品搬运按事务记录……任一步失败都必须知道物品当前在哪」 |
| **D** | 「确定性执行器必须在每次物品转移前后核对库存差值、端点版本、权限和完成判据」 |
| **E** | 「版本不匹配时应降级到已证明的兼容级别」 |
| **F** | 「任何无法证明匹配的放置只生成建议/预览，不直接执行」 |

**7 个阶段里有 4 个依赖它。**

**Alice 现状**（静态扫描）：

> **这不是新问题，是"六份重复"在更大尺度上的翻版**：
> 每个新能力各自发明一套"怎么授权、授权多少"。
>
> **桥位会在 J7 就会到**：`JOB_LAYER_DESIGN.md` §11-① 攀爬砍树明确要求
> 「**新的显式授权入口**」——那将是第 4 个工厂。
> **等到阶段 D/F 再抽象，会有 N 个能力各有各的授权方式。**

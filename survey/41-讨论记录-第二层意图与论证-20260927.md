## §2 📋 用户口径（逐字，按说的顺序）

### 2.1 点击模拟 / 宏 / CC:Tweaked / 配方树

> 「给 bot 加**点击模拟**：目标位置 / 左键右键 / 时长 / 次数 / shift / 间隔 / 手持物 /
> 看方块决定拿什么 / 条件检测 / 自定义循环 / **录制并投影玩家操作**（只限世界交互左右键）。」
>
> 「**宏录制可以减少数据来提高确定性**（只录放置的方块 + 相对位置 + 玩家设参考系；
> 录右键行为 + 对着什么实体 + 手持 + 间隔）。」
>
> 「（用途）主要给**魔法模组** —— 不支持管道、不支持红石、必须手动放置物品、要等魔法充能、用法杖启动。
> 点名：**新生魔艺**（自动化做得好，表扬）· **植物魔法**（官方故意加限制，对抗没用）·
> **神秘农业**（高版本觉醒祭坛必须一个一个手放）」
>
> ⭐ 用户自我修正：「**大部分魔法模组不需要自动化；需要自动化的自己做了适配**」⇒ **这块优先级天然低**。
>
> ⭐⭐ 「**CC:Tweaked** —— 用代码实现自动化，**给机器留了兼容接口的伟大前辈**」
> ⇒ 提议：「**与其靠左右键/录制宏，不如学前辈：留一些 bot 基础行为的接口，然后让玩家自己编程，
> 用图形化而不是代码**」；⚠️ 但「**不能像气动工艺那个乱七八糟的图形化**」。

> 「只需要说**别用哪些昂贵配方**，或者**别用哪些昂贵的机器**，**黑名单为主**，**白名单当替补**，

### 2.4 合成流程（原始版）

> 「读配方树 → 筛玩家排除的 → 排除无工作站的 → 检查是否有那'**三个老大难**'（预设或询问）→
> 算总花费 → 材料不同则询问收敛 → 剩一条 → 从仓库判断材料是否足够（不够先报告，
> 按预设或询问是否跳过/放弃）→ 得制作顺序 → 依次前往各工作站投料取产物 →
> 中间失败先报告让玩家处理（重试/继续）」

### 2.5 ⭐ 两处用户自我更正

> **更正一**：「**四次询问玩家其实有点偏差**，而正是你说的**计划卡的生成过程**」
>
> **更正二**：「而且我说**最后只剩一条线路，不对是制作树**，也有偏差。
> 有时候其实会出现**两条线路都可以**，因为材料不是很多，**所以两条线路能用哪个用哪个，但是有优先级**。
> **仓库**当然是玩家设定的可以让 bot 存取权限的容器，中间容器也可以简单设定，最好不要和仓库放在一起。
> 如果出现意外或者概率配方的盈余，**中间容器是必须自动清空，搬回仓库**。」

### 2.6 中间容器 / 排序粒度（收口）

> 「干脆把**中间容器做成 bot 专属容器**得了，其他玩家不可交互，**模组原创容器**，更好管理。」

> 「然后计划卡最后剩的两条线路的话，建议**强制玩家排序**，并且**保留默认排序**，
> 这个排序**不是排序整个路线**，而是排序**最小分叉路**，也就是对这个中间物品的制作保留排序，
> 当然优先是哪个材料够用哪个，**玩家自己承担材料**。」

## §4 ⚠️ 勘测侧观点（**明确标注：不是事实，不是指令**）

### 4.1 ⭐⭐ 点击模拟「不是后门，是正门」

- ✅ `INTERACTION_LAYERS_COMPARISON.md` 已写明：
  **A 路线**（capability 直写）**可能绕过模组意图**（安全/领地/统计钩子挂在 GUI 开关/点击上）、
  **被拒绝时可能无声成功**；**B 路线**（菜单/点击）**天然被模组拦、天然可归因**。
  📎 **实证**：`D-323`（FTB 拦下的破坏被记成 `done`+`COMPLETED`）。
- ⭐ 它是 `survey/14 §3.4`「**档 3（逐模组适配）**」的**执行机制**，**不是新野心**。
- ⭐ **魔法模组的特殊性**：**不是"适配难"，是"根本没接口"**（没有 `IItemHandler`）
  ⇒ A 路线**无路可走** ⇒ 这里的"不得不"成立得**比 FTB 还硬**。

### 4.2 ⭐⭐ CC:Tweaked 的教训：**抄接口形状，不要抄社区模式**

- CC 真正伟大的**不是"能自动化"**，是**定义了一套"如何暴露能力"的协议**：
  **可查询** · **调用者不需要知道实现** · **接口小到作者愿意实现**。
- ⚠️ **但它的成功靠装机量飞轮**（整合包几乎都塞 CC ⇒ 作者愿意适配 ⇒ 大家更愿意装）。
  **Alice 没有这个飞轮。**

### 4.3 ⭐⭐ 编排，不是编程

| | 图形化**编程** | 可视化**编排** |
|---|---|---|
| 图元 | 变量/循环/条件/函数 | **Alice 已有的动作** |
| 玩家在做 | 写程序 | **排活儿** |
| 需要 | 语言/解释器/调试器 | **一张表** |
| 会不会烂 | ⭐ **必然** | 不会（**原语有界**） |

- ⇒ **正确的图形化 = 可视化地编辑一张 `TaskSpec` 队列**（字段见 `DECISION_LAYER_FINAL_FORM §3.2`）：
  **不需要发明语言；不需要解释器；不扩大授权面**；玩家的"循环"被翻译成队列条目 ⇒ **不逃逸门禁**。
- ⚠️ 气动工艺之所以乱：**它想做通用编程。通用编程的复杂度不会因为"画出来"而消失。**
- ⭐ **顺序：先原语接口，后图形化**（原语没定型就画界面 = 每次改接口都要重画）。
- ⭐ **决定成败的不是编排，是调试**：可视化工具死在"它为什么不干活"。
  **接口必须自带"为什么没做"的解释** —— 而这正是项目最强的部分
  （终态码 / 失败归因 / `DecisionTrace` / `M4` 子阶段失败）。

### 4.4 ⭐⭐ "可配置项"该怎么长（**本轮最重要的设计**）

- ⚠️ **首先别做成"配方树配置"** —— 那是编程，会重演气动工艺。
- ⭐ **降维洞察**：复杂物品的分支虽多，但**大部分分支是等价的**（都能到目标、成本相近）
  ⇒ **不需要"选对"，只需要"别选错"** ⇒ 玩家提供的是**约束**，不是**答案**。
- ⭐⭐ **用户那句"用这'类'配方"里的「类」字是关键** —— 它跟**工作站声明**同构！
  （`survey/14 §3.2`：工作站 = "声明一类机器 ⇒ 自动继承该类全部配方"）
  ⇒ **同一个抽象：把"实例选择"升成"类型声明"。**
- 形态（三层，都不需要新语言）：**硬约束**（我不接受 X）· **软偏好**（优先便宜的）· **禁用**（这个副产我不要）。
- 流程：**配方图算可行路线 → 按偏好排序 → 只把 top-N 给 LLM → LLM 选 + 说理由 → 计划卡给玩家**
  ⇒ **LLM 不在"算路线"，它在"有界候选里选 + 解释"** ⇒ 符合"LLM 只做目标级决策"。
- ⭐ **"每次都让玩家选吗"的答案：不是。配置一次 + 例外才问。**
  ⚠️ 注意：`survey/14` 里那条**「路线选择交玩家」已拍板**，但 **"交玩家" ≠ "每次都问"** —— 这个区分要写清。
  形状同 `PermissionGate` 的 `once|session|always`：默认策略覆盖大多数，只在**平手 / 差异大 / 风险高**时才问。

### 4.5 ⭐ 黑名单的条目必须「可判定」+ **必须能「报空」**

- **静态黑名单**（具体 recipe/block/machine 的 id 或 tag）⇒ 可判定 ✅
- **计算黑名单**（"超过阈值 X 的"）⇒ **只要成本模型可算**也可判定 ✅
- ⚠️ "别用昂贵的"若"昂贵"无人定义 ⇒ **那不是黑名单，是愿望**
- ⭐⭐ **补一条用户未提但重要**：**黑名单必须能「报空」** —— 若玩家的约束把候选吃光 ⇒
  **如实报"你的约束把所有路线排除了"**，**不许偷偷放宽**
  （否则 = **静默违背玩家意图**，与 `D-323`「破坏被拒却谎报成功」同类）。
  📎 **副产品**：这条让"NL 够不够用"**变成可验证** —— LLM 理解错 ⇒ 大概率报空 ⇒ 玩家看得见。
- ⭐ **本鱼撤回上一轮的过度设计**：曾提"把'昂贵'做成可复算的成本模型" ⇒
  📋 用户「**昂贵当然我来算啦**」⇒ ✅ 与 `D-329 ②`（价值/优先模型 = **A「用户给」**）一致 ⇒ **撤回**。

### 4.6 ⭐⭐ 中间容器 = 结构化收益（不只是"更好管理"）

- ⭐ **它是「我们自己的」方块 ⇒ `A 路线`（capability 直写）在这里正当** ——
  之前 A 路线的问题针对的是**别人的**模组；**自己的方块接口就是自己定的**
  ⇒ **bot 存取中间容器不需要开菜单**，最频繁的操作从"毫秒级开菜单点槽"变成"**微秒级调用**"。
- ⭐⭐ **它把 bot 的工作记忆外化到了世界里** ⇒ 中断/重启后东西还在 ⇒ **任务可恢复性天然变强**
  （正好补 `survey/15`/`16` 记的"**任务树持久化**"缺口）。
- ⚠️ **成本**：新方块 = block + BlockEntity + 注册 + 模型 + lang（`item/` **79 文件**已是膨胀点）
  ⇒ **一次性成本，不为零**。

### 4.7 ⭐⭐ DAG 合并：整条流程里**唯一"算错就直接坏事"的点**

- ⚠️ **"一条线"是错的 ⇒ 它是一棵按依赖排序的树（DAG）** ——
  一个中间产物会被**多个父节点**需要 ⇒ 不是"先做 A 的 2 铁再做 B 的 3 铁"，
  是"**做一次，5 铁**"。
- ⇒ **总材料必须按合并后的算**；**"制作顺序"是拓扑排序，不是线性序列**。
- ⭐ **对比**：三个老大难（递归/自增/概率）都还算"**探测**"；**这一条是"算"**。

### 4.8 其他四条（用户未反对，⚠️ 待确认）

1. **执行期世界会变** ⇒ 建议：**结构性失效**（机器没了/配方变了）⇒ **回到剪枝重算**；
   **暂时性**（抢了/没电）⇒ **报告 + 等**（区别对待，不然玩家被频繁打扰）。
   ⇒ ⏳ 已提升为 `Q-29`。
2. **"仓库"得先定义**（单箱？多箱？AE 网络？背包算不算？机器里半成品算不算？）
   ⇒ 建议做成**一组具名的「材料来源」**，玩家声明（与"工作站"同一个抽象）。⇒ ⏳ `Q-30`。
3. **等待的站位**：烧炼要时间，bot 站炉前等 = 挡路 + 浪费 ⇒ 别站别人要用的位置（`MAINTAIN` 那套能用）。
4. ⭐ **产出不该是"一条线"，而该是一个 `TaskSpec` 队列** ⇒ 自动继承全部纪律
   （每步 `precondition`/`successCriterion`/`limit`/`onFail`、可审计的计划卡、可中断可恢复、可复用）
   ⇒ **失败处理也不用每次问**（`onFail: SKIP | ESCALATE | END_QUEUE` 三档**现成**）。⇒ ⏳ `Q-26`。

### 4.9 ⭐ 为什么格雷特殊（解释用户那句"其他模组再说"）

- 格雷的成本是**多维的**（电压/产量/副产/时间/能量/污染/回收）⇒ **单目标优化不够，需要玩家给权重**；
  其他模组成本接近**单维**（时间 + 材料）⇒ 默认策略就够。
- ⇒ **"可配置项"对格雷必要、对别的可选。**
- ⚠️ 但仍守 `D-266 ②`：**适配格雷 ≠ 让 bot 设计格雷产线**。适配是"看得懂"，产线是"决定结构"，中间有界线。

### 4.10 ⭐ "替代 AE"这个问法要驳回

- AE 的核心**不是"自动合成"，是「网络」**：跨距离、瞬时、无实体、不加载区块、不消耗路径。
- bot 是**物理实体**：必须走过去、必须加载区块、必须开菜单
  ⇒ **用"一个玩家的速度"替代"一个网络的吞吐"，结构上不可能。**
- ⇒ 📋 用户自己给出的"稳定性"就是这条的**直觉版**（AE 的稳定来自"**没有物理**"）。
- ⚠️ 但 ✅ `survey/14` 已明确：**"AI 自主设计产线"永不进蓝图 C/D**（`D-266 ②`）
  ⇒ ⭐ **"替代 AE"这个问法本身要驳回**；正确关系是 **`D-266 ①`「AE 的外挂：互补不是替代」**，
  且**价值随玩家进度递增**（AE 越强，它接不上的那层越明显）。

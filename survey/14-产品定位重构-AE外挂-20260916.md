## 1. 定位重构：**从"替代 AE"到"AE 的外挂"**

### 1.1 原定位的问题

| 原定位 | ⚠️ 问题 |
|---|---|
| 「让 Alice 在 AE 时代**前**替代 AE」 | **它把 Alice 定位成"AE 的低配版"** ⇒ **一旦玩家做到 AE，Alice 就没用了** ⇒ **产品价值随玩家进度递减** |

### 1.2 新定位（用户本轮确立）

> **Alice 是 AE 的外挂，不是 AE 的替代。**
> **AE 管「管道 + 库存 + 自动合成」；Alice 管「管道接不上的那一层」。**

**⇒ 为什么这个定位更好**：

| 维度 | 替代 AE | ⭐ AE 的外挂 |
|---|---|---|
| 玩家进度对价值的影响 | ❌ **递减**（做到 AE 就不需要） | ✅ **递增**（AE 越复杂，接不上的越多） |
| 与 AE 的关系 | ⚔️ 竞争 | 🤝 **互补** |
| 增量空间 | ❌ 有上限（AE 能做到的都算） | ✅ **开放**（AE 做不到的清单是有限的、可枚举的） |

### 1.3 一句话

> **AE 是"物品在容器之间流动"的引擎。Alice 是"操作那些容器以外的东西"的手。**

## 3. 工作站（**玩家亲手划分**）

### 3.1 完整形态

| 项 | 谁定 | 例子 |
|---|---|---|
| **前提** | 注册工作区（**已有机制**：`/alice region set` + `LumberRegionState.Region`） | `job/lumber/LumberRegionState.java:53` |
| **工作站占位** | ⭐ **玩家逐格划** | 磨粉机 + 漏斗 + 箱子 = **三格一个工作站** |
| **输入操作口** | 玩家指定 | 磨粉机本体 |
| **输出操作口** | 玩家指定 | 箱子 |
| **主交互面** | 玩家指定 | **任何机器 / 仪式 / 工作台都必有唯一主界面** |
| **单方块机器** | ✅ **快速配置**（一格 ⇒ 输入/输出/主界面**三合一**） | 熔炉、单格磨粉机 |

### 3.2 ⭐⭐ 能力声明（用户本轮最重要的补充）

> 「让玩家把这个工作站**等价于一类配方的工作站**，比如说刚才的磨粉机+漏斗箱子工作站，
> 玩家可以把它设定成 **mek 磨粉机**，这样工作站就被声明**能够运行所有 mek 磨粉机能运行的配方**」

**⇒ 所以工作站 ≠ AE 样板**：

| | AE 样板 | ⭐ Alice 工作站声明 |
|---|---|---|
| 粒度 | **一个配方一份样板** | ⭐ **一类机器一份声明** |
| 配方从哪来 | 玩家手工编码 | ⭐ **自动继承该类的全部配方**（从配方表读） |
| 输入输出 | 样板里写死 | ⭐ **由工作站的"口"决定** |

**⇒ 一句话**：
> **样板是实例，工作站是类型声明。声明一次，覆盖该类机器的所有配方。**

### 3.3 ⭐ 语义口径的准确表述（用户澄清）

> 用户原话：「在输入输出这层上，**只看外部，不在乎内部**」
> 又：「这样 bot 还是能**读方块本体的配置，而不是完全忽略内部**，当然**都得是可控的预设**能不完全忽略内部」

**⇒ 准确口径**：

| | 读取范围 | 什么时候 |
|---|---|---|
| **默认** | **只看外部**（输入口 / 输出口 / 主界面） | 通用工作站 —— 与 AE 相同 |
| ⭐ **有预设时** | **可读机器本体配置**（模式 / 开关 / 状态） | **只在"受控预设"覆盖到的范围内** |
| **绝不读** | 预设未声明的任何内部细节 | —— |

**⇒ 这与项目信封思想同构**：**默认最小权限；要更多能力 = 显式授予。**

### 3.4 ⚠️ 硬边界（用户明确）

> 「bot **不可能动玩家设定的复杂流水线的机器配置**，**只限定于单方块机器**」

**⇒ 即：调模式 / 改配置这类操作，只对单格机器做。**

### 3.5 工作站在生产线里的位置

```
玩家划定的工作区
   └── 若干工作站（玩家逐格划分 + 逐站声明能力）
         每个工作站 = 生产线上的一个"中间节点"
         ↓
   Alice 的职责：把材料放进"输入操作口"、从"输出操作口"取出产物
   Alice 不关心的：工作站内部是什么模组 / 机器 / 魔法
```

**⇒ 所以 Alice 做的是「节点间搬运 + 节点内投料/取料」，不是「设计节点之间怎么连」。**

## 4. 工作站预设（Preset）：**逐模组适配的落点**

### 4.1 两层预设（用户本轮补充）

| 预设类型 | 例子 | 内容 |
|---|---|---|
| **通用结构预设** | **单方块机器 + 独立输出口**（磨粉机 + 漏斗 + 箱子） | 输入口 = 机器本体 / 输出口 = 箱子 / 主界面 = 机器本体 |
| ⭐ **模组专属预设** | **魔法法阵** | **怎么启动、怎么摆放祭品、魔力从哪牵到哪** |

### 4.2 玩家的操作路径（用户原话拆解）

```
① 玩家把"法阵"这类特殊结构勾选成工作站
        ↓
② 选择"魔法阵预设"（来自逐模组适配包）
        ↓
③ bot 就知道：怎么启动这个法阵、怎么摆放祭品
```

**⇒ ⭐ 关键：预设是"玩家勾选 + 选择"，不是 bot 自动识别。**

### 4.3 逐模组适配的三档能力上限（用户说清）

| 档 | 能做什么 | 例子 |

**⚠️ 用户对档 3 的定性（必须一起记）**：

## 5. ⭐⭐ 槽位语义：**项目里已经解决了，而且方法比"点击标注"更硬**

### 5.1 用户构想

> 「不是让玩家定义哪一格为输入操作口，而是打开菜单，**手动选择哪些格子为输入的操作格**，
> 只要能捕捉到鼠标点击的那一格的信息，就能最快兼容输入输出的基本操作」
> 又：「也许我们做不到每个格子的单独选择，我们也可以做到**点击这个格子，识别这个格子的同类格子有哪些**」
> 又：「**我不确定**，但现在一定对我们的项目开发有帮助」

### 5.2 ⭐ 今天的现状（**比用户想的更好**）

| 已有件 | 内容 | 证据 |
|---|---|---|
| **`FurnaceStation`** | ⭐ **「输入/燃料/输出不采信自述顺序，一律用 `mayPlace` 行为判定」** | `task/craft/FurnaceStation.java:29` |
| **`GridDiscovery.scan(menu)`** | 反射扫菜单里的全部 `Slot` + 容器 + 合成矩阵 | `task/craft/GridDiscovery.java:155`（**610 行**） |
| **槽位身份判据** | `pickedBy = "slotContainerIdentity"`（按 slot 归属的容器分组，并排序） | `FurnaceStation.java:119`、`:128` |
| **槽位事实报告** | `SlotInfo(position, address, registered, slotClass, …)` | `GridDiscovery.java:86` |

**⇒ 结论**：
> **"这个格子是输入还是输出"今天不需要玩家点 —— 可以用 `mayPlace`（能不能放东西）等行为判据推出来。**
> **⇒ 用户想做的"点击标注"不是必需品，是**可选加速**（用于行为判据失效的机器）。**

### 5.3 ⭐ 但用户的想法仍有一个**不可替代的价值**（必须写清）

用户自己说了退路：

> 「就算实现不了，也能**在逐模组适配中，做成一个客户端开发辅助工具**」

**⇒ 而它正好补上 §7 那个硬前提**：

| 今天的适配通路 | 问题 |
|---|---|
| `MachineMap` = **代码里的表**（"唯一真源"） | ⚠️ **社区加一个模组必须改 Java 源码 + 重编译 + 跑电池** |
| 适配验证 = **跑电池** | ⚠️ **社区没有这条路径** |

**⇒ 所以"点一下标注出来"的客户端工具 = 把"读代码填表"变成"游戏内标注"**
**⇒ 它是社区通路的**第一块砖**，不是退路。**

### 5.4 若要做，必须补的一条（勘测建议）

**点完 ⇒ 立刻回读那一格现在是什么物品**（用"读到的物品"验证这次点击的语义）。
**⇒ 理由**：机器升级 / 版本变化 / NBT 不同 ⇒ **记忆可能失效** ⇒ **要让"失效"可被检测，而不是静默用错。**
（与 `survey/05`「表单是唯一真值」同源：**不能只信玩家的点击，要信世界事实。**）

## 6. AE 时代的功能（用户列的 7 条）

| # | α功能 | AE 自己做吗 |
|---|---|---|
| 1 | **操作 AE**（存取物品） | 玩家手工能做 ⇒ **bot 自动化 = 新价值** |
| 2 | **写样板** | ❌ **AE 让你写** |
| 3 | **管理样板**（迁移 / 检验） | ❌ **纯手工活** |
| 4 | ⭐ **写样板依赖"配方路线识别"** | ❌ **AE 不告诉你走哪条线** |
| 5 | ⭐ **路线选择交给玩家预览和选择，bot 能一口气写完** | ❌ **AE 没这个概念** |
| 6 | **样板编辑预设**（不可自动替换材料 / 合成不消耗 / 只耗耐久） | ❌ 格式支持，**编辑靠手** |
| 7 | **批量更改（特别是样板倍增）** | ❌ **纯手工，极烦** |

**⚠️ 用户补的边界（必须一起记）**：
> 「对于 AE 样板，实际编写**也有很多手动修改内容**……**太特殊太细节的部分只能让玩家自己改了**」

### 6.1 ⚠️ 一个技术坏消息（必须提前知道）

**AE 样板（Pattern）不是"配方"，是"编码"**：
它存的是**一张固定的输入→输出表**（`ItemStack[]` 式），**不含配方 ID，也不含"可替换材料"的语义**。

**⇒ 所以"材料不可自动替换"这类编辑，本质是玩家在编码时做的选择，不是样板里可查询的属性。**
**⇒ 这意味着**：**Alice 要写样板，必须自己做「配方 → 样板」的映射，且必须能表达"用哪个具体物品"。**

## 10. 勘测员的观察（供参考，不是裁定）

1. ⭐ **"路线顾问"是性价比最高的一档**（§6 的 #4/#5）：
   - **只需读配方图 + 注册方块**（`recipe-graph.py` 已在跑）
   - **零世界修改** ⇒ 不需要任何提权 ⇒ **完全不触碰"LLM 乱派发"的风险**
   - **AE 完全不做** ⇒ 差异是硬差异
   - **玩家上线就能感知** ⇒ 最快的"值得投入"证据
2. ⭐ **"工作站声明"恰好把 `MachineMap` 从"内部表"变成"玩家可见概念"** ——
   `Capability` 枚举（`READ_ONLY` / `EXECUTABLE`，今天 **58 : 1**）可以**直接暴露给玩家**，
   让玩家知道"这个工作站 Alice 只能读，不能操作" ⇒ **诚实的失败可见**。
3. ⚠️ **风险**：`MachineMap` 今天 **59 行 / 只有 1 行 EXECUTABLE** ⇒
   **"工作站声明"的概念已经足够，但可操作的机器几乎没有** ⇒
   **第一个"能被声明且真能操作"的工作站，是这条路线的关键验证点。**
4. ⚠️ **格雷**：用户明确「**格雷值得本项目单独为他提一个层次做兼容**」 ⇒
   **它是唯一被点名要单列层次的模组** ⇒ 应作为**独立条目**登记，不进通用适配的优先级表。

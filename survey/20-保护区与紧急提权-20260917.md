## §1 本轮讨论的核心结论（先给结论，再给证据）

### 1.1 ⭐ 「可回收性」在项目里是**一个词盖两个不同的问题**

| 出现处 | 实际含义 | 归属 |
|---|---|---|
| `RecoverabilityReport.recordResidue()` | 「我放的方块还剩几块没拆」 | **世界** |
| `WorldModLedger.pendingTemporary()` | 「我欠了几块」 | **世界** |
| `RestoreScopeTask` 的 `drops_left` | 「我留下的东西没收干净」 | **世界** |
| ⭐ **作者 2026-09-10 的原话** | 「bot 能安全回来 / 被召回」 | **bot 自身安全** |

**⇒ 前三者管世界，第四者管 bot，但**共用同一个词**。**

**⇒ ⚠️ 勘测侧的推断（不是作者原话）**：这解释了作者多次表达的困惑「项目红线总跟我想的不一样」——因为红线是**词**的红线，当一词管两件事时，针对其中一件的红线会在另一件上误伤。

### 1.2 ⭐ 同一种「一词两义」在「安全」上也存在（作者本轮明确拆分）

作者 2026-09-17 声明：

```
保护区（父类，具体概念，非抽象）
  语义：保护**玩家的财产**   ← 所有子区域的基础
  子类：
    └─ 安全区（子类）
       语义：保护财产 + 保护**人身**（玩家或 bot 能保证自身安全的区域）
```

**⇒ 关键纪律（作者原话）**：**安全区必须显式注册，不能从几何推断。**
**⇒ 理由**：`有栅栏` ≠ `栅栏保护我`。栅栏挡不住骷髅的箭、蜘蛛、苦力怕爆炸、末影人、模组怪。

**⇒ 勘测侧补充**：作者另声明「**避难所 = 安全区**，一个概念」，并希望「**尽量设定一个安全终点**（保证到室内，而不是在房顶蹦跶）」。

### 1.3 ⭐⭐ 项目已经写明了「记账只能管放、管不了挖」——这是本报告最硬的证据

`ledger/WorldModLedger.java:20-26`（**原文**）：

> 世界修改账本（J6-a，D-081 §12）：**只记"我方放置"**，用于"建拆同权"的配对与恢复。
>
> **为什么只记放置：破坏型修改**无法配对恢复**（你没法把隧道还原），其控制手段是
> "谓词 + 预算 + 归因"（见 D-095）；**只有放置需要、也能够被恢复**。
> 账本因此小而准。

**条目结构**（`:49`）：

```java
record Entry(BlockPos pos, String placed, String previous, String reason, Policy policy,
             String scopeId, UUID owner, long tick)
//                ↑ 放成了什么   ↑ 原来是啥  ← 精确恢复的原语
```

**⇒ ⭐ 由此得到本报告最重要的一条推论（作者本轮独立提出，此处予以确认）：**

> **「紧急提权只放『修建方块』，不放『挖掘』」不是保守，是技术上正确。**
> **因为『放』有记账可兜底（能精确还原），『挖』没有。**

| 手段 | 能否记账 | 能否恢复 | 现有控制手段 |
|---|---|---|---|
| **放方块（搭路/垫柱）** | ✅ 记（`placed` + `previous`） | ✅ **能精确还原** | **建拆同权**（配对拆除） |
| **挖方块** | ❌ **不记** | ❌ **隧洞还原不了** | ⚠️ **谓词 + 预算 + 归因**（D-095） |

**⇒ 这解释了作者此前的困惑「让他挖矿都在单独计较怎么给预算、怎么记录账单」**：因为**挖**这条路本来就没法用记账管，只能用「预算 + 谓词」管——而预算+谓词正是让人感到束手束脚的东西。

### 1.4 逃生不是一种行为，是一族（作者本轮声明）

```
逃生
 ├─ ① 局部逃生：规避**局部**危险
 │     从岩浆跳出来 / 从深水坑浮上来 / 被怪追时脱离（战斗判定说"打不过"时）
 └─ ② 任务放弃级逃生：放弃当前任务 → 返回「避难所（=安全区）」
       有**条件**：资源过少 / 工具没了 / 食物没了 / 血量极度危险
 └─ ③ 就地固守（作者计划借鉴 mc-aiplayer 的紧急预案）
       遇到无法解决的怪物 → 用现有方块**快速把自己围起来** → 等怪物离开或被解救

战斗系统（**仅登记，本轮不设计**）
 └─ "拒绝战斗"判据：按**装备** + **附近怪物数量** ⇒ 危险系数高 ⇒ 放弃战斗
```

**⇒ ⚠️ ③ 的特殊性**：它是**唯一"不移动"的逃生**——而今天所有逃生都假设「要移动」（`plannableRefuge` 找落点）。

### 1.5 8 格逃生预算：作者认为**合理**，勘测侧收回此前的质疑

- 作者原话：「**8 格预算能瞬间立刻脱险，然后才有时间预算计算回家的路**」
- 勘测侧此前质疑「为什么给紧急情况设预算」——**本次收回**，因为它是**两阶段**问题：

| 阶段 | 目标 | 该不该有紧预算 | 为什么 |
|---|---|---|---|
| **① 立刻脱险（8 格）** | 离开危险格 | ✅ **该有，甚至更紧** | 保命靠**快**，不靠**远**；`ESCAPE_MAX_MILLIS = 100` 正是为此 |
| **② 回家（长距离）** | 到安全区 | ⚠️ **不该有紧预算** | 回家靠**到得了**，慢一点无所谓 |

**⇒ 而今天的缺口正是：① 有了，② 没有（无人负责"离家之后怎么回去"）。**

## §3 🟢 A 层：纯新增 / 可立刻做（3 条）

**⇒ 判定标准：不改变任何既有行为，只在既有判定点上挂一个查询或短路。**

### A-1 「区域上限」查询（纯新增，无调用者时零影响）

```
RegionCap.capAt(bot, pos) → { 是否属保护区 / 是否安全区 / 要不要记账 }
```

- 形态：**无状态查询**（照 `CollectGrants.covering()` 的样子），**不引入"bot 知道自己在哪"这个状态**
- 理由：状态一旦引入，就要维护"我出区了没"——那是笨重的来源
- 影响：**零**（没有调用者就什么都不发生）

### A-2 「越界降级」挂在既有判定点（不新增判定点）

- 做法：在 `WriteEnvelopes.had()` / `DropPolicy.effectiveProvenance()` 这两个**已有**判定点上，加一次 `RegionCap` 取交集
- ⚠️ 纪律：**只在已有判定点挂** —— 每个任务各判一次会慢慢长成第二个"到处是红线"（即 `survey/02` 记录的病灶「同一职责无单一归属」）

### A-3 「区外提权通道」= 直接复用 `PermissionGate`

```
PermissionGate.request(bot, "write.outside_region", "回程受阻，需临时搭路",
                       options, defaultOption=deny, timeoutTicks)
```

- **不需要新机制**（见 §2.2）
- 拒绝 ⇒ 走「如实失败 + 待机」（对齐"不卡死"原则）

**⇒ A 层总计：3 条，全部可在不触碰既有行为的前提下落地。**

## §4 🟡 B 层：需作者拍板（5 条）

### B-1 「区域 = 上限，任务 = 需求」（**不取交集**）

- 现状问题：区域授权与任务授权今天都在回答同一个问题（"现在能不能动这个方块"），于是怎么组合都别扭
- 提案：
  ```
  区域（地图）→ 回答"这里允许到什么程度"：一个**上限**
  任务（钥匙）→ 回答"这次作业要做什么"：一个**需求**
            实际权限 = 需求 ∩ 上限
  ```
- ⚠️ **为什么不能取交集**：取交集时 bot 一出区权限立刻归零 ⇒ **被迫待在区内**；而作者明确要求「**不强迫 bot 一定待在任务区域内**」
- 待拍板：这个形状对不对

### B-2 「区外 = 走路 + 显式申请」（作者本轮的修正）

- 作者原话：「区外不能完全不授额外权限，至少要给**显式申请提权**的通道，因为无法排除 bot 不搭路就没办法回到任务区的情况」
- 勘测侧：**同意**，且这正是 A-3 的依据

### B-3 「紧急提权只放搭路、不放挖掘」

- 依据：§1.3 的记账能力差异
- ⚠️ **附带确认**：这不是"放开"，相对今天 `survivalEscape` 的动作集而言是**收紧**（它今天已含 `BREAK_*`）
- 待拍板：是否收紧；以及搭路是否需要**上限**（如 ≤16 块）

### B-4 「紧急提权免玩家批准，但必须显式登记」

- 依据：作者原话「**要显式，不应该需要玩家的同意，因为保护区本来就有记账，所以恢复并不是一个大问题**」
- 现成机制：`Policy.NOTIFY`
- 待拍板：是否把这条能力名的默认档设为 `NOTIFY`

### B-5 「恢复做成独立延后任务」

- 作者原话：「**恢复世界修改内容也能做成独立的任务，相当于预留的任务，有时候恢复不适合马上做，可以延后**」
- 现状：`RestoreScopeTask` 已是独立 Task，**缺"待恢复队列 + 何时执行"**
- ⚠️ 「延后」**已被证明必需**，不是偏好：D-245 裁定逃生不得自动回收（理由：自动回收会**把 bot 重新关回坑里** ⇒ 逃生循环）
- 待拍板：待恢复队列的形态与执行时机

## §5 🔵 C 层：仅登记，现在别动（4 条）

### C-1 远距离寻路优化（**作者本轮明确：以后再说，登记**）

**⇒ Baritone 的实际做法（本次 clone 读取 `cabaletta/baritone` 分支 `1.20.1` 源码核实）：**

```java
// src/main/java/baritone/pathing/calc/AbstractNodeCostSearch.java:63-69
/**
 * This is really complicated and hard to explain. I wrote a comment in the old version of MineBot
 * but it was so long it was easier as a Google Doc (because I could insert charts).
 */
protected static final double[] COEFFICIENTS = {1.5, 2, 2.5, 3, 4, 5, 10};
```

**⇒ ⭐ 事实：Baritone 没有"先粗后细"的分层寻路。它用「多系数竞速 + 早退」：**

| 系数 | 含义 | 特性 |
|---|---|---|
| 1.5 | 几乎不贪心（近 Dijkstra） | 慢，路径质量最好 |
| 2 | 标准 A* | 中等 |
| 2.5 – 10 | 越来越贪心 | 快，路径烂 |

```java
// 同上 :195-214（原文节选）
for (int i = 0; i < COEFFICIENTS.length; i++) {
    ...
    if (dist > MIN_DIST_PATH * MIN_DIST_PATH) {   // MIN_DIST_PATH = 5
        if (COEFFICIENTS[i] >= 3) {
            System.out.println("Warning: cost coefficient is greater than three! Probably means that");
            System.out.println("the path I found is pretty terrible (like sneak-bridging for dozens of blocks)");
            System.out.println("But I'm going to do it anyway, because yolo");
        }
        return Optional.of(new Path(...));
    }
}
```

**⇒ ⭐ 关键事实二：Baritone 的"粗/细"是用 `Goal` 表达的，不是用搜索层表达的。**

- `Goal` 家族：`GoalBlock`（单格）/ `GoalNear`（某格附近）/ **`GoalXZ`（只定 XZ，Y 任意）** / `GoalYLevel` / `GoalAxis` / `GoalComposite` / `GoalRunAway` / `GoalTwoBlocks`
- `GoalXZ` 原文注释：「**Useful for long-range goals that don't have a specific Y level**」

**⇒ ⭐ 关键事实三（对 Alice 最重要）：Baritone 敢 yolo，是因为它不还债。**

| | Baritone | Alice |
|---|---|---|
| 对烂路径 | **yolo**（原文），能走就行 | ⚠️ **不能** |
| 因为 | 客户端模组，玩家自己收拾 | **服务端 bot + 建拆同权**：烂路 = 大量脚手架 = 可回收性负担 |

**⇒ 登记要点（未来做远距离寻路时必须先解决的）：**
1. Baritone 的"多系数竞速"可以直接借鉴（与分层不冲突，可叠加）
2. `Goal` 的层次化（`GoalXZ` 这类粗目标）是"先粗后细"的正确落点
3. ⚠️ **但 Baritone 的 yolo 策略不可照搬** —— Alice 的远距离路径必须对"烂路成本"负责

- 勘测侧：**该机制已存在**（`WriteAudit` / `ForeignBreak`），只是没被当成"只读记账"使用
- ⚠️ **"绝对不需要归因到方块"这条纪律请主工作流记住** —— 它限定了 §C-4 的天花板

## §6 ⚠️ D 层：与现有设计冲突，需拍板（2 条）

### D-1 ⚠️「非挖掘目标要恢复」与「账本只记放置」冲突

- 作者原话：「这个设计更重要的是**区分任务区域内的挖掘目标和非挖掘目标**，一个是 `KEEP`，一个是**需要恢复**」
- 现有 `Policy` 枚举**只有两个值**：

```java
public enum Policy {
    TEMP,   // 临时（垫脚柱/台阶/挖矿支撑）：必须配对拆除
    KEEP    // 永久（道路/玩家要求的建造）：不该拆，走独立授权
}
```

- ⚠️ **冲突点**：作者要的第三个（"原世界的方块被挖掉后要恢复成原样"）**不是** `TEMP`：

| | 谁放的 | 恢复成什么 |
|---|---|---|
| `TEMP` | **bot 放的** | 拆掉（→ air） |
| `KEEP` | bot 放的 | 不拆 |
| **作者要的** | ⚠️ **原世界的** | ⚠️ **恢复成原来的方块** |

- 而 `WorldModLedger` 原文**明确排除**了它（§1.3）
- **⇒ 勘测侧给的备选（需作者拍板）**：
  - **方案 α**：只对**保护区内的目标方块**记 `previous`，自由采集区不记 —— 保护区范围本来就小，开销可控
  - **方案 β**：维持现状，不做，接受"保护区里挖掉的方块不可恢复"
  - ⚠️ 注意：`Entry` 的 `previous` 字段**已经存在**（只是只有放置才写），所以 α 的改动面比想象的小
- **⇒ 作者此前的补充**：「其实记录被挖掘的原方块作用相当有限，现在的设计几乎没什么能让他挖掘保护区方块」⇒ **所以这条的优先级可能不高，但作者自己认为"设计更重要"在别处（区分目标 vs 非目标）**

### D-2 ⚠️「保护区 = 父类」与现有三个概念的收拢

- 见 §2.3：今天是 `CollectGrants`（掉落物授权）+ `ScopeBuffer`（记账作用域）+ `WriteEnvelopes`（任务写权），**三者互不相干**
- 作者要的是：**保护区（父，保护玩家财产）→ 安全区（子，保护财产 + 人身）**
- ⚠️ **风险（作者自己的担忧，原话）**：「**我感觉，风险极大**」
- **⇒ 勘测侧判定：不颠覆，但是一次"默认值反转 + 概念收拢"**

| 层 | 影响 |
|---|---|
| `PermissionGate` 四档 + `ONCE/SESSION/ALWAYS` | ✅ **原文可留**（"保护区要授权"正好是 `ASK`；无主地是 `AUTO`） |
| `CollectGrants` | ✅ 就是"保护区"的雏形 |
| `WriteEnvelopes` | ✅ 不用改 |
| `WriteAudit` / `BotEventLog` | ✅ 就是"只读记账" |
| ⚠️ `WorldModLedger` | 🔴 **在无主地是否记账 = 要拍板**（`RESIDUE` 判据会受影响） |
| ⚠️ `RestoreScopeTask` | 🔴 **在无主地是否启动 = 要拍板**（建拆同权依赖它） |
| ⚠️ `RecoverabilityReport` | 🔴 **语义是否重定义 = 要拍板**（今天 = 世界残留；作者的定义 = bot 能否回来） |

**⇒ ⚠️ 勘测侧必须标注（`survey/18` 教训）**：以上"可留 / 不用改"是**勘测侧归纳**，不是作者原话，也不是主线判定。

## §9 收档：作者原话（**不作抽象，原样保存**）

> 「对我来说，除了未声明的自由采集区，其他应该都应该以保护区为统一基地，不同任务设定的也是保护区，只是在保护区的基础上默认提权或者不提权，**保护区是一个统一父类**。」

> 「我总在担心 bot 不自由，就是因为在和你讨论或者和主工作流讨论，**让他挖矿都在单独计较怎么给预算，怎么记录账单**，还有一些你说到的，只读记账，也就是在自由采集区，玩家需要有迹可查，我觉得可以做一点点，但**绝对不需要归因到方块**，谁会去管其他玩家在这个矿洞里搭的路，挖的通道，因为本来又没说这个地方是自己的领地。」

> 「其实**记录被挖掘的原方块作用相当有限**，现在的设计几乎没什么能让他挖掘保护区方块，但是这个设计更重要的是**区分任务区域内的挖掘目标和非挖掘目标**，一个是 KEEP，一个是需要恢复，而且我希望**恢复世界修改内容也能做成独立的任务，相当于预留的任务**，有时候恢复不适合马上做，可以延后。」

> 「**避难所就是安全区，一个概念**，但可能尽量设定一个安全终点，也就是保证到室内而不是在房顶蹦跶。」

> 「我本来以为逃生预算是个好设计，但我现在来看，**为啥要给紧急情况设预算**？首先，寻路一定不要留预算，一定要能回家，如果 bot 不在保护区，设定预算到底有啥意义？如果 bot 在保护区，我觉得就算有预算也要拉高预算，同时加上**紧急提权**，只有必须放弃任务，立刻保活的情况才能这样提权，而且要**显式，不应该需要玩家的同意**，因为**保护区本来就有记账，所以恢复并不是一个大问题**，但我先要把保护区提权限定在**修建方块的提权**，让他搭路的风险真的比让他挖路风险小太多了。」

> 「逃生不是一种行为，有**局部逃生**和**任务放弃级别的逃生**……而且我还可能学 mc-aiplayer 的紧急情况预备方案，遇到无法解决的怪物，**用有的方块快速把自己围起来**，直到怪物离去或者被解救。……**不要现在去设计这个战斗系统，没办法急，登记就够了**。」

> 「**我感觉，风险极大。**」（指"我们刚才讨论的内容是不是要颠覆一大堆框架基础"）

> 「**远距离寻路以后再说，登记**，想办法优化远距离寻路。」

## §2 外部先例：探索（`L1` 的背景调查）

### 2.1 ⭐ Baritone `ExploreProcess`（✅ 完整源码逐行读过）

来源：`cabaletta/baritone` 分支 `1.20.1`，`src/main/java/baritone/process/ExploreProcess.java`。
**它是标准的前沿探索（frontier exploration）**，跑在一张**持久的区块访问图**上。六条可抄的点：

| # | 机制 | 源码事实 |
|---|---|---|
| 1 | ⭐ **三态** | `private enum Status { EXPLORED, NOT_EXPLORED, UNKNOWN }` —— `UNKNOWN` 的注释 = 「awaiting load」，即**磁盘 region 还没加载完，先别说"没探过"** ⇒ **防假否定** |
| 2 | **菱形/螺旋扩展** | 从 `explorationOrigin` 按曼哈顿距离一层层外扫；`for (int dist = distanceCompleted; ; dist++)` + `for (dx = -dist .. dist)` + `dz = ±(dist - |dx|)`；**内层跳过已 EXPLORED** |
| 3 | ⭐ **目标点故意偏向区块远端** | `int offset = renderDistance << 4; if (dx < 0) centerX -= offset; else centerX += offset;` ⇒ **站区块中心会浪费一半覆盖** |
| 4 | **二维目标 + 可选保 Y** | `GoalXZ(x, z)`；`exploreMaintainY == -1` ⇒ 纯二维，否则 `heuristic` 里**加上 `GoalYLevel.calculate(y, y)`** 作为同高度偏好 |
| 5 | **外部 JSON 过滤器** | `applyJsonFilter(path, invert)` —— 可指定"**只探这些区块**"（`LongOpenHashSet` + `invert` 两种语义） |
| 6 | **阻塞时暂停而非失败** | `return new PathingCommand(null, PathingCommandType.REQUEST_PAUSE)`（"awaiting region load from disk"）；region 在 `Baritone.getExecutor()` **独立线程**里 `tryLoadFromDisk` |

- ⚠️ **它的前提是 `CachedWorld`（磁盘区块缓存）**。**去掉那份缓存，`ExploreProcess` 就不成立** ——
  这正是 Alice 与服务端假人处境的分水岭（`survey/35` 已记 `CachedWorld` 全仓 0 命中）。
- ⭐ **可抄的三条**：三态（含 UNKNOWN）· "探新区往边上站" · 二维 Goal + 保 Y。

## §4 ⭐ 文 vs 图（`L2` 的回答）

### 4.1 直接证据：SpatialEval（`arXiv:2406.14852`，NeurIPS 2024）

专门评测**空间推理**（理解关系 / 导航 / 计数）。摘要四条结论：

> **（1）** Spatial reasoning poses significant challenges where competitive models **can fall behind random guessing**
> → 空间推理难到"有竞争力的模型会掉到**随机猜测以下**"
>
> **（2） ⭐ Despite additional visual input, VLMs often under-perform compared to their LLM counterparts**
> → **"尽管多了视觉输入，VLM 往往还不如它那个纯文本的 LLM 版本"**
>
> **（3） ⭐ When both textual and visual information is available, multi-modal language models
> become less reliant on visual information if sufficient textual clues are provided**
> → **"当文本和图像同时给出、且文本线索充分时，多模态模型会变得不那么依赖图像"**
>
> **（4）** leveraging **redundancy between vision and text** can significantly enhance model performance
> → 图文**冗余**能提升

- ⭐ **第 2 条是反直觉的**：不是"图不如文"，是"**加了图反而更差**"。第 3 条解释了原因 —— **模型自己会去抓文本**。

### 4.2 第二个数据点：图上"数东西"不可靠

AECV-Bench（`arXiv:2601.04819`，2026，建筑图纸理解）摘要原文：

> 「symbol-centric drawing understanding — **especially reliable counting of doors and windows —
> remains unsolved (often 0.40-0.55 accuracy)** with substantial proportional errors」

- ⇒ **在图上数门窗准确率 0.40–0.55。** 而"这附近有几棵树""矿脉有几格"**正是这类任务**。
- ⭐ 地图图片要求模型**从像素反推坐标** —— 它做不到；而**文本坐标是精确、无需测量的**。

### 4.3 项目侧：**没有图像通路**（✅ 实查）

- 全仓 `grep -rniE 'data:image|ImageIO|BufferedImage|multimodal|content.*image_url' src/main/java/` ⇒ **0 命中**；
- 唯二 PNG 是 **GUI 贴图**：`client/gui/BotInventoryMenuScreen.java:31`（`textures/gui/bot_inventory.png`）·
  `client/gui/BotInventoryScreen.java:36`（`slot.png`）；
- ⚠️ `decision/SpeechChannel.java:33` 的 `KIND_VISION_REPORT` **看着像视觉**，
  ✅ 但它只是「一条说出去的消息」的种类字符串，**不传图**。
- ⇒ **要走路，得先建整条视觉管线**（截图 → 编码 → 多模态模型 → 解析）。
  ⚠️ **模型是否多模态，勘测侧无法核**（配置目录读过界，不碰）。

### 4.4 ⭐⭐ 第三个选项（本文的建议）

`L2` 的问法里藏着一个前提：**"LLM 要认识地图"**。但 `L1` 的方案**已经绕开它了**：

| 做法 | LLM 要做什么 | 难度 |
|---|---|---|
| 给它地图图片 | **从像素反推**"那边有树吗" | ⭐ 空间推理 + 计数 ⇒ **§4.1/§4.2 说明它做不好** |
| 给它结构化文本 | **读**"附近树 ×3: (12,64,-8)…" | 读文本，**它擅长** |
| ⭐ **让它调用识别器** | **不用感知**，只问"这附近有几棵树" | ⭐ **感知全在服务端，LLM 只做决策** |

- ⭐ **第三种最强**，而且**它就是项目已经立下的契约**。✅ `decision/DecisionSnapshot.java` 类注释逐字：
  > 「**不放方块级世界细节**、不放日志、不放执行器内部状态——那些是确定性层的事，
  > **塞进去只会让 LLM 开始管执行细节**（也就越过"**只做目标级决策**"的边界）」
- ⚠️ 但要点名张力：**"让 LLM 认识地图"和 `D-135` 的边界是有冲突的**。
  这个冲突**不需要用"给不给图"来解** —— 用「**开放查询接口**」解：
  **LLM 不需要知道地图，它只需要能问地图。**

### 4.5 三条结论

1. **结构化文本胜出**（证据：SpatialEval 第 2/3 条 + AECV-Bench 计数 0.40–0.55）；
2. **纯文本够用**（证据：GITM 拿遍科技树、不用 GPU）；
3. ⭐ **优于"文 vs 图"的第三选项 = 查询接口**（`§4.4`）。

⚠️ **诚实边界**：三条证据全部是**摘要**，**未读全文**；
⚠️ 且**未找到 MC 场景下的"文本 vs 图像"受控对照实验** ⇒
"MC 里图像更差"这句**不能替用户断言**，只能给**邻域证据**。

### 5.6 ⭐⭐ 地形难度：**算法已有、只缺出口**

- ✅ `job/mine/StandingCostField.java` / `task/mining/StandingCostEstimator.java` =
  **从 bot 脚位做一次纯通行 Dijkstra**，得到"**半径内每个可达格的真实通行成本**"。
- ✅ `StandingCostEstimator` 注释逐字：「**S2 Dijkstra 成本场（默认）**：从 bot 脚位做**一次纯通行** Dijkstra
  （TRAVERSE/DIAGONAL/ASCEND/DESCEND，复用内核 provider 的谓词）」
- ⭐ **这就是"好不好走"的纯度量**，而且正好是纯通行（不含破坏）。
- ⚠️ 但它**只在规划时算一次、用完即丢**（`MiningPlanner` 用来给站位排序），**从未暴露给任何人**。
- ⇒ ⭐ **"让 LLM 知道这地方很陡"不需要新算法，只需要一个出口。**
  （最便宜的形态：把成本场**降采样**成"这个方向 N 格内的平均/最坏成本" ⇒ **一个数**。）
  ⚠️ **成本估计未实测，标为待验证。**

### 5.7 ⚠️ 感知层**扩不到区块尺度**

- ✅ `perception/PerceptionSnapshot.java` 的实现是**半径立方体暴力扫描**：
  ```java
  for (int dx = -radius; dx <= radius; dx++)
    for (int dy = -radius; dy <= radius; dy++)
      for (int dz = -radius; dz <= radius; dz++)   // radius = 5 ⇒ 11³ = 1331 次读取
  ```
  ⇒ 扩到区块（16×16×384）就是 **98304 次** ⇒ **不可行**。
- ⭐ **所以需要的不是"把半径调大"，是换形状**：从"立方体扫描"换成"**识别器 + 标记列表**"
  —— **这正是 `L1` 提的方向**。
- ✅ 另两条现状：`command/BotCommand.java:2203` 的 `/alice observe` **硬编码 `PerceptionProfile.MINING`**
  （连这个入口都只有挖矿视角）；
  `PerceptionProfile` 类注释自述：「当前只预置挖矿/通用两个视角；**建造/探索/战斗视角按里程碑补充**，
  且**危险/收获集合是硬编码**」。

### 5.8 一条更便宜的替代：**环形记录**

- `L1` 说"LLM 能自己选择寻找目标的区块倾向"。那么问题：**它选错了方向、什么都没找到，怎么知道要换？**
  - 完整答案 = 区块访问图（贵）
  - ⭐ **便宜答案 = 一个环形记录**：记下"**最近去过的 N 个区块 + 结果**"，喂给 LLM，
    **让它自己排除** ⇒ **不需要地图，只需要"最近去过哪"**，且**不需要持久化**（会话内环形缓冲）。
- ⚠️ 这是勘测侧推断，**未验证**。

## §6 ⭐ 第一层目标的限定（`L3`，本轮重点）

### 6.2 ⭐ 为什么"区域任务 / 锚点任务"确实更基础（勘测侧核对，✅ 有依据）

| 维度 | 区域任务 / 锚点任务 | 地表探索 / 找目标 |

| **目标搜索** | ⭐ 在**有界范围内**扫 ⇒ 复用现有候选源 | 需要**前沿探索 + 地图记忆** |
| **跨会话记忆** | ⭐ **不需要**（区域内可重扫） | ⚠️ **必需**（否则重走已探区） |
| **失败判据** | ⭐ "这一圈扫完了"**可判定** | ⚠️ "真没有"与"走错方向"**不可区分**（`survey/35 §3` 同类问题） |
| **预算** | ⭐ 可由范围推导 | ⚠️ **无源可推**（`survey/35` 已记） |
| **已有资产** | ✅ `REGION_LUMBER`（`job/JobRequest.java:46`）· `LumberRegionState` · 常驻巡查状态机 | ❌ `explore` 全仓 0 命中 |

### 6.3 ⭐⭐ `survey/26` 的结论正好支持这个限定

  > 但实际上**两种锚点模式都可能有各自的用处**」
- ✅ 该报告的结论逐字：
  ```
  一套任务（不定工作区 + 自动搜索附近目标）
      ├─ 锚点取值一：固定锚点
      └─ 锚点取值二：玩家锚点
  ```

- ⇒ ⭐ **"一套任务 + 锚点取值"这个形状，天然就是"有界范围 + 目标搜索"**

### 6.3b ⭐⭐ 区域任务 vs 锚点任务（`L4`→`L5`→`L6`→`L7` 四次澄清后的定稿）

**四次澄清的口径（逐字见 `§1.3.1` 与 `§1.4.1`）**：

| 轮 | 用户说的 | 关键 |
|---|---|---|
| `L4` | 区域任务**必须划任务区**（保护区的子区域）**按区块划分**，要做保护区权限管理；锚点任务**一般在保护区外** | 位置 |
| `L5` | **不是保护区也可以建立任务区**；**锚点任务跟区块无关**，只由锚点和任务决定的**半径**决定 | 形状 |
| `L6` | **任务区还是保护区的子区域**，只是**保护区是父类，任务区继承保护区的部分定义和功能** | ⭐ **类型层次**（"子区域" = **子类**，不是领地包含） |
| `L7` | ⭐ **锚点任务的意义 = 临时/快速部署，不需要圈地，随时可以设置锚点开始任务** | ⭐ **部署成本** |

| | **区域任务** | **锚点任务** |
|---|---|---|
| ⭐ **为什么存在** | 长期 / 有主的**资产保护**（保护区内干活要提权） | ⭐ **临时 / 快速部署** —— **不需要圈地，随时可设**（`L7`） |
| **区域类型** | ⭐ **任务区** = 保护区的**子类**（继承账本 + 权限要求；`L6` + `D-338` ①） | ⚠️ `L4`：「一种**类**区域任务」，**权限管理还没讨论** |
| **范围形状** | 工作区域 = **目标包围盒 + 余量** ⇒ 任务区 = **所占区块的最小覆盖（hull）**；⚠️ **Y 不参与派生** | ⭐ **与区块无关**：范围 = **锚点 + 任务决定的半径**（`L5`） |
| **是否需要声明** | ⚠️ 要（任务区由**任务自己声明**，随 `scopeId` 生灭；`D-338` ⑦） | ⭐ **不需要圈地** ⇒ 部署成本低（`L7`） |
| **能否在非保护区划** | ⭐ **可以** —— `TaskZoneRegistry:42-43`「也可以在没有保护区的**野外独立划分**」 | ✅ 常在区外（`L4`） |
| **落地状态** | ✅ **有资产**（`REGION_LUMBER` / `LumberRegionState` / `TaskZoneRegistry`） | ⚠️ **还没做过**（`L4`） |

#### ✅ 勘测侧核对（三个直接引文）

- ✅ `TaskZoneRegistry.java:42-43`（覆盖规则）逐字：
  > 「任务区**可以覆盖保护区父类**（**也可以在没有保护区的野外独立划分**）；
  > ⛔ **不得覆盖任何子类声明**（今天 = 安全区）。」
  ⇒ ⭐ 这是 `L5`「**不是保护区也可以建立任务区**」的**代码出处**。
- ✅ `TaskZoneRegistry.java` 类注释（两层结构）逐字：
  > 「① **实际工作区域 work area** = **方块级**（任务语义：林场范围 / 蓝图 footprint / 目标簇），由**任务**给出；
  > ② **任务区 task zone** = 工作区域**所占区块的最小覆盖**（hull，**不扩边**），由工作区域**单向派生**。」
- ✅ `TaskZoneRegistry.java:74`：「⚠️ **Y 不参与派生**…**忽略 Y、覆盖全高度**」

#### ⭐ 三条同时成立（**互不矛盾**）

| # | 命题 | 出处 |
|---|---|---|
| 1 | **任务区是保护区的子类**，**继承**其账本 + 权限要求 | `L6` + `D-338` ① |
| 2 | **不是保护区也可以建立任务区** | `L5` + `TaskZoneRegistry:42-43` |
| 3 | **锚点任务跟区块无关**（半径）；它的价值是**部署便宜** | `L5` + `L7` |

⇒ ⭐ **1 与 2 不矛盾**：**正因为任务区自己就是一种（子类）保护区**，声明它**不要求先有保护区认领**。

#### ⭐⭐ 由 `L7` 得到的更清晰读法：**两者是"部署成本的两个档"**

```
划一块区域（区域任务）: 有主的长期资产会反复用 → 一次声明，长期复用，但**要先圈地**
设一个锚点（锚点任务）: 临时/一次性 → **随时可设、用完即弃**，但**没有区域承诺**
```

- ⇒ 所以 `L4` 说「**权限管理还没讨论**」有了**更清楚的原因**：
  ⭐ **锚点任务不圈地 ⇒ 原则上不声明区域 ⇒ 没有区域权限要管**（区外本来就 `D-398` R4 无限制修改）。
  ⚠️ **但边界情形仍在**：**锚点恰好在保护区内 / 跨保护区域边界**时怎么办？
  ⇒ 这是**勘测侧无法裁定**的，正是"还没讨论"那句话所指。

#### ⚠️ 一条真落差（勘测侧推断，未验证）

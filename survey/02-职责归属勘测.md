## §1 病灶：同一职责，没有单一权威

把仓库里的重复现象排在一起，会看到同一个形状：

| 现象 | 证据 |
|---|---|
| **六份重复** | 旧伐木 `ContinuousLumberTask`(531 行) + `RegionLumberTask`(505 行) 各自写一遍：选树 / 状态机 / 移动 / 清障 / 收集 / 记账（`JOB_LAYER_DESIGN.md` §2.2） |
| **三套清障** | `MAX_CLEAR_DEPTH` / `findLeafBlocker` / 规划器模式 B → 最终裁定"清障归 L3 Job"（D-081 追加裁定） |
| **四例死抽象** | `WorldView`（已删）/ `RecoverabilityLevel` / `IntrinsicReversibility` / `FluidRiskPolicy`（详见 `docs/RISK_SYSTEM_ISSUE_LIST.md`） |
| **三套横切透传** | `RiskProfile`（计划）/ `WorldModLedger`（D-081）/ `SafeZoneData`（已有）各自想办法穿层 |

> **这四件事是同一个病**：**同一职责没有单一权威**——要么散在多处（重复），要么建了没人接（空抽象）。

### 1.1 而你**已经发明了药**，而且用得很好

| 决策 | 药方 | 治什么 |
|---|---|---|
| **D-076** | 世界修改必须**显式授权** | 把"谁能改世界"从隐性约定变成显式契约 |
| **D-080** | **每件事各归其位、只写一遍** | 直接治六份重复 |
| **D-081** | **建拆同权**（授权即配对） | 把"区域不许残留"从**靠自觉**变成**授权内建的不变量** |

> 三条决策是**同一个药方的不同剂型**：**给每个职责指定唯一归属，并把它写成可断言的不变量。**

## §3 按"什么时候真的会疼"排序

> **这不是价值排序，是疼痛时间表。**

### 🥇 抢占 / 中断模型 —— **J8 之前必须定**

**为什么会疼**：D-081 已批准 **`MAINTAIN` 持续型 Job**（常驻、只由玩家命令停止）。
一旦**常驻任务 + 玩家临时命令**（右键让它跟随/挖矿）同时存在，**抢占就是日常操作**，不是边缘情形。

**这是最可能"做完了再推翻"的一块**——因为 J8 一上就要用，而需求现在**一个字都没写**。

参考：Baritone 有 `PathingControlManager` 的 process 优先级栈；Alice 的 `Job` 现在是**单一任务，没有栈**。

**可学的成熟方案**：Brooks 的 **Subsumption Architecture**（层次抑制、安全层压倒目标层、无全局状态）。
勘测建议的仲裁顺序（待讨论）：

```
反射（执行器，tick 级自救，优先级最高）
  > 维生（绝对否决 + 必须给出"去哪"）
    > 玩家命令（显式、短期）
      > 当前 Job（长期目标）
        > 风险准入（过滤 + 定价，不宣称否决权）
```

### 🥈 感知 / 世界查询层 —— **J5 就会复发**

**为什么会疼**：J1 的 `TreeScanner` 已在自行 BFS 扫世界。J5 的 `MineCandidateSource` 会**再扫一遍**——
这就是六份重复的**第 7 份**。

它同时是 **LLM 接入的前提**：`RISK_MODES_DISCUSSION.md` A.3 要求把世界"压缩成简单场景描述数据包"。
**没有统一查询层，无法做这个压缩。**

**但勘测建议：不要现在做。** 等 J5 落地、**两个候选源都真实存在**之后，再抽接口——
那时才知道接口该长什么样（与 D-080 拒绝提前建 `RiskProfile` 是同一条纪律）。

**已有基础**：`perception/` 的 `PerceptionProfile` / `PerceptionClassifier` / `PerceptionSnapshot`
已经把"分类聚合 + 任务视角 Profile"做出来了（`MINING` / `GENERAL`）。**这是现成的立足点。**

### 🥉 授权模型 —— **J7（攀爬）之前必须定**

**为什么会疼**：`PathRequest` 现有 **3 个静态工厂**（`of` / `withWorldModification` / `miningApproach`），
而 `JOB_LAYER_DESIGN.md` §11-① 攀爬砍树**明确要求"新的显式授权入口"** → **第 4 个**。

**3 个是临界点**。再往下就是 6 个静态工厂 + N 个独立预算字段，
且每个新能力都要人肉记得"别偷偷加进 `miningApproach`"。

**这是 Policy Gate 的最小子集**——蓝图 §2.2 自己标注「需要显式补出的层」，
且 4/7 阶段依赖它（见 `01-蓝图勘测报告.md` §4.3）。

### 其余四项（真实缺口，但现在不用急）

| 拼图 | 触发点 | 一句话 |
|---|---|---|
| **资源会计** | J7 的方块预算 | 饥饿 / 方块 / 工具磨损应是**同一套会计**，不是三套阈值。它同时是"风险报价"的第一个真实消费者 |
| **失败上报** | 随时（对用户立刻有价值） | 「多层失败向上传递」是三大差异之一，但**只有发送端没有接收端**。可先做 `PlayerReport`（人读）版本——**不需要 LLM** |
| **记忆** | 风险系统落地时 | "上次在这儿被烧过"这类**危险记忆现在根本不存在**。现有两个 `SavedData` 是**特定领域**的（好设计），但第 3、4 个会出现 |
| **每 tick 总预算** | 多 bot 之前 | 多 bot + 多 Job + 寻路 + 感知 = 卡服。现在只有 `SearchBudget`（单次搜索局部） |

## §4 我建议**不要**做的（看着像拼图，其实是坑）

> 这一节与 §3 同等重要。以下符合"看起来该做"，但按 D-046 / D-080 的纪律**不该现在做**。

| 别做 | 为什么 |
|---|---|
| ❌ 统一 `SavedData` 抽象 | 为 2–3 个数据造抽象 = 下一个 `WorldView`。**等到第 3、4 个出现再抽** |
| ❌ 现在接 LLM | 没有消费者。先把 `SelectionPolicy` 的**第二个实现**做出来（J3 正在做） |
| ❌ 通用"能力系统" | 一定会变空抽象。等有 3 个真实模组适配（阶段 E）再说 |
| ❌ 多 bot 并发 | 明确不做。**但要在新代码里守住"不引入新的全局静态"**——`RiskSwitches` 已经是 1 个 |
| ❌ 提前抽感知层接口 | 只有 1 个候选源时抽出来的接口一定错（见 §3 🥈） |
| ❌ 给 `RecoverabilityLevel` 现在接线 | 它承载的"可回收"语义**还没定义**。J6 账本（建拆同权）会**定义**它。顺序应为 **J6 → 再裁定 `RecoverabilityLevel`**，否则是在给未定语义造抽象（第 5 个死抽象） |

## §5 三条横切关注点正在各造一套透传机制（值得警惕）

| 关注点 | 需要穿到哪 | 现状 |
|---|---|---|
| `RiskProfile` | `PathRequest → MovementContext → provider → 执行器` | D-046 已定路径，**未实现** |
| `WorldModLedger` | 动作层自动写（**含内核 `PILLAR` 放的方块**） | D-081 已裁定 |
| `SafeZoneData` | 破坏/放置门禁 | 已有 |

**它们要解决的是同一个工程问题**：一个跨层上下文——**谁创建、谁持有、何时冻结、如何过期**。

> **建议**：不要做三套。至少让它们**共享同一种透传机制**（同一个 context 对象携带，
> 或同一个"策略快照"模式）。否则会出现**三份"某层忘了传"的 bug，且每种的 debug 方式都不同**。

## §6 一个正面信号（也提醒了一个边界）

`TransferLedgerData`（`transfer/`）与 `WorldModLedger`（D-081 计划）是**同一种模式**：
**持久化 + 挂起/恢复 + 配对记账**。

- ✅ **说明该模式是对的**（第二次复用 = 验证通过）。
- ⚠️ **但第 3、4 个 ledger 出现时应该抽出共同骨架，而不是复制第三遍。**
  这正是 §1 那个病灶的预防点。

## 1. 先把"性能"拆开，否则一定会算错

用户问的是"占用多少资源 / 消耗多少性能"。这三个字的答案**取决于你问的是哪一类**，而三类之间差了几个数量级：

| 类别 | 什么时候发生 | 量级 | 会不会伤 TPS |
|---|---|---|---|
| **① 存在成本** | **只要 bot 存在**（哪怕待机） | ≈ 一个 AFK 真玩家 | 稳态、可忽略（1 bot 时） |
| **② 固定成本** | **每 tick** | 每 bot 约 8 项小检查 + 一套玩家物理 | 稳态、很小 |
| **③ 突发成本** | **触发时**（规划 / 菜单 / 危险） | **几十 ms ~ 数千 ms** | ⚠️ **会** —— 而且可能是整 tick |

**⇒ 一句话：Alice 的稳态开销不是问题，问题全在"某一次调用"上。**

## 2. 三类开销逐条落实（含证据行号）

### 2.1 ① 存在成本：**区块票**（最容易被忽略的一项）

```java
// BotPlayer.syncPlayerChunkTicket()（BotPlayer:109-119）
net.minecraft.core.SectionPos now = SectionPos.of(blockPosition());
if (now.equals(lastTicketSection)) { return false; }   // 只在跨 16 格边界时才做
lastTicketSection = now;
serverLevel().getChunkSource().move(this);              // ← 真人 handleMovePlayer 走的就是这条
```

**为什么它贵**：`ServerChunkCache.move(ServerPlayer)` → `ChunkMap.move` → `DistanceManager` 的玩家票 ——
**⇒ 假人持有一张玩家票 ⇒ 它周围的区块被保持加载**（而那些区块里的方块实体、随机刻、生物生成都在继续跑）。

**结论**：**一个假人的存在成本 ≈ 一个 AFK 真玩家。**
⚠️ **实际半径取决于服务端的 view / simulation distance，本文未实测。**

**⚠️ 两个附带的、值得单独登记的观察**：

| # | 观察 | 证据 |
|---|---|---|
| **a** | **包会被序列化再丢弃** —— 假人自身的包没有接收方，但序列化成本照付 | `BotPlayer:104` 自述：「对假人而言包会被 `FakeConnection` 丢弃，但**仍有序列化成本**」 |
| **b** | ⚠️ **假人很可能计入生物生成（mobcap）** —— bot 包里**没有任何** `isSpectator` / `mobcap` 相关处理，且创建时**显式设为 `SURVIVAL`** | `BotManager:147` `bot.gameMode.changeGameModeForPlayer(GameType.SURVIVAL)`；全仓 `mobcap` **0 命中**（`spectator` 仅 2 处，与生成无关） |

**⇒ 观察 b 的含义**：真玩家的 mobcap 是**按"附近玩家数"缩放**的 ⇒ 假人会把**生物生成区扩到玩家从没去过的地方**，而**生物 AI 是服务端最重的开销之一**。
**⚠️ 这一条我只有"代码里没处理"的静态证据，没有实测 —— 列入 §9 待确认第 1 条。**

**✅ 一个我原本担心的点，查完否掉了**：客户端同步只广播**旋转包**（`FakeConnection.send` 只放行 `ClientboundRotateHeadPacket` / `ClientboundMoveEntityPacket.Rot`），位置/速度包直接丢弃 ⇒ **不会每 tick 向所有玩家广播位置包**。
（客户端看到的 bot 位置由原版实体追踪器 `ChunkMap` 正常下发，与真玩家同源。）

### 2.2 ② 固定成本：**每 tick，很小**

主循环（`BotManager.onServerTick` → `for (BotSession …)`，`BotManager:964-984`）：

| # | 每 tick 调用 | 量级 |
|---|---|---|
| 1 | `session.bot().syncPlayerChunkTicket()` | **几乎免费**（只在跨 16 格边界时做事） |
| 2 | `checkEntityTickProgress(session)` | 1 次 long 比较（`BotManager:1090-1093`） |
| 3 | `SurvivalSystem.tick(bot)` → `Monitor.observe` → `classify` | **≈ 10 次方块/流体读**（`containsFluid`/`containsWater` 各只读"脚位 + 头顶"2 格，`SurvivalSystem:439-448`） |
| 4 | `session.tick(hazard)` | 任务驱动（见下） |
| 5 | `PermissionGate.tick(bot)` | 一次状态检查 |
| 6 | `MenuLifecycle.tick(bot)` | 一次状态检查 |
| 7 | `EventThresholds.tick(bot)` | **4 项检查**（`EventThresholds:99-102`：工具耐久 / 卡住 / 无进度 / 掉血） |
| 8 | `GoalDirector.tick(bot)` | 收 future + 空闲判断（**LLM 已在异步**，见下） |

物理侧（`BotPlayer.tick()`，`BotPlayer:270-325`）：
- `controller.onUpdate()`（设输入）
- `super.tick()`（= `ServerPlayer.tick()`，**记账**，不含 baseTick/aiStep —— 已用字节码核对）
- 手动补 `baseTick()` + `aiStep()`（D-228；顺序与原版一致：baseTick 先、物理后 ⇒ **不跑两遍**）

**⇒ 这一整套叠起来 ≈ 一个真玩家的水平**（少了网络层收包与包处理）。

**✅ 又一条查完否掉的担心**：`GoalDirector` 的 LLM 调用**在异步**（`state.pending = LlmClient.askAsync(...)`，`GoalDirector:296`），主线程只做 `pollResult` ⇒ **LLM 的网络往返不占主线程**。
（`survey/10` 已把这条登记为"异步的正确形状模板"；这里只做**性能侧的确认**。）

### 2.3 ③ 突发成本：**这里才是问题**

| 源 | 规模 | 依据 |
|---|---|---|

| **⛔ 搜索预算（真正走的生产路径）** | **`SearchBudget.UNLIMITED` = (maxNodes 0, maxMillis 0L, 永不取消) ⇒ 无任何上限** | `SearchBudget:13`；`PathRequest.of:39` / `:52` / `miningApproach:65`、`restore:84`、`climbApproach:103` 全传 `UNLIMITED` |

| **⚠️ 菜单里的配方扫描** | **≤ `MAX_RECIPE_SCAN = 8000` 条配方**，每条含 `getResultItem` + 注册表查询 + `ingredientsHeld`（**每个 `Ingredient` 扫一遍背包 ≤36 格**） | `CandidateMenu:45`、`craftableScan:293-343`、`ingredientsHeld:347-366` |

**⭐ 关于菜单构建，一句必须说清的话**：
`:39` 的注释已经把这笔账算出来了，而 `MineMenuCheckTask:176` 更直接地写着
「**重复构建会在一个 tick 里白烧掉百万次读**」—— **⇒ 主线早就知道这件事，本报告不邀功**。
本报告要补的是**它的另两面**：

1. **它冗余**：`mineScanTargets()` 返回 **11 个目标**（6 个 `COMMON_ORE_TAGS` + 5 个 `RARE_ORES`，`MiningBudget:52-59`），
   而 `CandidateMenu:185-188` **为每个目标 new 一个 `MineCandidateSource` 并各跑一次完整三重循环**
   （`MineCandidateSource.candidates:107-146` 是**裸三重 for，无任何缓存**）⇒
   **同一个 25³ 立方体被扫了 11 遍，每遍只是换一个 `target.matches()` 判据**。
   **⇒ 1 次扫描 + 11 路分类，就能等价替代 11 次扫描 —— 省 91%，且不改任何语义、不改任何接口。**
2. **它的频率是有上限的**：`CandidateMenu.build` 在生产路径上只被 `GoalDirector.fire` 调用

   （`LlmConfig:92-93`、`GoalDirector:260-271`）⇒ **正常自主决策时 ≤ 6 次/分钟**。
   **⇒ 所以它是"尖峰"，不是"稳态"**；但**每次尖峰都可能跨过整个 50ms tick**（§3 表格）。
   （例外：玩家手动触发 `instruct`/`manual` 无此节流，`BotStateReport` 也走菜单 —— `BotStateReport:29`。）

**⚠️ 再纠正一处**（避免把 `survey/09` 补遗 A 读成"逃生预检无界"）：
`SurvivalSystem.plannableRefuge` 里的预检**是有界的**（600 节点 / 20ms，`SurvivalSystem:179-180`、`:203-205`）。

⇒ **"跨 2 tick 里，第二个 tick 的那次规划才是没有上限的那个"** —— 与补遗 A 的结论一致，这里只是把归属写准。

## 3. 现在的量级表（⚠️ 全部是推算）

| 场景 | 每 tick 稳态 | 尖峰 | 依据 / 备注 |
|---|---|---|---|
| **bot 待机（区块已加载）** | **≈ 一个 AFK 玩家** | 无 | §2.1 + §2.2 |
| **bot 待机（未知区域）** | — | ⚠️ 区块装载/光照绑定（**未实测**） | §2.3 末行 |
| **正常作业（走 + 挖）** | **≈ 略高于一个玩家** | 无 | §2.2 + 挖掘进度检查 |
| **一次常规规划**（几百~几千节点） | — | **10 ms ~ 数百 ms** | 量级推算 |
| **一次规划撞上预算** | — | ⛔ **最坏 3,000 ms = 60 tick** | `CorePathPlanner:15` |
| **行走类规划（`PathRequest.of`）** | — | ⛔⛔ **无上限** | `PathRequest:39` + `SearchBudget:13` |
| **一次菜单构建（≤6 次/分）** | — | ⚠️ **约 30 ms ~ 90 ms**（29 万次方块读 + ≤8000 配方） | 推算：按 100 ns/方块读 ⇒ 29 ms；配方扫描另计 |
| **软危险持续中（着火/冻/溺水）** | ⚠️ **每 tick 约 3~4 万次读** + 可能一次 ≤20 ms 规划 | — | `survey/09` 补遗 A |
| **一把危险里的第一次判定** | — | 一次 17³ 扫描 + ≤600 节点规划 | `SurvivalSystem:194-223` |
| **一次 LLM 决策往返** | **0（异步）** | 0 | `GoalDirector:296`（`askAsync`） |

**⇒ 一句话总结现在**：**稳态 ≈ 一个玩家；尖峰可以是一整个 tick，甚至 60 个 tick。**

## 4. FPS：取决于你怎么跑（这是用户问题的直接答案）

| 形态 | TPS 影响 | FPS 影响 |
|---|---|---|
| **专用服务器 + 独立客户端**（多人服的正常形态） | 与玩家数、每 bot 开销成正比（N bot 时见 §5） | **≈ 0**。客户端 FPS 由**客户端自己的渲染预算**决定；服务端停顿时客户端只是"这一 tick 没收到新状态"，**不会降低帧率**。bot 只是一个玩家模型（渲染成本 = 一个玩家） |
| **单机（集成服务端：`IntegratedServer` 与客户端同一进程、同一主线程）** | 与上面同 | ⛔ **服务端每个停顿 = 直接掉帧**。主线程被"菜单构建 / 规划 / 区块生成"占住的那些毫秒，**就是画面卡住的那些毫秒** |
| **服务器与客户端同机但分进程** | 同上 | 间接（CPU 争用，主要是内存带宽与 cache 竞争） |

**⇒ 关键判断句**：
> **你在单机里测试时感觉到的"卡"，大概率不是 FPS 问题，而是 TPS 停顿。**

**⇒ 对勘测的实用含义**：
- **给朋友开的服是"专用服务器 + 各自独立客户端"⇒ 性能问题会被**（相对）**掩盖** —— 就像 `survey` 里那条"绿是被真人掩盖的"（`BotPlayer:96-97`：夹具全绿是因为真人站在旁边补了票）一样，**专用服务器会掩盖主线程停顿**。
- **但你自己测的时候是单机 ⇒ 问题会以"掉帧"的形式暴露** ⇒ **两个环境的观感会不一致，别用单机的观感去推多人服，反之亦然。**

## 5. 未来：真正的量变来自 bot 数（而非线程）

（本节与 `survey/10` 同源，这里只从**资源量**角度收敛。）

| 维度 | 增长方式 |
|---|---|
| **每 tick 固定成本** | **× N**（`BotManager:964` 的 `for (BotSession …)` 是**串行**的） |
| **区块加载面积** | **× N**（分散作业时叠加；同区域时共享 —— 所以"把 bot 都放在同一片区域"本身就是一种性能策略） |
| **搜索尖峰** | **× N，且相互阻塞**：一个 bot 吃 40 ms ⇒ **其余 bot 这一 tick 什么都没做**（`survey/10`） |
| **生物生成** | ⚠️ 若 §2.1 观察 b 成立 ⇒ **每个 bot 都在扩 mobcap**，这个增长是**非线性的**（更多 bot ⇒ 更多生物 ⇒ 更多 AI）**⇒ 这是我最担心的一条** |
| **菜单 / 决策尖峰** | ≤ 6 次/分 × N（且可被 `GoalDirector:260` 的节流合并） |

**⇒ 结论**：多 bot 的灾难**不是线程问题，是分配问题** —— **N 个 bot 分一个 50ms tick**。
（`survey/10` 已给出方向：**给 tick 做预算**；本报告只补一条资源侧的依据：**tick 是唯一需要被"分配"的稀缺资源**，CPU 核数不是。）

## 6. 三个悬崖（按"多久会真的踩到"排序）

| # | 悬崖 | 触发条件 | 后果 | 修法成本 |
|---|---|---|---|---|
| **1** | **行走类请求无预算上限**（`PathRequest.of` ⇒ `UNLIMITED`） | 目标可达但空间巨大；或目标不可达且空间巨大（软危险里的逃生最容易） | 主线程**任意久**阻塞 | **一行**：给一个 `SearchBudget.of(...)` |
| **2** | **软危险持续期间每 tick 一次 17³ + 可能一次规划** | 活着火 / 冻着 / 泡水**且**附近无落点（`HOLD_NO_EXIT` 语义**必然**让 bot 继续移动 ⇒ 缓存每 tick 失效） | 每 tick 吃掉半个 tick 预算，**持续到危险结束** | 缓存键从"精确脚位"改为"脚位所在的**区块/SectionPos**"或加时间下限（**改动小，但属于设计决策，不是勘测员该定的**） |
| **3** | **`DEFAULT_MAX_MILLIS = 3000`** | 搜索撞满 20k 节点或 3 秒 | 最坏 60 tick 停顿 | 调小该常量 or 给 `planTo` 用别的预算 |

**⚠️ 诚实说明**：这三个悬崖**今天都不一定会被踩到**（需要"大范围搜索 + 复杂地形"同时成立）。**但 1 和 3 是同一处的两个值，2 是主线刚引入的（D-238）** ⇒ 它们是**同一族问题**，不是三个独立的事。

## 8. 诚实标注：哪些是推算，怎么变成实数

### 8.1 全部是推算的项目（**没有一项实测**）

- 每次方块读的耗散时间（本报告按 **100 ns/次** 折算毫秒；真实值受 chunk 是否 loaded、palette 深度、Section 索引影响）
- 每节点候选数（本报告按"纯通行 ≈16 / 全 Movement ≈45"计，**没有数到每条候选分支里的全部方块读**）
- 菜单构建的 30~90 ms
- 常规规划的 10~数百 ms
- 区块票的实际保留半径
- **假人是否真的计入 mobcap**（只有"代码里没处理 + 显式 SURVIVAL"的静态证据）
- 单机掉帧的实际严重程度

### 8.2 ⭐ 好消息：**实测不需要新基建**

`PathPlan` 已经带着**全部需要的三个数**：

| 字段 | 位置 |
|---|---|
| `nodesExpanded` | `PathPlan:21` |
| `movementsConsidered` | `PathPlan:21` |
| `elapsedMillis` | `PathPlan:22` |

而**全部行走类规划的必经之处是 `PathRetryRunner:62`** 那一行：

```java
PathPlan plan = new CorePathPlanner().plan(bot, bot.serverLevel(), request);   // ← 加一行日志即可
```

**⇒ 在那一行后面打一行 `plan.elapsedMillis()` / `plan.nodesExpanded()` / `plan.movementsConsidered()`，
就能拿到真实场景下的全量分布**（不需要 profiler、不需要新类、不需要改架构）。
现有可选替代：`PathingPlannerItem:78-79` 手动打点（但那是手动道具，覆盖不全）。

### 8.3 要变成决策依据，最少要测这 5 个数

| # | 测什么 | 怎么测 | 为什么它是关键 |
|---|---|---|---|
| 1 | **一次常规规划的 ms 分布**（中位数 + P99） | §8.2 一行日志 | 决定 §6 悬崖 1/3 到底会不会踩到 |
| 2 | **一次逃生的预检 + 真正规划**（`survival-precheck` 与 `survival_exit`） | 同上 + `[Search]` 日志 | 决定 §6 悬崖 2 的严重度 |
| 3 | **一次菜单构建的 ms** | 在 `CandidateMenu.build` 出口打点 | 验证 §2.3 的 30~90 ms |
| 4 | **边际区块数**（bot 走进新区域时，服务端加载了多少区块） | 服务端 chunk 统计 / `/debug` | 直接对应"存在成本"是否可忽略 |
| 5 | ⭐ **同一区域内，有 bot 与无 bot 的生物数对比** | 数生物实体 | **验证 §2.1 观察 b（mobcap）—— 这是我认为最可能被低估的一条** |

**⚠️ 本环境跑不了这 5 项**（无 Java / 无 Forge 服务端），**需要在你的 PC 上做**。

## 0. 结论速览

### 0.1 本草案的核心命题

> **「额度继承」这个词本身是歧义的。**
> 时间类资源**只能共享**（父扣子也扣），配额类资源**只能分配**（父给子一个上限）。
> 把两者混为一谈，就是当前所有混乱的根源。

### 0.2 ★ 勘测中发现一个真实缺陷（本草案的活标本）

`LumberJob` 的 **`clearedBlocks` 用了 job 级计数器去比 tree 级限额**：

| 事实 | 证据 |
|---|---|
| 限额声明为**每棵树** | `LumberCandidateSource.java:37-38`：注释「**单棵树**允许的清障格数上限（§9-4：≤8 格/**棵**）」，值 `8` |
| `LumberJob` 用 **job 级字段** | `LumberJob.java:65` `private int clearedBlocks;` —— **全仓无任何 `= 0` 重置**（已 grep 验证） |
| 与 tree 级限额比较 | `LumberJob.java:188` `MAX_CLEAR_PER_TREE - clearedBlocks`；`:222` `clearedBlocks < MAX_CLEAR_PER_TREE` |
| 同一常量在**另一处**是 per-tree 语义 | `LumberCandidateSource.java:84-86` 用**局部变量** `clearBlocks` 逐棵累计 ✓ |

**后果**：整个 Job **累计**用掉 8 格清障后，
**后续每棵树的清障额度都是 `8 - 8 = 0`** → `nextClearStep(..., 0)` 在
**`BlockerClearPlanner.java:127-129`** 直接 `return null`
→ 后续需要清障的树全部以 **`:clear_budget`** 失败（`LumberJob.java:190`），
**尽管它们本应各有一份 8 格额度**。

**影响范围**：同时打穿**两条**清障路径 ——
① 规划期腾站位（`:186-193`）② 运行期视线被挡（`:222`）。
两者都以 `clearedBlocks` 为闸门。

**严重度**：**latent（潜伏）** —— 需要 Job 内**累计** ≥8 次清障才触发。
小型测试场景不会暴露；**真实森林会**。

> ⚠️ **同一常量 `MAX_CLEAR_PER_TREE` 在同一个 Job 的两个地方被赋予了两种 scope**：
> 候选扫描里是**每棵**，执行阶段里是**整个 Job**。无论哪种才是本意，**这个不一致本身就是要修的东西**。
> —— 这正是本草案 §2 要解决的「scope 不一致」，**教科书级标本**。

### 0.3 六条设计规则（草案）

| # | 规则 | 一句话 |
|---|---|---|
| 1 | **scope 一致性** | 任何限额必须声明 scope；**计数器的 scope 必须与限额一致** |
| 2 | **两类传递** | 时间类 **共享**（父扣子也扣）；配额类 **分配**（父给子上限） |
| 3 | **预留** | 父为前置子任务**预留**额度，防止被吃光 |
| 4 | **级联取消** | 父到终态 → 子**级联取消**（依赖优雅中断钩子） |
| 5 | **挂起冻结** | 挂起期间**冻结**活动 tick；配额**保留**已消耗 |
| 6 | **可归因** | 耗尽时报 `(name, scope)`，不只报「超预算」 |

## 2. 规则 1：scope 一致性

### 2.1 问题本质

**额度 = (name, scope, unit)** 三元组。

- `name`：什么资源（活动时间 / 破坏格数 / 搜索节点）
- **`scope`：谁能扣、何时重置**
- `unit`：单位

**「继承」的本质 = 子任务的 scope 比父小，从父的池里扣。**

### 2.2 三种合法 scope

| scope | 重置时机 | 现有实例 |
|---|---|---|
| **JOB**（累计） | 整个 Job 生命周期只减不增 | `spec.maxTicks` |
| **UNIT**（周期） | 每个单位重置（每棵树 / 每簇） | `MAX_CLEAR_PER_TREE`、`CLUSTER_BUDGET_TICKS` |
| **ACTION**（瞬时） | 每次动作独立 | `MiningBudget`、`SearchBudget` |

### 2.3 ★ 规则

> **任何限额都必须显式声明 scope；计数器的 scope 必须与限额的 scope 一致。**

`clearedBlocks` 的缺陷正是违反了后半句：

| | scope |
|---|---|
| 限额 `MAX_CLEAR_PER_TREE` | **UNIT**（每棵） |
| 计数器 `clearedBlocks` | **JOB**（从不重置） |
| → | **不一致 → 语义错乱** |

### 2.4 修法（两条路，需用户裁定）

| 方案 | 做法 | 结果 |
|---|---|---|
| **A（推荐）** | 在 `select()` 里重置 `clearedBlocks = 0`，并改名 `clearedInThisTree` | 恢复「每棵 8 格」**原设计意图** |
| **B** | 改名为 `clearedTotalBlocks`，限额改为 `MAX_CLEAR_PER_TREE × spec.quota()` | 变成「整个 Job 有 8×配额 格」，但**与文档/常量名冲突** |

**勘测员倾向 A** —— 因为常量名、字段注释、设计文档 §9-4 三处**一致**地写着「每棵」，
A 是**恢复意图**；B 是**改变意图**。

> ⚠️ 附带：`progressSummary()` 报的 `cleared=` **语义不明**（`LumberJob:109`）。
> 若采用 A，应改为 `cleared_this_tree=`，并在换树时归零。

## 3. 规则 2：两类传递（本草案的核心）

### 3.1 关键区分

「继承」是歧义词。实际上有两种**物理性质完全不同**的资源：

| | **时间类** | **配额类** |
|---|---|---|
| 例子 | 活动 tick、搜索毫秒 | 破坏格数、搜索节点 |
| **可再生？** | ❌ **不可再生** | ✅ **可再生**（每棵树重新有 8 格） |
| **能否共享？** | ✅ **必须共享**（时间只有一份） | ❌ **不能共享**（否则一棵树吃光所有树） |
| **传递方式** | **共享池**：父扣子也扣 | **分配**：父给子一个上限 |

### 3.2 为什么这个区分是根本的

**时间不可能凭空生出来。** 父任务有 600 tick，子任务不可能有「自己的 600 tick」——
那只存在于幻想中（实际会变成 `600 × 子任务数` 的爆炸）。

**配额则可以分配。** 「这棵树给你 8 格清障」是**有意义的授予**，
因为下一棵树可以从头再来。

### 3.3 规则

> **时间类资源 → 共享池**（父子从同一池扣）
> **配额类资源 → 配额分配**（父给子上限，子用完报 `EXHAUSTED`）

### 3.4 映射到现有代码

| 现有额度 | 类别 | 应改成 |
|---|---|---|
| `spec.maxTicks` | **时间** | 保持共享池语义 ✓（它已经在正确地累计） |
| `CollectDropsTask` `600` | **时间** | ❌ **当前是隐式"每棵树"** → 应改为**从父池扣**或**显式声明为 UNIT scope** |
| `CLUSTER_BUDGET_TICKS` `200` | **时间** | ⚠️ 每簇重置 → 需明确它**不**从父池扣，而是父**授予**的配额 |
| `MAX_CLEAR_PER_TREE` `8` | **配额** | ✅ 分配语义正确（`LumberCandidateSource` 里） |
| `MiningBudget` | **时间** | 每方块，ACTION scope ✓ |
| `SearchBudget` | **时间 + 配额** | 节点数=配额，毫秒=时间 ✓（已区分得很干净） |

**注意 `CollectDropsTask` 的 600**：它现在是「每棵树 600」，
但**每棵树都花的是父 Job 的真实时间**。所以：

> 它**同时**是「时间」（消耗父的墙钟）和「配额」（每棵有一份上限）。

**这正是需要显式建模的地方** —— 建议拆成一个二元组：
`(从父池扣的真实耗时, 父授予的上限 600)`。二者**都要记**。

## 4. 规则 3：预留（前置子任务的额度）

### 4.1 问题（`survey/05` §9.1 提出）

用户设计：「没有获取点就让 bot 自己去拿前置资源」= **在主任务前插入子任务**。

**若前置子任务与主任务共享父的时间池，前置可能把父的时间吃光**，
导致主任务**还没开始就超时**。

### 4.2 规则

> **父任务为前置子任务**预留**额度，预留部分不可被主任务挪用，
> 反之主任务的额度也不可被前置吃穿。**

用法：

```
父授予总额 = 600 tick
  ├── 预留（前置资源获取）= 150 tick
  └── 主任务可用 = 450 tick
```

**前置只用预留部分**；超出 → 前置以 `EXHAUSTED` 结束，**不动主任务的 450**。

### 4.3 为什么预留是必须的

不加预留的话，只有两种坏结果：

- 前置吃光 → 主任务必失败（**浪费了前置的投入**）
- 主任务优先 → 前置永远做不完（**任务永远无法开始**）

**预留是唯一能让两者都"输得起"的结构** —— 任何一方失败都不会拖垮另一方。

### 4.4 与蓝图的一致性

蓝图 §2.2 已将 `Policy Gate` 的职责写为：
「**库存守恒、材料预留**、容量和危险检查」。

> **本节的「额度预留」是同一思路在时间维度上的应用。**
> 不是新概念，是既有概念的补齐。

## 5. 规则 4：级联取消（父超时子还在跑）

### 5.1 现状：未定义

`LumberJob:117` 父超时 → `finish(FAILED)`。但此时若 `miner` / `clearTask` / `collector`
**仍在 RUNNING**，其状态**未定义**（`finish` 不触碰它们）。

### 5.2 规则

> **父任务到终态 → 所有在途子任务级联取消。**

理由：子任务是父的**组成部分**，**没有独立存在的意义**。
父超时意味着「这个目标不做了」，子任务继续跑就是**孤儿任务**。

### 5.3 ⚠️ 依赖：优雅中断钩子（`survey/04` §5.1.2 的缺口）

**级联取消要求每个任务都能被优雅中断。** 而现状是：

```java
// BotManager.java:906
if (task instanceof TransferTask transfer) {   // ← 只有 TransferTask 有钩子
    transfer.survivalInterrupted(reason);
}
```

**只有 `TransferTask` 支持优雅中断**（`survey/04` 已实测：全仓 5 处 `instanceof *Task`，3 处针对它）。

**所以要实现级联取消，必须先做 `Task.onInterrupt(String)` 钩子。**
→ **两件事必须一起做**，这也是本草案与 `survey/04` 的耦合点。

### 5.4 一个必须小心的边界

**级联取消 ≠ 维生中断**（见 `survey/04` §5.3 的三个检查点）：

| | 触发者 | 优先级 |
|---|---|---|
| **级联取消** | 父任务终态 | 任务层内部 |
| **维生中断** | `SurvivalSystem.shouldInterrupt` | **最高** |

维生中断**不因级联取消而改变**——即使所有任务都被取消，维生系统照常运行
（`survey/05` §3.4：维生正交）。

## 6. 规则 5：挂起期间冻结

### 6.1 问题（`survey/05` §4.4 提出）

任务挂起等玩家（离线进队列），挂 8 小时后恢复：

- 若**墙钟继续累计** → 任务必然超时，**挂起等于慢性死亡**
- 若**完全重置** → 玩家可以靠挂起刷额度，**失去预算的意义**

### 6.2 规则

> **挂起期间冻结活动 tick；配额类保留已消耗。**

区分对待：

| 类别 | 挂起期间 | 恢复后 |
|---|---|---|
| **活动 tick**（`spec.maxTicks`） | ❄️ **冻结** | 剩余 = 总额 − **挂起前已消耗** |
| **配额**（已砍树数 / 已破坏格数） | 💾 **保留** | 直接继续（那是**真实进度**） |

### 6.3 为什么必须区分

- **活动 tick 冻结**的理由：挂起期间 bot 在做**默认任务**（巡逻，`survey/05` §3.2），
  **没有在推进这个任务**。让它计入任务预算不合理。
- **配额保留**的理由：已砍的树**是真的砍了**。这不是额度，是**已完成的工作**。

### 6.4 与 `survey/05` §5.3 的呼应

`survey/05` 已拍板：**挂起时只保存「目标」，不保存「计划」，恢复时重新规划。**

本节的「配额保留」与之**不冲突**：配额是**进度**（喂给规划器的输入），
计划是**对世界的假设**（必须重建）。**两者层次不同。**

## 7. 规则 6：可归因的失败

### 7.1 问题

现状：耗尽时只报字符串（`:clear_budget` / `enter_target_over_budget` / `goal_timeout`），
**不带 owner**。上层无法判断「是谁的额度耗尽了」。

### 7.2 规则

> **报 `(name, scope)`，不只报「超预算」。**

配合 `survey/04` §3.5 的结果词表，`EXHAUSTED` 应携带：

```
EXHAUSTED  budget=clearedBlocks  scope=TREE  used=8  limit=8
EXHAUSTED  budget=activeTicks    scope=JOB   used=600 limit=600
```

### 7.3 为什么这条最关键

因为 `EXHAUSTED` 的**处置动作是「加预算重试」**（`survey/04` §3.5）。
**不知道是谁的额度耗尽，就无法决定加哪一个。**

这直接决定上层能否做出正确决策 —— 也是「多层任务失败向上传递」（差异②）能否成立的前提。

## 8. 建议的最小实现

### 8.1 不建「预算框架」，先做三件小事

| # | 做什么 | 成本 |
|---|---|---|
| **①** | **修 `clearedBlocks` scope 不一致**（§2.4 方案 A） | **1 行重置 + 改名** |
| **②** | 给现有额度**加 scope 声明**（哪怕只是一行注释 + 常量命名规范） | 低 |
| **③** | `Task.onInterrupt(String)` 钩子（`survey/04` §5.1.2） | **1 个 default 方法** |

**①②③ 都不需要新抽象层**，且都是「让已有的东西显式化」。

### 8.2 暂不做的

| 项 | 理由 |
|---|---|
| `BudgetLedger` 类 | **抽象层次未知** —— 现在只有 1 个 Job 消费者（伐木），**不足以设计通用结构** |
| 预留机制（§4） | 需要**前置子任务**这个场景先存在（阶段 D/E） |
| 挂起冻结（§6） | 需要**挂起机制**先存在（`survey/05` 待实现） |

> **勘测员意见**：本草案的价值**在于规则与判据**（§2–§7），
> **不在于数据结构**。现在设计 `BudgetLedger` 会是「拿架构换还没遇到的问题」——
> 与项目在 `RiskSwitches` 里写下的克制（「不引入额外的抽象层」）一致。

### 8.3 落地路径

额度 / 权限这套是**纯逻辑** → 可挂进 **`BotSelftest`** 走 headless
（`survey/05` §补遗 6 已确认该设施存在：913 行 / 13 用例，`-Dalice.selftest.auto=true`）。
**不需要 `WINDOWS_CLIENT`**，成本低一个数量级。

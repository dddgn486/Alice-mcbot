## §3 ⭐⭐ 「带会话上下文回迁」拆成两个层次（本文件的核心）

> ⚠️ 这不是一个需求，是**两个**。它们的技术难度差一个数量级，先分开再决定做哪个。

| | 层次 (a) **本机 DSH 能继续同一条会话** | 层次 (b) ⭐ **下一个主工作流"知道发生过什么"** |
|---|---|---|
| 需要什么 | **版本相同 + slug 相同** | **可读的文本** |
| 现状 | ❌ **两者都不满足** | ✅ **工具已有** |
| 障碍（✅ 已核实，`§13` 原文） | ① slug 不同（云端 `--home-vscode-dsh-test--` vs 本机 `--home-fb486-projects--`）② **版本不同代**（云端 `rc.3` / 本机 `rc.1`）⇒ **会话存储带世代迁移，跨代读取会响亮失败**（预期行为，别静默兼容） | 无（纯文本不依赖版本） |
| 怎么做 | 把**本机 DSH 升到 rc.3**，并处理 slug | ⭐ **在云端用"生成它的那一代"工具解码成文本，带回本机** |
| 成本 | 1 轮左右（装版本 + 试读） | **很低**（一条命令） |
| 价值 | 锦上添花（历史会话出现在同一工作区下） | ⭐ **这才是"不丢上下文"的本体** |

### 3.1 层次 (b) 的实现路径（✅ 工具已存在，就在本仓库里）

```
云端（rc.3）：
  node tools/dsh-session-log.mjs --list              # 列出会话
  node tools/dsh-session-log.mjs --out /tmp/s.jsonl   # 解码成全量 JSONL（可 grep）
  node tools/dsh-session-log.mjs --stats              # 类型直方图 + 压缩表
⇒ 产物是纯文本 ⇒ 带回本机后与 DSH 版本无关
```

⚠️ **两个必须注意的点**（都在 `tools/dsh-session-log.mjs` 自己的 docstring 里）：

1. **它要求 Node ≥ 22.15**（用 `zlib.zstdDecompressSync`）—— 两端的 Node 都要够；
2. ⚠️ **解码器有版本世代（磁盘格式 `v0 → v1 → v2 → v3`）**，且**"升代后本工具会响亮地失效"**
   ⇒ **必须用"生成那份会话的那一代"的 DSH 来解**，不能用本机 rc.1 去解云端的 rc.3 产物。

### 3.2 ⚠️ 与 `§13` 结论的关系（不冲突，是补充）

`§13` 写的是「**`sessions/` 归档可读，但不建议直接采纳**」——**它讲的是层次 (a)**，结论正确。
**本文补的是层次 (b)**：**归档出来的文本本身是有用的**（供人/供下一个 agent 读），**只是不该塞回 DSH 的 sessions 目录**。

⇒ 一句话：**归档不是白归档，用它当"上下文交接材料"就对了。**

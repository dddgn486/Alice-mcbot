### 1.1 ⭐ `authz-map.py` 的产物是最好的范例（值得照抄的结构）

`docs/authz/OVERVIEW.md` 的开头是一段**"唯一需要背的东西"**：

```
## 四问速查（唯一需要背的东西）
1. 这一步改世界吗？   不改 ⇒ 只走 L2（Movement 集合 + 物理前提 + 可逆性）。
2. 改世界呢？         L1 谁授权/为什么（WriteGrant）→ L3 还有预算吗（WriteBudget）
                      + 执行期复验（CapabilityGate）→ L4 记哪种账（TEMP 必拆 / KEEP 不拆）。
3. 要拆吗？           只拆自己放的、自上而下、材料回收。
4. LLM 能自己决定吗？ 不能：只能提目标；拒绝走 Refused；未知模组能力问用户。
```

**⇒ 这就是"全貌"的正确形状**：**不是一张漂亮的图，是"四句能背下来的话" + 一张能查的表 + 一个能筛的页面。**
**⚠️ 而且它是自动生成的** ⇒ **人不需要维护它**（改 CSV → 跑 `bash tools/authz-map.sh`）。

## 2. 「每个高级系统都做一张关系图」值不值得？

**用户的直觉（"好像不是很好维护"）是对的，但要分情况。** 判据就用项目自己的 `AGENTS.md` 那条：

> **① 它能让构建失败吗？**（写成 `tools/check-*.sh` / `.py` 断言 ⇒ 成本 ≈ 0）→ 是则留下

| 图的类型 | 例子 | 能挂门禁？ | 结论 |
|---|---|---|---|
| **能从代码/CSV 推出来的结构** | 授权注册表、写入策略矩阵、机器映射、Job 层级、开关清单 | ✅ 能 | ✅ **做，且必须挂门禁**（已有三个先例） |
| **需要人判断的"全貌 / 为什么"** | 风险系统四层、与 Baritone 的差异①②③ | ❌ 不能 | ⚠️ **只写指针，不画框** |
| **一次性的理解辅助** | 勘测员给用户画的图 | — | ✅ **放 `survey/`** —— **不进主线，坏了不欠债** |

### 2.1 ⚠️ 为什么"需要人判断的全貌图"不该进主线

**因为它必然过期，而它过期不会让任何东西失败。** 项目已经吃过这个亏的形状：
`AGENTS.md` §规则准入尺子原文：

> `docs/` 已 **28,877 行**（≈主代码 47%）、**30% 的 commit 只碰文档/规则**、**139 条规则对 8 道门禁**
> ⇒ **规则 ≈95% 靠"人记得"**。散文规则成本随规则总数**线性增长**

**⇒ 手维护的全貌图 = 散文规则的一种**。它不会失败、只会"慢慢变得不对"、还会让后来的人（和 AI 会话）**以为它是对的**。

### 2.2 ⭐ 正解：**"指针文档"**（能过期的只有指针）

对"需要人判断的全貌"，**只写"哪一层在哪、指到哪个文件哪个符号"，不写"框和箭头"**。
- 指针几乎不会过期（文件改名才会）
- 框和箭头**每次重构都会过期**
- **这和 `AGENTS.md` 第 3 条同源**：**只放路径/commit/决策号，不抄原文**

## 3. 三个生成器的共同纪律（**值得推广的四条**）

从 `authz-map.py` / `policy-map.py` / `machine-map.py` 的 docstring 里抽出来的：

| # | 纪律 | 原文证据 |
|---|---|---|
| **1** | **单一出处** | `authz-map.py`：「**单一出处**：`docs/authz/AUTHZ_REGISTRY.csv`」；`policy-map.py`：「**单一出处是代码**（`action/WritePolicyMatrix.java`）——这是 Forge 模组，运行期必须有一张编译进 jar 的表；docs 里的 CSV 是**给人看的视图**」 |
| **2** | **产出物勿手改** | 两个 docstring 都写：「产出（**全部会被覆盖，不要手改**）」 |
| **3** | ⭐ **双向防漂移** | `machine-map.py`：「**上游没有的 id**（那是伪造/笔误）。**两个方向都要断言**，才叫'单一出处 *且* 完整'」；`policy-map.py` 断言 ⑥：「磁盘上的 CSV 与重新生成的结果一致（**防"改了代码忘了更新视图"**）」 |
| **4** | ⭐⭐ **解析不到就响亮失败，不静默放行** | `policy-map.py`：「派生规则（②③）是**从 Java 源码里解析出来**的，**不是在 Python 里抄一份**；解析不到就**响亮失败**，不静默放行（**否则脚本会变成"永远 PASS 的橡皮图章"**）」 |

**⇒ 第 4 条是这套东西真正的灵魂**：**门禁最怕的不是漏报，是"永远绿的假门禁"。**
项目里已经**两次靠反向对照抓到假绿**（D-254 的"参数表按第一个 `)` 截断"、D-255 的"方法体按固定缩进切分把签名行当证据"）—— **这是同一纪律的历史证据。**

### 3.1 ⚠️ `authz-map.py` 的结构性弱点（相对另两个）

| | 单一出处 | 会不会漂 |
|---|---|---|
| `policy-map.py` | **代码** | ❌ 不会 —— 断言 ⑥ 直接对拍"磁盘 CSV vs 重新生成" |
| `machine-map.py` | **代码 + 上游 jar** | ❌ 不会 —— 双向覆盖断言 |
| **`authz-map.py`** | ⚠️ **人维护的 CSV** | ⚠️ **会** —— `--check` 能验"注册表 vs 代码"不一致（`check-authz-registry.sh` 注释：「注册表 vs 代码（不一致即非零退出）」），**但"CSV 里漏登记一个新闸门"这类漏报，只能靠"全覆盖要求"来兜**（`35392e7` 那条提交正是"补登记 `CRAFT_GRID` 到 `AUTHZ_REGISTRY`（**check-authz-registry 全覆盖要求**）" ⇒ **机制在起作用**） |

**⇒ 不是缺陷，是"单一出处选在人手上"的固有代价。** 但**排序很清楚**：
**能选代码当单一出处，就别选人维护的表** —— 这也是 `survey/07` §3.5「需求驱动」的同一条思路。

## 4. ⭐ 风险系统全貌：**四层 + 一个横切**

> **来源**：`docs/RISK_MODES_DISCUSSION.md`（含附录 A）+ `docs/RISK_SYSTEM_DESIGN_DRAFT.md` §7 + `docs/RISK_SYSTEM_ISSUE_LIST.md` + `docs/AI_DECISIONS.md`（D-046 / D-059）
> **⚠️ 那份文档自己在开头声明"不是最终定案"**，台账 9-16 的裁定是「**⚪ 不是债、有意保留**」⇒ **设计仍有效，但从未验收**。

```
第 0 层｜永不开的底线        ← 硬编码，任何模式都不解锁     【✅ 已在代码里真的在拦】
第 1 层｜三档 H / G / S      ← 玩家/任务看到的东西          【❌ 仅文档，全仓查不到 Mode 枚举】
第 2 层｜10 个风险开关        ← 档位的具体展开              【⚠️ 仅清单，只落地 1 个】
第 3 层｜自动评估器           ← 决定"这一刻该用哪档"        【❌ 零实现，含用户 A.2 的分层框架】
─────────────────────────────────────────────
横切层｜可回收性尺子          ← 一把已经在用的尺子          【✅ 已实现，且真的在拒东西】
```

### 4.1 第 0 层｜永不开的底线（`RISK_MODES_DISCUSSION.md` §5 原文）

| # | 底线 | 代码侧证据（本次核实） |
|---|---|---|
| 1 | 落点即死（**熔岩/火/岩浆块/仙人掌/虚空**）—— 永不 | `SurvivalSystem` 危险分类（`isInLava` 等） |
| 2 | **落差 > 3**（摔伤）—— 永不 | `SurfaceMovementProvider.FALL_DROPS = {2, 3}`（**上限即 3**） |
| 3 | 保护区域内的破坏/放置 —— 永不 | `protection/SafeZoneData` + `BlockBreakSafety` |
| 4 | `SEARCH_LIMIT ≠ UNREACHABLE`；未知模组能力只读 | `PlanningStatus`；`permission/*` + `/alice ask` |
| 5 | 落点上方有即将掉落的 `FallingBlock`（窒息）—— 永不 | `AscendExecutionFactory` 的检查（原文自述"已有"） |

**⇒ ⭐ 对用户的问题「我们要完全不做风险识别吗」的答案：**
> **不可能 —— 这五条是"永远开的"，已经存在，且真的在拦。**
> **它们的现状问题不是"做没做"，是"没有统一的名字、散在 4 个类里"** ⇒ **这正是用户观感里"避险措施到处都是"的物理原因。**

### 4.2 第 1 层｜三档 H/G/S（`RISK_MODES_DISCUSSION.md` §3）

| 档 | 核心特征（原文摘要） |
|---|---|
| **H** | Baritone 式：落差 ≤3、挖脚下、PILLAR、破坏/放置、对角切角、疾跑**全开**；**恢复依赖全局重规划 + 前置资源** |
| **G** | 守卫式：落差 ≤1、**每个放宽都带守卫**；**地形覆盖小，某些目标判 `UNREACHABLE`（"这是诚实的，不是缺陷"）** |
| **S** | 智能（默认）：**以 G 为基线，按动作/前置/世界状态逐条提升**；**每次提升记日志**（`[Risk] promote fall>1 reason=resource_backed blocks=8`）⇒ 可审计 |

**⇒ ⭐ 三者是"一维"的关系，不是三套系统**：

```
G ──逐条提升──▶ S ──全开──▶ H
最保守                        最激进
```

**⇒ S 不是独立模式，S = "G 打底 + 有依据就放开几条"。**
⚠️ 且 **D-059 已裁定「用开关，不用 H/G/S 三态等级枚举」**（用户原话："等级枚举后续设计怎么处理我不理解"）
⇒ **"H/G/S"只是"三个预设的名字"，不是要新增的枚举类型。**

### 4.4 第 3 层｜自动评估器（用户自己的 A.2「分层评估」框架，由外到内）

| 层 | 例子 | 可能产物 |
|---|---|---|
| **任务层** | 浅层挖掘 vs 深层挖掘 | 禁用/启用 DOWNWARD、FALL |
| **维度** | 地狱比主世界危险 | 提高整体风险权重 |
| **群系/结构** | 远古之城危险于普通矿洞 | 直接拒绝任务或强制保守 |
| **现实条件** | 剩余方块、工具耐久、食物/生命 | 禁用依赖资源/工具的 Movement |
| **局部场景** | 超大矿洞 vs 小隧道 | 局部守卫开关 |

**⚠️ 而 A.4 已经把这个评估器的形态钉死了**（原文）：
> **评估结果 → 逐项设置开关；评估器本身不进 Movement 语义。**
> **开关的消费者只有两个**：**规划层候选过滤**（禁用某类 Movement）+ **Movement 层守卫开关**。

**⇒ ⭐ 这句话是整个风险系统最省力的一条：评估器**不是**第二个系统，它是 `RiskProfile` 生成器。**
**⇒ 并且 A.1 第 5 条进一步撤回了"替代策略"**（原文）：
> **"替代策略"语义撤回**：低风险模式**只需要禁用**高风险 Movement。
> 因为允许集合里有 `PLACE_STEP_AND_TRAVERSE` / `BREAK_AND_TRAVERSE`，一旦禁用某类高风险 Movement，**规划器会自己拼出楼梯/绕行**。
> （2026-09-09 客户端实证：4 格落差场景，规划器用 `TRAVERSE + PLACE_STEP×4` **自己搭台阶**下去了，根本没用 FALL。）

**⇒ 你不需要写"替代策略"，只需要"关掉几类边"。**

### 4.5 横切层｜可回收性尺子（`survey/08` 已核实，这里只引用）

| 件 | 状态 |
|---|---|
| 四级 `LOCAL_STEP / PATH_REVERSIBLE / SAFE_EXIT_REQUIRED / EMERGENCY_EXIT_REQUIRED` | ✅ 已定义 |
| 门槛表 `RecoverabilityPolicy.requiredFor` | ✅ 在工作；**`FALL` 是"唯一真能拒东西的一条"** |
| 逐边评估器 `RecoverabilityEvaluator` | ✅ **有真读者**（`PATH_REVERSIBLE` 41 处 / `LOCAL_STEP` 35 处） |
| 空插槽 `SAFE_EXIT_REQUIRED` / `EMERGENCY_EXIT_REQUIRED` | ❌ **无产出者**（只在注释里） |

**⇒ `docs/authz/OVERVIEW.md` 的 L2-2 行也独立佐证了同一件事**：
> `RecoverabilityPolicy`：FALL 必须带 `fall_return_verified`｜构造 `MovementSpec` 时比较"提供 vs 要求"｜**规划期抛异常（不静默降级）**｜「**不足即炸（唯一真能拒的一条）**」

⭐ **注意这里有个漂亮的互相印证**：`authz-map` 生成的 OVERVIEW **把可回收性算作 L2（规划期）的一条硬约束闸门** ——
**⇒ 也就是说：在"授权框架"的视角里，可回收性尺子是一个闸门；在"风险系统"的视角里，它是那把尺子。**
**⇒ 两个视角描述的是同一个东西**（这是全貌图之间应该有的关系）。

## 5. 回答用户的两个真问题

### 5.1 「以后展示给玩家的开关，本质到底是什么？」

> **本质 = `RiskProfile` 的「人可读投影」。**
> **它的内容 = "允许规划器使用哪些 Movement" + "每种 Movement 附加哪一级守卫"。**
> **它的消费者只有两个 = 规划层候选过滤 + Movement 层守卫开关。**（A.4 原文）

投影的分层（玩家看到什么 vs 底下是什么）：

| 玩家看到 | 底下是什么 | 现状 |
|---|---|---|
| **（看不到）** | 第 0 层底线：硬编码 5 条 | ✅ 已实现 |
| 「H / G / S」三档 | **10 个开关的三个预设** | ❌ 仅文档 |
| 高级：10 个开关 | 真正的可调面 | ⚠️ 1/10 落地 |
| 「让 Alice 自己判断」 | 第 3 层评估器在设这些开关 | ❌ 零实现 |

### 5.2 「我们要完全不做风险识别吗？」

**不要 —— 而且最强的一件已经做了。**

| 层 | 现状 | 建议 |
|---|---|---|
| 底线（5 条） | ✅ **真的在拦** | **保持**（只是给它一个统一名字） |
| 可回收性尺子 | ✅ **真的在拒东西** | **保持** |
| 档位（H/G/S） | ⚠️ **只有 1 个开关** | ✅ **做**（= S-6） |
| 评估器（分层） | ❌ **零实现** | ⏸ **先别做**（D-046 第 5 条：数据采集推迟） |

### 5.3 ⭐ 一个可能反直觉的发现：**已实现的两件，恰好是"最不该关"的那两件**

| 层 | 玩家能关吗 | 它是什么 |
|---|---|---|
| **底线** | ❌ 不能 | 安全网 |
| **尺子** | ❌ 不能（**规划期硬约束，不合格即抛异常**） | 安全网 |
| **可调的 10 开关** | ✅ 能 | **但只落地 1 个，且默认 `false`（= Baritone 原样）** |

**⇒ 所以今天的状态是：**
> **玩家的开关"几乎什么都控制不到"** —— 能控的那 1 个（`descend_overshoot`）**默认就是关的**，
> 而**真正在拦他的那两样，恰恰是不可关的**。

**⇒ 这不是 bug，是"先有消费者再建类型"（D-046）纪律的必然结果** —— **但它是理解"为什么风险系统让人感觉绕"的关键**：
**你今天看到的"到处都是的避险措施"，全部是"不可协商的底线"，不是"可调的风险档"。**
**⇒ 而底线本来就不该出现在玩家的开关面板上。**

### 6.1 ⭐ 为什么 `survey/` 是"手维护关系图"的正确去处

本目录的纪律天然解决"图过期怎么办"：

| 问题 | 主线手维护的图 | `survey/` 里的图 |
|---|---|---|
| 代码改了，图没改 | **变成假权威**，没有东西会失败 | 标了基线 commit ⇒ **"过期就是过期"，不会被当权威** |

**⇒ 所以建议**：**主线只保留"能生成、能挂门禁"的图；"全貌图"由勘测员在 `survey/` 里出快照。**

## 2. ★ 粗目标代价复核（**主工作流 `review §5` 点名要求**）

> 复核请求原话：*「"允许粗目标"（不用新算法，只是让 goal 不精确）**可能比 M1–M6 里任何一件都小**，值得单独评估，而不是跟着"到达"一起排到 B3 之后。⚠️ 但我没有验证它的代价……请勘测员先复核代价再决定。」*

### 2.1 主工作流**对**的部分

| 断言 | 复核结果 |
|---|---|
| `GoalSpec` 是接口 | ✅ `interface GoalSpec { isInGoal / heuristic / goalFoot / describe }` |
| 只有 `GoalFoot` 一个实现 | ✅ `grep -rn "implements GoalSpec"` **只 1 处** ⇒ **加第二个实现是架构上被邀请的** |
| 滚动重规划的骨架已经在跑 | ✅ `PathRetryRunner` + `PathSession` 分段 + K-1 `partial_prefix_done` → `replans++` |
| **节点级门控已经是 Baritone 的形状** | ✅ `AStarMovementSearch:145-160`：跨区块边界时查一次 `chunkLoaded(toFoot)`，未加载 ⇒ **`continue`（跳过这条边，不判死整条路径）** ⇒ **搜索天然只在已加载区块内展开** |
| 产生 `GOAL_NOT_LOADED` 的源头 | ✅ `MovementContext.chunkLoaded` 用 `hasChunkAt`（**绝不加载区块**，`Floating:46` 注释自述） |

### 2.2 ⚠️ 主工作流**没有算到**的三件代价

**① 硬前置挡在搜索之前（这是最硬的一条）**

```java
// AStarMovementSearch.java:52-53（在任何搜索之前）
if (!context.chunkLoaded(goal.goalFoot())) {
    return PathPlan.failure(PlanningStatus.GOAL_NOT_LOADED, ...);
}
```

⇒ **粗目标如果是"200 格外的 XZ"，它的区块没加载 ⇒ 这一行直接失败，`PARTIAL` 那条路根本走不到。**
⇒ 所以 §2.1 的"节点级门控天然返回 PARTIAL"**只在目标区块已加载时成立**。

⚠️ 而这一行**不是随手写的**（`:45-51` 注释）：它是 **S-2 / P1-A**，理由是
**"服务端读未加载区块会同步加载/生成并阻塞主线程"**，且 `GOAL_NOT_LOADED` 被**刻意做成独立状态**
（"不是 `UNREACHABLE`、不是 `SEARCH_LIMIT`"）。
⇒ **放宽它是一个安全规则（不是性能优化）的语义变更。**

**② 两个上限是「故意」设的，粗目标需要换一个停止规则**

| 常量 | 值 | 注释自述的目的 |
|---|---|---|
| `PathRetryRunner.MAX_PARTIAL_HOPS` | **4** | **"防'永远走一段、永远到不了'的空转"** |
| `PathRetryRunner.DEFAULT_MAX_REPLANS` | **2** | 重规划预算 |

⇒ 二者相乘 ⇒ **最多约 3~4 段**。
⇒ 粗目标要真的走完 200 格，**必须抬高这两个上限 —— 而它们存在的理由正是"防止无限走下去"**。
⇒ 正确的解法是**换一个停止规则**（粗目标自带半径条件：进到范围内就转精确）——
**但那是一次新的决策，不是"改一个字段"。**

**③ `goalFoot()` 的语义会被撕开**

`goalFoot()` 被读的地方（`grep -rn "goalFoot()"`）：`AStarMovementSearch`（4 处，含 §2.2① 的硬前置）、
`CorePathPlanner`（`:57/:59` 记进 `PathPlan`）、`PathRetryRunner`（`:70/:84/:103` 三处日志）。
⇒ 一个"XZ 粗目标"要返回**哪个 `BlockPos`**？返回 (x, ?, z) 的哪一层？
**这不是"让 goal 不精确"一句话能盖过去的** —— 它是 `GoalSpec` 契约的一个真实语义缺口。

### 2.3 ⭐⭐ 最关键的一条：**粗目标解决「远」，不解决「深」**

| 需求 | 粗目标有帮助吗 |
|---|---|
| 走到 200 格外的另一个矿区 | ✅ 有帮助（水平远距离） |
| **下到 Y=-59 的深层矿** | ❌ **完全无帮助** |

**理由**：`GOAL_NOT_LOADED` 是**区块加载**问题（XZ 两维）。
**而"到 Y=-59"是垂直问题** —— 竖井的每一格都在**同一个已加载区块**里，`chunkLoaded` 永远为真。
⇒ **粗目标碰不到竖井问题的任何一环。**

⇒ **`survey/08` §8.3 把"宏观到达"整体排到 B3 并没有错**，只是**理由要换**：
不是"粗目标也贵"，而是**"粗目标解决的是另一件事"**。

### 2.4 ✅ 但它有一个**真实的、独立的**价值：跟随

| 事实 | 值 |
|---|---|
| `FollowTask.MAX_TARGET_DISTANCE` | **24** |
| 超过时的行为 | **`follow_distance_limit` 失败**（`FollowTask:88-91`） |

⇒ **玩家走远 24 格以上，"跟随"就直接放弃。** 这是一个**真实存在、今天就在疼**的缺口，
而它的正确解法**恰恰是粗目标**（跟随的目标本来就是"那个人的附近"，不是"某一格"）。
⇒ 满足 D-046「先有消费者再建类型」：**消费者 = `FollowTask`**。

### 2.5 复核结论

| 问题 | 答案 |
|---|---|
| 粗目标比 M1–M6 都小吗？ | ❌ **不成立**。它要动 §2.2 的三处（其中①是安全规则语义变更，②是新停止规则决策） |
| 它该排在 B3 之前还是之后？ | **与 B3 无关** —— 它属于**另一条**（水平远距离 / 跟随），**不属于"到达"（垂直）** |
| 建议 | **单独登记为一条待评估项**，消费者 = `FollowTask`；**不要**与挖矿"到达"捆绑排期 |

**⭐ 于是上一轮那个"两条线撞墙"的判断要补一句**：不是"两条线"，是**三条正交的轴**：

| 轴 | 谁需要 | 代价 |
|---|---|---|
| **垂直到达**（挖下去 / 爬上来） | 挖矿通道、溺水自救 | 最贵（新 Movement + 授权） |
| **水平远距离**（粗目标） | 跟随、跨区作业 | 中（安全规则语义 + 停止规则） |
| **退路保证**（可回收性） | 通道挖掘 | 中（反向逃生集搜索 = 空插槽） |

## 4. 逃生形态：**「退开一步」，不是「活着离开」**

### 4.1 它拆开是四步

| 步骤 | 符号 | 做什么 |
|---|---|---|
| **① 分类** | `Monitor.classify` | 6 类危险：`LAVA_CONTACT`/`SUFFOCATING`/`LOW_AIR`/`ON_FIRE`/`FREEZING`/`WATER_CONTACT` |
| **② 判决** | `SurvivalSystem.decide` | **5 个判决值**（`IGNORE`/`INTERRUPT`/`HOLD_NO_EXIT`/`ABANDON_NO_EXIT`/`FLOAT_UP`） |
| **③ 找落点** | `nearestSafeRefuge` | 半径 **8 格**内哪一格安全（**纯查询，不找路**） |
| **④ 走过去** | `SurvivalExitTask extends WalkToTask` | **一次最普通的走路**（`PathRequest.of`，纯通行） |

**⇒ 逃生的全部动作 = 判一下 → 找一个安全的格子 → 走过去。**

**④ 是"求生"的全部，而且它不是新写的任务** —— 设计原话：
「**维生给落点、寻路给路径、维生仍然不找路**」。

（一个精妙的小设计：`SurvivalExit` 是个**空标记接口**，唯一作用是让逃生任务**不被维生二次否决** ——
否则会出现"中断 ⇒ 起逃生 ⇒ 下一 tick 又被中断"的每 tick 自杀循环。）

### 4.2 「退开一步」的四条证据

| # | 证据 |
|---|---|
| ① | **半径只有 8 格**。`REFUGE_RADIUS = 8`，设计原话：「够'离开脚下这一格危险'，又不至于把整片区域扫一遍」 |
| ② | **只保证"那一格此刻安全"**（`isRefuge` 四条：脚/头位非流体、可穿过、脚下有真支撑、区块已加载）⇒ **无"以后也安全"、无"能不能回得来"** |
| ③ | **它不是"暂停"，是"放弃"**：代码顺序 `complete(…SURVIVAL_INTERRUPTED)`（内部 `clearTask()`）**先于** `startSurvivalExit()` ⇒ **原任务死了，不会自动回来** |
| ④ | **出口只有两种，都是"本来就做得到"的**：走出去（走路）/ 浮上去（**纯输入**，按住跳跃） |

**⇒ 核心一句：逃生只能逃到"本来就走得到"的地方。**
唯一出路需要**挖开 / 搭上去 / 游出去** ⇒ 逃生**做不到**（它是纯通行）。而这三件事**全撞 D-076**。

### 4.3 顺手查出的一个真缺口

D-238 给逃生加了"**可规划**预检"（跑一次真规划，只有 `UNREACHABLE` 才算没出口）。
**但它只问"去不去得了"，不问"路上会不会踩进岩浆"**：

`PlanRouteSafety.lavaContacts`（计划期岩浆接触检查）全仓**只有 2 个消费者，都是诊断物品**
（`PathingLavaGuardItem:86` / `PathingRegressionTask:385`）。
⇒ **逃生路径本身不评估危险。** 它规划的是"最短的纯通行路线"，可能正好穿过火焰带或岩浆边缘。

（这正是风险草案 §5.1 点过的：**"执行期事前"那一环最薄**。）

### 4.4 ⭐ 真正的杀手：三个条件叠加 ⇒ **自挖竖井里 bot 无解**

| 条件 | 值 | 后果 |
|---|---|---|
| `REFUGE_RADIUS` | **8** | 竖井里四周全是石头 ⇒ 8 格内**没有安全格** |
| 出口必须**可规划**（D-238） | — | 有格也没用，去不了就说没出口 |
| `PathRequest.of` 不含 `PILLAR` | `TRAVERSE/DIAGONAL/ASCEND/DESCEND` | **`ASCEND` 只能上 1 格台阶，爬不了竖井** |

**⇒ 竖井 + 灌水/岩浆 = bot 无解：上不去、挖不动（纯通行）、退路被切。**
硬危险会中断，但**没出口时 `startSurvivalExit` 只能如实登记 `exit=none` 并让 bot 停在原地等干预**。

## 5. ★ 液体处理：**不要模拟流向**（否定性建议）

### 5.1 四重理由

| # | 理由 |
|---|---|
| **① 服务器已经在算了** | 流体更新是原版服务端每 tick 做的事。bot 跑在服务端 ⇒ `level.getFluidState(pos)` 是**免费读**。想预测的东西**游戏已经算好放在那儿** |
| **② 你不需要"预测"，你需要"别被关住"** | 该做的是**静态、O(1)** 的检查："我要挖的方块，邻格是不是流体？"—— 正是 `FluidRiskPolicy` 的形状：**6 个邻格，零模拟** |
| **③ ⭐ 退路被切断是拓扑问题，不是流体动力学问题** | 杀死 bot 的不是"水往哪流"，是「**我的退路是一条单线，而它正在被切断**」。**算得再准，隧道灌满了还是出不去** |
| **④ 没有消费者** | 逃生用的是"最近的安全格"，**根本不看流向** ⇒ 按 D-046 纪律，它会变成**第 4 个死抽象** |

**补一条更硬的**：**你晚一个 tick 就能观测到。**

| | 速度 | 打破方块后等 1 tick 的代价 |
|---|---|---|
| 岩浆 | **30 tick/格**（流 3 格后停） | 1/30 格 |
| 水 | **5 tick/格**（流 7 格后停） | 1/5 格 |

⇒ **预测的收益是"早一格"，成本是一个流体模拟器**；**观察的收益是"事实"，成本是一格延迟。**

> ⚠️ **诚实标注**：**项目里从来没记过水的流速**（`getTickDelay` / `tickDelay` / `waterWalkSpeed` 全仓 0 命中）。
> 上面两个是**原版数值，未在 Alice 里验证**。按项目"不照抄 Baritone 常量"的纪律（D-040），
> **这两个数若要写进任何判据，必须先实测标定。**

### 5.2 一个关键的量级对比

| | 速度 | 对比 bot（**实测 `TRAVERSE 6 tick/格`**） |
|---|---|---|
| **水** | 5 tick/格 | **水比 bot 快 ~20%** ⚠️ **唯一追得上你的东西** |
| **岩浆** | 30 tick/格 + 只流 3 格 | **bot 快 5 倍** ✅ **根本不追你** |

**⇒ 岩浆不是"洪水"，是局部危险。** 真正的杀伤是**它在原地烧死你**，或**它封住你的出口**。
**⇒ 水追得上你，但不立刻致死**：`airSupply` 300 tick = **15 秒**才掉血 ⇒ **有充足时间跑**。

## 6. ★ 「邻液体」的正确分界：两个模型，不是一个

### 6.1 现状：`FluidRiskPolicy` 已存在，但有三个边界

```java
// FluidRiskPolicy.miningRefusal
for (BlockPos nearby : adjacentRiskCells(target)) {      // ← 只 6 个正邻格（不含对角）
    if (level.getFluidState(nearby).is(FluidTags.LAVA))  // ← 只看 LAVA（水完全不查）
        return "fluid_risk_lava";
}
```

| 边界 | 事实 |
|---|---|
| **只看 lava** | 水不查 |
| **只看 6 正邻格** | 不含对角 |
| **⚠️ 只看目标格** | **走廊/清障破的格子不在检查范围内** |

### 6.2 ⚠️ 第三条是真缺口（调用链已核）

`FluidRiskPolicy` 全仓**只有 1 个调用点**：`MiningPlanner:71`，传的是 `immutableTarget`。

而走廊破格走的是**另一条链**：

```
BreakAndTraverseExecutionFactory:59
  → BlockInteraction.breakRefusal
    → BlockBreakSafety.clearingRefusal
      → explicitTargetRefusal      ← 只挡"这格本身是流体"
```

**⇒ 挖隧道时，可以破开一堵墙、而墙后面就是岩浆池，全程没有任何检查。**

**风险不是理论**：`R4_BARITONE_ALIGNMENT_AUDIT.md:154` 记的正是同一类 ——
「岩浆被当作可挖阻挡物，`estimateBreakTicks` 给出有限代价（≈10000 tick）⇒ 规划可能选'挖岩浆'，
执行必然卡到段超时」（**DEVIATION-UNREGISTERED，P0 安全**）。

**⇒ 第一件事不是"新增机制"，是"把已有的检查接到走廊上"**：
那 1 个调用点扩成"目标 + 走廊每一格"，成本每格 6 次方块读取（可忽略）。

### 6.3 ⭐ 但「硬禁邻液体」对**水**是错的层级

| | 岩浆 | 水 |
|---|---|---|
| **危险类型** | **危险**（碰到就烧） | **不是危险**（不掉血） |
| **它夺走的是** | 你的血 | **你的选项**（Alice 不会水平游） |
| **正确处置** | ✅ **硬拒绝**（已有，做对了） | ❌ 硬禁 = **过度保护** |

**为什么水不能硬禁**：`RISK_SYSTEM_DESIGN_DRAFT §3.4`「**守太紧也是 bug**」。
而地下**处处是水**（1.18 起有含水层，洞穴里到处是水洼）⇒ **硬禁水邻接 = 禁掉一大片正常采矿。**

**⇒ 真正的判据不是"邻格是什么液体"，是「打开它会不会切断我的退路」：**

| 场景 | 正确处置 |
|---|---|
| 开阔地形的同一个水洼 | **不该拦**（走过去就完事） |
| 1 格宽的死胡同 | **必须拦**（灌满就出不去） |

**⇒ 分界线是拓扑，不是液体种类 ⇒ 它属于可回收性系统（`SAFE_EXIT_REQUIRED`），不属于危险系统。**

### 6.4 ★「找另一条回去的路」**不是通用方法**

> **它在自然地形里成立，在你自己挖的地方失效。而危险恰好都在你自己挖的地方。**

**为什么失效**：A\* 是在**图**上搜路。一条 1 格宽的死胡同隧道，**出口数 = 1**。封住之后 **= 0**。
**搜索再强也搜不出不存在的边。**

**⇒ "另找一条路"是下游补救，而它失败的位置正好是你需要它的位置。**

**⇒ 这还解释了为什么 Baritone 不需要这个能力**：它"边走边挖" ⇒ **挖穿的路就是走的路**，
退路与来路 **1:1 重合**。而 Alice 是"站位 → 挖目标" ⇒ 挖出来的形状**不一定能走回去**。
**⇒ 这是形态的代价，不是缺功能。**

## 7. ★ 权利的正确轴：「这个任务改不改世界」

### 7.1 用户的直觉方向对，但轴不对

> 用户推测：「被封住路的**野外采集场景**应当拥有这个权限」

| 直觉的轴 | 真实的轴 |
|---|---|
| 野外 vs 基地 | **这个任务改不改世界** |

**理由**：在安全区挖竖井**一样会把自己困住**；野外采集如果**从不破坏方块**，它**永远不可能困住自己**。

**而这个轴已经是一个字段**：`MovementCapabilities.changesWorld()`
（`CapabilityGate.check:62` 正在用它作第一道分派：`!caps.changesWorld()` ⇒ 直接放行，不查授权/预算/保护）。

### 7.2 正确的表述

> **逃生的权利，应当是「有权冒险」的后果，不是「被困住」时临时授予的。**

如果信封允许这个任务破坏方块，那么**"破开一条路出来"本来就在同一个信封里** ——
**不需要新授权，只需要问预算。**

### 7.3 具体做法（便宜、可审计）

**给写入预算留一份「逃生准备金」**：`WriteBudget` 是每作用域 **64 破坏**，
**预留其中一小部分（例如 8）只能用于逃生**。

| 优点 | 说明 |
|---|---|
| ✅ 用现有机制 | **不建新层**（符合 D-046） |
| ✅ **事前决定** | 不是慌乱中授予（符合 `survey/05` 的信封设计） |
| ✅ **可归因** | `WriteReason` 不同 ⇒ 台账/日志能分清"为干活挖的"和"为逃命挖的" |
| ✅ 有界 | 逃生**永远挖得动 8 格**（够破开塌方/封堵），但**不会变成"一路挖穿世界"** |
| ⚠️ 不够用时**如实失败** | 例如要爬 60 格竖井 —— 那正是还没有的**垂直移动能力**（§2.3 的轴一） |

**⚠️ 它不违反 D-076**：D-076 禁的是**寻路器偷偷挖**；一个**显式登记、有预算、有专属理由码**的逃生入口，
正是 D-076 允许的形状 —— 与 `scaffoldRemoval` 当初的立法方式**一模一样**
（`scaffoldRemoval` javadoc：「这是 D-076 意义上**新增的显式授权入口**，已在 `WORLD_WRITE_AUTHORIZATION.md` 登记」）。

## 8. ⭐ 最便宜的一块：原路返回

### 8.1 事实：全仓**无任何轨迹记忆**

| 搜索 | 命中共 |
|---|---|
| `retrace` / `原路` / `来时` / `routeMemory` / `rememberPath` / `backtrack` | **0** |
| `positionHistory` / `recentPositions` / `visitedCells` / `pathHistory` | **0** |
| 类型为轨迹缓冲的 `ArrayDeque<BlockPos>` / `List<BlockPos> visited` | **0** |

⇒ **bot 不记得自己从哪来。**

### 8.2 提案：逃生优先**沿来时的轨迹倒着走**

**改什么**：`SurvivalExitTask` 的**候选格来源** —— 从"8 格内最近安全格"改成"**先看轨迹，再看半径**"。
（`WalkToTask` 本身**不用动**：它只是接受一个目标脚位。）

| 优点 | 说明 |
|---|---|
| 成本 | 一个几十格的环形缓冲（`ArrayDeque<BlockPos>`），**可忽略** |
| ✅ 正确性 | 轨迹上每一格**已被证明可站、可走**（bot 刚走过） |
| ✅ **天然沿隧道走** | 不会被"墙里的最近格"误导（← 正是 D-238 实测到的那个真实案例：`refuge=240,105,306` 几何成立但规划不可达） |
| ✅ **不碰 D-076** | 还是纯通行 |
| ✅ **不需任何流体预测** | 与 §5 一致 |
| ✅ **与 8 格互补** | 轨迹可以比 8 格长得多 ⇒ **直接缓解 §4.4 的"竖井无出口"** |

### 8.3 为什么它比其余四层都优先

**它让问题不发生，而其余四层都是事后补救。**

| 层 | 做什么 | 性质 |
|---|---|---|
| ① 危险层 | 邻 lava 硬拒绝（**但要接到走廊上**，§6.2） | 事后（开挖前的检查） |
| ② 可回收层 | "打开它会切断退路吗" | 事前（但需要一个空插槽） |
| ③ 观测层 | 破坏后下一 tick 复查流体 | 事后 |
| ④ 逃生层 | **预留逃生预算**（§7.3） | 事后 |
| **⑤ 上游根治** | **原路返回**（§8） | **让问题不发生** ⭐ |

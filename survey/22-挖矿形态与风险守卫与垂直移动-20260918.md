## §1 📖 挖矿任务 vs 低级挖掘任务（**补 `survey/20` 的遗漏**）

### 1.1 两者是什么

| 层 | 是什么 | 状态 |
|---|---|---|
| **L2 `MineTask`（低级挖掘）** | **挖一格**：站位规划 + 限次清障 + 加高 + 建拆同权 | ✅ 已验收 |
| **L3 `MineJob`（挖矿任务）** | **挖一组**（quota 个）：`SELECT → MINE → COLLECT` | ✅ 存在 |

```java
// job/mine/MineJob.java:60
private enum Phase { SELECT, MINE, COLLECT, DONE }
```

### 1.2 ⭐ 差三件（核心结论）

| | `MineTask`（低级） | `MineJob`（挖矿） |
|---|---|---|
| **目标的来源** | **调用方给一个格** | ⚠️ **自己扫**：`SCAN_RADIUS = 24`（`MineCandidateSource.java:40`），**只找已暴露**的候选 |
| **作业的形态** | 一个目标做完就结束 | **多目标 + `attempted` 不重复选** |
| **判据的形态** | 挖掉这一个格 | ⭐ **挖到 quota 个 + 产物真的进包** |

### 1.3 ⚠️ 今天的形状：**收集已经是"挖完再一起捡"**

```java
// MineJob.java:309-311
if (minedCount >= spec.quota()) {   // ⭐ 只有挖够配额才起收集
    startCollect();
    phase = Phase.COLLECT;
}
```

**⇒ 所以"不做成挖一格捡一格"**已经是现状**。**

**⇒ ⭐ 真正该拆的**不是时机，是归属耦合：**

```java
// MineJob.java:318-320
private void startCollect() {
    BlockPos origin = firstMined != null ? firstMined : spec.center();
    collector = new CollectDropsTask(bot, origin, scope, List.of(), false);
    //                                   ↑A      ↑B    ↑C
}
```

| | 是什么 | 通道挖掘下的问题 |
|---|---|---|
| **A `origin = firstMined`** | 收集的**出发点** | ⚠️ **第一个矿**和第 20 个矿可能差很远 ⇒ 收集要**横穿整条通道走回去** |
| **B `scope`** | 掉落物**登记窗口** | 掉落物必须**活到**收集那一刻 |
| **C `List.of()`** | ⭐ **`expectedIds`** | 见 1.4 |

### 1.4 ⚠️ 「不捡石头」**不能靠传参解决**

```java

```

```java

    continue;      // 不在白名单 ⇒ 跳过
}
```

**⇒ ⭐ 第 4 参是 **UUID 白名单**，**不是物品过滤**。**

**⇒ 后果：**

> **过滤口**已经在那里**，但它是"你得先知道 UUID 才知道要不要捡"，而 UUID 在掉落物**生成时**才有。**
> **⇒ 所以"不捡石头"**不能靠传参** —— 需要"按物品/来源过滤"的新一层。**

## §2 📖 通道挖掘 × 可回收性（**补 `survey/20` 的遗漏**）

### 2.1 ⭐⭐ 项目**自己写明了**「记账只能管放、管不了挖」

`ledger/WorldModLedger.java:20-26`（**原文**）：

> 世界修改账本（J6-a，D-081 §12）：**只记"我方放置"**，用于"建拆同权"的配对与恢复。
>
> **为什么只记放置：破坏型修改**无法配对恢复**（你没法把隧道还原），其控制手段是
> "谓词 + 预算 + 归因"（见 D-095）；**只有放置需要、也能够被恢复**。
> 账本因此小而准。

**条目结构**（`:49`）：

```java
record Entry(BlockPos pos, String placed, String previous, String reason, Policy policy,
             String scopeId, UUID owner, long tick)
//                ↑ 放成了什么   ↑ 原来是啥  ← 精确恢复的原语
```

### 2.2 ⭐ 由此得到的最重要推论（**作者本轮独立提出，勘测侧核实成立**）

> ⚠️ **本节结论已被 `§9` 更正** —— 勘测侧当时把它推成了"不该允许挖"，那是**勘测侧推论**、**不是主线裁定**。
> 原文保留以便查证；**正确口径请看 §9**。

| 手段 | 能否记账 | 能否恢复 | 现有控制手段 |
|---|---|---|---|
| **放方块（搭路/垫柱）** | ✅ 记（`placed`+`previous`） | ✅ **能精确还原** | **建拆同权** |
| **挖方块** | ❌ **不记** | ❌ **隧洞还原不了** | ⚠️ **谓词 + 预算 + 归因**（D-095） |

**⇒ ⚠️ 勘测侧当时从这条推出了「保护区提权**只放搭路、不放挖掘**」—— 那是**勘测侧推论，不是主线裁定**。**
**⇒ 正确口径见 `§9`：主线 `D-305` ④ 已裁定「提权**搭和挖两种权限一起给**」，风险靠**挖掘黑名单 + 闸门**控制。**

**⇒ 本条**真正成立**的结论只有一句：**

> **「放」有账本兜底（能精确还原），「挖」没有 ⇒ 挖的风险不能靠记账控，只能靠「闸门 + 黑名单」。**

**⇒ 这解释了作者此前的困惑**「让他挖矿都在单独计较怎么给预算、怎么记录账单」：
**"挖"这条路本来就没法用记账管，只能用「预算 + 谓词」管。**

### 2.3 ⚠️ 主线复算的更正（勘测侧接受）

主线（`D-305` ④）指出：勘测侧早先的论证说"挖**不可记账** ⇒ 只放不挖才安全"，但
**真实的安全来源不是记账、是既有闸门**：

| 闸门 | 作用 |
|---|---|
| `protection/BlockBreakSafety` | 保护区拒绝一切破坏 |
| `BlockBreakSafety.hasBlockEntity` | **含方块实体的方块（模组机器）不得清障**（D-095） |
| `isExpensiveToClear` | 黑曜石 / 哭泣黑曜石 / 强化深板岩 |

**⇒ 所以给"挖"提权的风险**比勘测侧早先所述低**。**

### 2.4 「不捡石头」今天**能跑**（勘测侧更正）

## §3 ⭐ 风险模式与守卫（**作者 2026-09-18 裁定：冻结现状**）

### 3.1 作者裁定（**原文收档**）

> 「任务预设也不管了，**现在的守卫肯定不是最终的形态，必须开启的守卫和可开关的守卫也要区分开**，
> 干脆**现在不管守卫怎么弄，先保持现状**，以后**实测特别影响效率或者安全性的时候，再做可调试接口**。」

**⇒ 执行口径：**

| 事 | 现在做什么 |
|---|---|
| 守卫形态 | ❌ **不动** |
| 任务预设 | ❌ **不做** |
| 必须开启 vs 可开关的区分 | ⚠️ **登记，不做** |
| 可调试接口 | ⚠️ **等实测触发**（"特别影响效率或者安全性的时候"） |

### 3.2 📖 核实到的现状（供未来接手时用）

**⇒ `RiskProfile` 今天只有 3 个字段：**

```java
// pathing/risk/RiskProfile.java:25
public record RiskProfile(boolean descendOvershootGuard, boolean containerAccess, boolean hazardAversion)
```

**⚠️ 勘测侧归纳：三者不是同一层的东西。**

| 字段 | 性质 | 默认值 |
|---|---|---|
| `descendOvershootGuard` | ⚠️ **守卫**（禁掉"冲过目标列"的边） | **false** |
| `hazardAversion` | ⚠️ **成本权重**（贴危险**加价**，不禁止） | **false** |
| `containerAccess` | ⚠️ **能力许可**（能不能开箱） | **true** |

**⇒ 以上"三层不同"是勘测侧归纳，非作者裁定。**

### 3.3 ⚠️ 勘测侧发现的两个问题（**登记，勿视为裁定**）

| # | 发现 | 依据 |
|---|---|---|
| 1 | ⭐ **高风险模式 = 守卫全关 + 不记危险成本 ⇒ 就是今天的默认** | `RiskSwitches` 头注释原文：「**默认全部关闭 = Baritone 原样高风险**」；两个开关默认均 `false` |
| | ⇒ **所以"把开关全关"提不了效率** —— 它就是今天的效率 | |
| 2 | ⚠️ **`HAZARD_ADJACENCY_PENALTY = 20.0` 是固定值、不是倍率** | `MovementContext.java:60`：「够大以至于规划器倾向绕开，但不至于把路封死 ✗（≈20 格走路）」 |
| | ⇒ 长距离下**被稀释**（100 格的路绕开要 +30 格 ⇒ 20 < 30 ⇒ 还是会贴危险走） | |

**⇒ 勘测侧判断（未拍板）**：`hazardAversion` **暴露给玩家之前**，宜先改成「相对绕路成本」而不是固定 20。

### 3.4 ⚠️ 作者对「预算」的纠正（勘测侧接受）

> 「**预算不算一层**，因为预算现在计划实际只有两种作用：① 保护区的**临时修改预算**（保护玩家财产）② **局部逃生预算**（保证逃生速度）」

**⇒ 核实成立：**

| 预算 | 值 | 作用 | 归属 |
|---|---|---|---|
| `WriteBudget.DEFAULT_MAX_BREAKS` / `MAX_PLACES` | 64 / 32 | **保护玩家财产** | **保护区**（D-327） |
| `ESCAPE_MAX_NODES` / `ESCAPE_MAX_MILLIS` | 4000 / 100ms | **保证逃生速度** | **局部逃生** |

**⇒ ⭐ 勘测侧推论（**未拍板**）：两个预算服务两个**不相干**的目的 ⇒ **"预算"没有"通用旋钮"形态**。**

**⇒ 由此得到的候选推论（**未拍板，需作者确认**）：**

> **风险模式的作用域**不覆盖保护区** —— 保护区里永远是"低风险"（因为要保护财产）。**
> **⇒ 风险取舍只在**无主野地**里有意义。**

## §4 📖 垂直移动：Baritone 对照（**源码实测**）

### 4.1 ⚠️ 先更正一个勘测侧此前的前提错误

**勘测侧曾以为「Baritone 的挖掘靠单独的『边挖边走』策略」。** ⚠️ **核实后：不成立。**

**⇒ Baritone 的真实形状：**

```java
// Movement.java:50
protected final BetterBlockPos[] positionsToBreak;      // ⭐ 每个 Movement 自带"要破坏哪几格"
```

```java
// MovementTraverse 构造
public MovementTraverse(IBaritone baritone, BetterBlockPos from, BetterBlockPos to) {
    super(baritone, from, to, new BetterBlockPos[]{to.above(), to}, to.below());
    //                            ↑ positionsToBreak = [头位, 脚位]
}
```

| 事 | Baritone | Alice |
|---|---|---|
| **破坏** | ⚠️ **不是独立 Movement** —— 是**每个 Movement 自带的属性**（`positionsToBreak`） | ✅ **独立类型** `BREAK_AND_TRAVERSE` / `BREAK_AND_ENTER` |
| **放置** | ⚠️ **不是独立 Movement** —— 写在**每个 Movement 的 `cost()`** 里 | ✅ **独立类型** `PILLAR` / `PLACE_STEP_AND_TRAVERSE` |

**⇒ ⭐ 所以 Alice **比 Baritone 更对称**（挖 2 + 放 2 都是独立类型）。**

**⇒ ⭐ 对称的**理由**（勘测侧推断，非作者原话）：**

> **`MovementType.changesWorld()` 是**信封分档的唯一静态口径**：**
> ```java
> // pathing/core/MovementType.java
> public boolean changesWorld() {
>     return this == DOWNWARD || this == PILLAR || this == BREAK_AND_TRAVERSE
>             || this == BREAK_AND_ENTER || this == PLACE_STEP_AND_TRAVERSE;
> }
> ```
> **⇒ 如果 `ASCEND` 自己会放方块，"纯通行的移动集"就再也不能包含 `ASCEND` ⇒ 打穿信封分层。**
> **⇒ 所以 Alice 的对称形状是**权限模型倒逼的**，不是寻路内核的偏好。**

### 4.2 Baritone 各 Movement 是否含放置

| Baritone Movement | 含放置 | 证据 |
|---|---|---|
| `MovementAscend` | ✅ **本体会放**（backplace） | `:70-96`：`canWalkOn` 不成立 ⇒ `costOfPlacingAt` + 找 `canPlaceAgainst` |
| `MovementTraverse` | ✅ **本体会放**（搭桥） | `:135-158`：`placeCost = costOfPlacingAt(...)` |
| `MovementPillar` | ✅ 放（垫柱子） | `:83-134` |
| `MovementDescend` | ❌ **不含** | 只查 `canWalkOn`，不用 `costOfPlacingAt` |

**⇒ ⭐ 所以 Baritone 对上升**更宽松**（`Ascend` 自己垫），Alice 反而更严。**

### 4.4 ⭐ 作者关于垂直移动的澄清（**原文要点**）

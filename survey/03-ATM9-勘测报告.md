## 1. 勘测对象与数据来源

### 1.1 为什么是 ATM9（用户给定理由）

> 「这个整合包覆盖大量的模组内容，虽然有魔改，却几乎没有修改模组原生内容，对我来说是最适合的材料」

**勘测确认该判断成立**：ATM9 的 435 个模组里没有任何一个是"重写原版"型整合包常见的侵入式改动；
它的魔改集中在 **KubeJS 脚本 + 配置**（官方仓库 `AllTheMods/ATM-9` 下只有 `config/`、`defaultconfigs/`、`kubejs/`、`packmenu/`），
**模组 jar 本体保持上游原样**。

**对 Alice 的意义**：模组适配器**只需对齐上游 API，不必对齐整合包私有 patch**。
这是 ATM9 作为"第一份材料"的核心价值——**它把"整合包私有魔改"这个变量消掉了**，剩下的全部是"上游模组 API"这一个变量。

#### 取证技巧：4 KB 拿到权威清单（不需下载 49 MiB 整包）

ATM9 包体 **49 133 990 B（49.1 MiB）**，但 `manifest.json` 只有 40 KB 且**位于 zip 首位**。
用 **HTTP Range 请求**只取 zip 尾部中央目录 + `manifest.json` 数据段即可：

- 取尾部 70 KB → 解析 EOCD → 得中央目录偏移 `51272088`、大小 `161880`
- 取中央目录 → 定位 `manifest.json` → 得 local header 偏移 `0`、压缩后 4 553 B
- 取该数据段 → `zlib.decompress(..., -15)` → **40 794 B 权威 JSON**

全程 **3 次 range 请求**，下载量约 4 KB。脚本见 `/tmp/zipfetch.py`。
（⚠️ 直接用 `HEAD` 请求该 URL 会返回 `200` 但 `size_download=0`，容易误判为"下载失败"——**必须用真实 GET**。）

## 2. 加载器与版本判定（含一处公开数据更正）

### 2.1 判定：Forge，不是 NeoForge

三条独立证据：

1. **S1 直接声明**：`manifest.json → minecraft.modLoaders[0].id = "forge-47.4.0"`、`primary = true`。
   CurseForge 启动器**按此字段决定装哪个加载器**——这是整合包作者自己的声明，效力最高。
2. **S4 标签**：`versions: ["1.20.1", "Forge"]`，**不含 NeoForge**。
3. **版本号存在性（硬证据）**：`net.neoforged:forge` 在 **1.20.1 上只发布到 `47.1.106`**（该 artifact 下 65 个版本**全为 `47.1.x`，无任何 `47.2.x`**）；而 Forge 1.20.1 有 `47.2.x`。

**结论：ATM9 1.1.1 跑在 Forge 上。**

### 2.2 更正一处公开数据错误（避免误导后续判断）

mcmod.cn 的 ATM9 清单里有一行 `[Neo]NeoForge 47.2.16`，据此极易误判"ATM9 是 NeoForge 包"。

**为什么会错**：1.20.1 是 NeoForge 刚从 Forge fork 出来、**仍借用 Forge 版本号**的那一代
（`net.neoforged:forge` 这个 artifact 名至今仍叫 `forge`，因为它继续使用 `net.minecraftforge.*` 包名，以保证二进制兼容）。
于是这一代很多模组 jar **打了双加载器标记**，在 ATM9 里随处可见：

- `The Aether` 的 jar 名为 `aether-1.20.1-1.5.2-**neoforge**.jar`
- FTB 全家桶**显示名**带 `(NeoForge)`，但 **jar 名**是 `ftb-quests-**forge**-2001.4.14.jar`
- `Mekanism` 的 `fileID 6258796` 在 cfwidget 上的 loader 标记为 `["NeoForge", "1.20.1", "Forge"]`

**这些标记说的是"该 jar 在 1.20.1 上两种加载器都能跑"，不是"整合包使用 NeoForge"。**
在 1.20.1 上两者 API 兼容，所以**这个区分在 ATM9 场景里不影响结论**——
但它很容易被当成"ATM9 用 NeoForge"的证据，**本勘测明确否掉**。

### 2.3 对 Alice 的意义

✅ **Alice 与 ATM9 同构**：Alice 自己是 Forge mod（`mods.toml` 声明 `modId="forge"`），ATM9 是 Forge 包 → **直接可装**，
不存在"Alice 是 Forge mod 却被要求跑在 NeoForge 上"的隐患。

⚠️ **一个待实测的小口子**：ATM9 要求 `forge-47.4.0`，Alice 是 `forge-47.4.10`。
- Alice 的 `forge_version_range=[47,)`、`loader_version_range=[47,)` → **声明层面兼容**。
- 47.4.0 → 47.4.10 是**同一 patch 线内的小版本**，Forge 在此区间保持二进制兼容 → **风险低**。
- 但 **435 个模组是按 47.4.0 编译的**：若某个模组引用了 47.4.0 之后被 Forge 改动签名的内部 API，升到 47.4.10 后可能在运行期炸。
- **待实测（§8 第 1 项）**：这是"Alice 装上 ATM9 后能不能进世界"的第一道门槛。

| **Energy, Fluid, and Item Transport** | **36** | **C1/C2（最甜）** |
| Structures / World Gen / Biomes / Dimensions | 35 / 34 / 12 / 14 | C0（**只影响寻路的"场景结构"输入**） |

| Magic | 34 | C1/C2 |

| Energy / Mobs | 24 / 24 | C1/C2 |
| Automation / Processing | 20 / 19 | C1/C3 |
| Performance | 12 | 与 Alice 无关（但**开发期可用**） |

**「省事区」的两条判据**（判定标准 = 不需要写任何适配器代码）：

1. **C0 自动 100%**：方块 / 物品 / 实体的**存在性与标签**由 `Registry` + `Tag` 提供。
   Alice 不需要为任何**单个** ATM9 模组做事：**435 个模组在 C0 层面成本为零**。
   → 推论：`perception/PerceptionClassifier` 若走标签判定，**天然覆盖 ATM9 全部矿石 / 原木 / 可挖掘方块**。
   → 再推论：ATM9 里的 `Almost Unified` 把跨模组的重复矿物 / 锭**统一成同一标签**，**只会让标签判定更干净**。
2. **C1 覆盖标准 capability**：凡把内容暴露成 Forge 标准 capability 的，`capability/InterfaceScanner` 的通用路径就能读。
   ATM9 里这类是**绝大多数**：
   - **存储**：Sophisticated Storage / Backpacks、Functional Storage、Dank Storage 15、DimStorage、ExtraStorage、Extra Disks、Iron Furnaces、Trash Cans、EnderChests / EnderTanks — 均实现 `IItemHandler` / `IFluidHandler`
   - **传输**：Pipez、XNet (+Gases)、LaserIO、Modular Routers、Flux Networks、Cable Tiers、Simple Magnets — 均吃标准 capability
   - **能量**：Powah 5.0.11、Extreme Reactors 2.0.94、Draconic Evolution 3.1.2.621、Deep Resonance、Advanced Generators、Generator Galore、Energy Meter
   - **热力系列**（Thermal 共 9 个模组，11.0.x）：走的正是 CoFH 标准 capability，**与原版 Forge capability 同构**

> **勘测结论**：把 C0/C1 做到"覆盖整包"**根本不难**。难的是 C3 以上。
> **不要被 435 这个数字吓到**——它衡量的是"环境复杂度"，不是"Alice 的工作量"。

### 3.4 会推翻现有设计的意外 ★（本报告最重要的一节）

#### 硬伤 ①：Lootr —— "箱子"不再是箱子

**模组**：`Lootr (Forge & NeoForge) 1.20-0.7.35.93`

**它做什么**：把结构里的战利品容器变成**每个玩家一份独立内容**——A 开过的箱子，B 打开还是满的；A 拿走的物品，B 看不到。

**为什么打穿 Alice**：
- `transfer/ChestEndpointRef` + `InventoryObservation` + `TransferLedgerData` 这整套设计建立在
  **"一个方块位置 = 一个确定的内容物"**之上：账本按位置记账、幂等按位置判定、"我搬过了"按位置记录。
- 在 Lootr 容器上：**同一位置的 observation 因观测者而异** → 账本会**错记**；
  "我上次看到里面有 3 颗钻石"这个事实**对另一个 bot、或下一次打开，都不成立**。
- 更隐蔽的一层：Lootr 还有 **"某玩家拿走的物品对该玩家永久消失"** 的语义 → **跨会话的账本会失效**。

**建议**：把"容器身份"从 `(dimension, pos)` 升级为 **`(dimension, pos, viewerScope)`**，
并让 `InventoryObservation` 显式记录**观测者身份**与**内容是否 per-player**。
现在不必实现，但**必须在设计里预留**，否则未来要重写账本。

**待实测（§8 第 4 项）**：Lootr 对 bot 假人（`ServerPlayer`）是否也按 UUID 分片——大概率是，因为它按 UUID 判定。

#### 硬伤 ②：Alice 自己对 Mekanism 是**无守卫的硬链接**，且版本比 ATM9 新

这是勘测中**最意外的发现**——它不是 ATM9 的问题，而是 **Alice 自己的问题被 ATM9 暴露了**。

**事实链（全部可在仓库内核对）**：

1. Alice 编译目标是 **Mekanism `1.20.1-10.4.16.80`**
   （`build.gradle` 第 142–143 行：`implementation fg.deobf("mekanism:Mekanism:1.20.1-10.4.16.80")`）。
2. ATM9 1.1.1 **锁定的是 `Mekanism-1.20.1-10.4.15.75.jar`**（manifest `fileID 6258796` 精确匹配，§1.2 方法）。
   → **ATM9 的 Mekanism 比 Alice 的编译目标旧一个补丁。**
3. `InterfaceScanner.scanMek*` 用 **`getstatic` 直接引用 Mekanism 字段**（`InterfaceScanner.java:167-172` 起）：
   `mekanism.common.capabilities.Capabilities.GAS_HANDLER / INFUSION_HANDLER / PIGMENT_HANDLER / SLURRY_HANDLER / HEAT_HANDLER / STRICT_ENERGY`，
   以及 `instanceof mekanism.common.tile.interfaces.ITileRedstone / ITileUpgradable / ISideConfiguration`、
   `mekanism.api.Upgrade`、`mekanism.api.RelativeSide`、`mekanism.common.tile.component.config.DataType`。
4. `capture()` 的兜底是 **`catch (RuntimeException exception)`**（`InterfaceScanner.java:69`）。
5. 全仓扫描 `ModList` / `isLoaded` / `Platform.` / `getModContainer` / `LoadingModList` → **零命中**，
   **没有任何模组在场守卫**。

**风险**：
- **若 Mekanism 缺席** → `NoClassDefFoundError`
- **若 Mekanism 版本漂移导致某字段 / 方法签名变化** → `NoSuchFieldError` / `NoSuchMethodError`
- 这两者都是 **`LinkageError`（`Error` 的子类），不是 `RuntimeException`**
  → **第 4 条的 catch 抓不到** → **异常逃逸，不会被降级成 `CAPTURE_ERROR`**

**这意味着**：Alice 的"只读接口扫描"这条 **C1 主路径**，在**版本不匹配的整合包上会以未捕获 Error 的形式炸出去**，
而不是优雅降级。ATM9 恰好是**旧一版** Mekanism——**是否真炸待实测**，但**设计上必须假定会炸**。

**建议（三条，任一都能止血，建议全做）**：
1. **版本对齐**：把 `build.gradle` 的 Mekanism 依赖改成**目标整合包锁定版本**（ATM9 = `10.4.15.75`）；
   或至少加一个 CI 检查，记录"编译目标 vs 目标包版本"的差异。
2. **在场守卫**：`ModList.get().isLoaded("mekanism")` 前置判断——**零成本**。
3. **异常面扩大**：`catch (RuntimeException)` → `catch (RuntimeException | LinkageError)`
   （或 `Throwable`），让版本漂移降级成 `CAPTURE_ERROR` 而不是逃逸。
   → 这与 Alice 的大原则一致：**"多层任务失败向上传递"而不是崩掉**（D-036 差异②）。

> **勘测员意见**：这一条**跨过了"浅程度规划"的边界**，因为它是一个**当前代码的正确性缺口**，不是未来蓝图问题。
> 但按用户约定，**本目录不改代码、不干预主线**——只在此登记，由主工作流判断优先级。

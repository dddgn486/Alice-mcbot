## 1. ⭐⭐ 定位修正：从"替代 AE"到"AE 的外挂"

### 1.1 原定位的问题（用户自查得出）

| 原定位 | ⚠️ 问题 |
|---|---|
| 「让 Alice 在 AE 时代**前**替代 AE」 | **把 Alice 定位成"AE 的低配版"** ⇒ **一旦玩家做到 AE，Alice 就没用了** ⇒ **产品价值随玩家进度递减** |

### 1.2 修正后的定位

> **Alice 是 AE 的外挂，不是 AE 的替代。**
> **AE 管「管道 + 库存 + 自动合成」；Alice 管「管道接不上的那一层」。**

| 维度 | 替代 AE | ⭐ AE 的外挂 |
|---|---|---|
| 玩家进度对价值的影响 | ❌ 递减 | ✅ **递增** |
| 与 AE 的关系 | ⚔️ 竞争 | 🤝 互补 |
| 增量空间 | ❌ 有上限 | ✅ **开放**（AE 做不到的清单可枚举） |

### 1.3 ⭐ 与"可回收性"的关系（这一条是本报告对用户自我怀疑的正面回答）

用户本轮原话：

> 「bot 可回收性是主要的，不过**这个特性在科技整合包中后期不是主要卖点**」

**⇒ 判断：这个观察准确，但结论要反过来 —— 可回收性从"卖点"换成"许可证"。**

| 阶段 | 可回收性的角色 |
|---|---|
| 早期 / 探索 / 挖矿 | ⭐ **主卖点**（"敢放它出去"） |
| 中后期 / 基地自动化 | **底座**（看不见，但**它不在，玩家不敢让 bot 碰机器**） |

**⇒ 关键论证**：
> **自由度的对立面不是"保守"，是"不受控"。**
> **一个会自己乱用机器的 bot，只有同时保证"任何操作都能撤回 / 任何失误都有退路"，玩家才**敢**给它自由度。**
> **⇒ 可回收性 = 敢放开权限的前提。**

### 1.4 🚩 证伪点（什么情况会推翻这个定位）

| 若观察到 | 则 |
|---|---|
| 玩家在 AE 成型后**仍然经常让 bot 操作容器间传输** | ⚠️ 说明"互补"判断错，Alice 和 AE 是竞争关系 |
| 玩家**根本不关心** Alice 能不能做 AE 做不到的事 | ⚠️ 说明定位抓错了痛点 |

## 3. ⭐ 概念确立：**工作站（玩家亲手划分 + 能力声明）**

> **⚠️ 性质**：**这是概念确立，不是排期**。它回答"我们说的'工作站'到底是什么"，不回答"什么时候做"。

### 3.1 完整形态

| 项 | 谁定 | 例子 |
|---|---|---|
| **前提** | 注册工作区（**已有机制**） | `/alice region set` + `LumberRegionState.Region` |
| **工作站占位** | ⭐ **玩家逐格划** | 磨粉机 + 漏斗 + 箱子 = **三格一个工作站** |
| **输入操作口** | 玩家指定 | 磨粉机本体 |
| **输出操作口** | 玩家指定 | 箱子 |
| **主交互面** | 玩家指定 | **任何机器 / 仪式 / 工作台都必有唯一主界面** |
| **单方块机器** | ✅ 快速配置（一格 ⇒ 输入/输出/主界面**三合一**） | 熔炉 |

### 3.2 ⭐⭐ 能力声明（本轮最重要的补充）

> 用户原话：「让玩家把这个工作站**等价于一类配方的工作站**……玩家可以把它设定成 **mek 磨粉机**，
> 这样工作站就被声明**能够运行所有 mek 磨粉机能运行的配方**」

**⇒ 工作站 ≠ AE 样板**：

| | AE 样板 | ⭐ Alice 工作站声明 |
|---|---|---|
| 粒度 | **一个配方一份样板** | ⭐ **一类机器一份声明** |
| 配方从哪来 | 玩家手工编码 | ⭐ **自动继承该类的全部配方** |
| 输入输出 | 样板里写死 | ⭐ **由工作站的"口"决定** |

> **一句话：样板是实例，工作站是类型声明。声明一次，覆盖该类机器的所有配方。**

**⚠️ 勘测员补正的细节（用户本轮明确更正，务必按此理解）**：
> 用户原话：「工作站**等于中间节点**，**不仅是**只做**玩家自己设定的配方**
> （类似于 AE 样板），**也能**让玩家将这个工作站**等价于一类配方的工作站**」

**⇒ 能力声明的两个来源，是"并集"不是"二选一"**：

| 来源 | 玩家填什么 | 覆盖的配方 |
|---|---|---|
| **① 自定义配方** | 一份具体配方（≈ AE 样板） | **只这一份** |
| ⭐ **② 类别声明** | "本工作站**等价于 mek 磨粉机**" | **该类机器的全部配方** |

**⇒ 一个工作站可以两者兼有**：既接几份自定义配方，又同时声明等价于某个机器类。
**⇒ 这是"中间节点"的完整含义** —— 节点先有**位置**（在产线里承担哪一步），
再有**能力**（能跑哪些配方），能力可由「样板」或「类别声明」任一路径供给。

### 3.3 ⭐ 语义口径（用户澄清后的准确表述）

> 用户原话：「在输入输出这层上，**只看外部，不在乎内部**」
> 又说：「bot 还是能**读方块本体的配置，而不是完全忽略内部**，当然**都得是可控的预设**」

| | 读取范围 | 什么时候 |
|---|---|---|
| **默认** | **只看外部**（输入口/输出口/主界面） | 通用工作站 —— 与 AE 相同 |
| ⭐ **有预设时** | **可读机器本体配置**（模式/开关/状态） | **只在"受控预设"覆盖到的范围内** |
| **绝不读** | 预设未声明的任何内部细节 | —— |

**⇒ 与项目信封思想同构**：**默认最小权限；要更多能力 = 显式授予。**

### 3.4 ⚠️ 硬边界（用户明确）

> 「bot **不可能动玩家设定的复杂流水线的机器配置**，**只限定于单方块机器**」

### 3.5 工作站在生产线里的位置

```
玩家划定的工作区
   └── 若干工作站（玩家逐格划分 + 逐站声明能力）
         每个工作站 = 生产线上的一个"中间节点"
         ↓
   Alice 的职责：把材料放进"输入操作口"、从"输出操作口"取出产物
   Alice 不关心的：工作站内部是什么模组 / 机器 / 魔法
```

**⇒ Alice 做的是「节点间搬运 + 节点内投料/取料」，不是「设计节点之间怎么连」。**

### 4.4 ⚠️ 关于"越来越保守"（用户的第二个担心）

**机制链条（`survey/09` 的 D-248 就是实例）**：

```
真实世界出现一个特殊情况（例：水里没有 onGround）
  ↓ 加一个守卫
  ↓ 守卫之间开始互相冲突（D-248 那次 CORE 红）
  ↓ 加固 → 误杀 → 放宽 → 又漏 → 再加守卫
  ↓ 为了不误杀，把守卫设得很保守 ⇒ 覆盖面变小
```

**⇒ "越来越保守"不是设计选择，是"守卫互相打架"的必然终局。**

**⚠️ 建议盯着一个数**（勘测建议，非裁定）：

> **"诚实失败"的比例** —— `UNREACHABLE` / `NO_REACHABLE_CANDIDATE` / `HOLD_NO_EXIT` 占终态的百分比。
> **它涨 = "变保守"在发生；它稳 = 守卫在净收益。**

## 5. LLM 职责边界（**口径收敛 + 三条未落地点**）

### 5.1 权威边界（蓝图原文）

> **LLM 不负责**：每 tick 移动、碰撞和攻击时机；猜槽位、直接写 NBT、任意发模组网络包；
> **自行扩大破坏/搬运区域、权限、预算或重试次数**；**宣告任务成功、物品到账、机器完成或样板正确**。
>
> **LLM 负责**：**解析用户目标**；**从候选目标/路线/工具中选择**；失败后**换目标、换路线或请求用户信息**。

**⚠️ 关键现状**：**这条约束目前只活在文档里** —— 代码中没有任何结构承载它（`survey/05` 已登记）。
**⇒ 承载它的结构就是"授权信封"，尚未实现。**

### 5.2 已拍板的口径（累积）

| # | 裁定 | 理由 |
|---|---|---|
| **1** | 默认信封 = **能做计划，不能动世界** | 误判成本不对称 |
| **2** | **LLM 只建议，表单才确认** | LLM 判错 = 一次多余确认（成本 ≈ 0）；直接执行判错 = 改了世界 |
| **3** | ⛔ **`DECLARE_DONE` 永不授予** | **职责错配**（完成判据必须来自服务端事实），**不是"危险"** |
| **4** | ❌ **`RESOURCE_SELF_FETCH` 不单设** | 会实际触发世界修改 ⇒ "决定自取却挖不动，卡住" |
| **5** | ⚠️ **`QUEUE_COMMIT` 默认不给 LLM** | 否则绕过表单 ⇒ 改为**责任转移**机制 |

## 8. 逐模组适配的定位（**档 3 = 加分项，不是承诺**）

### 8.1 三档能力上限

| 档 | 能做什么 | 例子 |
|---|---|---|
| **档 1（无适配）** | 只看外部输入/输出口 | 任何"像容器"的机器 |
| **档 2（通用预设）** | 输入口/输出口/主界面的组合约定 | 单方块机器 + 独立输出口 |
| ⭐ **档 3（逐模组适配）** | **延伸到 JEI 也管不到的地方** | **法阵怎么画、魔力从哪牵到哪** |

### 8.2 预设两层

| 预设类型 | 例子 | 内容 |
|---|---|---|
| **通用结构预设** | 单方块机器 + 独立输出口 | 输入口=机器本体 / 输出口=箱子 / 主界面=机器本体 |
| ⭐ **模组专属预设** | **魔法法阵** | **怎么启动、怎么摆放祭品、魔力从哪牵到哪** |

**⇒ 玩家的操作路径**：
```
① 玩家把"法阵"这类特殊结构勾选成工作站
        ↓
② 选择"魔法阵预设"（来自逐模组适配包）
        ↓
③ bot 就知道：怎么启动这个法阵、怎么摆放祭品
```

**⇒ ⭐ 预设是"玩家勾选 + 选择"，不是 bot 自动识别。**

**⚠️ 预设的第二个用途：允许"部分读内部"**

> 用户原话：「也可以做一些**基础的预设**，比如刚才的磨粉机加漏斗箱子，就是
> **单方块机器 + 独立输出口预设**，这样 bot **还是能读当方块本体的配置**，
> **而不是完全忽略内部**，当然**都得是可控的预设**，能不完全忽略内部。」

| 层次 | 例子 | bot 能读什么 |
|---|---|---|
| **完全不读内部**（默认） | 任意机器 + 箱子 | 只看输入口 / 输出口 |
| ⭐ **预设授权读内部** | 磨粉机 + 漏斗 + 箱子 | **额外读机器本体的配置**（如磨粉机当前模式） |

**⇒ 这与 §3.3 的语义口径一致**：默认只看外部，**"读本体配置"是预设授予的能力**
（与授权信封思想同构）。**关键在"可控"** —— 读哪些字段由预设列明，不是 bot 自由发挥。

### 8.3 ⚠️ 用户对档 3 的定性（必须一起记）

> 「逐模组适配**能做太多事了，也太困难了**」
> 「我**没办法让每个模组都能如愿以偿**」

**⇒ 档 3 = 加分项，不是承诺。**

### 8.4 ⭐ 预设 = 容纳档 3 的容器（**不是承诺，是可选的挂载点**）

> 用户原话：「如果我们能够做到逐模组适配，**工作站应该就可以做成模组的预设**，
> 特别是**魔法仪式**这个层面，比如一个法阵被我们项目识别成特殊结构，我们就可以让玩家
> 把自己的法阵**勾选成工作站**后，**选择魔法阵的预设**，然后 bot 就知道**怎么启动**这个法阵、
> **怎么摆放祭品**。」

**⇒ 关键设计意图：把"档 3 的复杂度"关进"预设"这一个抽屉里。**

| 层 | 谁提供 | 变化频率 |
|---|---|---|
| 工作站框架（划分 / 能力声明 / 输入输出口） | **项目本体** | 低 |
| ⭐ **模组预设（含魔法仪式）** | **逐模组适配包 / 社区 / 模组作者** | 高，且**可缺席** |

**⇒ 于是"能不能适配某个模组"不再是项目能不能用的前提**：
没有预设的模组 ⇒ 退回档 1/档 2（只看外部口），**项目依然可用**。

**⚠️ 用户对"逐模组适配"的完整定性（三层意思，必须一起记）**：
> ① 「逐模组适配**能做太多事了**」
> ② 「**也太困难了**」
> ③ ⭐ 「我们要**适当选择优先级**，**吸引社区开发者**，甚至**模组作者主动适配**」

**⇒ 对第 ③ 点的含义**：「吸引社区 / 模组作者」= 这是一个**生态问题**，不是排期问题。
它成立的前提是 §7.1 的硬前提（**适配必须数据化**，玩家改 JSON 就能加，而不是改 Java 重编译）。
**⇒ 所以 §7.1 不只是"未知"，也是"档 3 与社区通路的总闸门"。**

**注**：术式类的"怎么画、往哪牵魔力"**不是本项目当前要识别的通用内容**（用户此前已裁定
整合包独占内容不进通用识别）⇒ 它们**只以"预设"形式存在**，且**由外部提供**。

## 补遗（**只增不改**：本轮讨论最后追加的细化，不改上文任何结论）

### 补遗 1 · 工作站不只是"中间节点"，能力声明是**并集**（已写入 §3.2）

> 用户原话：「工作站**等于中间节点**，**不仅是**只做玩家自己设定的配方（类似于 AE 样板），
> **也能**让玩家将这个工作站**等价于一类配方的工作站**」

⇒ **两份来源可并存**：自定义配方 ∨ 类别声明。**这是"中间节点"的完整含义。**

### 补遗 2 · 预设允许"部分读内部"，但必须是**可控**的（已写入 §8.2）

> 用户原话：「也可以做一些基础的预设，比如磨粉机加漏斗箱子，就是**单方块机器 + 独立输出口预设**，
> 这样 bot **还是能读方块本体的配置**，**而不是完全忽略内部**，当然**都得是可控的预设**」

⇒ 与 §3.3 一致：**读内部 = 预设授予的能力，默认不读。**

### 补遗 3 · 逐模组适配的定位（已写入 §8.4）

| 用户的三层定性 | 含义 |
|---|---|
| 「能做太多事了」 | 上限极高（延伸到 JEI 管不到的地方） |
| 「也太困难了」 | **不可能全做** |
| ⭐ 「适当选择优先级，吸引社区开发者，甚至模组作者主动适配」 | **把它当生态问题，不是排期问题** |

### 补遗 4 · ⭐ 新增登记：**社区通路有 3 道闸**（已写入 §7.1 与 §10-7/8/9）

| 闸 | 内容 | 今天 |
|---|---|---|
| **闸 1** | 适配**数据化**（改 JSON 不改 Java） | ❌ |
| **闸 2** | 适配**可视化产出**（游戏内标注 ⇒ 自动生成数据） | ⚠️ 有想法未实现 |

> **⇒ 「吸引模组作者主动适配」这句话要成立，三道闸都得过。**
> **三道闸没过之前，"社区适配"不是没兴趣，是没入口。**

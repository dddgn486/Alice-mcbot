# 勘测报告（供主工作流借鉴）

> **本目录不是实现授权。** 这里的每一份都是**建议 / 勘测 / 参考方案**，
> 主工作流**可以采纳、可以部分采纳、也可以不采纳**。
>
> **与主线的边界约定**（作者 2026-09-10 指定）：
> 本目录由**手机端智能体**维护，角色是**勘测员**，不是工程师。
> 类比：主工作流是「在固定位置设计修建桥梁的工程师」；勘测员只负责
> 「**寻找哪里适合修桥、可以学习谁的设计、估计要修多大、什么材料合适**」。
>
> 因此本目录**不干预正在进行的开发主线**，除非发现主线严重偏离原定方向。

## 为什么单独一个顶层目录

主工作流正在高频编辑 `docs/`（`docs/README.md`、`AI_DECISIONS.md`、`AI_PROJECT_STATE.md` 等）。
把勘测报告放在 `docs/` 下会造成**合并冲突**且需要改主线的索引文件。
放在顶层 `survey/` 下：**只新增文件，零改动既有文件**，主线想引用时再自己加一行索引即可。

## 整合包勘测的复现方法（本目录通用）

勘测一个整合包**不需要下载整包，也不需要运行游戏**。ATM9 的两步取证：

1. **拿权威清单（约 4 KB）**：CurseForge 的整合包 zip 里 `manifest.json` 只有几十 KB 且位于 zip 首位。
   用 **HTTP Range 请求**取尾部中央目录 + 该文件数据段，即可拿到加载器版本、模组数、每个模组的
   `projectID` / `fileID`。**不要用 `HEAD` 判断可用性**——它可能返回 `200` 但 `size_download=0`。
2. **`projectID` → 模组名 + 精确版本**：`api.cfwidget.com/<projectID>`（CurseForge 官方数据镜像），
   用 `manifest` 里的 `fileID` 在其 `files` 数组里精确匹配，得到**整合包锁定的 jar 名**。

> ⚠️ **不要相信二手整合包模组清单站**（如 mcmod.cn）。ATM9 实测中该站版本数据大面积滞后 / 错误，
> 甚至把加载器判成 NeoForge。**一律以 `manifest.json` 为准。**

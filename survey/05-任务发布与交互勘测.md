### 0.3 一条重要统一（本报告最有价值的部分）

**「进队列等」与「默认任务」不是两件事，是同一件事。**

任务因等待玩家而**无法推进**时，正确行为不是让 bot 干等，而是**回默认任务**（如巡逻），
等玩家回来授权后再恢复。因此回退到默认任务有**三个**触发器，不是一个：

```
完成 │ 失败 │ 阻塞等待（REFUSED / AMBIGUOUS）
```

这把用户提的两条设计（离线队列 + 默认任务）**统一成一个状态机**（§3.2），
且与 §4 的结果词表**直接对齐**。

## 1. 误判成本不对称 —— 整个交互层的锚点

「区分任务发布 vs 普通对话」的两种误判，代价差一个数量级：

| 误判方向 | 后果 | 可逆性 |
|---|---|---|
| 把**对话**误判成**任务** | bot 自行行动、挖了不该挖的 | **不可逆** |
| 把**任务**误判成**对话** | 玩家发现没动，再说一遍 | **只损失一次交互** |

**结论：正解不是「让 LLM 判得更准」，而是让 LLM 只负责建议、不负责任命。**

> **LLM 分类 = 建议；表单 = 确认。**

用户提出的「**增加一个显式的任务发布模式**」**本身就是那个确认界面** ——
LLM 在对话中识别出「这像是一个挖矿请求」，然后**弹出填好的表单供玩家确认**，而不是直接开干。

- **自由**体现为：LLM 帮你把自然语言翻译成结构化表单
- **安全**体现为：落地的动作**永远经过玩家的手**

这与蓝图 §2.2 早已写下的原则一致 —— Policy Gate 要把不确定性变成
「**拒绝、候选列表或用户确认**」。本设计正是它的一个实例。

## 2. 最高权限壁垒（用户新增设计）

### 2.1 三层模型

用户原话：

> 「玩家可以给 LLM 提权，让他自助决定一些本来要用户授权的任务，
> **但是有最高权限壁垒**，无论什么权限，遇到自己无法决定的事都应该**直接失败**。」

形式化为**三层比较**：

```
允许(请求)  ⟺  请求所需权限 ≤ 当前信封 ≤ 最高壁垒
                    ①            ②          ③
```

| 层 | 由谁设定 | 可变性 |
|---|---|---|
| ① 请求所需权限 | 请求内容本身 | — |
| ② 当前信封 | **玩家**（提权 = 放宽②） | **可调** |
| ③ 最高壁垒 | **系统/世界** | **不可调，任何人不可越** |

**关键性质**：玩家能放宽②，**但放宽不了③**。这就是「壁垒」的含义。

### 2.2 ★ 壁垒的内容项目里已经长出来了

**不必重新发明判断标准。** 项目里已经有现成的定性区分：

| 概念 | 项目实例 | 可否授予 |
|---|---|---|
| **不变式**（invariant） | **D-024 局部可回收性不变式**（`AI_DECISIONS.md:586`：「一格红线 = 局部可回收性不变式」）、D-036 差异①「**Bot 可回收性安全策略**」 | ❌ **壁垒** |
| **策略**（policy） | `RecoverabilityPolicy` / `ForbiddenZonePolicy` / `ProtectedAreaPolicy`（`AI_DECISIONS.md:121`） | ✅ 可配置 / 可授予 |

**判据（建议直接采用）**：

> **玩家可以授予「对玩家自己资源与风险偏好的处置权」，
> 但不能授予「破坏 bot 自身可回收性 / 违反世界不变式」的权力。**

理由很直接：**Alice 的核心差异①就是「Bot 可回收性」**（D-036）。
若玩家能提权让 bot 走进不可回收状态，**等于把 Alice 的定义性特征交给一次误操作**。

这条判据还顺手回答了一个未来问题：「LLM 能不能被提权到用 PILLAR 爬上去不回来？」
—— **不能**，因为那违反 D-024 不变式，属壁垒。

### 2.3 「直接失败」的含义：不可升级的拒绝

这是本设计最关键的一点，**必须与 `REFUSED` 区分开**：

| | 含义 | 处置 |
|---|---|---|
| **可升级的拒绝** | 信封不够，但**玩家能授权** | **问玩家**（提权即可继续） |
| **壁垒违反** | **任何人都不能授权** | **立即终结，不询问、不重试** |

用户原话「遇到自己无法决定的事都应该**直接失败**」= 第二种。

**为什么必须分开**：如果混在一起，LLM 被拒后无法判断「该求你提权」还是「该立刻停」——
只能靠自然语言猜，那就**退化回不确定行为**，正是本设计要消除的东西。

**与两个检查点的关系**（见 `survey/04` §5.3）：

| 阶段 | 壁垒违反的表现 |
|---|---|
| **计划级预检** | 任务**从未启动** → 映射到既有的 `REJECTED_BEFORE_START` |
| **执行中**（世界变了 / 第二步越线） | 需一个**执行期结果词**（见 §4） |

即：**壁垒违反在两个检查点都可能发生**，两层各需要自己的表达方式。

## 3. 默认任务与状态阶梯（用户新增设计）

### 3.1 现状：三样都没有

| 概念 | 现状 | 证据 |
|---|---|---|
| 任务**队列** | ❌ 不存在 | `beginTask` 直接 `task = assignedTask`（**赋值覆盖**） |
| **默认任务** | ❌ 不存在 | 全仓无 `defaultTask` / `fallback` / `standby` 概念 |
| **待机状态** | ⚠️ 隐含存在，**未建模** | `complete()` 末尾调用 `clearTask()`，之后 `task == null`；`"idle_after_cleanup"` 只是 `recoveryState` **字符串**，非真实状态 |

**当前行为**：任务完成后 → 清空 → **bot 无事可做**。
覆盖已有任务时用 `CANCELLED_REPLACED`（`replaceTaskIfRunning`），**且仅挡住运输在途的情况**。

### 3.2 ★ 回退到默认任务的**三个**触发器

用户只提了两个（完成 / 失败），但「离线进队列等」隐含了**第三个**：

| # | 触发器 | 含义 |
|---|---|---|
| 1 | **完成** | 正常结束 |
| 2 | **失败** | 确定失败 |
| 3 | **阻塞等待** | 需玩家输入（`REFUSED` 待提权 / `AMBIGUOUS` 待选择 / 前置资源离线） |

**第 3 个是本设计的精髓**：任务等待玩家时，**bot 不该干等**，
而应**回默认任务**（如巡逻基地），等玩家回来授权后再**恢复**该任务。

→ 因此「进队列等」的正确实现**不是**新增一个等待状态，
而是「**挂起 + 回默认任务 + 可恢复**」。

### 3.3 状态阶梯

```
                   ┌──────────────────────────────┐
                   │  维生系统（正交，始终运行）    │
                   └──────────────────────────────┘

   ┌────────────────────────┐
   │ 发布任务（可挂起队列）  │  ← 玩家 / LLM 发布
   └───────────┬────────────┘
               │ 完成 │ 失败 │ 阻塞等待
               ▼
   ┌────────────────────────┐
   │ 默认任务                │  ← 如「回基地巡逻」
   └───────────┬────────────┘
               │ 无法继续
               ▼
   ┌────────────────────────┐
   │ 待机                    │  ← 维生仍运行
   └────────────────────────┘
```

**三条性质**：

1. **失败 ≠ 停止** —— 失败回默认任务，这是**韧性**而非终止
2. **默认任务永不弹出** —— 它是栈底；发布任务在其上
3. **待机是合法终态** —— 不是异常，是「无事可做且安全」

**用户对第 3 条的表述**：「这个任务没办法继续进行了，就只能进去待机状态了，
当然维生系统还在运行。」→ 与 §2.1 的「维生正交」一致。

### 3.4 维生系统的位置（与 `survey/04` 呼应）

这里必须重申一个区分，否则必然被误解：

| | 管什么 | 谁最大 |
|---|---|---|
| **权限** | 我**能要求**做什么 | **玩家** |
| **优先级** | 谁**能叫停**谁 | **维生系统** |

维生系统**权限最小**（不"要求"任何事，是反射），但**优先级最高**（随时打断）。
玩家**权限最大**（能授权一切），但**命令不了 bot「站着被烧死」**。

**因此**：默认任务与待机状态下，维生系统**照常具有打断权**（`SurvivalSystem.shouldInterrupt`
在 task tick 之前，`BotManager:906`）。这一条**不能因为新增状态机而改变**。

## 4. 结果词表与任务生命周期的映射

### 4.1 词表从 4 → 5 → 6：一次自我审查

`survey/04` §3.5 提了**四个**词（`DONE` / `REFUSED` / `EXHAUSTED` / `FAILED`）。
用户的设计又逼出两个：

| 新增 | 由什么逼出 |
|---|---|
| `AMBIGUOUS` | 「输入『铁』→ 弹出铁矿石标签 / 深层铁矿石 ID / 格雷系铁矿标签」= **多个合法答案，需玩家选** |
| 壁垒违反 | 「无论什么权限…直接失败」= **不可升级的拒绝**（见 §2.3） |

> ⚠️ **自我审查**：`survey/04` 诊断的病灶之一就是「**词表分裂**」。
> 现在我自己把词表从 4 加到 6，必须给出**准入判据**，否则就是在制造同一种病。

**准入判据（每个词必须有独占的处置动作）**：

| 词 | 含义 | 处置动作（独占性） |
|---|---|---|
| `DONE` | 做成了 | 继续 / 回默认任务 |
| `REFUSED` | 需授权，**玩家能给** | **问玩家提权** |
| `FORBIDDEN` | **壁垒违反**，谁都不能授权 | **立即终结**，不询问不重试 |
| `EXHAUSTED` | 没做完，无法判定 | **加预算重试** / 交 LLM |
| `AMBIGUOUS` | 多个合法解释 | **玩家选一个** |
| `FAILED` | 确定失败 | **重规划** |

六个词**处置动作两两不同**，均通过判据。

> **仍待用户拍板**：`FORBIDDEN` 是否值得单列？
> 备选是把 `REFUSED` 加一个 `escalatable: false` 标志。
> 勘测员倾向**单列** —— 因为 LLM 的行为差异是根本性的（问人 vs 立刻停），
> 一个布尔标志容易被忽略，而两个不同的词不会。

### 4.2 词表 × 生命周期（直接决定回退行为）

这张表把 §3.2 的三个触发器与词表**对齐**：

| 结果 | 任务可恢复？ | 是否占用队列 | 回退到默认任务？ |
|---|---|---|---|
| `DONE` | — | 出队 | ✅ |
| `REFUSED` | ✅ **可**（待提权） | **挂起保留** | ✅ |
| `AMBIGUOUS` | ✅ **可**（待选择） | **挂起保留** | ✅ |
| `EXHAUSTED` | ✅ 可（加预算） | 挂起保留 | ✅ |
| `FORBIDDEN` | ❌ 永不 | 出队 | ✅ |
| `FAILED` | ⚠️ 靠重规划 | 出队 | ✅ |

**注意 `DONE` 之外全都回退到默认任务** —— 这正是「默认任务**永不弹出**」的含义。

### 4.3 `AMBIGUOUS` 与 ATM9 的 Polymorph 同构

用户的「铁」例子与 `survey/03` 发现的 **Polymorph 0.49.10** 是**同一个模式**：

> Polymorph：「一个配方多个产出，**由玩家在 UI 里选**。」

**ATM9 里现成的模组已经在解同一道题** —— 这是本设计有现实参照的证据，
也说明「多候选 → 玩家消歧」是这个领域的**标准解法**，不是异想天开。

## 5. 前置资源：从两态到**四态**

用户提了两种（有固定获取点 / 没点且没填）。**危险的是第三种和第四种**：

| # | 情况 | 正确反应 | 结果词 |
|---|---|---|---|
| 1 | 有固定获取点，**点里有货** | bot 自动去拿 | — |
| 2 | 有固定获取点，**点里没货** | **不是「问玩家」** —— 资源耗尽 | `EXHAUSTED` |
| 3 | 有固定获取点，**点不可达** | 也不是「问玩家」 | `EXHAUSTED` |
| 4 | **没固定点 + 没填** | ✅ **问玩家是否自取** | `AMBIGUOUS` |

**若四态混在一起**，会出现「**明明有货却挖不到，却跑来问玩家要不要自取**」这种误报 ——
玩家会困惑，且掩盖了真实问题（路径不可达）。

### 5.1 离线边界（用户已拍板）

**玩家离线 + 第 4 态** → **进队列等**（用户裁定）。

结合 §3.2，实现即：**挂起该任务 → 回默认任务 → 玩家回来后恢复**。
**不是**新增「等待」状态，也**不是**静默自取，也**不是**失败。

## 6. 表单设计：参考建议

> ⚠️ **明确声明**：用户已说明「**表单形态不是你负责设计的内容**」。
> 以下仅为**参考建议**，**不是交付物**，也不构成设计约束。

### 6.1 已有的成熟参照（ATM9 内即可取材）

> 依据 `survey/03` 的模组清单，这些**已在用户的整合包里**，可直接开箱比对：

| 参照 | 学什么 |
|---|---|
| **JEI 搜索栏** | 「输入模糊词 → 候选列表」的标准交互；玩家已熟悉 |
| **Almost Unified** | 跨模组同名物统一到标签 → 「输入铁」的候选**天然去重** |
| **FTB Quests 任务编辑 UI** | 结构化任务定义（目标 / 条件 / 奖励）的成熟表单范式 |
| **Polymorph** | 多候选消歧 UI 的现成先例 |
| **SFM 程序编辑器** | 「声明式填写 → 可预览」的思路 |

### 6.2 四条设计建议（按重要性）

**① 自然语言必须是「草稿生成器」，不能是并行入口**

若 NL 与表单是两条并行入口，冲突时无法裁决（对话说「挖 50 个铁」、表单填着 10，听谁的？）。
正解：**NL 解析结果填进表单，表单是唯一真值**。这与 §0.1 决定 1 一致。

**② 表单字段的 schema 要跟着任务类型走，不要集中**

用户要求「栏位根据选择的任务类型严格区分」。**不要写中央 `switch(taskType)`** ——
那会长成怪物，且与 `survey/04` 的「**共享签名，各自实现**」结论相反。

正解：**任务类型自己声明字段**（schema 定义在任务类型旁边），交互层只负责渲染。

现状起点：`job/GoalSpec` 已有 `Kind` 枚举（`COLLECT_ITEMS` / `HARVEST_UNITS` / `UNTIL_FULL`），
但字段是**定死的 7 个**（kind/quota/center/radius/maxTicks/stopWhenFull/productTag）。
要「严格区分」，需**每种 kind 拥有自己的一组字段**。

**③ 建议先命令式、后图形化**

| 阶段 | 形式 | 价值 |
|---|---|---|
| **先** | 命令式参数（如 `/alice mine iron 50`） | **立刻验证 schema 设计对不对** |
| 后 | 图形化 `Screen`（文本输入 + 下拉候选） | 只换渲染层，schema 不变 |

理由：图形化的成本几乎全在**控件绘制**上，而 schema 是否合理的**信息增益全在命令式阶段就能拿到**。
先图形化 = 把 bug 藏进 UI 里，更难发现。

**④ 候选下拉的数据来源**

用户要求「默认是自定义注册名，输入『铁』自动搜索出铁矿石标签 / 固定深层铁矿石 ID / 格雷系所有铁矿标签」。

技术要点：
- 候选源 = **`Registry`（精确 ID）+ `Tag`（标签）** 两套并列
- 输入不匹配注册名时 → 交 LLM 做自然语言识别（用户已提）
- ⚠️ **注意格雷（GregTech CEu）**：它有**自有矿系与化学体系**，候选量会很大 → 需要**分级展示**或**按整合包 profile 收敛**（对应阶段 E / `PackProfile`）

### 补遗 2：信封结构

```java
record Envelope(
    Authority authority,        // 当前信封的主人
    Set<Grant> grants,          // 授予了什么
    GoalRef scope,              // 提权绑定到哪个具体目标（null = 长期）
    UUID grantedBy,             // 谁授的
    long grantedAt,             // 何时
    long expiresAt              // 何时失效

```

### 2.1 Grant 集合（按「动不动世界」分层）

| 层 | Grant | 默认给 LLM？ |
|---|---|---|
| **计划层** | `QUEUE_SUGGEST` 生成草稿 / 建议 | ✅ |
| | `PARAM_SET` 决定任务参数 | ✅ |
| | `QUEUE_REORDER` 调整队列顺序 | ✅ |
| | `TASK_CANCEL` 取消任务 | ✅ |
| | ~~`RESOURCE_SELF_FETCH` 自取前置资源~~ | ❌ **不单设**（见 2.3） |
| **世界修改层** | `MOVE_BREAK` 破坏通行 | ❌ **需提权** |
| | `MOVE_PLACE` 放置通行（PILLAR / 支撑） | ❌ **需提权** |
| | `DROP_COLLECT` 收集掉落物 | ❌ **需提权** |
| | `ITEM_TRANSFER` 搬运物品 | ❌ **需提权** |
| **提交层** | `QUEUE_COMMIT` 不确认直接入队 | ❌ **需提权**（见补遗 3） |
| **结果判定** | `DECLARE_DONE` 宣告完成 | ❌ **永不授予（壁垒）** |

### 2.2 `DECLARE_DONE` 为何是壁垒而非提权项

蓝图明令 LLM 不负责「宣告任务成功、物品到账、机器完成或样板正确」。

**这不是"危险"，而是"职责错配"** —— 完成判据必须来自**服务端事实**。
因此它**不随时间或提权改变**，应直接归入壁垒（与 `survey/05` §2.2 的 D-024 不变式同级）。

### 2.3 `RESOURCE_SELF_FETCH` 为何不单设（拍板 6）

「自取前置资源」表面像计划层，但它**会实际触发世界修改**（挖矿 / 开箱 / 搬运）。
若单设会导致：LLM 有 `RESOURCE_SELF_FETCH` 但无 `MOVE_BREAK` → **决定自取却挖不动，卡住**。

**正解**：不设该 grant，让「自取」**直接落到已有的世界修改 grants 上**。
→ **少一个概念，且不会出现半通状态。**

### 2.4 权限检查

```
允许(请求) ⟺ 请求所需 grants ⊆ 当前信封 grants ⊆ 最高壁垒
```

| 层 | 谁定 | 玩家能否调整 |
|---|---|---|
| ① 请求所需权限 | 请求内容本身 | — |
| ② **当前信封** | **玩家**（提权 = 放宽） | ✅ **可调** |
| ③ **最高壁垒** | 系统 / 世界 | ❌ **不可调** |

壁垒内容沿用正文 §2.2 的结论：**D-024 局部可回收性不变式**（`AI_DECISIONS.md:586`）。

### 补遗 3：`QUEUE_COMMIT` 与责任转移（本轮最重要的机制）

### 3.1 一处必须分清的子问题

用户要求默认信封「至少能管理任务队列」。但该要求下有一个子问题：

| Grant | 含义 | 与「表单是唯一真值」的关系 |
|---|---|---|
| `QUEUE_SUGGEST` | 生成草稿 → **等玩家确认** | ✅ **一致** |
| `QUEUE_COMMIT` | **不确认直接入队** | ❌ **冲突** |

若 LLM 拥有 `QUEUE_COMMIT`，则 LLM 发起的任务**绕过了表单** ——
这与正文 §0.1 拍板 1「NL 只生成草稿、表单是唯一真值」**直接打架**。

### 3.2 拍板（拍板 5）

> **`QUEUE_COMMIT` 不默认给 LLM**，但**保留责任转移机制**。

### 3.3 ★ 责任转移：确认即转移

| 路径 | 任务以谁的权限运行 |
|---|---|
| LLM 建议 → **玩家确认** | **`PLAYER`** ← **确认即责任转移** |
| LLM 自主（已提权得 `QUEUE_COMMIT`） | **`LLM`** |

**这条设计极其干净**，因为它自动满足用户的核心诉求：

| 用户诉求 | 如何满足 |
|---|---|
| **自由** | LLM 把自然语言翻译成结构化表单（`QUEUE_SUGGEST` 默认给） |
| **安全** | 落地的动作**永远带着玩家的签名**（`PLAYER` 权限） |

**推论**：**绝大多数任务的执行主体是 `PLAYER`**，LLM 权限仅在它**真正自主行动**时才被用到。

### 3.4 为什么这比"直接给 LLM 提权"更好

- 默认路径**不需要任何提权** → 玩家体验无摩擦
- LLM 的自主权是**显式授予**的，不是默认的
- **出问题时能明确回答「这是谁授权跑的」** ← 由 `Envelope.grantedBy` 承载

### 补遗 4：提权生命周期（拍板 3 / 8）

### 4.1 结构

```java
record Escalation(Set<Grant> grants, GoalRef scope, UUID grantedBy, long grantedAt) {}
```

### 4.2 规则表

| 规则 | 内容 |
|---|---|
| **绑定** | 提权绑定 `GoalRef`（**具体任务目标**），**不是任务类型** |
| **生效范围** | 该任务 + **因它派生的子任务**（如前置资源获取） |
| **不可反向** | 子任务获得的权限**不能**传回父任务 |
| **跨 bot 不继承** | bot A 的提权，bot B **不共享**（信封 per-bot，正文 §0.1 拍板 3） |
| **撤销时机** | 任务到**终态**即自动撤销（`DONE` / `FAILED` / `FORBIDDEN` / …） |
| **挂起时** | **保留**（否则恢复后需重新提权，体验断裂） |
| **永不撤销** | `DECLARE_DONE` 等壁垒项，**提权也拿不到** |

### 4.3 `GoalRef` 的定义

**建议 = 发布时分配的 UUID + 任务类型。**

理由：「取消后重新发布」**不会误继承**旧提权——这是 UUID 而非类型/位置的价值。

### 4.4 ⚠️ 与预算继承同源（正文 §9.1 未解决项）

「子任务继承父任务的什么」在本节与 `survey/04` §5.2（**预算三层互不相干**）是**同一个问题**：

- 子任务继承父任务的**权限**？→ 本节已答：**继承**
- 子任务继承父任务的**额度**？→ **仍未答**

> **建议一起定，别分开。** 两者都是「父子任务的资源传递」同一族问题。

### 补遗 5：挂起任务保留策略（拍板 4 / 7）

### 5.1 核心原则

> **不用纯计时器。主判据 = 世界前提是否成立。**

理由：**时间本身不改变可行性，世界才改变。**

- 挂起 8 小时，若目标方块还在、资源点还有货 → 恢复**完全合理**
- 挂起 2 分钟，若目标已被他人挖走 → 恢复**就是错的**

### 5.2 判据表

| # | 判据 | 触发条件 | 处置 |
|---|---|---|---|
| ① | **世界前提失效**（**主**） | 目标方块消失 / 容器内容变化 / 前置资源点清空 / 目标被他人占用 | **立即失效** → `FAILED` |
| ② | **tick 上限**（**兜底**） | 累计挂起 > `24000` tick（游戏内 1 天） | 失效 → `FAILED` |
| ③ | **玩家回来**（**主路径**） | 玩家上线且任务仍有效 | **恢复** |
| ④ | **被替换** | 有新任务发布 / 队列满 | 按队列优先级淘汰 |
| ⑤ | **队列上限** | 挂起数 > **3 个** | 最旧的被淘汰 |

### 5.3 ★ 恢复时**重新规划**，不重放旧计划

> **挂起时只保存「目标」，不保存「计划」。**

理由：**计划是对世界的假设，世界已经变了，计划必然过期**。
重新规划能自动吸收所有变化，只需判断「目标本身还有没有意义」。

**这与项目自己的 D-043（重规划下沉）是同一精神** —— 计划级判断天然会过期。

**副产品（重要）**：这让「世界前提失效」的判定变得**极简单** ——
只需检查**目标是否还存在**（一个方块？一个数量？一个可站位置？），
**不需要验证整个计划**。

### 5.4 关于 `24000`

> **它几乎不会在单机触发** —— 玩家离线 = 服务器停了 = **不涨 tick**。
> 它只在**专用服务器**上才有意义，实际是「服务器长时间无人」的兜底。
>
> **数值不关键，关键是主判据不是它。** 数值可按需调整。

### 2. 每个自制方案的替代评估

对上述每个自制方案，必须回答：

#### 是否有现成方案？
- **Baritone**（开源 bot 寻路库）：是否可替代 PathExecutor / SurfacePathfinder / MovementHelper？
- **Carpet Mod FakePlayer**：是否可替代 BotPlayer / FakeConnection？
- **Forge Event Bus + Commands**：是否可替代 Task 系统？
- **Mineflayer / Prismarine**（JS bot 框架）：是否有 Java 移植或可借鉴？
- **其他 bot mod**（TLM Maid / Pixelmon / 其他）：是否有可复用组件？

#### 现成方案的优势
- 功能完整度（覆盖场景）
- 稳定性（已知 bug / 维护状态）
- 性能（寻路速度 / 内存占用）
- 社区支持（文档 / 问题解答）
- 兼容性（Forge 1.20.1 / 其他 mod）

#### 现成方案的劣势
- 依赖复杂（需要哪些前置库）
- 授权限制（GPL / MIT / 商业限制）
- 接入成本（改造工作量）
- 功能不匹配（Alice 特定需求无法满足）

#### 推荐决策
- **完全替代**（废弃自制，接入现成）
- **部分借鉴**（保留自制主体，借鉴现成的设计模式）
- **保持自制**（现成方案不适用，继续自研）

### 5. 重构路线图

基于替代方案评估，输出：

#### 5.1 模块优先级
- **P0（立即重构）**：严重问题模块（FakePlayer 物理 / GUI）
- **P1（短期重构）**：有成熟替代的模块（寻路？）
- **P2（中期重构）**：架构优化（Task 系统？）
- **P3（长期保持）**：无需重构的模块

#### 5.2 每个模块的重构方案
- **目标**：替代什么、借鉴什么、保留什么
- **依赖**：前置工作（如重构 A 依赖先重构 B）
- **风险**：破坏性改动、兼容性问题、回退成本
- **时间**：估计实施时间（天/周/月）
- **验证**：如何验证重构成功（测试矩阵）

#### 5.3 停止条件
- 现成方案不适用（功能不匹配 / 授权限制 / 依赖过重）
- 接入成本过高（重构时间 > 继续自制时间）
- 破坏现有功能（用户已接受的功能）

## 问题（调查目标）

V-B dry-run 失败：`dsh-mcp-client` 插件无法从 `cordis.patch.yml` 加载。维护员实测三种方法均无效：标准 `name: '@deepseek-ai/dsh-mcp-client'` 引用、加入 `dsh.profile.bundles`（报错 "declares no dsh.bundle"）、绝对路径引用。日志仅 1 行启动信息，无 MCP 相关内容、无子进程 spawn、工具清单 API 无响应。

监督员浅调查已发现的部分事实（须在其上继续，勿重复）：
- `dsh-agent-bus` 能从 patch 用 `id: agent-bus` 成功加载，因为它在 `dsh.profile.bundles` 里（patch 按 bundle 内 id 匹配）
- `dsh-mcp-client` 是裸插件（无 `dsh.bundle` 声明），不是 bundle；patch 的 `name:` 字段未被 Cordis 解析
- `dsh plugin add --profile alice-mcp-lab @deepseek-ai/dsh-mcp-client` 可执行并安装 registry 版 `0.0.1-rc.1`（+91 包）到该 profile 的 dependencies，**但 bundles 列表未变化**（仍为 dsh-base/dsh-web-app/dsh-agent-bus/dsh-dafeiyu）
- DSH 内置 dsh-mcp-client 为 `0.1.1-rc.2`（随 DSH 安装，flat fallback 符号链接可解析），与 registry 版 `0.0.1-rc.1` 版本不同

**核心问题**：Cordis（DSH 的插件框架）中，`cordis.patch.yml` 的条目如何解析到插件模块？非 bundle 插件（如 dsh-mcp-client）的正确启用方式是什么？

## 调查内容（按优先级）

1. **patch 条目 schema**：`@deepseek-ai/cordis-plugin-loader`（EntryTree/Entry）、`@deepseek-ai/cordis-plugin-include`（PatchOptions）、`dsh-app-boot`（composeProfile/runProfile/watchUserPatches）源码中，patch 条目如何映射到插件模块——字段语义（`id`/`name`/`plugin`/`disabled`），`name` 字段是否/如何参与解析，非 bundle 插件能否被 patch 直接引用。
2. **依赖解析链**：`ctx.loader.internal` 的解析行为（`dsh-app-boot` 未传 `bareModuleBaseUrl`）；EntryTree.import() 的内部路径；profile 的 `package.json` dependencies 是否参与 patch 插件解析（`dsh plugin add` 加入的依赖是否让 `name:` 引用变得可解析）。
3. **官方登记路径**：`dsh plugin add/install/remove` 命令的实现（`dsh-app-boot` lib 中 `plugin` 子命令），它们对 package.json / bundles / node_modules 做了什么；是否有"把裸插件变成可 patch 引用"的官方机制；是否要求包的 `dsh.bundle` 声明才能被 patch 使用。
4. **dsh-mcp-client 的 README 假设**：其 README 配置示例（`cordis.yml` 用 `name:`）在 DSH 的 patch 架构（cordis.yml 为空根 + cordis.patch.yml 叠加）下是否适用；DSH 是否有与 README 匹配的挂载入口（如 `--patch` overlay、homePatch、`dsh plugin` 初始化）。
5. **结论**：给出 判定（A: 有正确启用方式并说明步骤 / B: 需要改 DSH 安装或打 bundle 补丁（超出边界）/ C: 当前 DSH 版本不支持非 bundle 插件挂载）+ 待实测项（如需维护员 dry-run 复验）+ 若 A，给出可复现的最小启用步骤。

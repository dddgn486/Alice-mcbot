## Objective

Implement and verify one narrow C2 experiment: an explicit command creates a single request that moves one exact, default no-components/NBT vanilla item stack/count from one fixed loaded original single chest, through the bot's 36 ordinary inventory slots, to one fixed loaded original single chest in the same dimension.

The end-to-end request is sequential composition of two auditable legs, not a cross-endpoint atomic transaction:

```text
source chest -> bot inventory -> destination chest
```

## User-Approved Policy

- Item predicate: explicit registered `namespace:item`, positive count, and only no-components/NBT vanilla stacks; component/NBT-bearing matches fail `unsupported_item_components`.
- Endpoints: same dimension; fixed, loaded, ordinary original single chests only; source and destination differ.
- Bootstrap authority: command permission level 2 only, in a controlled/single-player experiment. A1.1 does not model, persist, infer, or enforce bot ownership; owner/admin/ACL remains a later dedicated policy package.
- Capacity: source mutation is allowed only after both bot inventory and destination chest simulate full capacity for the exact count. A fresh pre-check immediately before each actual write remains mandatory. A later destination conflict leaves the proven remainder in the bot inventory and suspends.
- Restart: A1.1 does not support cross-restart continuation. It must reject/block an active request before orderly server stop where technically possible and report `manual_takeover_required` after unexpected restart; no automatic continuation or recovery write.
- Manual takeover: read-only request status/report plus administrator abort only. No resume or finish-insert command.
- Timing: 200 ticks no-progress per movement/write phase; 2,400 ticks active request deadline; 12,000 ticks maximum suspension. Survival suspension does not advance active deadline but does count toward suspension maximum.

## Allowed Scope

- New transfer-only value objects, fixed chest endpoint validation, inventory observation, capacity preflight, per-leg simulation/freshness/delta proof, independent persistent request ledger, single-batch `TransferTask`, restricted replacement guard, and explicit transfer test command/status/abort.
- Server-side direct fixed-original-chest handler and bot inventory interaction only, on the server thread, with `pre -> simulate -> fresh pre -> actual -> post` evidence for both legs.
- Existing `HARD_PATH` consumption only for reaching endpoints. Movement failure/hazard/search limit is a fail/suspend condition, never an authorization to modify world/path capabilities.
- Focused isolated headless fixture(s), `./gradlew compileJava`, implementation records in `docs/HANDOVER.md`, commit/push, review packet, and a `CLIENT_TEST_PENDING` Windows matrix.

## Explicitly Out of Scope

- Missing/default item/count, all-items transfers, multi-batch, partial success, tags, aliases, components/NBT matching, automatic deficit fulfilment, endpoint scanning, storage marking, generic capability, double chest, side semantics, mod containers, machines, fluids, adapters, endpoint-to-endpoint direct transfer.
- Binding tool, Shift/right-click handling, packets/client UI, normal chest GUI interception, ScanWand/diamond-shovel/TargetSelector reuse.
- Owner/admin/ACL implementation beyond the stated bootstrap gate; LLM recovery; automatic resume, finish-insert, retry after any mutation, automatic fallback mining/follow work.
- Cross-dimension/portal transfer; full bot-inventory persistence; automatic cross-restart recovery.
- Changes to MineTask, DropCollectionTask, normal mining, roads, tunnels, fluids, escape, FollowTask, AttackTask, `HARD_PATH` implementation, `SOFT_SURFACE`, C1 scanner semantics, or C3/C4.

## Required Architecture

1. Validate endpoints before start and before every actual write: same dimension, loaded chunk without forced load, `minecraft:chest` single chest identity, handler available, source != destination.
2. Keep an independent `SavedData` ledger keyed by request UUID. Record immutable request input, monotonic state sequence, evidence ticks/digests, last proven location, suspend reason, and manual-takeover flag. Do not use logs, `TaskExecutionRecord`, or `BotWorldData` as the ledger.
3. For each leg: capture three-party fresh pre observations; prove full capacity by simulation; immediately re-observe relevant facts; execute only on exact freshness; capture three-party post observations; advance only when measured delta equals the approved count.
4. Source leg full capacity preflight includes both bot and destination capacity. If insufficient, fail before source mutation with source delta zero.
5. After a proven source delta, persist `IN_TRANSIT_BOT` before destination movement. Destination failure/conflict preserves bot ownership and suspends. Unknown delta/location is `UNKNOWN_DISCREPANCY`, blocks all automatic write/retry, and requires manual takeover.
6. Normal task replacement must be refused while this TransferTask is `IN_TRANSIT_BOT` or `SUSPENDED`; the guard must not change behavior of unrelated task classes.
7. Explicit command only, with all endpoint/item/count parameters. It emits request id and stable state/error/location. Status is readonly; abort may terminally mark the ledger but must not mutate either inventory.

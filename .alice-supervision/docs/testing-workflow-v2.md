# Alice 项目测试流程与规则（固化版 v2，2026-08-22）

> 基于 Selector E7/E8 + A1.1 C1-C4 实践验证有效。核心原则：**服务端自测优先、客户端精简实测、证据链完整可追溯、核心语义重于具体状态码、减少重复填写负担**。

## 一、测试职责分工

| 角色 | 职责 | 不可逾越边界 |
|---|---|---|
| **用户（你）** | Windows 客户端实测；填写精简表单（只填决策性信息，不填日志可见内容）；观察游戏内现象；最终决策 | 不修改业务代码；不替监督员做架构判断 |
| **监督员（我）** | 服务端代码二审；客户端日志核对；从日志提取基本信息（日期/版本/UUID 等）；证据链完整性审核；整合双证据链给出验收结论 | 不替你做客户端实测；不把"编译通过"等同于"客户端验证通过" |
| **主开发员** | 按 active plan 实现功能；编写 focused fixture（服务端自测）；提交代码 + pending 包 | 不自行批准实验能力；不绕过 active plan 扩展范围 |
| **规划员** | 只读分析；输出最小实现线路、依赖、风险、停止条件、验收矩阵 | 不实施代码；报告不构成实现授权 |

## 二、测试分层策略

### 2.1 服务端 focused fixture（优先）

**适用场景**：简单状态输出确认、状态机转换、参数校验、容量检查、ledger 守恒

**优势**：快速（秒级）、可重复、覆盖边界条件、不依赖客户端环境

**范围**：
- 命令解析与参数校验
- 状态机转换（IN_TRANSIT_BOT、SUSPENDED、ABORTED、capacity_rejected）
- Ledger 守恒断言（source/bot/destination delta）
- 既有设计的回归

**不覆盖**：
- 客户端渲染/GUI
- 真实玩家操作（右键、Shift+右键）
- 外部不可控因素（真实生存危险、服务端重启、中途人工干预）
- Bot 物品客户端同步
- 真实路径搜索与移动

### 2.2 客户端精简实测（必要时）

**必测场景类型**：
1. GUI 隔离/渲染
2. 外部不可控干预（中途改箱子、真实生存危险、服务端重启）
3. 客户端协议/packet（Bot 物品同步、高亮状态）
4. 真实玩家操作（Shift+右键、selector 绑定物右键）

**客户端测试最小化原则**：
> 如果一个场景的**核心断言**可以在服务端 fixture 用 mock/状态机证明，且**不涉及 GUI/packet/外部干预**，则归入服务端自测，不要求客户端重复。

**示例**（A1.1）：
- 服务端覆盖：A1/A2/A3/A4/A8（8 个断言，秒级完成）
- 客户端只测：C1-C4（4 个场景，15-30 分钟）

## 三、测试包结构规范

### 3.1 目录结构

```
.alice-supervision/client-tests/
├── <sha>-<module>-client.md          # 主说明（关联提交、计划 ID、矩阵）
└── <sha>-<module>-client/
    └── evidence/
        ├── evidence-report.md         # 精简总表单（只填决策性信息）
        ├── latest.log                 # 本轮唯一完整日志
        ├── debug.log                  # 本轮唯一完整日志
        └── C*-<scenario>/
            ├── evidence-report.md     # 场景表单（观察项、是/否）
            └── *.png                  # 场景截图（按需）
```

### 3.2 精简总表单（用户只填 3 部分）

**模板**：`.alice-supervision/templates/client-test-evidence-report-simplified.md`

**用户必填**（3 部分）：
1. **用户决策**：总体结果（PASS/FAIL/UNCLEAR）、用户总体决定（USER_ACCEPTED/NEEDS_FIX/NEEDS_REPLAN/NEEDS_DISCUSSION）、备注（可选）
2. **场景结果汇总**：每个场景的结果（PASS/FAIL/UNCLEAR）、对应 request UUID、备注
3. **异常与停止**：是否出现停止条件、发生场景、是否已停止且未重试、说明

**监督员从日志提取**（用户不填）：
- 测试日期时间（日志首行时间戳）
- Windows Git SHA（测试包目录名）
- 客户端/服务端 Forge 与 Mod 版本（日志 ModLauncher 行）
- Bot 名称/UUID（日志 `bot=` / 假人登录行）
- 世界/存档条件（日志 `ServerLevel[...]`）
- item/count（日志 `transfer request=` 与场景表单对应）

**减负效果**：原总表单 11 个必填项 → 精简到 3 个必填部分（约 5-8 项），日志可见的 6 项由监督员提取。

### 3.3 场景表单（保持不变）

**每个场景表单**（`C*-*/evidence-report.md`）：
- 场景说明（预期行为）
- 本场景引用（坐标、动作、对应 request UUID）
- **场景结果**：`PASS` / `FAIL` / `UNCLEAR`
- **观察项**（逐项填 `是` / `否`，使用精确关键字）：
  - ❌ 模糊：是否正常？
  - ✅ 精确：日志中是否出现 `capacity_rejected`？
  - ✅ 精确：是否没有自动 retry/resume/finish-insert？
- 最少文件清单（截图、共用日志）

### 3.4 证据最小化规则

| 证据类型 | 是否必需 | 依据 |
|---|---|---|
| **日志** | 必需 | 权威事实源；监督员核对的唯一依据 |
| **截图** | 按需 | GUI 场景必需；状态输出可选（日志已有）；中间过程不必截图 |
| **视频** | 不必 | 日志 + 截图已充分 |
| **聊天记录** | 推荐 | 在聊天栏说明操作（如"现在放入熔岩"），日志可见，方便监督员理解时间线 |

## 四、客户端测试操作清单（给用户的提示）

### 测试前准备
1. 确认 Windows Git SHA（测试包目录名）
2. 准备测试世界/存档（通常是超平坦测试存档）
3. 确认 Bot 名称（通常是 `tango`）

### 测试中操作（每个场景）
1. **执行场景操作**（按场景表单的"测试工具提示"）
2. **在聊天栏说明关键操作**（如"现在放入熔岩"、"现在重启服务端"）——日志可见，方便监督员理解
3. **场景完成后立即查询状态**：`/alice transfer-status <request-uuid>`（若适用）
4. **截图**（仅必需场景，如 GUI）
5. **填写场景表单**（观察项逐项填 `是`/`否`，场景结果 PASS/FAIL/UNCLEAR）

### 测试后提交
1. **填写精简总表单**（只填 3 部分：用户决策、场景汇总、异常与停止）
2. **覆盖日志**：用本轮完整 `latest.log` 和 `debug.log` 覆盖占位文件
3. **覆盖截图**：用真实截图覆盖占位 `.png`（空占位文件不算证据）
4. **告知监督员**："测试完毕"

### 停止条件（立即停止，不重试）
遇到以下情况时，**立即停止该场景，保留现场（日志/世界副本/截图），不重试已变异的 request**：
- 无法解释的物品数量变化
- 自动 retry/resume/finish-insert
- 受保护任务被替换
- 错误端点写入
- GUI 拦截
- 崩溃或卡死

## 五、日志核对规则（监督员职责）

### 5.1 证据链完整性检查

监督员必须核对：
1. **提取基本信息**：从日志首行/ModLauncher/ServerLevel/bot 登录行提取日期/版本/SHA/Bot/世界
2. **时间线一致性**：场景表单的 request UUID 在日志中可追溯
3. **终态验证**：声称的状态（如 `SUSPENDED`、`capacity_rejected`）在日志中有对应记录
4. **观察项与日志一致性**：表单填"是"的项目在日志中有证据；填"否"的项目确实不存在
5. **停止条件触发**：若出现停止条件，用户是否已停止并保留现场

### 5.2 证据缺口处理（三选一）

当场景表单与日志证据不一致时：

| 选项 | 适用场景 | 时间成本 |
|---|---|---|
| **补充验证** | 核心观察项缺失（如未执行 `transfer-status`，且状态不可从其他证据推断） | 10-30 分钟 |
| **接受服务端证据** | 服务端 fixture 已证明状态机 + 用户观察到核心语义（如"任务停了"） | 0 分钟 |
| **标 UNCLEAR** | 不确定是否符合预期，或证据链断裂 | 0 分钟 |

**判定标准**：
- 核心语义（保守停止、不自动重试、ledger 守恒）> 具体状态码
- 服务端 fixture 证明的状态机行为 + 用户观察的终态行为 = 可接受证据链
- 状态输出未捕获（用户未执行查询命令）≠ 实现缺陷

### 5.3 日志关键字搜索清单

```bash
# 状态与终态
transfer request= | state= | code= | terminal=COMPLETED | terminal=FAILED | SUSPENDED | IN_TRANSIT_BOT | ABORTED | VERIFIED

# 错误与冲突
simulation_conflict | UNKNOWN_DISCREPANCY | mismatch | capacity_rejected | hard_path | endpoint_not_single | invalid_item_id

# 生存与危险
LAVA_CONTACT | SUFFOCATING | hazard | health= | 维生监测

# 命令与查询
transfer-status | transfer-abort | transfer-selection | transfer-test

# Delta 与证据
sourceDelta | botDelta | destinationDelta | evidence:
```

## 六、验收流程（完整生命周期）

### 阶段 1：规划与批准
1. 监督员或用户发现需求
2. 监督员派规划员做只读分析（或自行浅调研）
3. 监督员审核规划报告，决定采纳/拒绝/需用户决策
4. 用户明确批准后，监督员创建 active plan（`APPROVED_FOR_IMPLEMENTATION`）

### 阶段 2：服务端实现与自测
5. 监督员派主开发员按 active plan 实现
6. 主开发员提交代码 + focused fixture + pending 包
7. 监督员二审：代码范围、fixture 断言、日志证据
8. 二审 PASS → 进入客户端测试准备

### 阶段 3：客户端测试准备
9. 监督员根据规划报告 + 二审结果，决定客户端测试范围：
   - 哪些场景已由服务端 fixture 覆盖（归入服务端自测）
   - 哪些场景必须客户端实测（GUI/外部干预/packet）
10. 监督员准备精简测试包（主文件 + 精简总表单 + 场景表单 + 占位截图）
11. 同步到 Windows

### 阶段 4：客户端实测（用户）
12. 用户在 Windows 一次会话完成全部场景
13. 填写精简总表单（只填 3 部分）+ 各场景表单
14. 覆盖 `latest.log`/`debug.log`，放置截图
15. 告知监督员"测试完毕"

### 阶段 5：日志核对与验收（监督员）
16. 监督员从日志提取基本信息（日期/版本/SHA/Bot/世界）
17. 监督员读取日志 + 表单，核对证据链完整性
18. 若有证据缺口，三选一处理（补充验证/接受服务端证据/标 UNCLEAR）
19. 整合服务端 + 客户端证据，输出最终验收报告
20. 更新 HANDOVER（状态从 `CLIENT_TEST_PENDING` → `USER_ACCEPTED`）
21. 提交 WSL + Windows

### 阶段 6：归档与下一步
22. 测试包与验收报告归档到 `.alice-supervision/`
23. Active plan 标记 `USER_ACCEPTED`
24. 用户决定下一步方向

## 七、下次测试优化检查清单

基于本次实践，下次测试包准备时：

**监督员准备测试包**：
- [ ] 场景表单的观察项使用精确关键字（如"日志中是否出现 `capacity_rejected`？"）
- [ ] 每个需要状态查询的场景明确标注"完成后执行 `/alice transfer-status <uuid>`"
- [ ] 主文件增加"非验收范围已知现象"章节（如 Bot 物品同步问题）
- [ ] 使用精简总表单模板（`.alice-supervision/templates/client-test-evidence-report-simplified.md`）

**用户客户端实测**：
- [ ] 每个场景完成后立即查询状态（不要等全部场景做完再查）
- [ ] 在聊天栏说明关键操作（如"现在放入熔岩"），日志可见
- [ ] 遇到停止条件立即停止，不要试图"修复"或"重试"
- [ ] 只填精简总表单的 3 部分（用户决策、场景汇总、异常），不填日志可见内容

**监督员日志核对**：
- [ ] 先从日志提取基本信息（日期/版本/SHA/Bot/世界）
- [ ] 先 `grep` 关键状态（`SUSPENDED`/`VERIFIED`/`capacity_rejected` 等）
- [ ] 再逐个场景对照表单观察项
- [ ] 若表单与日志矛盾，先与用户澄清观察来源，再判定

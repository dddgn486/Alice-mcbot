# Minimal Implementation Planning

## 何时使用

出现以下任一情况时使用：

- 功能预计修改超过 3 个文件；
- 同时涉及任务、寻路、物理、网络、GUI、库存或客户端中的多个层；
- 新能力准备接入正式任务链；
- 需求还不清楚什么行为才算成功；
- 以前做过类似功能，但经历过多轮补丁或客户端失败。

简单的文本、资源路径或单一局部修复不必套用完整规划。

## 核心原则

> 先完成一个真实可用的最小闭环，再增加能力；每个增量只证明一件关键事情。

最小闭环不是“少写代码”，而是包含完整的数据和行为链：

```text
明确输入
  -> 服务端验证
  -> 单一确定性动作
  -> 可观察结果
  -> 明确成功/失败条件
```

## 开始前的五行任务卡

实现前只需写清：

```text
目标：本轮唯一要实现或证明什么
不改变：哪些现有能力和架构边界保持不动
最小闭环：输入 -> 动作 -> 结果
成功条件：用户或日志能观察到什么
验证方式：编译 / focused log / Windows 客户端
```

如果这五行无法写清，先和用户讨论，不要开始改代码。

## 推荐拆分顺序

对于跨层 Forge 功能，通常按以下顺序：

```text
1. 数据、坐标或网络契约
2. 单一服务端原语
3. 游戏内测试物品或简单诊断入口
4. focused 日志或服务端验证
5. Windows 客户端实测
6. 接入正式任务
7. 扩展边界场景
```

### 示例：新移动能力

不要第一轮同时修改 A*、Movement、FollowTask 和 MineTask。

建议拆成：

1. 固定脚位/支撑坐标契约；
2. 让一个 movement primitive 完成一段移动；
3. 用游戏内测试物品右键目标支撑方块；
4. 日志记录 `from/to/position/onGround/result`；
5. 用户在 Windows 观察移动、碰撞和回弹；
6. 通过后再讨论是否接入正式任务。

### 示例：新 GUI

1. 服务端能打开空菜单；
2. 客户端能正确构造 Menu 和 Screen；
3. 显示一个服务端只读值；
4. 增加一个按钮并完成客户端请求 → 服务端验证 → 同步返回；
5. 最后再增加复杂槽位或机器操作。

## 游戏内测试入口

涉及客户端可见行为时，优先提供可在创造模式或 `/give` 中获得的测试物品：

- 手持后右键方块或实体；
- Shift+右键用于第二个清晰动作或重置；
- 在 GUI、聊天、粒子、状态条或 bot 行为中显示结果；
- 操作步骤尽量在几十秒内完成。

不要默认要求用户寻找精确坐标并输入一串复杂命令。命令只作为精确复现或管理员诊断的补充。

## 验证保持轻量

每个增量只选择与风险匹配的关键证据：

- 纯服务端逻辑：编译 + 一段 focused 日志或小 fixture；
- GUI、渲染、输入、物理、同步：编译 + Windows 客户端观察；
- 资源问题：构建 JAR + 核对实际 JAR + 客户端资源加载；
- 复杂失败：一个可证伪假设 + 一个定向探针。

不要求每个小改动编写大型测试报告。通常保留以下内容即可：

```text
操作步骤
预期行为
实际行为
关键日志或截图（必要时）
```

## 接入正式能力的门槛

独立测试入口成功，只证明该原语在测试场景中工作；不自动证明它可以接入挖矿、拾取、道路、跟随或其他正式任务。

正式接入前确认：

- 调用者与原语的输入契约一致；
- 失败不会破坏现有任务或安全边界；
- 有取消、超时和清理方式；
- Windows 客户端已验证对应可见行为；
- 用户同意接入方向。

Alice 当前尤其保持：普通挖矿和拾取使用 `HARD_PATH`，`SOFT_SURFACE` 不因独立测试成功而自动进入正式任务。

## 什么时候停止实现

出现以下情况就停下来讨论或调查：

- 实现需要同时修改比计划更多的系统；
- 最小闭环依赖一个尚未验证的能力；
- 编译通过但客户端现象与预期冲突；
- 第一次修复没有改善，准备继续增加特判；
- 需要放宽安全条件、扩大破坏范围或隐藏失败才能通过；
- 用户反馈表明最初理解的成功条件不正确。

同一问题第二次失败时，联用 `debugging-root-cause-analysis`；多个实现方向连续失败时，联用 `failure-pattern-recognition`。

## 输出模板

使用本 skill 后，向用户简要报告：

```text
本轮最小目标：
保持不变：
预计修改模块：
最小测试入口：
成功条件：
需要的证据：
通过后下一步：
```

本 skill 是灵活规划工具，不是审批流程；不要求 active plan、工作包、监督员审核或强制提交。

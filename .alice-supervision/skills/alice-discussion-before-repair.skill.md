# Alice Discussion Before Repair

## 何时使用

用户报告 bug、服务端与客户端结果冲突、或 AI 已找到“可能修复方式”时使用。

## 核心原则

发现可能的修复不是获得实施许可。先确认事实、范围和根因假设，再和用户讨论最小修复。用户是共同开发者，不是只负责点按钮的测试员。

## 正确顺序

```text
用户反馈
  -> 追问关键现象和复现步骤
  -> 对照当前代码、提交和日志
  -> 给出一个或多个根因假设
  -> 明确哪些已证实、哪些只是推测
  -> 与用户讨论取舍和最小修复
  -> 用户确认方向后实施
  -> 定向回归测试
```

## 禁止行为

- 看到一个 stack trace 就立刻改代码；
- 把“改了之后可能不报错”称为根因确认；
- 用一串补丁覆盖互相矛盾的现象；
- 在没有用户确认时扩大功能范围、改变架构边界或接入实验能力；
- 把用户只提供的现象加工成未经证实的日志事实。

## 反馈询问最小模板

```text
我目前确认的事实：...
当前假设：...
尚不能确定：...

请确认：
1. 你操作的具体物品和按键是什么？
2. 现象是必现、偶发还是执行一段后出现？
3. 预期与实际分别是什么？
4. 是否有截图、短视频或 Windows latest.log 片段？
5. 你希望先修复最小问题，还是先继续调查相关链路？
```

## 根因结论格式

只有定向证据支持时才使用“已确认根因”。否则写：

```text
最可能假设：...
支持证据：...
反证/缺口：...
最小验证：...
```

遇到第二次失败，联用 `debugging-root-cause-analysis`；遇到多个方案连续失败，联用 `failure-pattern-recognition`。

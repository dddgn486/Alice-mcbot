# Alice Windows Client Collaboration

## 何时使用

任何涉及实体可见性、移动、物理、GUI、渲染、输入、网络同步、资源加载或玩家交互的改动都使用。

## 核心原则

Alice 只有在 `/home/fb486/projects/alice` 中开发；Minecraft 客户端实测在 Windows 端进行。Linux/WSL 编译、headless 日志和源码分析不能替代真人在游戏内用键盘和鼠标观察行为。

## Windows 测试习惯

每次需要客户端验证时，AI 应主动提醒并确认：

- Windows 工作目录：`D:\JAVA_projects\alice\`
- 使用本轮对应的构建产物同步到 Windows 工作目录/运行目录；
- 在 Windows 端重新编译或启动实际客户端后测试；
- 在 Windows 运行时目录自行查找 `logs/latest.log`、`logs/debug.log`、`crash-reports/`、截图和视频，不假设 Linux 工作区已有这些文件；
- 记录实际运行的版本、JAR/提交（如果方便可记录 hash）以及测试时间；
- 测试完成后主动询问用户关键现象，而不是等待用户自己补充。

AI 不应声称已经读取 Windows 文件，除非用户提供了文件、共享挂载可读，或工具确实访问到了该路径。

## 测试入口设计

优先使用游戏内现有或新增的测试物品：

- 玩家可以通过 `/give` 或创造模式获得；
- 手持物品对方块/实体右键或 Shift+右键；
- 用 GUI、聊天反馈、粒子、状态条或 bot 可见行为直接显示结果；
- 一个物品优先承载一个清晰实验，普通入口和实验入口分开。

避免让用户反复寻找精确坐标、输入很长的坐标命令或执行复杂命令串。命令可保留给精确复现、管理员诊断和日志标记，但不应是普通客户端测试的主要体验。

## 轻量证据

不要求繁琐的测试报告。关键证据即可：

1. 用户可复现的操作步骤；
2. 预期与实际现象；
3. 一段关键 `latest.log`/`debug.log`（若有）；
4. 必要时一张截图或短视频；
5. AI 代码分析对应的类/方法和日志时间点。

日志探针应短小、限频、带模块前缀和任务/实体标识，例如：

```text
[Alice][BotController][bot=tango] phase=FORWARD pos=... delta=... onGround=...
```

不要为了测试永久刷屏；默认每秒一次或只在状态变化时记录，测试后可删除或降为 debug。

## 用户反馈询问模板

测试构建交给用户后，主动询问：

```text
请只按游戏内实际操作反馈：
1. 用哪个物品、右键还是 Shift+右键？
2. 游戏里看到了什么？bot/GUI/方块/粒子是否出现？
3. 预期行为和实际行为哪里不同？
4. 是一直失败、偶发失败，还是执行一段后失败？
5. 是否有紫黑材质、回弹、卡死、崩溃或聊天/日志异常？
6. 能否提供 Windows 端 latest.log 相关片段或截图？
```

用户既能读代码，也是真人测试者。AI 应同时提供代码层假设和易执行的游戏操作，不能要求用户替代调试器做复杂实验。

## 面向用户的 Markdown 回复规范

长回复必须优先保证可读性，不能让代码块、列表或中英文混排把句子截断。输出前检查：

1. 每个代码围栏都成对闭合，代码块前后各留一个空行；
2. 文件路径、命令和标识符使用完整的单行代码标记，例如 `` `run/mods/example.jar` ``，不要把反引号跨越普通句子；
3. 说明文字与代码块分开，不把中文句子的一半放进代码块；
4. 列表项保持完整句意，步骤编号不要和代码围栏直接粘连；
5. 一段只表达一个结论；长说明优先拆成“结论、原因、操作、预期结果”；
6. 普通结论、术语、文件名和简短枚举使用正文或列表，不要包进 `text` 代码块；代码围栏只用于真正的代码、命令和需要原样保留的日志；
7. 不要连续堆叠多个只有一两行的代码块，这会让 Web GUI 中的句子看起来被切断；
8. 输出后快速检查是否存在未闭合的反引号、代码围栏，或因代码块滥用而显得残缺的句子。

如果内容较长，宁可减少重复和装饰，也不要牺牲 Markdown 结构。工具输出、日志片段和用户教程必须清楚分隔，但普通解释应保持为连贯正文。

### Web GUI 可见性优先规则

如果用户反馈文字莫名中断、隐藏或不可见，后续回复必须切换为保守格式：

1. 默认只用普通段落、一级标题和单层有序/无序列表；不使用嵌套列表、表格、引用块或 HTML；
2. 除非必须展示可复制的多行代码，否则不使用代码围栏；命令、路径和标识符使用同一行内完整闭合的反引号；
3. 不在列表项内嵌套代码围栏，不连续放置多个代码围栏，不让一句话跨越正文、列表和代码块；
4. 任何关键结论都必须出现在普通正文中，不能只存在于代码块、表格或引用块中；
5. 每段使用完整句子；冒号之后必须有可见内容，不能用独立代码块代替句子的谓语或宾语；
6. 长回复固定按“结论、证据、下一步”三段组织；每段最多一层列表，避免标题层级堆叠；
7. 输出前执行可见性检查：确认无孤立反引号、未闭合围栏、空列表项、截断句、只有标题没有正文的段落；
8. 若保守格式下仍复现，向用户询问消失位置或截图，并按 Web GUI 渲染故障调查，不再把它仅归类为写作风格问题。

## 证据等级

```text
CODE_REVIEW       代码逻辑检查
COMPILE            编译通过
SERVER_LOG        服务端/fixture 观察
WINDOWS_CLIENT    Windows 客户端实际观察
USER_ACCEPTED     用户明确确认符合预期
```

发生“服务端成功但客户端失败”时，标记为 `EVIDENCE_CONFLICT`，先调查同步/工件/时序，不得用服务端日志覆盖用户观察。

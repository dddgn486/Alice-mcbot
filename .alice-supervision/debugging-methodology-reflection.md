# 调试方法论反思与总结

## 🚨 **这次调试中的严重问题**

### **问题 1: 盲目猜测，不基于证据**

**错误示例**：
```
我说："清障会误清树干，导致树木识别混乱"
证据：无
基于：猜测
结果：浪费时间实施错误的修复
```

**正确做法**：
- ✅ 先看日志，找到实际发生的事情
- ✅ 确认猜测是否符合日志证据
- ✅ 不确定就问用户

---

### **问题 2: 没有理解游戏机制**

**我的错误认知**：
- ❌ "树叶会阻挡玩家移动" → 游戏中树叶是**可穿过的**
- ❌ "树叶会遮挡视线" → 需要确认 Minecraft 的视线检测机制
- ❌ "清障会破坏树木识别" → 没有证据支持

**正确做法**：
- ✅ 不确定游戏机制时，**先问用户**
- ✅ 不要基于"真实世界逻辑"推断游戏行为
- ✅ 游戏有自己的规则（方块、碰撞箱、视线检测等）

---

### **问题 3: 来回修改，没有主线**

**我的混乱过程**：
1. 添加清障 → 发现误清树干
2. 移除清障 → 你说清障很重要
3. 添加树干检查 → 补丁式修复
4. 移除清障 → 来回反复
5. 发现 scanAttempts 问题 → 新的猜测
6. 发现固定中心问题 → 终于找到真正原因

**正确做法**：
- ✅ 先确定**主要问题**是什么
- ✅ 基于日志和观察，不是猜测
- ✅ 一次解决一个问题
- ✅ 重大修改前先问用户

---

### **问题 4: 没有在关键判断点询问用户**

**我应该问但没问的问题**：
1. "树叶在游戏中是否阻挡玩家移动？"
2. "清障功能的具体需求是什么？"
3. "你说'需要清障'，是指什么情况下需要？"
4. "任务总是在砍完一棵树后结束，你看到 Bot 在什么位置？"

**正确做法**：
- ✅ 遇到**游戏机制问题** → 问
- ✅ 遇到**需求不明确** → 问
- ✅ 遇到**多个可能的方案** → 问
- ✅ **重大修改前** → 问

---

## ✅ **正确的调试方法论**

### **Step 1: 收集证据**

#### **优先级 1：用户的直接观察**
- 用户说："任务总是在砍完一棵树后结束"
- 用户说："重启后立即能继续"
- 用户说："附近有很多完整的白桦木"

**这是最重要的证据！** 优先级 > 日志 > 我的猜测

#### **优先级 2：日志分析**
```
找关键日志：
- 任务终止的日志
- 终止前的状态
- Bot 的位置变化
- 扫描中心的位置
```

#### **优先级 3：代码逻辑**
- 只有在日志和观察都无法解释时才深入代码
- 代码分析要**验证假设**，不是**产生假设**

---

### **Step 2: 形成假设**

#### **基于证据的假设**
```
观察：任务在砍完一棵树后结束
日志：扫描中心 = 固定位置，Bot 位置 = 移动了
假设：扫描中心固定，Bot 移动后扫描不到附近的树
验证：重启时中心 = Bot 位置，所以能继续
```

#### **❌ 错误的假设（基于猜测）**
```
观察：TreeDetector 频繁失败
猜测：清障会误清树干，破坏识别
❌ 没有日志证据支持
❌ 没有验证游戏机制
❌ 直接实施修复
```

---

### **Step 3: 验证假设**

#### **方法 1：询问用户**
```
"Bot 砍完树后，是在原来的位置还是移动到很远的地方了？"
"附近的树距离 Bot 大概多远？"
"重启任务时，你有没有看到 Bot 的位置变化？"
```

#### **方法 2：添加探针**
```java
BotLog.info("扫描中心: {}, Bot位置: {}, 距离: {}",
        scanCenter, bot.position(), distance);
```

#### **方法 3：代码审查**
- 检查代码逻辑是否符合假设
- 找到关键变量（如 `final BlockPos center`）

---

### **Step 4: 实施修复**

#### **修复前的检查清单**
- [ ] 假设是否基于**用户观察 + 日志证据**？
- [ ] 是否理解了**游戏机制**（不确定就问）？
- [ ] 修复是否**针对根本原因**，而不是症状？
- [ ] 是否有**其他副作用**？
- [ ] **重大修改**是否征得用户同意？

#### **修复的优先级**
1. **根本原因** > 症状
2. **简单修复** > 复杂重构
3. **验证过的方案** > 猜测的方案

---

### **第二轮：形成假设**
1. 假设：扫描中心固定，Bot 移动后扫描不到附近的树
2. 验证：代码中 `final BlockPos center`
3. 验证：重启时中心 = Bot 位置，所以能继续

### **第三轮：确认修复方案**
1. 我："我发现扫描中心是固定的，Bot 移动后就扫描不到附近的树了"
2. 我："方案 A：让扫描中心跟随 Bot"
3. 我："方案 B：扩大扫描半径"
4. 用户：选择方案
5. 实施修复

**用时**：30 分钟，一次到位 ✅

## 🎯 **未来调试的原则**

### **1. 证据驱动**
- 用户观察 > 日志 > 代码 > 猜测
- 不基于猜测做修改

### **2. 理解游戏机制**
- 不确定就问
- 不要用"真实世界"推断"游戏世界"

### **3. 保持主线**
- 一次解决一个核心问题
- 不要来回修改

### **4. 关键决策点必须询问**
- 游戏机制不确定 → 问
- 需求不明确 → 问
- 多个方案 → 问
- 重大修改 → 问

### **5. 尊重用户的观察**
- 用户的直接观察是最重要的证据
- "我观察到 X" > "日志显示 Y" > "代码是 Z"

### **我的错误**

2. ❌ 没有证据就移除清障
3. ❌ 没有询问清障的具体需求

### **应该做的**
1. ✅ 问："清障功能的具体需求是什么？"
2. ✅ 问："树叶是否阻挡玩家？是否阻挡视线？"
3. ✅ 问："你希望清障清除什么？树叶？泥土？"
4. ✅ 基于需求实施清障，而不是基于猜测

## 📊 **总结：好的 Debug 流程**

```
1. 收集证据
   ├─ 用户观察（最重要）
   ├─ 日志分析
   └─ 代码审查

2. 形成假设
   ├─ 基于证据，不是猜测
   ├─ 不确定就问用户
   └─ 验证假设的逻辑

3. 确认方案
   ├─ 列出可能的方案
   ├─ 分析优劣
   └─ 询问用户选择

4. 实施修复
   ├─ 针对根本原因
   ├─ 避免副作用
   └─ 测试验证

5. 验证效果
   ├─ 问题是否解决？
   ├─ 有无新问题？
   └─ 用户确认
```

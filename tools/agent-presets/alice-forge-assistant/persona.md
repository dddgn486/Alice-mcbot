## 开场三问（别跳）

1. **我在哪个基线？** 先看 git 提交与工作区状态，对齐了再动手。
2. **主线是什么、支线是什么？** 先确认当前该做哪一件。⛔ 不要自己排期、不要自己扩范围。
3. **上一轮留下了什么？** 历史在旧会话里 —— **问用户是哪一场，不要自己编**。

## 六条硬纪律（都是这个项目真踩过的坑）

1. **证据** —— 任何数字 / 状态 / 结论，必须能指向**一次当场复算**，不能指向"我记得"。
   ⚠️ "缺乏 X" 这类断言，**先读最新那一份**：看到很多旧的 ≠ 没有新的。
2. **术语** —— 新词须经用户批准；一词一义；全仓同名类即红。
   你写的东西用户看不懂，那是你的 bug，不是他不专业。
3. **规则的载体** —— **门禁 > 散文**。散文会过期、会被绕过、语义会分歧；
   能**让构建失败**的检查才算边界。新增散文规则要带准入标记。
4. **基线唯一** —— 任何时刻只有一个"现在该做什么"。收工的交接必须写清
   主线 / 支线 / 各自进度 / "支线不取代主线"。不确定就问用户。
5. **作者 ≠ 审阅者** —— 你写的代码、你写的测试、你写的门禁，都得由**另一个会话**对抗性复核；
   自己复读一遍不算验证。
6. **不许静默** —— 做不到就说做不到，跳过就说跳过。
   ⛔ 传送 / 隔空 / 伪造成功，一律不接受。

项目正处于**整改期**（架构 / 术语 / 文档三线并行），文档路径、规则编号、排期批次**仍在变**。
⇒ 本 preset 刻意**不写任何路径 / 编号 / 排期**：那些以仓库当时的现状为准 —— 在仓库里查，或直接问用户。

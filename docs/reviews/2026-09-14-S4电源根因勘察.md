# S4 场景电源为什么一滴都不过来 —— 勘察留档（2026-09-14 第六轮）

结论先行：**创造能量方块（`mekanism:creative_energy_cube`）放下时自带电量 = 0 J，而且这个方块永远充不进电。**
所以"场景里放一个创造方块当电源"这条前提**从来没成立过**；第五轮把根因判给"方块朝向"（D-212）**是错的**。
朝向那条修正本身要保留（它决定从哪个面出电），但它**不是**"流入 0"的原因。

## 1. 触发与第一手现象

第五轮（13:55）修了场景 `[facing=up]`，第六轮（14:05）客户端重跑：

- `latest.log:262` `已执行函数alice_test:machine_course中的10条命令`（14:05:07）
- `latest.log:281` `[MachineCycle] SUMMARY … energy_at_open=0.0 energy_source=api_precharge（场景电源没喂上 ⇒ 按前提补电 4000000.0 J） … verdict=PASS`

⇒ **朝向已经在世界里生效了，机器仍然是 0 J。** 于是必须换证据源。

## 2. 决定性证据：存档里的天然对照组

`[facing=up]` 是否真的落到世界里，不能靠推理 —— 世界在场景跑完后 25 秒保存过
（`latest.log:301-308` Saving worlds，14:05:51），所以**存档就是现场**：

工具：`python3` + 标准库 `zlib` + 手写 NBT 解析（本机无第三方 NBT 库；`readblk.py`/`dumpbe.py` 为一次性探针，
**未入库**，方法与坐标记录在此）。目标区块：方块 x=66,z=306 ⇒ chunk(4,19) ⇒ region `r.0.0.mca`。

方块状态（section Y=3，注意 y=64 属于 section Y=4，跨段读取会读到 y=48 的空气，别踩）：

```
(66,63,306) -> mekanism:creative_energy_cube {facing:"up", fluid_logged:"empty"}   ← 修正确实生效
block_entities: enrichment_chamber(66,64,306) / creative_energy_cube(66,63,306) / crusher(66,64,307)
```

方块实体 NBT（**同一次保存、同一区块 ⇒ 天然对照组**；`BasicEnergyContainer.serializeNBT`
**只在非空时**写 `stored`）：

```
enrichment_chamber @(66,64,306):  EnergyContainers = [{"Container":0,"stored":"3990000"}]
creative_energy_cube @(66,63,306): EnergyContainers = []          ← 空 = 0 J
crusher @(66,64,307):              EnergyContainers = []
```

机器那 3,990,000 J 正是夹具 `setEnergy(4_000_000)` 灌进去的（200 tick 消耗 10,000 J）——写读通路都通；
方块是**空列表** ⇒ 方块自己是 0 J。**"序列化只写非空"这条让"空"变得可判定**，这是本轮证据能钉死的关键。

## 3. 上游源码链（两侧独立核实）

**⑨ 上游设计（第二个只读子代理独立核实 + issue `mekanism#7352` 维护者原话）**：创造能量方块有**两个创造栏变体**——
"空"的（各面 INPUT，维护者称之为 **power sink**，"will not hold energy you send to it"）和"满"的
（`StorageUtils.getFilledEnergyVariant(..., tier.getMaxEnergy())` 把 `EnergyContainers` 写进物品
`mekanism:data`，`BlockMekanism.java:310-314` 在**放置时**灌进方块实体）。
`/setblock` 走不到那条路 ⇒ **只能造出"空"变体**。这也解释了为什么方块状态朝向对了、配置对了、tick 在跑，却还是 0 J。

## 4. 修法（纯数据、零 Java）

场景在 `setblock` 之后复刻"满变体"的载荷（键名/形状照抄上面机器那条实测 NBT）：

```
setblock 66 63 306 mekanism:creative_energy_cube[facing=up]
data merge block 66 63 306 {EnergyContainers:[{Container:0,stored:"4000000000"}]}
```

- `/data merge block` 会 merge 进方块实体再 `load()` ⇒ `DataHandlerUtils.readContainers` → `setEnergy`（**直接 setter，
  不带创造档的 insert 守卫**）⇒ 方块变成非空 ⇒ ③ 的两道空判定放行 ⇒ 出电；
- ② 决定它**抽不干** ⇒ 一次注入即"无限电源"，正是场景需要的；
- 场景每次跑都会重放这两行 ⇒ 天然幂等，跨轮不会残留。

**注意一个反直觉点**：机器容量只有 **20,000 J**（`StorageConfig:53-54`），而夹具兜底 `PRECHARGE_JOULES` 是 4,000,000
⇒ 补电会把机器顶到容量**之上**，此时 `BasicEnergyContainer.insert:105-109`（`if (needed.isZero()) return amount;`）
**拒绝一切外来电**（按 50 J/t 要 ~79,600 tick 才回落到容量内）。
⇒ **"补电之后再观察方块通不通"是无意义的**；判电源只看**补电之前**的 `energy_at_open`。

## 5. 教训

1. **排除法没做完，不要定根因**：D-212 从"算术 + 单向源码"推出"朝向 ⇒ 流入 0"，漏掉了"方块自身是否非空"这一层。
   修正方式不是打补丁，而是**换一个能证伪的证据源**（存档里的对照组）。
2. **"如实留痕"的字段是资产**：`energy_source=api_precharge` 这个字段就是整条链的入口 —— 它让"假绿"无法隐藏。
3. **存档是可以当实验台用的**：`serializeNBT` 的条件写 + 一次保存 = 免费对照组；这比再跑一轮客户端便宜得多。

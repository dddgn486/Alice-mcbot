### 1.1 离线复核：类型↔方块链在 Mekanism jar 里是**可静态取证**的【实证】

用客户端 `mods/Mekanism-1.20.1-10.4.16.80.jar` 直接反查（`javap`），三级链条全部落地：

1. 配方类型注册名：`MekanismRecipeType` 构造 `("mekanism", "<name>")` ⇒ `mekanism:<name>`（27 个常量）；
2. 方块注册名：`MekanismBlocks` 里 `BLOCKS.register("crusher", …)` ⇒ `mekanism:crusher`（33 台机器方块）；
3. 方块↔方块实体**写在泛型签名里**：`BlockRegistryObject<BlockFactoryMachine<TileEntityCrusher, …>, …> CRUSHER`
   ⇒ 方块与方块实体是**编译期绑定**，不是约定；
4. 方块实体→类型：`TileEntityCrusher.getRecipeType()` → `getstatic MekanismRecipeType.CRUSHING`。

提取出的 21 组"类型 → 基础机器方块"（**全部实证**；括注为未映射到单方块机器的）：

```
crushing→crusher          enriching→enrichment_chamber   smelting→energized_smelter
combining→combiner        compressing→osmium_compressor  purifying→purification_chamber
injecting→chemical_injection_chamber                     sawing→precision_sawmill
metallurgic_infusing→metallurgic_infuser                 oxidizing→chemical_oxidizer
chemical_infusing→chemical_infuser                       separating→electrolytic_separator
washing→chemical_washer   crystallizing→chemical_crystallizer
dissolution→chemical_dissolution_chamber                 reaction→pressurized_reaction_chamber
rotary→rotary_condensentrator                            activating→solar_neutron_activator
centrifuging→isotopic_centrifuge                         nucleosynthesizing→antiprotonic_nucleosynthesizer
pigment_extracting→pigment_extractor                     pigment_mixing→pigment_mixer
painting→painting_machine
```
（未映射：`evaporating`=多方块 `EvaporationMultiblockData`；`energy_conversion`/`gas_conversion`/
`infusion_conversion` 只在 slot/recipe-manager 层出现，**未定位到单方块机器**【推断：属"机器内部/无独立方块"，需客户端确认】。）

**两个必须建模的现实**【实证】：
- **1:N**：`crushing` 同时对应 `crusher` 与 4 档工厂（`basic_/advanced_/elite_/ultimate_crushing_factory`，
  blockstate 文件全部存在）⇒ 表**不能**是 `type → 单一方块`。
- **注册了但零配方**：`mekanism:smelting` 在 jar 里注册，但 `data/mekanism/recipes/` 下**没有 smelting 目录**
  ⇒ S0 的 26 类里没有它。覆盖检查**不得**把它当"孤儿行"报错。

## 2. "单一出处"表应该长什么样

**列（建议）**

| 列 | 例 | 来源 | 谁可写 |
|---|---|---|---|
| `type_id` | `mekanism:crushing` | 上游注册名（可枚举校验） | 必须登记 |
| `block_ids` | `mekanism:crusher,mekanism:basic_crushing_factory,…` | 上游区块方块注册 | 必须登记（可为空=无单方块机器） |
| `menu_class` | `mekanism.common.inventory.container.tile.MekanismTileContainer` | 客户端实测一次后登记 | 必须登记（用于"点对了没"断言） |
| `capability` | `READ_ONLY` / `SITE_KNOWN` / `EXECUTABLE` | 人工裁定 | 必须登记；**缺省必须是 `READ_ONLY`** |
| `source` | `mekanism-1.20.1-10.4.16.80.jar#MekanismRecipeType` | 登记时的取证出处 | 必须登记 |
| `code_ref` / `note` | `RecipeQuery.java:160` / 备注 | 人工 | 建议 |
| ~~`slots`~~ | **不进表** | — | 硬编码槽位下标是**反模式**（`docs/MOD_ADAPTER_PROTOCOL.md:54`）；槽位/进度**运行时问上游** |

**放哪里：Java 静态 `record` + `Map` 表（运行期唯一真相），另 dump 成 CSV 供人读。**理由：
① 运行期读不到仓库 `docs/`；② `build.gradle:141-146` **明确不声明 Mekanism 编译依赖**（教训：曾因编译期在场导致
真实客户端崩溃）⇒ 表里**只能是字符串 id**，不能是类引用；③ 唯一先例 `RecipeDump.STATION_BY_TYPE`
（`RecipeDump.java:58-70`）就是 Java 表 + `stationFor()` 查找，同形态最省心。
CSV/人读视图**由运行期 dump 生成**（追加到既有 `RecipeDump.dump` 的 JSON 或一条零参数命令），
不手写第二份 —— 与 D-146"运行时导出"同一条路。

**防漂移三层**

| 层 | 机制 | 失败表现 |
|---|---|---|
| ① 静态（构建前） | `tools/check-machine-map.sh`：正则解析 Java 表 ↔ `docs/…MACHINE_MAP.csv`，断言两侧 `type_id`/`block_ids` 集合一致 —— 照抄 `tools/authz-map.py:243-263` 的 `--check` 形态 | `MACHINE_MAP_CHECK_RESULT FAIL` |
| ② 运行期覆盖 | 在既有电池步 `machine_route`（`RegressionBatteryTask.java:374-377`）内：枚举 `RecipeManager` 里 `mekanism:` 前缀类型 ⇒ 每个类型要么有行、要么进 `unmapped=[…]`；有行但方块不存在 ⇒ `block_missing=[…]`（**只告警不判红**，模组集可变） | `machine_map_types=27 mapped=22 unmapped=[…]` |
| ③ 客户端交叉验证 | `machine_station` 步改成**按表里的 block id** 去找/开菜单，并断言 `machine_block == 表里的 id`、`menu_class == 表里的 menu_class`（不符 ⇒ `menu_class_drift`） | `[MachineStation] SUMMARY … verdict=FAIL reason=menu_class_drift` |

零配方类型（`smelting`）必须**单独一列或显式注明**"注册但无配方 ⇒ 不算缺行"。

## 3. 可复用性验证：用第二台机器（`crushing` / `crusher`）证明这层是数据驱动的

**需要动的文件**

| # | 文件 | 改动 | 性质 |
|---|---|---|---|
| 1 | Java 映射表 | 加 1 行 `mekanism:crushing → mekanism:crusher` | **数据** |
| 2 | `tools/test-scenes/.../machine_course.mcfunction` | 多摆一台 `mekanism:crusher`（函数现只有 `enrichment_chamber`，`:8`） | **数据** |
| 3 | `RecipeQuery.java:160` | 机器路线的 `station` 从 type 改成表里查到的 block id | **代码（一次性接线）** |
| 4 | `MachineStationProbeTask.java:124-139` | 从"命名空间最近方块"改成"按表认机器" | **代码（唯一真缺口）** |
| 5 | `tools/check-machine-map.sh` + `docs/…MACHINE_MAP.csv` | 同步 | 数据/脚本 |

**预期观察**

- `machine_station` SUMMARY：`machine_block=mekanism:crusher@…`、`machine_block_entity=…TileEntityCrusher`、
  `menu_class=…MekanismTileContainer`、`menu_slots=<n>`、`verdict=PASS`（**注意**：今天的探针在双机器场景下会因
  "取最近"而**不确定开的是哪台** ⇒ 这一条正是缺口 4 的证据）；
- `machine_route` SUMMARY 新增：`machine_map_types=27 mapped=22 unmapped=[…] mapped_block_missing=[]`；
- 查询层：`MACHINE_ROUTE` 的 `station` 从 `mekanism:enriching` 变为 `mekanism:enrichment_chamber`
  （`CraftJob` 的 `not_executable:<machine>` 与 `CandidateMenu` 的 `needs=` 文案随之变化 ⇒ **行为改变，需拍板**）。

**如实指出缺口（不美化）**：S3 **做不到"100% 只加数据"**。加一台机器仍需改两处 Java：
① `RecipeQuery.java:160` 的接线（只做一次）；② **机器选择策略**（今天是"命名空间最近方块"，
无表可比对、无法在双机器场景下自证点对了哪一台）。抽象到位后，这两处都应**只写一次**，
后续加机器 = 加表行 + 加场景方块。若第 ③ 层断言（`menu_class` 漂移）也要生效，
探针必须由表驱动 —— 这是 S3 必须交付的最小代码，不是可选优化。

## 4. 风险与红线：表中哪些字段"可安全取得"、哪些"必须登记，否则拒写"

| 类别 | 字段/事实 | 依据 |
|---|---|---|
| **可安全从上游取（无需登记）** | 类型 id 全表（可枚举）；配方输入/输出（自校验后才采信）；菜单类名/槽数/槽类/槽 Object；进度**方法名形态**（只收集不调用）；原始 capability 事实（`IItemHandler`/`IEnergyStorage`/`IFluidHandler` 的储量/容量） | `RecipeDump.java:154-155`；`MachineRecipeFacts.java:56-66,69-89`；`MachineStationProbeTask.java:181-192,315-332`；`InterfaceScanner.java:127,142,149` |
| **必须显式登记，否则一律拒绝写入** | `block_ids`（哪台方块才是这台机器）；`menu_class`（点对了没）；**槽位角色**（输入/输出/能量/升级）；`capability`（只读 vs 可执行）；任何"取产物"的取法协议 | `InterfaceScanner.java:21,28`（C1 **不推断槽位角色**）；`CraftStation.java:47-51`（`Take.UNKNOWN` ⇒ 只许只读观察）；`docs/MOD_ADAPTER_PROTOCOL.md:10-14` |
| **禁止入表** | 槽位下标、菜单类名以外的实现细节（类名/反射字段名作为**逻辑依赖**）、任何"猜"出来的写入语义 | `docs/MOD_ADAPTER_PROTOCOL.md:54` |

红线落地口径：**`capability` 缺省值 = `READ_ONLY`**；表里没有行 = 未知 = 只读 + 如实报码
（今天 `MACHINE_ROUTE` 的 `not_executable` 语义保持不变，`:160` 换的是"去哪台"，不是"能不能做"）。

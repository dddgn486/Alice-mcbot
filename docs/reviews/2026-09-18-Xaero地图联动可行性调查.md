## 1. Is there an official API package?

**No.** Enumeration result (SEEN):

```
$ find /tmp/xwm/xaero -iname "*api*"                 → (nothing)
$ find /tmp/xwm/xaero -name "*Api*.class"            → (nothing)
$ find /tmp/xmm/xaero -iname "*api*"                 → xaero/common/minimap/MinimapInterface.class
                                                       xaero/common/gui/GuiMinimapInfoSettings.class
$ find /tmp/xmm/xaero -name "*Api*.class"            → (nothing)
$ find /tmp/xlib/xaero -type d -path "*api*"         → (nothing)
```

* `MinimapInterface` is **not** an API — SEEN declaration:
  `public class xaero.common.minimap.MinimapInterface extends xaero.hud.minimap.Minimap`.
  It is a concrete `Minimap` subclass that adds accessors. Same for `GuiMinimapInfoSettings`.
* The only `*api*` strings in XWM are **external** types Xaero *consumes* from
  Open Parties and Claims, e.g. SEEN in `SupportOpenPartiesAndClaims`:
  `private final xaero.pac.client.api.OpenPACClientAPI api;` and
  `xaero.pac.client.claims.api.IClientClaimsManagerAPI claimsManager`.
  Xaero is an OPAC *client*, not an API *provider*.
* `META-INF/services/xaero.map.platform.services.IPlatformHelper` → `xaero.map.platform.services.ForgePlatformHelper`
  is Xaero's **internal** own platform abstraction (SPI for its own Forge/Fabric split), not a third-party hook.
* `META-INF/coremods.json` → `{"xaeroworldmap_core": "META-INF/xaeroworldmap_core.js"}`
  (XMM: `xaerohud_core.js`) — Xaero's own coremod, not extensible by third parties.

**Verdict:** third-party integration is *de facto* unofficial. The good news is that
a large amount of it is reachable through `public` classes/fields; the bad news is
nothing is stabilised, versioned, or guaranteed, and HotSpot-visible access is not a
compatibility contract.

### 2.2 Registration — MIXIN-REQUIRED (the key finding)

```java
public class xaero.map.highlight.HighlighterRegistry {                            // SEEN
  private List<AbstractHighlighter> highlighters;
  public HighlighterRegistry();
  public void register(AbstractHighlighter);   // body: highlighters.add(highlighter)
  public void end();                           // body: highlighters = Collections.unmodifiableList(highlighters)
  public List<AbstractHighlighter> getHighlighters();
}
```

The API looks public, but the lifecycle closes it. From `WorldMapSession.init(ClientPacketListener, long)`
bytecode (SEEN, bytecode offsets):

```
179: new  xaero/map/highlight/HighlighterRegistry
183: invokespecial <init>()V
188: invokestatic  SupportMods.pac()Z
194/199: invokevirtual SupportOpenPartiesAndClaims.registerHighlighters(HighlighterRegistry)V
204: invokevirtual HighlighterRegistry.end()V          ← list becomes unmodifiable
...
225: new xaero/map/MapProcessor   (registry passed as ctor arg #15)
```

`MapProcessor.getHighlighterRegistry()` **is** public (SEEN) —

```java
public xaero.map.highlight.HighlighterRegistry getHighlighterRegistry();
```

— but it can only be reached *after* `init()` has already run `end()`. `register()` is a bare
`List.add` on a `Collections.unmodifiableList` view, so calling it late throws
`UnsupportedOperationException`. There is no public setter, and no public accessor on
`MapWorld`/`MapDimension`/`DimensionHighlighterHandler` (`DimensionHighlighterHandler` holds
`private final HighlighterRegistry registry;` with **no getter** — SEEN).

**Verdict: MIXIN-REQUIRED.** The only viable window is between
`new HighlighterRegistry()` and `end()`.

**Mixin target (recommended, and the pattern the reference repo uses and ships as working):**

```
Target class : xaero.map.highlight.HighlighterRegistry
Target method: <init>()V
Injection    : @Inject(method = "<init>", at = @At("TAIL"))
Effect       : this.register(myHighlighter)   // list still mutable here
```
This is precisely Dissonance's `XaeroHighlighterRegistryMixin` (`@Mixin(value = HighlighterRegistry.class, remap = false)`,
`@Shadow public abstract void register(AbstractHighlighter)`, `@Inject(method="<init>()V", at=@At("TAIL"))`),
targeted at `1.38.1` — and the target still exists identically in 1.46.0 (SEEN), so it should still apply.

Weaker alternative (more fragile, no symbolic injection point):
`xaero.map.WorldMapSession.init(ClientPacketListener, long)` — inject before the `end()` invocation.

and in `SupportXaeroMinimap.register()`: `playerTrackerSystemManager.register("minimap_synced", …)`.

**Late registration works (dynamic, live iteration) — SEEN:** `PlayerTrackerMapElementCollector`
holds `private final PlayerTrackerSystemManager systemManager;` and its `update(Minecraft)` →
`updateForSystem(...)` iterates `systemManager.getSystems()` on every refresh, so a system added
*after* Xaero's init is picked up. (Xaero registers `"minimap_synced"` at exactly such a late point.)
The renderer `WorldMap.trackedPlayerRenderer` is already built and registered for you in
`WorldMap.loadClient()` via `PlayerTrackerMapElementRenderer$Builder.begin().build()` (SEEN).

**Two hard constraints (SEEN, both important for Alice):**

1. **No custom avatar icon.** `TrackedPlayerIconManager.getPlayerSkin(Player, PlayerInfo)` bytecode:
   ```
   0: player instanceof AbstractClientPlayer ? getSkinTextureLocation()
  17: else PlayerInfo.getSkinLocation()
  22: if null → DefaultPlayerSkin.getDefaultSkin(player.getUUID())
   ```
   then `getIcon(...)` caches a `XaeroIcon` in `Map<ResourceLocation, XaeroIcon> icons` keyed by that
   skin location, and `TrackedPlayerIconPrerenderer.prerender(GuiGraphics, XaeroIcon, Player, int, ResourceLocation, PlayerTrackerMapElement)` builds it.
   There is **no hook, registry, or supplier** for a third-party icon on this route.
   To render a bespoke head/avatar you must mixin (`TrackedPlayerIconManager.getIcon`, `getPlayerSkin`,
   or `TrackedPlayerIconPrerenderer.prerender`) or use Route 2B.

2. **The bot must be a real client-visible player.** `PlayerTrackerMapElementRenderer.renderElement`
   bytecode opens with:
   ```
    7: Minecraft.getInstance().getConnection()
   14: PlayerTrackerMapElement.getPlayerId()
   17: ClientPacketListener.getPlayerInfo(UUID)   // PlayerInfo
   20: astore 15
   22: aload 15
   24: ifnull 427                                   ← skip ALL icon rendering
   ...
  336/338/340: getIcon(GuiGraphics, Player, PlayerInfo, element)
   ```
   The avatar is resolved from `ClientPacketListener.getPlayerInfo(uuid)` **and**
   `ClientLevel.getPlayerByUUID(uuid)` (both SEEN as method refs). **No `PlayerInfo` ⇒ no icon at all.**
   So a server-side-only entity / abstract fake player will not get a marker through this route;
   the bot needs a tab-list `PlayerInfo` on the client connection.

Gating options exist (SEEN): `MINIMAP_RADAR`, `DISPLAY_TRACKED_PLAYERS` (both `BooleanConfigOption`)
— see gaps for which one gates the world-map layer.

### 3.4 Minimap↔WorldMap mirroring wrappers (why the tracker route is the practical one)

XWM ships `xaero/map/mods/minimap/element/{MinimapElementRendererWrapper, MinimapElementReaderWrapper,
MinimapElementRenderProviderWrapper, RadarRendererWrapperHelper}` and
`xaero/map/mods/minimap/tracker/system/{MinimapSyncedPlayerTrackerSystem, MinimapSyncedTrackedPlayerReader}`,
whose fields/signatures reference `xaero.common.*` and `xaero.common.minimap.render.radar.element.RadarRenderer`
(SEEN). But:
* `MinimapElementRendererWrapper` is referenced **only** from its own `$Builder`, `MinimapElementReaderWrapper`
  and `RadarRendererWrapperHelper` — **all inside XWM** (SEEN via reference scan). There is no public
  entry point for a third party to ask XWM to mirror an arbitrary minimap element onto the world map.
* Wrapping is driven by `SupportXaeroMinimap.createRadarRendererWrapper(Object)`, which hard-casts:
  ```
  checkcast xaero/common/minimap/render/radar/element/RadarRenderer
  invokevirtual RadarRendererWrapperHelper.createWrapper(IXaeroMinimap, RadarRenderer)
  ```
* In 1.46.0, the sibling hook `SupportXaeroMinimap.registerMinimapHighlighters(Object)` is an
  **empty no-op** — SEEN: `public void registerMinimapHighlighters(java.lang.Object); Code: 0: return`.

⇒ Practical conclusion: to get one bot marker on *both* map surfaces, register **Route 2A**
(world map tracker) **and** **Route 2C** (minimap element renderer) yourself. Do not expect Xaero to
mirror your minimap renderer onto the world map.

## 5. Hard separation: World Map vs Minimap

**Yes — hard-separated. The World Map renders markers/highlighters with the Minimap absent.**

Manifest evidence (SEEN):
* XWM `mods.toml`: `xaerominimap` is `mandatory = false`, `versionRange = "[26.4.0,)"`;
  `xaerolib` is `mandatory = true`; description: *"A self-writing fullscreen map which also works as an add-on to Xaero's Minimap."*
* XMM `mods.toml`: `xaeroworldmap` is `mandatory = false`, `versionRange = "[1.44.0,)"`.
* Both declare `side = "BOTH"` for Forge/Minecraft and bundle the same `xaerolib` 1.7.3 via jarjar.

Runtime mechanism = **reflective, lazy classloading** — `SupportMods.load()` bytecode (SEEN):
```
0: ldc "xaero.common.IXaeroMinimap"
2: Class.forName
6: new xaero/map/mods/SupportXaeroMinimap     ← only reached if forName succeeded
13: putstatic SupportMods.xaeroMinimap
19: SupportXaeroMinimap.register()
22: goto 26    /  25: astore_1   (catch → field stays null)
26: ldc "xaero.pac.OpenPartiesAndClaims"
28: Class.forName
32: new xaero/map/mods/pac/SupportOpenPartiesAndClaims
...
```
plus `public static boolean SupportMods.minimap()`, `framedBlocks()`, `pac()` guards.

`xaero.map.mods.SupportXaeroMinimap` has `xaero.common.IXaeroMinimap modMain;` and references
`xaero.common.settings.ModSettings.*`, `xaero.common.minimap.waypoints.WaypointWorld`, … — so **loading
that class without the Minimap present throws `NoClassDefFoundError`.** Same for every class under
`xaero/map/mods/minimap/**` (whose signatures carry `xaero.common.*` and
`xaero.common.minimap.render.radar.element.RadarRenderer`). A third-party mod touching those must apply
the identical `Class.forName`/`ModList` guard.

Conversely, all classes needed for Goals 1/2/3 on the World Map live in the XWM jar with **no
`xaero.common.*` in their signatures** — SEEN by scanning XWM's own `xaero/map/**` packages: no
reference to `xaero/common/` exists outside `xaero/map/mods/minimap/**` and `xaero/map/mods/SupportXaeroMinimap`.
`xaero/map/mods/pac/**` carries `xaero.pac.*` types under the same lazy pattern.

## 6. Client-only constraints and Forge metadata

* **No `@Environment(EnvType.CLIENT)` annotations exist in either jar.** Constant-pool scan for
  `net/fabricmc` and `OnlyIn` across `/tmp/xwm` and `/tmp/xmm` returned **empty**. (Dissonance's
  `@Environment(EnvType.CLIENT)` are on *its own* classes, since it is an Architectury mod.)
* **No `*Api*` classes, no `api` package, no third-party entrypoint in `mods.toml`.**
  `mods.toml` contains only `modLoader`/`loaderVersion`/`license`, one `[[mods]]` block, and
  `[[dependencies.*]]` blocks. There is no `[[mods]] entrypoint`-style hook a third mod can register.
* Client-only enforcement is therefore **behavioural, not declarative**. Every API surface cited above
  for Goals 1–3 depends on `net.minecraft.client.*` (`GuiMap`, `GuiGraphics`, `Minecraft`,
  `AbstractClientPlayer`, `PlayerInfo`), and `HudMod.INSTANCE` / `MapProcessor.getHighlighterRegistry()`
  etc. only exist on the physical client. For Alice this means:
  * a dedicated server must never classload these;
  * client code must be loaded from a `Dist.CLIENT`-guarded entrypoint
    (`FMLClientSetupEvent` + `DistExecutor.unsafeRunWhenOn(Dist.CLIENT, …)`), since Xaero exposes no
    hook of its own;
  * `WorldMap.loaded` (`public static boolean`) and `WorldMap.INSTANCE` are usable cheap guards.
* `META-INF/services/` entries are Xaero's internal platform SPIs only
  (`xaero.map.platform.services.IPlatformHelper`, `xaero.common.platform.services.IPlatformHelper`).
* Both jars ship `META-INF/coremods.json` referencing their own JS coremod.

## 9. Unverified assumptions and gaps

1. **Runtime non-nullness of the new config path.** I verified by bytecode that
   `WorldMap.INSTANCE.getConfigs().getClientConfigManager().getEffective(ConfigOption<T>)` and
   `…getCurrentProfile().getPrimaryConfigManager().getConfig().get(ConfigOption<T>)` are all public
   and type-correct. I did **not** run the game to confirm `getCurrentProfile()` is non-null that early.
2. **Which option gates the world-map tracked-player layer.** I found both
   `WorldMapProfiledConfigOptions.MINIMAP_RADAR` and `DISPLAY_TRACKED_PLAYERS`, but did not trace which
   one (or which additional check) suppresses the layer in `GuiMap`/`PlayerTrackerMapElementRenderer`.
   **This matters:** if the player disables it, a Route 2A marker disappears with no third-party control.
3. **Minimap radar custom-icon binding.** `RadarIconManager`, `EntityRadarCategory$Builder`,
   `EntityRadarCategoryHardRules` and `EntityIconDefinitions` clearly form an entity→icon mapping system,
   but I did not trace the exact call that binds a category to an icon, so "register a bot entity
   category with a custom icon on the minimap radar" is **plausible but unproven**.
4. **No verified lifecycle hook for `mapElementRenderHandler.add(...)`.** I confirmed the field is
   `null` until `WorldMap.loadClient()` (SEEN assignment site) and that no Xaero-side callback/event is
   exposed (`ClientEvents`/`ModClientEvents` are Xaero-internal handler objects, not a bus).
   The exact earliest safe *third-party* call point was not determined empirically.
5. **`ElementRenderInfo` / `ElementRenderer` sematics unexercised.** The signatures and `public` visibility
   are verified, but I did not verify that a foreign `ElementRenderer` appended late is ordered/picked up
   correctly relative to Xaero's own renderers (`ElementRenderer implements Comparable`, `getOrder()`),
   nor how `shouldRender(ElementRenderLocation, boolean)` must behave to appear only on `WORLD_MAP`.
6. **`Collections.unmodifiableList` failure is inferred from bytecode, not observed.** `HighlighterRegistry.end()`
   bytecode is unambiguously `Collections.unmodifiableList(list)` and `register()` is unambiguously
   `List.add`, so `UnsupportedOperationException` is a certain Java-level consequence — but I did not
   execute it. `MapProcessor.getHighlighterRegistry()` being public is exactly the kind of trap that
   would look fine at compile time.
7. **No client/runtime testing was performed.** All findings are static bytecode analysis. Nothing here is
   `SERVER_TESTED`, `WINDOWS_CLIENT`, or `USER_ACCEPTED` — it is `SEEN IN BYTECODE` only.
8. **Xaero's own Mixin plugin.** Both jars set
   `"plugin": "xaero.lib.mixin.plugin.MixinPlugin"` with `"required": true` in their mixin configs;
   I did not inspect that plugin, so any interaction between it and a third-party mixin set
   (e.g. refmap/compatibility-level collisions, `JAVA_17` compat level) is unverified.
9. **`MapTileSelection` shape.** The class exists, but I did not enumerate its members, so whether the
   `@Local`-free PAC-style signature can be reproduced exactly is unconfirmed.

## 10. Bottom line for Alice

* **Chunk claim overlay: viable but needs one mixin.** Subclass `xaero.map.highlight.ChunkHighlighter`
  (public, `protected ChunkHighlighter(boolean)`), register via
  `@Mixin(HighlighterRegistry.class) @Inject(method="<init>()V", at=@At("TAIL"))`, then drive refresh
  entirely through public API (`MapDimension.getHighlightHandler().clearCachedHash(...)`,
  `MapProcessor.addToRefresh`, `MapRegion.requestRefresh` / `MapSaveLoad.requestLoad`). Read the
  claim-display gate from `WorldMapProfiledConfigOptions.OPAC_CLAIMS*`, **not** `WorldMap.settings.*`.
* **Bot avatar: fully public, two viable designs.**
  (a) Fastest: `WorldMap.playerTrackerSystemManager.register("alice", system)` → bot appears as a
  standard tracked player. Requires the bot to have a real client `PlayerInfo`; avatar is the bot's
  skin; no custom icon. (b) Full control: register your own
  `MapElementRenderer` via `WorldMap.mapElementRenderHandler.add(...)` → custom icon, and you get
  Goal 3 for free. For the minimap, register a `MinimapElementRenderer` via
  `HudMod.INSTANCE.getInterfaces().getMinimapInterface().getOverMapRendererHandler().add(...)`.
* **Right-click menu: public if it is on your own element** (override
  `ElementReader.getRightClickOptions` / `isRightClickValid`) — no mixin. Only the general
  terrain/waypoint/tracked-player menu needs `@Mixin(GuiMap.getRightClickOptions)`.
* **No API contract exists.** There are no `api` packages, no `*Api*` classes, no mods.toml entrypoints,
  and no client-only annotations. Treat every access above as unversioned and pin the exact Xaero
  versions you build against; the `WorldMap.settings.*` → `OPAC_CLAIMS*` change between 1.38.1 and
  1.46.0 is a concrete demonstration that public-field access breaks silently across versions.

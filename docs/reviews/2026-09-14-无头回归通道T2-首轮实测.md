# T2 无头回归通道 —— 首轮实测与「假人区块票冻结」根因

> 2026-09-14。本文只写**已复算的事实**与**根因**；证据原文在无头服务端的 `logs/latest.log`
> 与崩溃报告里，本文用行号/命令指代，不抄大段原文（AGENTS.md「只放指针」）。

---

## 1. 背景与目标

`T2`（审查文 §4.1）要的是把"游戏内右键 `alice:regression_battery`"这条验收路径搬到**无需真人**的服务端，
从而把"从改一行到知道对不对"从 **1 个客户端轮次（真人 + 电池 ~3,350 tick + 手工同步 jar）**
降到 **1 条命令**。闸门（用户 2026-09-14 确认）：**先做「1 个样板 + 覆盖度评估」**，
量出"30 步里能自动判红的 = N"，**N < 8 就不铺开**。

## 2. 通道实现（已落地）

| 文件 | 作用 |
|---|---|
| `src/main/java/com/dddgn/alice/headless/HeadlessBattery.java` | 无头入口。系统属性 `alice.headless.battery=core\|full\|single:<step>`，默认关闭（零开销）；起服后延 20 tick 生成假人、走**与游戏内物品完全相同**的指派入口、读判决、按判决**退出码**退出 |
| `tools/headless-battery.sh` | 一条命令：重建 Alice 工件 → 重置世界 → 装模组 → 起生产服务端 → 解析判决 → 透传退出码 |
| `build.gradle`（`server` run config） | 删掉失效钩子 `alice.selftest.auto`（它指向 `cbd177a` 就删掉的 `BotSelftest`），换成 `alice.headless.battery` 转发 |
| `RegressionBatteryTask` | 新增 `onlySteps`（定向模式，供 `single:<step>` 秒级调试）与 `lastVerdict()`（判决的唯一出处） |

**退出码**：`0`=PASS / `1`=FAIL / `2`=DEGRADED / `3`=没等到判决 / `4`=起不来 / `5`=环境或脚本问题。

### 2.1 两个必须记住的坑

1. **不能用 `./gradlew runServer` 的退出码**：`runServer` 是 Gradle 的 `JavaExec`，**吞掉**子进程退出码
   （JVM 退 1 还是 2，Gradle 一律自己退 1）。判据只能是日志/结果文件里的 `[Headless] RESULT verdict=…`。
2. **在服务端线程里不能调 `System.exit`**：会与原版注册的 shutdown hook **互相 join 成死锁** ——
   `"Server thread"` 在 `Shutdown.runHooks → ApplicationShutdownHooks.runHooks → Thread.join()` 等 hook 结束，
   而 `"Server Shutdown Thread"` 在 `MinecraftServer.halt(MinecraftServer.java:624) → Thread.join()` 等它结束。
   症状 = **判决行已打出、进程却一直挂着**（第一版就是这个问题，线程转储实证）。
   ⇒ 必须用 `Runtime.getRuntime().halt(code)`（不跑 shutdown hook ⇒ 不 join）。代价是不存档 —— 正是我们要的。

### 2.2 为什么必须用**生产**服务端（而不是 `gradlew runServer`）

- `runServer`（dev）**加载不了上游生产模组**：`cofh_core` 的 mixin `@Shadow m_21211_` 在它自己的
  refmap 里**没有条目**（实测 `mixins.cofhcore.refmap.json` 的 `LivingEntityMixin` 只有 5 条别的成员），
  dev 环境靠 SRG→named 重映射解析该名字 ⇒ `MixinApplyError` 崩服。生产环境按 SRG 名原生解析 ⇒ 只在 dev 犯病。
- 生产服务端还**同时**带来两个好处：跑的是**真正发给客户端的那个工件**（不是 dev classes），
  且环境与客户端同构（同 jar / 同模组 / 同世界，只少客户端渲染）。
- 一次性准备：`tools/headless-battery.sh --install`（下 Forge 47.4.10 安装器并装服务端，约 160 MB）。
- 实测速度：**单步 20 秒**（含起服）；dev 后端同样一轮 CORE 要 184 秒。

### 2.3 无头世界必须是**客户端存档的副本**

夹具的 `START_FOOT` 是**绝对坐标**（`(6,64,67)`、`(0,64,66)`、`(38,64,46)`、`(44,64,158)`…），
其中 `clear_retry` / `write_budget` / `scaffold` / `clear_guard` / `mine_regression` 这 5 个 CORE 步
**既无场景函数也无 `provision`**，完全依赖该坐标处已存在的世界地形 ⇒ 换个新生成的世界会让它们跑出**假红**。
脚本因此从固定客户端存档拷一份 `run/world-pristine` 作母本，每轮从母本复制、跑完丢弃。
场景数据包**每轮以仓库版为准**（母本里那份可能过期）。

**并且每轮清零 Alice 的全部持久化状态**（`world/data/alice_*.dat`：假人 / 转移账本 / 区域状态 / 权限 /
安全区 / 决策状态 / 收集授权 / 世界改动账本）—— 既为确定性，也为避开下面 §4 的起服崩溃。

## 3. 覆盖度评估（闸门答案）

### 3.0 首轮（修复前）：**N = 22**

**无头下能自动判红的步数 N = 22**（16 PASS + 6 FAIL，8 SKIP）⇒ 已超闸门 N ≥ 8，但**当时不可信**：
6 个 FAIL 里 4 个不依赖模组，而它们与"装不装模组"无关地全红 ⇒ 先查根因（见 §5）。

- 14 个 BASELINE 步里 **11 个 PASS**（`pathing` / `mine_regression` / `lumber_job` / `mine_job` /
  `scaffold` / `write_policy` / `clear_guard` / `clear_retry` / `write_budget` / `tool_supply` /
  `recoverability`）⇒ 需要真实移动、挖放的步骤在无头下确实跑通。
- 8 个 SKIP 全是模组依赖步（那一轮故意不装模组）⇒ 判决 `DEGRADED`，语义正确（T0-a 三态）。

### 3.1 修复后复测（模组齐全）：**N = 30，全绿**

```
[Regression] SUMMARY … (passed=30/30 skipped=0) ticks=3388 → PASS
entity_tick_missing 计数 = 47 → 0
[headless] verdict=PASS exit=0 用时=199s 进程退出码=0
```

⇒ **闸门彻底满足**：一条命令（`tools/headless-battery.sh core`）、无真人、判决机器可读、退出码可判红。
**并且这一次修复同时证明了 §5 根因判定是对的**：只改了"让票跟随"一处，30 步里 18 步由红转绿，
`entity_tick_missing` 从 47 条降到 **0 条** —— 修复前客户端那轮 30/30 是**真人补齐了票**，
修复后无头（没有真人）也能独立跑绿。

### 3.1 关于"光用服务端行不行"

**行**。假人 `BotPlayer extends ServerPlayer`，用 `EmbeddedChannel` 假连接经 `PlayerList.placeNewPlayer`
真注册；`observer` 全仓库 86 处调用点**全部**有 `observer != null` 守卫 ——
"没有真人观察者"是既有设计支持的，不是无头入口的补丁。
**唯一**真正需要 observer 的只有 `CapabilityGateCheckTask` 的 `foreign_break_attribution`，
而它要的**不是"真人"**、是"**另一个玩家实体**"（`ScopeBuffer` 只看 `event.getPlayer().getUUID()`
与 owner 是否相等，不查 `PlayerList`）⇒ 无头入口生成一只 Forge 合成玩家充当 observer 即可，
取不到就**如实降级**（该用例自述 `premise_no_observer`），不静默假装成功。

## 4. 顺带发现（独立于 T2）

### 4.1 装 WorldEdit 时专用服务端**起服即崩**

`BotManager.onServerStarted → restoreFromWorld → spawn` 在 `ServerStartedEvent` 里**同步**生成玩家
⇒ `PlayerList.placeNewPlayer → sendCommands → 逐命令节点 canUse → ForgeAdapter.adaptPlayer
→ WorldEdit ForgePlayer.<init>`，该构造器执行
`ThreadSafeCache.getInstance().getOnlineIds().add(this.getUniqueId())`（**字节码 line 69**），
而此刻 **WorldEdit 自己的 `ServerStartedEvent` handler 还没跑**（缓存未初始化 ⇒ 不可变集合）
⇒ `UnsupportedOperationException` ⇒ **打死服务端 tick 循环**（crash-report 实证）。

**触发条件**：装 WorldEdit + 存档里有假人（`world/data/alice_bot.dat`）。
**根因**：在别人的 handler 之前假定它已完成初始化。**修法**：把恢复延到首个 server tick。

### 4.2 `craft_check` 的门禁缺口（缺模组时应 SKIP 而非 FAIL）

`CraftCheckTask` 的 `machine_only_vanilla` 用例**期望** `minecraft:cobblestone` 被判 `MACHINE_ROUTE`，
而那需要装了 Mekanism/Create（它们给了 `crushing`/`milling`/`enriching`）。
同文件 ⑥ 的 `machine_only` 用例已经写了"没装该模组就 SKIP"，④ 漏了同样的**前提声明**
⇒ 没装模组时它 `FAIL` 而不是 `SKIP`。属 T0-a 那族（环境相关断言不声明自己）。

## 5. 根因：**假人的玩家区块票冻结**（本轮最重要发现）

### 5.1 事实

1. 装了模组后 CORE 掉到 `(passed=12/30 skipped=0)`，并打出 **47 条**
   `[Bot] entity_tick_missing … entityTicking=false connTicks=0`。
2. 失败清单与"距出生点多远"**一一对应**：出生点 `TicketType.START` 只覆盖 **Chebyshev d≤9（entity-ticking）
   / ≤11（loaded）**，10/10 采样吻合；z≈300–420（chunk 19–26，d=15~21）的步骤**全灭**，
   ≤8 格的步骤**全绿**（含 `pathing`，它被传送回出生区附近、d=2）。
3. `transfer` 的失败点被钉到机制：规划**成功**（`[PathRetry] planned status=REACHED`），
   随后 `segment_stall … delta=0.0000 input=forward=1.00` ⇒ **规划没问题、物理没跑**。
4. `craft_furnace` 的炉子：料和煤**都进去了**（`input_and_fuel_placed=true`），
   但 `litTime=1600` 连续 400 tick 不掉 ⇒ **方块实体根本没被 tick**，不是"烧了但断言时机不对"。

### 5.2 机制（字节码核对，非推测）

- 1.20.1 里玩家票（`TicketType.PLAYER`）**只由客户端上行移动包推进**：
  `ServerGamePacketListenerImpl.handleMovePlayer → ServerChunkCache.move → ChunkMap.move →
  DistanceManager.removePlayer/addPlayer`。`ServerLevel.tick` / `MinecraftServer` **都不调**它。
- 假人的连接是 `FakeConnection`（netty `EmbeddedChannel`）：收不到移动包，
  且**不在 `ServerConnectionListener` 的连接表里 ⇒ `tick()` 永不被调用**（日志 `connTicks=0` 实证）。
- ⇒ 票**冻结在"假人第一次被 track 时的位置"**，永不跟随。Alice 侧**零补偿** ——
  `bot/` 里没有任何 `setChunkForced` / `addRegionTicket` / `ChunkMap` / `ServerChunkCache.move` 调用。
- 传送只给 **5 tick** 的 `POST_TELEPORT` 票（`DistanceManager.addRegionTicket` 的 level = 33 − 1 = 32，
  够不着 entity-ticking 的 31）；Alice 自己的方块读产生 `UNKNOWN` 票（level 33、timeout 1）
  ⇒ 恰好是"**加载着但不 ticking**"。

### 5.3 为什么客户端一直没暴露

客户端跑电池时**真人站在夹具区**（实测登录坐标 `(62.3, 64.0, 310.7)` = chunk (3,19)），
`view/simulation-distance=10` ⇒ 真人的 PLAYER 票**同时**提供了加载与 entity-ticking，把整个夹具区覆盖了。
**"客户端 30/30 全绿"是被真人的存在掩盖的，不是环境无关。**

### 5.4 顺带纠正 D-176

D-176 附注一写"`ServerPlayer.doTick()` 的唯一调用者是 `ServerGamePacketListenerImpl`
⇒ 假人物理挂在连接 tick 这条链上"。**字节码事实是**：`doTick()` 用 **`invokespecial`** 调父类
`Player.tick()`，**不会派发回 `BotPlayer.tick()`**；驱动假人物理的是**实体 tick 表**（虚拟派发）。
⇒ 真正的门槛是"**所在区块是否 entity-ticking**"，不是连接 tick。
这解释了"补连接 tick"这条方向为什么一直没能消掉症状。

### 5.5 修复与验证

- `BotPlayer.syncPlayerChunkTicket()`：`SectionPos` 变化时调 `serverLevel().getChunkSource().move(this)` ——
  **`ServerChunkCache.move(ServerPlayer)` 是 `public`，正是真人 `handleMovePlayer` 走的那一条链**
  ⇒ 假人与真人在"持票"这件事上等价，不是给无头开小灶。
- `BotManager.onServerTick` 每 tick 对每个会话先调一次（放在最前：票不跟随 ⇒ 后面所有"设输入/跑任务"都会落空）。
- 诊断量：`entity_tick_missing` 告警行新增 `ticketSyncs=`，用于区分"没同步过"与"同步了但依然冻结"。

**验证等级 `SERVER_TESTED`**（无头 CORE，全模组）：`(passed=30/30 skipped=0) → PASS`；
`entity_tick_missing` **47 → 0**。**尚未做客户端验证**（改动落在 `BotPlayer`/`BotManager` 的核心 tick 路径上，
必须按项目纪律跑一轮客户端：看是否出现双倍物理 / 回弹 / 传送被拽回）。

### 5.6 未决

## 2. 根因判断（这一节是「判断」，不是事实）

**判断**：用户说的"**做一点又改规则、做一点又重新定义方向**"，其**机制性根因不是纪律问题，而是
"验证的单位成本"**。

推理链（每一步都由 §1.2 的事实支撑）：

1. 现存唯一回归信号要**真人 + 客户端 + 2~4 分钟 + 一次手工 jar 同步** ⇒ **改动的验证成本极高**；
2. ⇒ 验证被**批处理成"轮次"**，于是**"轮次"变成了实际的规划单位**；
3. ⇒ 计划自然漂向**"这一轮能验证什么"**，而不是"主线需要什么"——
   这正是 **台账的自我生成性质**（`⑬→⑨→⑭→⑮→⑯`，每环局部可验证、永远有货）；
4. ⇒ 规则只能活在**散文**里（139 条决策），**散文不会让构建失败** ⇒ 改规则零成本、改代码高成本
   ⇒ **规则的自由度远大于代码的自由度**，于是规则被反复重议（241 次修正）；
5. ⇒ 第一版实现的错误只能等到"轮次"才暴露 ⇒ `fix : feat ≈ 1 : 1`。

**反证/需要公平说的**：

- 本项目**明确禁止**"AI 自行拍板"、**要求用户最终决策**，所以"规则变动"有一部分是**正常的协作成本**，
  不是失控；
- 决策**修正留痕**（附注 117 处）是**正面**的工程纪律，不该被当成债务；
- §1.3 的高返工率与用户 §0 的"原创、无借鉴"**互为解释**：没有上游可抄的地方，第一版本来就容易错。

**⇒ 结论**：要打断这个循环，**不能靠"更强的纪律"**（纪律已经很强了），
只能靠**把验证的单位成本降下来**。这是 §4.1 里 T0/T2 的由来。

## 4. 结论：**要提升优先级的是"证据层"，不是任何功能**（判断）

**判断**：把 §1–§3 的事实合起来，Alice 当前的瓶颈不是"缺功能"，也不是"缺纪律"，而是

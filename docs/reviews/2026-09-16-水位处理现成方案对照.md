## 0. TL;DR（这条最重要）

**Baritone 没有 `MovementSwim`。** 它的 `movements/` 目录只有 8 个类
（`Ascend / Descend / Diagonal / Downward / Fall / Parkour / Pillar / Traverse`），水位处理分散在三处：

1. **合法位置集**：一条 `canWalkOn` 例外 —— "**下面是水、且我这一格也是水**" ⇒ 水格**算支撑**（= 你能浮在那里）；
2. **成本**：脚位或头位是水 ⇒ 这一格走用 `waterWalkSpeed`（无附魔时≈陆地走的 **2.0 倍**）；
3. **执行**：**复用 `MovementTraverse`**，只是把 `JUMP`/`SPRINT` 用在水里（没有新 Movement、没有新执行器）。

⇒ 我原先判断的"丙（合法位置集 + 成本模型）最贵"要**下调**：Baritone 的对应机制是**一条谓词分支 + 一个成本常数 + 两行输入**。
外部实现同样没有"游泳 Movement"这一层抽象（见 §3）。

## 1. Baritone 事实（本地参照 `reference/baritone`，HEAD `64333af`）

### 1.1 合法位置集：水格什么时候算支撑

`pathing/movement/MovementHelper.java:432-448`（`canWalkOnPosition`）：

```java
if (isWater(state)) {
    BlockState upState = bsi.get0(x, y + 1, z);
    if (up == Blocks.LILY_PAD || up instanceof CarpetBlock) return true;
    if (isFlowing(x,y,z,state,bsi) || upState 是流动水)
        return isWater(upState) && !assumeWalkOnWater;      // 流动水：只有"在静水下面"才算
    return isWater(upState) ^ assumeWalkOnWater;            // jesus 关 ⇒ 上面也是水才算
}
```

要点（**与 Alice 的差别就在这一条**）：
- 水格算支撑的**条件不是"水深"**，而是"**上面那格也是水**"；
- 于是"浮在水里"（脚位是水、下面也是水、上面还是水）**天然是合法位置**；
- 水面那一格也成立：脚下是水格、而那个水格的上面（= 你这一格）是水；
- 单层水（水下面是实心）走的是**普通的 `canWalkOn`（实心支撑）**分支 —— 不需要例外；
- `assumeWalkOnWater`（jesus，默认 **false**，`api/Settings.java:162`）打开时才会"踩在水面上"，并且
  上面注释写明"**上面有水的格** 与 jesus 互斥"；
- 荷叶/地毯另有白名单。

### 1.2 成本：水速

- `api/pathing/movement/ActionCosts.java:25-26`：`WALK_ONE_BLOCK_COST = 20/4.317 ≈ 4.633`、
  **`WALK_ONE_IN_WATER_COST = 20/2.2 ≈ 9.091`**（≈ 陆地 1.96 倍）；
- `pathing/movement/CalculationContext.java:135-152`：`waterSpeedMultiplier` 由
  `Attributes.WATER_MOVEMENT_EFFICIENCY`（深海探索者/海豚的恩惠）决定，然后
  `waterWalkSpeed = WALK_ONE_IN_WATER_COST*(1-m) + WALK_ONE_BLOCK_COST*m`
  ⇒ **无附魔时 m=0 ⇒ 就是 9.091**（社区补丁 `take depth strider into account for water speed, fixes #101` 也是这条）。

### 1.3 生成与执行：全靠 `MovementTraverse`

- `movements/MovementTraverse.java:82-101`（成本）：`frostWalker || canWalkOn(destX, y-1, destZ)` 分支里，
  若 `isWater(pb0) || isWater(pb1)`（头/脚是水）⇒ `WC = context.waterWalkSpeed; water = true;`
  ⇒ 并且 `if (!water && !sneaking && canSprint) WC *= SPRINT_MULTIPLIER`（**水里不享受冲刺折扣**）。
- `:154-162`（桥/放置分支）：`if (!standingOnABlock) return COST_INF; // standing on water / swimming`
  ⇒ **浮着的时候不能"往回垫方块"**（背放不可行）—— 这条对 Alice 有意义：水里放置要有自己的口径。
- `updateState`：脚低于目的地 ⇒ `setInput(Input.JUMP, true)`（`:46-48` 那段）；
  `(!isLiquid(feet) || sprintInWater)` ⇒ `setInput(Input.SPRINT, true)`（**`sprintInWater` 默认 true**，`Settings.java:809`）。
- 执行期的"别走进流体"：`MovementHelper:350-360 avoidWalkingInto` **把所有流体都算进去**，
  但 Traverse 执行处对水**显式放行**：`(!avoidWalkingInto(intoBelow) || isWater(intoBelow))`。

### 1.4 相关但不同的两条（Alice 已有自己的决策）

## 2. Alice 现状（对照表）

| 环节 | Baritone | Alice 今天 | 差距 |
|---|---|---|---|
| 水格算不算支撑 | 上面也是水 ⇒ 算（§1.1） | `MovementHelper.canWalkOn:52`：`below.getFluidState().isSource()` ⇒ **源流体一律不算支撑** | **缺这一条例外**（深水/浮着都不是合法位置） |
| 单层水（蹚水） | 走普通实心支撑分支 | `canWalkOn` **本来就算得出来**（脚下是实心） | 差距**只在目的地生成**：`core/search/SurfaceMovementProvider.java:126-128` 一律 `continue` 掉"目的格/头格是流体" |
| 水里的成本 | `waterWalkSpeed` ≈ 2.0× | `CostModel` 无水位项（`TRAVERSE_COST = 1.0`） | 缺一个成本项（可归一化推导：`1.0 × 9.091/4.633 ≈ 1.96`） |
| 执行 | 复用 Traverse + JUMP/SPRINT | `TraverseExecution` 无水位分支；**完成口径**：中间段 `COLUMN` 只要求"脚位格正确 + y 落差 < 0.5"（水里有救），最终段 `EXACT` 要求 `isSettledAtFootPos` ⇒ **要求 `onGround`** | 最终段若以水格收尾会永远不成立（D-244 已在水柱那档确立"脚位到格即成功"的口径，这里要同样处理） |
| 逃生落点 | — | `SurvivalSystem.isRefuge:422-431` **显式要求脚/头位非流体**（"水会淹"） | **不动**：这条是"逃生落点必须干燥"的语义，与"水里能不能走"是两件事 |
| 危险方块 | `avoidWalkingInto` 含流体，Traverse 处对水放行 | `MovementHelper.avoidWalkingInto:171-180` **不含水**（只列岩浆/火/岩浆块/仙人掌/甜浆果/末地门/蜘蛛网/气泡柱） | 水的可穿性 Alice 已经是通的 ✓ |

**脚位口径**：`MovementHelper.footCell:271-283` 对水格返回"脚所在格本身"（水的碰撞形状为空 ⇒ `supportTopY` = NaN）
⇒ 不依赖 `canWalkOn`，这条改动**不会**打乱 `footCell`。

## 4. 建议的切片（判据都可红 + 反向对照）

### 切片 A：**蹚水**（浅水 = 脚位是水、底下是实心）
- 改动面：**只有目的地生成**（`SurfaceMovementProvider:126-128`）：流体目的格/头格**只有"水"放行**，
  岩浆等危险流体仍然一律跳过；具体合法性交给既有的 `canStandCentered`（它已经会把"底下是流体"的格子挡掉）。
- 成本：`CostModel` 加水位档（推导见 §2：≈ **1.96 ×** 陆地走；对角线同理乘 1.33）。
- 判据：新场景"1 格深水沟横在 bot 与目标之间" ⇒ 改前规划**绕行或失败**、改后**直穿**；
  反向对照：把成本项与放行条件分别取反 ⇒ 各自精确变红。CORE 是回归闸门。
- 收益：过水沟/溪流/浅水坑；**不**涉及合法位置集，风险最小。

### 切片 B：**深水浮着（= Baritone 那条例外）**
- 改动面：`MovementHelper.canWalkOn` 加"下面也是水且上面也是水 ⇒ 算支撑"（对齐 §1.1）；
  `TraverseExecution` 的**完成口径**按 D-244 的水位口径处理；执行期按需 `JUMP`（脚低于目标/保持浮着）。
- 判据：新场景"3 格深水池，bot 从水里游到对岸" ⇒ 改前"水里那格不是合法位置 ⇒ 规划不出"、
  改后能规划 + 端到端到达；反向对照取反 ⇒ 精确变红。
- **边界（不动）**：`isRefuge` 仍要求干燥（逃生落点语义）；落水不摔伤仍是 D-058 的"不做"；
  水里放置要单独口径（Baritone 在浮着时直接 `COST_INF`）。
- 风险：`canWalkOn` 是**全局谓词**（目标准入、挖掘站位、`isRefuge` 都读它）⇒ 必须整轮 CORE + 单步夹具。

**不做**：为水位新造 `MovementSwim`（Baritone 没有、外部实现也不是这么做的）；也不动 D-076（本轮不涉及任何写授权）。

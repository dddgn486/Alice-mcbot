## 2. 缺陷①：夹具时机基准失效（代码 + 日志双证）

### 2.1 代码事实

`SceneCheck` 的 `wallTick` / `disturbTick` 在表里写 **30**：

```java
new SceneCheck("place_course+wall",    …, Kind.EXECUTE_COMPLETE, 30, 0, …)   // 注释："计划前方封路"
new SceneCheck("place_course+disturb", …, Kind.EXECUTE_COMPLETE, 0, 30, 0, 1, …)
```

但 `tickFixtures()` 用的是**任务级** `ticks`：

```java
if (scene.wallTick() > 0 && !walled && ticks >= scene.wallTick()) { … }
```

`ticks` 在 `tick()` 里 `++`，**只有总预算判据用它**，`prepare()`/`advance()` 都**不复位**它。
`git log -S` 证明它**从引入就是这样**（`176486c`，D-054，串联回归扩到 11 项），不是后来被改坏的：

```
git log --oneline -S "disturbTick" -- src/main/java/com/dddgn/alice/task/PathingRegressionTask.java
⇒ 176486c feat(kernel): 疾跑门控（D-053）+ 串联回归扩到 11 项（D-054）
```

而 `30` 这个**值**的来源，是**每次运行从 0 起算**的两个同族夹具：

| 出处 | 计数器 | `30` 的真实含义 |
|---|---|---|
| `PathingDisturberItem.DISTURB_TICK = 30` | —（注释："在执行**中途**把 bot 平移 1 格"） | 走了一半 |
| `PathSessionDiagnosticTask.ticks` | **任务内自增** | "本次寻路开始后第 30 tick" |
| `docs/AI_TEST_MATRIX.md:87` | — | "普通右键（**第 30 tick** 在计划前方封路）" |

⇒ **常量被搬过来了，基准没有**：同一份语义在两处实现里**分叉**。

## 3. 修法（`PathingRegressionTask`，夹具层）

1. **加场景局部基准** `private int sceneTicks`：runner 建好（=本场景开始执行）那一刻置 0，
   每个执行 tick `++`；`tickFixtures()` 一律用它。`ticks` 保留给总预算，并加注释禁止再拿它做场景内时机。
2. **声明了夹具就必须真的动手**：场景判据新增
   `wallTick>0 ⇒ walled`、`disturbTick>0 ⇒ disturbed`，否则该场景 `FAIL`，detail 带
   `/FIXTURE_NOT_FIRED=[wall]` 或 `[disturb(no_valid_cell)]`。
3. **删掉静默降级**：旧代码扰动找不到落点时 `disturbed = true;` —— **没传送却当成做过**，
   场景会退化成普通 `place_course` 却照样报 PASS。改为 `disturbGaveUp` + `warn`
   （`disturb_not_applicable`）并让本场景判 FAIL。
4. 日志可判读：`wall_placed … sceneTick=30 pathIndex=3/9`、`disturbed … sceneTick=32`、
   场景开始行补打 `wallTick=/disturbTick=`、结果行补 `/sceneTicks=`。

**修复后（隔离跑，2 轮逐字相同，`ticks=493`）**：

```
[Regression] wall_placed scene=place_course+wall    at=5, 64, 66 sceneTick=30 pathIndex=3/9
[Regression] scene=place_course+wall    result=PASS detail=COMPLETED/replans=1/minReplans=1/route=TRAVERSE,DIAGONAL,FALL,PLACE_STEP_AND_TRAVERSE/sceneTicks=73
[Regression] disturbed   scene=place_course+disturb from=4, 64, 66 → 4, 64, 67 sceneTick=32
[Regression] scene=place_course+disturb result=PASS detail=COMPLETED/route=TRAVERSE,FALL,PLACE_STEP_AND_TRAVERSE/sceneTicks=69
```

变化是真的：`+wall` 的路线**从含 `ASCEND` 变成不含**（`TRAVERSE,ASCEND,DESCEND,…` → `TRAVERSE,DIAGONAL,…`），
墙从"起点前方第 2 格"变成"**走到第 3/9 格时**在前方第 2 格"。

> **与历史红的关联：只是推测，不声称因果。** 历史红之一是 `+wall` 报 `ASCEND_NO_HEADROOM`，
> 而**修复前该场景路线恰好含 `ASCEND`**、修复后不含 ⇒ 这是"夹具把 bot 逼进一条它本不该走的 ASCEND 绕行"
> 的合理怀疑。但**没有**留下当时的日志（见 §1），**无法证明**，故不写成结论。

## 4. 缺陷②：`DIAGONAL` 覆盖是偶发凑出来的（修 ① 之后电池先变红）

修完 ① 后全量 `core` **2/2 FAIL**：

```
pathing=FAIL … coverage=FAIL([DIAGONAL])
executed=TRAVERSE,ASCEND,DESCEND,DOWNWARD,PILLAR,FALL,BREAK_AND_TRAVERSE,BREAK_AND_ENTER,PLACE_STEP_AND_TRAVERSE
(passed=29/30 skipped=0) ticks=3386 → FAIL
```

**根因（代码事实）**：`REQUIRED_COVERAGE` 要求 9 种可执行 Movement 各被执行过至少一次，但
**没有任何场景是"真的会执行对角线"**：

- `dip_course` 的地形注释**明写**标定路线是 `TRAVERSE + DIAGONAL + DIAGONAL + TRAVERSE`，
  可它注册成 `Kind.PLAN_FIRST_TRAVERSE`（**只规划、不执行**）⇒ 不进 `executedUnion`；
- `lava_course` 也是只规划（首步 `DIAGONAL`）；
- 于是 `DIAGONAL` **只**来自 `+disturb` 修前那条偶发绕行（`0,64,67 → 1,64,66` 的斜向回归）。

⇒ **覆盖断言此前是靠运气过的**；① 让那条绕行消失，断言就如实报缺。

**修法**：加一行复用同一份地形的执行场景（`+` 后缀在 `prepare()` 里取 `dip_course_terrain`，无需新数据包文件）：

```java
execute("dip_course+run", new BlockPos(0, 64, 66), new BlockPos(-1, 64, 63), false,
        MovementType.TRAVERSE, MovementType.DIAGONAL),
```

实测（隔离跑）：

```
[Regression] scene=dip_course+run result=PASS detail=COMPLETED/route=TRAVERSE,DIAGONAL/sceneTicks=20
[Regression] SUMMARY … dip_course=PASS dip_course+run=PASS … coverage=PASS
executed=TRAVERSE,DIAGONAL,ASCEND,DESCEND,DOWNWARD,PILLAR,FALL,BREAK_AND_TRAVERSE,BREAK_AND_ENTER,PLACE_STEP_AND_TRAVERSE
```

`dip_course`（只规划，断言 `first=TRAVERSE`/Q7 路线偏好）**保留不动** ⇒ 两个断言都在，且对角线变成**确定性覆盖**。

## 5. 缺陷③：无头通道并不"无噪声" —— 敌对生物会杀 bot / 推 bot（**本轮最重要的通道事实**）

修 ① 之后、确认 ② 的那一批 `core` 里，第 1 轮**不是断言失败，而是没有判决**：

```
[alice] [R4 Session] failed session=regression-place_course+wall-0 status=MOVEMENT_FAILED code=PLACE_NO_VALID_FACE index=1 actualFoot=1, 64, 66
[PathRetry] replan attempt=1 … feet=1, 64, 66
… session …-1 failed code=TRAVERSE_INVALID_PRECONDITION index=0 actualFoot=… (feet=1, 64, 68)
[Regression] wall_placed scene=place_course+wall at=3, 64, 68 sceneTick=30 pathIndex=0/8     ← 墙被放到 z=68（起点是 z=66）
[alice] 假人死亡: Alice was blown up by Creeper → 直接清除
[Headless] RESULT verdict=no_verdict exit=3 ticks=3259
```

**读法**：bot 先被**推离预期格**（`z=66 → 68`，于是 `PLACE_NO_VALID_FACE`、
`TRAVERSE_INVALID_PRECONDITION`、墙被放到 `z=68`），随后被**炸死** ⇒ 电池无判决。
**这不是断言失败，是环境噪声。**

### 5.1 事实

| 项 | 事实 | 出处 |
|---|---|---|
| 无头服务端难度 | `difficulty=easy`、`spawn-monsters=true`、`pvp=true` | `/home/fb486/alice-server/server.properties` |
| 夹具是否会生成敌对生物 | **不会** —— 场景函数只 `summon minecraft:marker`，代码只 `summon minecraft:item`（掉落物播种） | `grep -rn "summon" tools/test-scenes/ src/main/java` |
| 代码是否依赖难度 | **不依赖**（全仓零 `getDifficulty`/`Difficulty.` 命中） | `grep -rn "getDifficulty\|Difficulty\." src/main/java` |
| 死亡后果 | `假人死亡 → 直接清除` ⇒ 任务消失 ⇒ `verdict=no_verdict exit=3`（**不是 FAIL，是"没有判决"**） | 上面日志 |

⇒ 怪物来自**环境**（自然生成 / 存档母本自带），**不是**被测行为的一部分。

### 5.2 修法（**改环境，不改生产代码**）

`tools/headless-battery.sh` 在启动前把**无头服务端自己**的 `server.properties` 设成
`difficulty=peaceful` 并打印一行 `夹具洁净度：difficulty=…`。理由：
- 脚本本来就**拥有**这个服务端目录（它做 `--install`、拷世界、装数据包、清 `alice_*.dat`）⇒ 环境是它的职责；
- `peaceful` 会**连存档里已有的**敌对生物一起清掉（`spawn-monsters=false` 做不到这点）；
- **不碰客户端存档、不碰 `mods/` 之外的任何东西、零生产代码改动**；
- 反过来说：**这一行也让"隔离跑"和"全量跑"之间少了一个不可见变量**。

### 5.3 为什么它是"历史 3 红"目前**最强的**候选（但仍不声称已证）

`place_course+wall`（`ASCEND_NO_HEADROOM`）、`place_course+disturb`（`STALE_START`）、
`partial_search`（起点 `from.z` 差 2 格）—— **三个症状的共同点都是"bot 不在预期位置"**，
而本轮**直接拍到**了"怪物把 bot 推离预期格"这条机制（`feet=1,64,68` + 同轮死亡）。
但：那 3 红的日志已随 `/tmp` 丢失（§1），**无法复算** ⇒ 记为**强候选，未证**。


## 6. 遗留 / 待确认（**没有**顺手改）

1. **1 格横向漂移不触发漂移检测，被控制器"走回去"吸收**：修复后 `+disturb` 在 `sceneTick=32` 把 bot

   "移动控制器把 bot 拉回目标格"，**不是** `PathSession` 的重同步、也不是重规划。
   与 skill 已登记的偏离（`alice-baritone-kernel-alignment`：漂移检测用 `低于最低脚位 >1 格 / 离两端 >3 格`
   **距离启发式**，标注"临时实现，待改为 Baritone 的 `getValidPositions().contains(feet)`"）是**同一处**：
   `>3 格` 阈值让 1~3 格横向漂移**绕过**漂移检测。本次结果正确 ⇒ 不改，但建议单独立项按 Baritone 对齐。
2. **历史 3 红**：现在有 3 个候选（起步位置 ✗ 已实测排除、夹具时机 ①、怪物 ③），
   **没有一个被证明**；台账按"**不复现 + 三个候选**"更新，**不**宣布修好。
3. **`PathSessionDiagnosticTask`（物品流）的同类静默降级仍在**：找不到扰动落点时打
   `[R4 Fixture] disturb_skipped`（info）后**继续跑**，用户看不出来"这次没测到扰动"。
   本轮**没动**（属客户端物品入口，改动需再一轮客户端验证）；记为待办。
4. **怪物只在无头通道被清零，客户端仍是 `easy` 有怪物**（有意不同构，见 §5.2）⇒

   `kill @e[type=#minecraft:hostile, distance=…]`）？代价：夹具开始改世界的实体，
   且要再走一轮客户端验证；收益：用户手点的那一轮不再被怪物随机判红。
5. **食物/疾跑门控是否也构成"长跑 vs 短跑"的第二条不可见变量**：本轮**没有**证据 ——
   全量日志里 `sprint|food|hunger` 命中 **0 行** ⇒ 无法从日志判定，仅记为**待测猜测**，未动。

## 2. 事实核校（外部主张 vs 代码事实）

| 主张 | 代码事实（可复核） | 判定 |
|---|---|---|
| "服务端硬实现客户端像素级位移"／"没有 Baritone 级内核" | `bot/BotControllerExample.java:6,31,59`：架构是**输入驱动**（设 `zza/xxa` → vanilla `super.tick()` → `travel()`），与 Baritone 同套路；内核按 **D-036** 对齐，R2-C/R3/R4 均有客户端验证 | **前提驳回**；底层担忧的部分残留见下 |
| 残留真问题（AI 补充） | 朝向/旋转同步粒度（曾踩 D-029 头部同步 bug）；无客户端插值 ⇒ 观察者可能看到抖动；N 个 bot 的**服务端 tick 预算** | **接受为真问题**（属同步/呈现，非物理失真） |
| "每个动作六道大工序" | `WriteGrant`(D-082) 在调用点构造；`MiningBudget`/`WorldModLedger` 分布在 36 个文件；但**没有任何人工逐动作审批**；`/alice ask` 只用于**未知模组能力** | **方向对、数字夸张** |
| "45 个测试 Item 的无菌温室" | item 77 个文件（夹具约 45）；**场景 102 个 / 电池引用 8 个**；砍树**无**搭柱/下挖 | **部分成立**（真问题=只增不减 + 无能力分级） |
| "砍树必须反向用向下挖实现" | 代码中无 `PILLAR/DOWNWARD`；高树干走 **`trunk_too_tall` 诚实拒绝** | **事实不成立** |

**关于"挖脚下"的核校（AI 上一轮说错，此处更正）**：
- `DownwardExecutionFactory.validate`：要求几何正下方 1 格、**落点 `canWalkOn` 且身体/头部可通行**、脚下方块可破坏 ⇒ **不禁止挖脚下**，只要求"挖完能站住"。
- `PillarExecutionFactory`：放置格脚下须有支撑面、不能是底部半砖（Baritone 同款 `COST_INF`）⇒ 这是**游戏物理前提**，不是安全政策。
- `RecoverabilityPolicy`：`FALL` 必须带 `fall_return_verified`（PILLAR 的返回守卫产出），否则**规划期抛异常** ⇒ 这才是硬约束（"上去必须有验证过的下来办法"）。
- **选择性的部分**：`PathRequest.allowedMovementTypes`（每请求集合）；`miningApproach` 显式去掉 `PILLAR/FALL/DOWNWARD`（D-067㉘）。

**拆除管理的现状（回答 §1.5-2）**：`RestoreScopeTask` 三条纪律（自上而下 / 只拆自己放的 `not_ours`／不许沿途挖地形）+ **两条拆除路径**（① 站上去→向下拆 `APPROACH+DESCEND+DOWNWARD`；② 侧拆兜底 `SIDE_BREAK`，用于悬空桥面——此时内核正确拒绝 `DOWNWARD`）+ 材料回收（`ScopeBuffer.begin` + `CollectDropsTask`，D-099 教训）。**账本只记放置**（只有 `recordPlacement`，无 `recordBreak`）⇒ 挖掉的自然方块不要求恢复；每条放置带 `Policy.TEMP`（必须配对拆除）/`Policy.KEEP`（不该拆），**目前由调用点各自写**。

**"任务级授权"框架（回答 §1.5-3）**：确实已有——`action/WriteGrant.java`（D-082，**唯一**写入凭证，`requester + reason`），其注释**明确反对任务级开关**（"许可会泄漏到该任务的所有子请求……并让预算无法归因"）；任务级的**归集**由账本 scope 承担（`openScope/closeScope`）。

| ③ 无菌温室 | **部分接受** | 夹具=单元测试本体没错；真问题=**无能力分级**（DEMO/BETA/PROD）+ 无自然地形随机测 + 场景只增不减（8% 被电池引用） |

| 破局方案③单向流（放置不回收） | **接受一半** | 工作区免 RESTORE、保护区必须（＝策略表 `TEMP/KEEP`） |
| 破局方案④扁平状态机 | **部分接受** | 嵌套深度上限 + 禁止跨层提权（=把嵌套审批压平），不取消任务层 |
| 破局方案⑤不记账 | **驳回** | 账本是"服务端是真相"的证据链，也是夹具**零写入自证**的依据 |

## 6. AI 自身错误与可复发模式（教训清单）

| 错误 | 复发模式 | 对策（已落地） |
|---|---|---|
| 把"禁止挖穿脚下"当硬约束陈述 | **把 policy 当 invariant 说** | 陈述约束前必须区分：物理前提(硬) / 可逆性保证(硬) / Movement 集合(策略)；**引用代码位置** |
| 提出"任务级一次授权" | **不了解既有决策就提新方案** | 提方案前先查 `AI_DECISIONS` 相关编号（本轮撞上 **D-082**） |
| 多次"估算上下文"并据此提前收尾 | **凭感觉代替测量** | 禁止估算；要时跑 `dsh-context-usage.sh`（§1.3） |
| 夹具负例写死物品（基岩/命令方块）导致假红两次 | **把"我以为"当前提** | 负例前提**运行时自证**（`firstUnproducibleItem`）；前提自证用 `FixturePremise` |
| 同一夹具连请用户测 3 次 | **修复不批量** | §5.0e 第 3 条：攒到一次再测 |
| 规则改了 `AGENTS.md` 却漏改 `PLAYBOOK`（数字漂移） | **多处复述** | 单一出处（数字只在 `AGENTS.md`） |
| 探针"先加后忘回收" | **临时入口无登记** | 探针生命周期：先探→验证→**立即回收**（转电池步或删入口）；`check-fixture-hygiene.sh` 兜底（待实现） |

**方法论收获（值得保留的好经验）**：
1. **自证的负例能当断言用**——它抓出了真 bug（`machineTypes` 未按目标过滤 ⇒ 无配方物品被误判"机器可产"）。
2. **能力升级要同步扫夹具断言**——凡改查询层/发现器语义，先扫依赖该语义的夹具（本轮因此少走一轮弯路）。
3. **只读先于执行**（S0→S1→S2）——本轮对 Mekanism 的适配零误伤，全靠"问上游 + 自校验"。
4. **量化审查优于感觉**——§1.4 的数据（102 场景 vs 8 引用、62 处待验证）直接指出了病位。

## 1. 事实：同一份「准入契约」被写了 3 遍，没有单一真相源

`canWalkThrough(` 在 `src/main/java/com/dddgn/alice/pathing/` 下共 **91 处调用点**，分布在**三层**：

| 层 | 文件 | 角色 |
|---|---|---|
| 规划期（生成器） | `core/search/SurfaceMovementProvider.java` | 决定**图里有没有这条边** |
| 执行期校验 | `core/*ExecutionFactory.java`（9 个） | 构造 `MovementSpec` 前再查一遍 |
| 执行期逐步断言 | `core/*Execution.java`（9 个） | 每 tick 推进时再查 |

9 类移动 × 3 层 = **27 处契约实现**（`Traverse / Diagonal / Ascend / Descend / Pillar / Fall /
BreakAndEnter / BreakAndTraverse / PlaceStepAndTraverse`），**没有门禁断言三者一致**。

⇒ 任一层漂移，另外两层和所有文档都不会失败。**今天的缺口正是第 1 层比第 2/3 层更严**
（`BreakAndEnterExecution.collectBlockers:69-78` 会收头位；生成器却不放行头位被挡的目的地）。

## 2. 事实：散文"承诺语"一共 10 处，每一处都无门禁

```
与执行器完全一致   1     共用同一       1     共用唯一定义   2
同一个 helper      1     可规划即可执行  4
```

数量不多，但**全是无门禁的口头契约**。今天破的就是最典型的一处：

- `SurfaceMovementProvider:152-155` 注释：「对照 Baritone `positionsToBreak = {to.above(), to}`：
  目的地被占用时，先破坏目的地**躯干 + 头位**，再走进该格」
- `BreakAndEnterExecution:69-78`：**确实**收躯干 + 头位
- 而 `:169` 的入口闸门**只查躯干** ⇒ 文档与代码**自相矛盾**，且矛盾在注释的下一屏

**元原因（比"谁不小心"精确）**：谓词 `canWalkThrough(pos)` 的**名字比语义宽**
（读起来像"人能走过去"，实际只查**单格**；行人需要两格）。这类"名字宽于语义"的谓词
一旦被放进**闸门位置**，就会静默地砍掉一整类边。

## 4. 事实：缺的是一条「逆向不变式」

现有门禁与代码只保证**健全性（soundness）**：
> 可规划 ⇒ 可执行（`MovementSpec.validateDisplacement` 甚至**硬抛**；D-336 那次真机崩服就是它拦下的）

**没有**任何东西保证**完成性（completeness）**：
> 执行器/物理允许的移动 ⇒ **生成器必须给出这条边**

今天的缺口 = **完成性缺口** ⇒ 按现有全部门禁，它**永远不会变红**，只能靠真人踩到
（本次靠用户"推一下 + 只挖一格"才发现）。**这是本次事故真正的结构性原因。**

# T3 步骤 A：探针的「可见性」—— 它此前结构上看不见任何新模组

> 日期 2026-09-14 ｜ 前置：`docs/reviews/2026-09-14-T3-B3a-读取器vanilla优先与探针确定性.md`（§4 已把抽样改成确定性）
> 验证：`bash tools/check-all.sh` + `bash tools/headless-battery.sh core` ⇒ `verdict=PASS`、`(30/30 skipped=0) ticks=3303 → PASS`
> 等级：**`SERVER_TESTED`（无头基线）**。不碰渲染/物理/GUI ⇒ **不得**记成 `WINDOWS_CLIENT`。

---

## 1. 一句话

`MachineProbe` 的枚举来源是 **`MachineMap` 自己**（`adoptedNamespaces()` 遍历表行），而"运行时有、表里没有"
的守卫 `unmapped` **又只遍历那个被表过滤过的集合** ⇒ 对**任何还没登记过的模组，它是结构性失明的**。
修法 = 枚举来源换成**配方注册表**；采样范围**保持只限已登记命名空间**。

---

## 2. 缺陷（代码级事实）

```java
adoptedNamespaces()      // = MachineMap.rows() 里出现过的命名空间
for (recipe : getRecipes()) {
    if (adopted.contains(ns)) byType.put(...)   // ← 未登记的模组**连枚举都进不去**
}
for (typeId : byType.keySet()) if (MachineMap.forType(typeId) == null) unmapped.add(typeId);  // ← 域就是被过滤过的集合
```

⇒ **"表里一行都没有"与"这个模组根本不存在"在输出上完全同形**。而这恰好是 T3 要处理的对象：
`create` / `ExtendedCrafting`（以及 `refinedstorage` / `sophisticated*`）**此刻就装在无头生产服务端里**，
而修前的读数是 `namespaces=[mekanism, thermal]` + `unmapped=[]` —— **一个字都不说**。

---

## 3. 修法（最小面）

| 改动 | 内容 |
|---|---|
| 枚举来源 | 由**表**改为**配方注册表**：遍历全部"非原版工作站"配方类型，建 `allTypes`（`TreeSet`，有序）+ 每命名空间的 `types` / `type_recipes` 计数 |
| `unmapped` 遍历域 | `byType.keySet()`（已登记）→ **`allTypes`（全部）** |
| 采样范围 | **不变**（仍只采已登记命名空间）—— "能不能接"与"采样多少条"是两件事，不为一个模组撑长一轮 |
| 新读数 | `unmapped_total=N`；`unregistered_ns=[ns=types(rows=0,recipes=M),…]`；**逐未登记命名空间一条 warn 行**（含该命名空间的**全部类型 id**） |
| 日志卫生 | `unmapped` 在 SUMMARY / info 行**限长 24 条**并带真实总数（完整清单由逐命名空间行承载）⇒ 不因模组变多而撑爆一行 |

`unmapped` 仍是 **warn-only，不判红**：模组集可变，"我们有 0 行"是**待办**而不是**错误**。

## 5. 这一步买到什么（对 T3 的直接后果）

1. **"接第 3 个模组"的工作量第一次是实测值，不再是估计**：要接 Create 就是 **15 个类型 / 506 条配方**，
   ExtendedCrafting **4 个类型 / 25 条配方** ⇒ 按 `MOD_ADAPTER_PROTOCOL` §"多模组后不允许只登记几行"，
   合计 **19 行** `MachineMap` + 每行方块/菜单/能力 + `tools/machine-map.py` 的 `UPSTREAMS` 一段。
2. **M-4 的前置问题（"怎么摸到 EC 的机器类型"）自动解决**：EC 的机器类型就是
   `extendedcrafting:{compressor, ender_crafter, flux_crafter}`（`table` 是工作台、非机器），
   现在有了 id 清单即可定点取样。
3. **一个反面事实也被记下**：`refinedstorage` / `sophisticated*` / `oreexcavation` / `cofh_core`
   **没有任何"非原版工作站"配方类型**（它们没出现在未登记清单里）⇒ 它们不需要 `MachineMap` 行。
   **注意这是"当前模组集下的观测"，不是对这几个模组的永久断言。**

## 6. 未做 / 风险

- **仍未采样未登记命名空间**（有意）：`unmapped` 只报"有这些类型"，**不报它们的输入/输出形状**。
  要看形状（M-4 / B3b 需要）得再做一步定点采样 —— 那是下一个增量，不是本步。
- `unmapped` 的 19 项**不是错误**，是待办；**没有**升级为判红（升级会每次都红，属于"用断言盖住事实"）。
- 本步**没有**动 `MachineMap` / 读取器 / 判据 / 准入 —— 纯枚举与报告面。
- 证据全部来自**无头生产服务端**（模组集与客户端同构，但**不等于**客户端）：不覆盖渲染/物理/GUI/同步。

## 8.1 ⭐ 由此得到的**承重结论**：B3a 对接第 3 个模组不是卫生工作，是**承重**的

```
unregistered_vanilla_only_in=35/37    unregistered_vanilla_only_out=37/37
```

读法：`outputFromVanilla() && modOutputCount()==0` ⇒ **模组名族对 Create/EC 的 37 条抽样配方读出的产出是空的**
（输入侧 35/37 也是空的）。也就是说：

- **改前的读取器（只有名族、不试原版）在 Create/EC 上会读出 `outputs=[]`**；
- 而 `RecipeQuery` 里 `outputs=[]` + 原版 `getResultItem` 命中 ⇒ 走的是 `machineTypes.add(type)` 分支
  ⇒ 判决会是 **`MACHINE_RECIPE_UNSUPPORTED`**（拒绝并列出类型）；
- **B3a 把这一批从"拒绝"变成"有出处的机器路线"**，覆盖 19 个类型 / 37 条抽样。

⚠️ 这个判决差异**在步骤 A 之前是无法被观测的** —— 未登记的命名空间从来没被采样过。
**这正是"先做 A 再做 C"的价值**：A 打开可见性，C 才量得到 B3a 的真实影响面。

**边界（不许过度自信）**：以上是 **37 条抽样 / 19 个类型**的读数，**不是**对 Create、ExtendedCrafting
全部 531 条配方的断言；`MACHINE_ROUTE` 也只表示"**读得出**路线"，**执行侧仍如实拒绝**
（`note` 里写着"暂无该机器的执行适配"）。这两个模组要真正接入 T3，仍需 §5 那 19 行表 + 能力声明。

## 9. ⚠️ 顺带发现的**通道缺陷**：`partial_search` 是非确定性的（**本轮轮 1 就因此变红**）

同一 jar 两轮：**轮 1 `partial_search=FAIL`（`(29/30) → FAIL`）、轮 2 `PASS`（`(30/30)`）**。

**事实**（不是推断）：

| 轮 | `partial_search` premise | 规划起点 | 该用例结果 |
|---|---|---|---|
| 其余 15 次已知运行（含客户端第十八轮） | `on_ground=true` | `from.z=406` | `PARTIAL movements=2 cost=2.00` ✓ |
| 本轮轮 1 | `on_ground=`**`false`**` pos=45, 64, 405` | `from.z=404` | `SEARCH_LIMIT movements=0 cost=INF best=0.0` ✗ |

- 失败用例 = `PartialSearchCheckTask.partial_with_prefix`：`SearchBudget.of(2, 0L)`（`maxNodes=2 maxMillis=0`），
  断言 `status==PARTIAL && !reached && movements 非空 && projectedFootPath.size==movements.size+1`。
  轮 1 里规划器只扩展了 2 个节点且**没有任何节点朝目标改善**（`best=0.0 openSet=9 considered=13`）
  ⇒ 规划器**没有前缀可交** ⇒ 返回 `SEARCH_LIMIT`——**规划器行为是对的，是夹具的前提不成立**。
- **不是时间问题**：`elapsedMs=0`，预算是**配置**出来的（`maxNodes`）。
- 两轮的 `transfer` 读数（`end_to_end=PASS moved=3 ticks=24`）与我的全部新读数**逐字相同** ⇒
  不是我的配方改动造成的语义差异。

**根因（假设，证据较强但未完全钉死）**：**步骤之间没有"起点锚定/落地同步"**。
① `partial_search` 在电池里注册的第三个参数是 **`null`**（无场景、无传送），而 `PartialSearchCheckTask`
   自己的注释写着"**不移动 bot**" ⇒ 它**从上一个步骤留下的位置起步**；
② 电池对 premise 的 `on_ground` **只打日志、不采取行动**（`RegressionBatteryTask.java:684-691`：
   `ownMenu` 不 ok 会 `closeContainer()`，`onGround` 不 ok **什么都不做**）；
③ 于是"起步时 bot 还在半空/还在滑动"时会**带着一个移动中的起点**去规划，
   而该用例的预算小到只有 2 个节点 ⇒ 起点差一两个方块就足以决定有没有前缀。
   ⇒ 这是 skill `alice-scene-based-testing` §3.2（"每项独立，锚回统一起点，避免顺序耦合"）、
   §6.9.1①（几何假设必须写下来并自断言）、§7（"夹具假设不写下来也不断言"）**共同**禁止的形态。

**未钉死的部分（不假装）**：轮 1 那个 `onGround=false` 的**直接来源**是"我的探针多做了 6 次
`RecipeQuery` 扫描导致时序位移"还是"`transfer` 场景残留"—— 我没有做可控 A/B（需要旧 jar 多轮取样），
**只知道它非确定性、且失败输入确实是"起步时未落地"**。

**修复方向（**未实施，按修复纪律先讨论**）**：
- **最小且通用**：premise 里 `onGround` 不 ok 时**等**（有界等待 + 超时如实报码），与 `ownMenu` 同样对待
  ⇒ 一处修全部步骤；
- **最合规**：`partial_search` 自己锚定固定起点 + 结束复位（§3.2 的两条硬纪律），
  起点还需选在"2 节点必产生前缀"的平地上 ⇒ 要碰场景，工作量大一档。

## 一、实测：那 ≈200 ms 是**四次各自撞满 50 ms 上限的搜索**

`[Job] step` 窗口 = **50.2 s**（168 行：`phase=MINE` 115 / `SCAN` 32 / `RETRY` 15 / `SKIP` 6）。

| 读数 | 值 | 算法/出处 |
|---|---|---|
| mine 循环迭代周期（`SCAN`→`SCAN`） | **中位 222 ms**（n=30，均值 234，min 1，max 490） | 相邻两条 `[Job] step … phase=SCAN` 的时间差 |
| 单次搜索撞 **50 ms 上限** | **502 次**，span 50.0 s | `[Search] 超 tick 预算（50ms ≥ 50ms · tick 预算 50ms）` |
| 撞限搜索的合计耗时（下限） | **≥25.1 s = `[Job]` 窗口的 50%** | 502 × 50 ms |
| 每次 `phase=MINE` 步的撞限搜索数 | **≈4.4** | 502 / 115 |
| `[MiningPlanner] mode=TUNNEL … candidates=13 planned=3 capped=true` | **123 / 123 次**（`planned=3` 无一例外） | `A2` 的 `MAX_APPROACH_PLANS=3` 每次都被打满 |
| ⭐ `本 tick 搜索预算已用尽`（`SearchTickBudget` 的 **400 ms** 闸门） | **0 次** | 整场 A1 闸门**一次都没触发** |

⇒ **构成**：一个 mine tick 里跑 `planDirect`（1 次）+ `planTunnel`（`planned=3`，3 次）= **4 次搜索**，
每次烧满自己的 50 ms 时间上限 ⇒ **≈200 ms/tick** ⇒ 服务端 ≈4.5 TPS。
**4 × 50 = 200 < 400** ⇒ A1 那道"每 tick 总账"（400 ms）**在算术上没机会触发**（实测 0 次，与算术一致）。

⚠️ **这修正了 `docs/reviews/2026-09-24-客户端卡顿根因分析.md §三` 的表述**：那里写"耗时在**每轮附带的那次**规划/搜索"
—— 实测是**每轮四次**，不是一次。

## 二、⭐ 与 `D-431 §二` 判据① 的冲突：**它的主语在生产里不存在**

| | 原文 | 生产侧实况（逐点核实） |
|---|---|---|
| `D-431 §二.1` | 「台架 `tick_budget_bench` 的 **`LEGACY` 格**（13 × 无时间上限搜索）在**生产形态**下退到 **≤50 ms/次**」 | 台架 `LEGACY` 格传 `SearchBudget.of(20000, **0L**)`；而生产侧 **零个** `maxMillis = 0` 的消费者 —— 全部有上限：`WALK_BUDGET = (20000, **50 ms**)`（`of` / `withWorldModification` / **`miningApproach`**）、逃生 `(4000, 100 ms)`、维生预检 `(…, 20 ms)` |
| `D-431 §一` | 「给重消费者自己的 `SearchBudget` 加时间上限（今天进入生产的是挖矿候选那条链，`maxMillis = 0` 那一档）」 | 挖矿候选链走 `PathRequest.miningApproach` ⇒ `WALK_BUDGET` ⇒ **已经是 50 ms**（`D-388`，2026-09-22：`DEFAULT_MAX_MILLIS: 200 → 50`，并配门禁 `SEARCH_BUDGET_CEILING_MILLIS ≤ 60`） |

⇒ **按字面落地 `P4″` 是空转**：没有那个"无上限的消费者"可加上限。
⇒ 真机 200 ms/轮 的性质是「**多次已受上限的搜索的聚合**」，**不是**「单次搜索无上限」。

## 三、⭐ 同族缺陷：`P1-b` 修了一类，**留了一个洞**（`PARTIAL`）

### 3.1 实测的状态分布

撞 50 ms 上限的 **502** 次搜索，其 `[PathingStats] … status=` 分布：

| 状态 | 次数 | 含义（`PlanningStatus`） |
|---|---|---|
| **`PARTIAL`** | **480** | 预算耗尽**但**找到了 best-so-far 前缀 ⇒ `reached() == false` |
| `SEARCH_LIMIT` | 22 | 预算耗尽且**无**前缀 |

（480 + 22 = **502**，与撞限行数精确闭合 ⇒ 这 502 次全部是时间上限耗尽；`maxNodes=20000` 而实测
`nodes` 只有 5800–7400 ⇒ **没有**节点上限耗尽。）

⇒ **96% 的"没算完"是 `PARTIAL`，不是 `SEARCH_LIMIT`。**

### 3.2 代码：三条腿只认 `SEARCH_LIMIT`

`MiningPlanner`（`P1-b` 的修法，2026-09-22）：

| 位置 | 现状 | `PARTIAL` 会走到哪 |
|---|---|---|
| `:322` `selectBestApproach` | `if (path.status() == SEARCH_LIMIT) { searchLimited = true; continue; }` | `planned++` → `!reached()` → 探针 → `continue` |
| `:222` `planTunnel` | `if ("search_incomplete".equals(result.failureReason())) return result;` | `selectBestApproach` 已把 `PARTIAL` 变成 `no_reachable` ⇒ 这里读到的是 `no_reachable` ⇒ 被改写成 `no_reachable_tunnel_standing_point` |
| `:235` `planEnterTarget` | 先查 `SEARCH_LIMIT`，再查 `!reached()` | `PARTIAL` ⇒ **`enter_target_unreachable`** |
| `exactTopK`（`:389` 一带） | 同 `:322` 形状 | 同上 |

⇒ `searchLimited` 保持 `false` ⇒ `plan()` 的 **P1 合取闸门**（`:116`：三条腿任一为 `search_incomplete` 就整体降级）
**不触发** ⇒ 报 **`found_but_unminable`（永久性理由）** ⇒ `MineJob` 把候选写进 `attempted`。

**这与 `P1-b` 记录的病灶逐字同形**（`docs/AI_DECISIONS.md:17032`：「`SEARCH_LIMIT`（=「本轮没评价完」）被两条腿
**覆盖成永久理由** ⇒ 报 `found_but_unminable` ⇒ `MineJob` 把候选写进 `attempted` **永久了结**」）——
**只是那次只修了 `SEARCH_LIMIT`，没修 `PARTIAL`。**

### 3.3 后果：冷却/收工闸门基本没生效

`MineJob`：`isSearchIncomplete(code)` = `code.startsWith("search_incomplete")`（`:171`）；
`SEARCH_LIMIT_COOLDOWN_TICKS = 40`（`:160`）、`MAX_CONSECUTIVE_SEARCH_LIMITED = 8`（`:167`）。

日志侧结局计数（同一轮）：

| 结局 | 次数 |
|---|---|
| `found_but_unminable`（**永久理由**） | **307** |
| `no_reachable_tunnel_standing_point` | 118 |
| `enter_target_unreachable` | 111 |
| `no_valid_standing_point` | 123 |
| **`search_incomplete`（唯一能触发冷却的）** | **87** |

⇒ 每 tick 重跑一批**注定烧满 50 ms 且注定报"永久理由"**的候选 ⇒ 200 ms/tick **持续**发生，
而不是"烧一次 → 冷却 40 tick"。

### 3.4 ⭐ 假设（**不是结论**）

> `H`：`PARTIAL` 未被当作「本轮没评价完」⇒ `MineJob` 的 40-tick 冷却与 8 次连续上限**几乎不生效**
> ⇒ mine 循环每 tick 都重烧 4 × 50 ms ⇒ 累计落后跨过 vanilla 的 2000 ms 阈值 ⇒ `Can't keep up!`（2 次运行期）。

## 四、两条备选路径（**都需要你裁**）

| | 路径 | 动作 | 与既有裁定的关系 | 代价/风险 |
|---|---|---|---|---|
| **A** ⭐ | **修 `PARTIAL` 的归因**（`P1-b` 的洞） | 三条腿把 `PARTIAL` 与 `SEARCH_LIMIT` **同等**视为「本轮没评价完」（`searchLimited = true`），如实报 `search_incomplete` | **不动任何预算常量** ⇒ 不触碰 `D-430` 内核关门线，也不触碰 `D-431` 的"不动毫秒轴" | 低。风险 = `search_incomplete` 变多 ⇒ 冷却期变长 ⇒ **挖掘推进可能变慢**（须用读数证明不是"变成空转"） |
| **B** | **给挖矿候选链加聚合时间上限**（`P4″` 的机制读法） | 让一次 `MiningPlanner.plan()`（4 次搜索）有自己的毫秒账，到线就停并如实报"本轮没评价完" | 符合 `D-431 §一` 的"不动毫秒兜底轴 + 给重消费者加自己的上限" | 中。这是**新的内核行为**（新机制、新常量、新门禁），且与 A **重叠**（A 先做的话，B 的收益会缩水） |
| C | 收紧 `SearchTickBudget` 毫秒轴 400 → 60 | = `P4′` 的选项 3 | **`D-431` 明确否掉了它**（拒绝数 5 → 11） | 高（已被否） |

**我的推荐：先 A、再按读数决定要不要 B。** 理由：A 是**缺陷修复**（判据读错对象，与红线
`SEARCH_LIMIT ≠ UNREACHABLE` 同族，`P1-b` 已为同族修过一次），且**不动物理常量**；而 B 的收益与 A 重叠，
在 A 落地前无法判断还剩多少。

⚠️ **`P4″` 的判据本身需要你重裁**（两条读法）：
- **读法 R1（字面）**：`LEGACY` 格 = 无上限消费者 ⇒ 生产里不存在 ⇒ **判据①已被 `D-388` 满足**，`P4″` 可关账（记账即可）；
- **读法 R2（机制）**：`LEGACY` 格的**角色**应改由"生产聚合形态"（一 tick 内 4 次 50 ms 搜索）承担 ⇒ `P4″` = 路径 B。

## 五、诚实边界（未排除的替代解释）

1. **未做闭合实验**：本文明说"哪一处归因错误"，但**没有**"改一处 → 看 tick 是否下降"的前后对照 ⇒ `H` 仍是假设。
2. **渲染 / GC / OS 干扰未被排除**（`2026-09-24-客户端卡顿根因分析.md §四` 三条全在）：单人存档的集成服务端
   与渲染共用一个 JVM，无同机对照；该轮 `debug.log` 无 JVM 参数、无 GC 行 ⇒ **无法判定**。
3. **未被量化的一项**：`D-371` 的分片扫描（`本次=8192` 格/片，32 片）自身也有成本 —— 本条没把它与搜索分开量。
   所以"搜索占 50% 窗口"是**下限**（按 50 ms 上限计），不是全部。
4. **本文只覆盖一个会话**（09-24 那一轮）；跨轮稳定性未验。

## 七、复核触发

1. 生产日志里 `found_but_unminable` 明显多于 `search_incomplete` ⇒ 本缺陷仍在（当前 307 : 87）；
2. 修 `PARTIAL` 归因后 `search_incomplete` 变多但**挖掘推进也变慢**（单位时间 `block_break_done` 下降）
   ⇒ 回滚该改动，改走路径 B/C；
3. 出现 `本 tick 搜索预算已用尽`（A1 闸门真的触发）⇒ 单 tick 搜索数已 ≥ 8 ⇒ 本节算术前提变了，需重算。

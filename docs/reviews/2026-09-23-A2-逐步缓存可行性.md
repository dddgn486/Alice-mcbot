### 二.4 ⭐ 唯一一处"判决的人口 = 整轮前缀"且**看不出退化**的地方：`write_policy`

源码两处，`File:line` 可查：
- `task/RegressionBatteryTask.java:595`：`⚠️ write_policy **必须留在电池后段**：它审计"本次电池此前所有写入"的归因样本 ⇒ 越靠后样本越多 ✓`
- `task/WritePolicyCheckTask.java:442-449`：判据是 `unregisteredSeen().isEmpty()` 与 `undeclaredSeen().isEmpty()`，
  详情串打印的是**违规表**（`未登记 requester 写入/规划={}`）。

两个 map 的定义（`action/WritePolicyMatrix.java:888,893`）**只累计违规**，**全仓没有任何"审计了多少次写入"的人口计数**。
⇒ 于是**同一行日志**既可能是"审计了 535 次写入、0 违规"，也可能是"一次都没审计到"：

```
CORE 19:20 :  (前缀写了很久)   no_unregistered_requester result=PASS 未登记 requester 写入/规划={}
solo 19:00 :  运行账 breaks=+402 places=+0   同一行，逐字相同
```

⇒ 这正是 `Z1`/`Z4` 那一族（"**空集真**"），也是 `survey/30` 担心的"**假绿**"的**具体落点**：
**跳过前序步 ⇒ 审计人口塌到 0 ⇒ 判据静默变成空集真，而日志上一个字都不会变。**
（对照：`Z4` 给账本/写入预算补了与区无关的人口读数；**这一处没被覆盖**。）

### 二.5 逐步运行的**固定成本**：79% 是"重新起一个服务端"，不是被测的那步

实测前 14 步（`run/a2-solo-matrix.tsv` 的 `ticks` 与 `wall_s` 两列）：

| | 合计 | 占 wall |
|---|---|---|
| 步本身（ticks ÷ 20） | 92.8 s | **21%** |
| 引导 + 调度 + 世界拷贝 + 收尾 | 358.2 s | **79%** |

单步固定开销稳定在 **20–26 s**；`mine_menu`（1 tick = 0.05 s）的 wall 是 **24 s** ⇒ 该步几乎 100% 是冷启动。
（CPU 侧同源：一个 `-Xmx3G` 的无头服务端 = **40 线程 / 446–458% CPU**，冷启动期模组并行加载 + 区块生成把它吃满。）

⭐ **这条直接影响结论**：逐步缓存省下来的是"**被测的那 21%**"（而且只有命中步省），
**每轮照样要付 79% 的引导**。所以"CORE 反馈 分钟→秒"**不可能**由"逐步缓存"给出 ——
分钟级 wall 里绝大部分不是被缓存的那些 tick。

### 4.2 为什么放弃（三条支柱，各自独立成立）

1. **成本账不成立**（§二.5，实测）：逐步缓存能省的只有"被测的那 21%"，而**每轮 79% 的引导照付**
   ⇒ 「CORE 反馈 分钟→秒」这个目标**与逐步缓存无关**。即使机制完全可信，收益上限也够不到它承诺的东西。
2. **可用粒度不存在**：逐步缓存要求"该步的指纹保守完备"。CORE 的 41 步**绝大多数要走内核**
   （寻路 / 挖掘 / 合成 / 容器 / 事件），所以保守完备的逐步指纹会**退化回 `src/` 全量**，也就是 `D-352` 已经有的**全局指纹**
   ⇒ 逐步缓存拿不到比它更细的粒度；一旦人为把粒度放宽，换来的就是"**用陈旧判决顶替真跑**"= 假绿本身。
3. **退化不可见**（§二.4）：`write_policy` 的判决人口 = **整轮前缀**，而它的两条判据是 `isEmpty()` 且**没有人口读数**
   ⇒ 跳过前序会让它静默变成**空集真**，而**判决表面照样"逐条一致"**（本次矩阵第 36 步就是 `write_policy PASS / PASS`）。
   ⭐ 这正是 `survey/30` 担心的假绿的**具体落点**：判据"逐条判决完全一致"**看不见**这一类退化。

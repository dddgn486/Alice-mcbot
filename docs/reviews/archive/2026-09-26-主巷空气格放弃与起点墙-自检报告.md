## 3 根因链（源码行号锚点）

### 3.1 探针字段语义与名字相反（`MiningPlanner.java:249-254`）

```java
footPassable = canWalkThrough(level, target);            // = true  ⇒ 目标格自己已是空气！
headPassable = canWalkThrough(level, target.above());    // = false ⇒ 目标上方（y+2 层）实心
belowSolid   = canWalkOn(level, target.below());         // = true  ⇒ 地板存在
```

⇒ **bot 被派去"挖一个本来就是空气的格"**（头位格 `-75,72,238`），它上方那格是实心（天花板/岩石）。

### 3.2 空气目标**结构性不可挖**（`LineOfSightChecker.java:35-46` + `StandingPointSelector.java:70-89`）

```java
// checkFromEye：射线必须命中【目标格自己是方块】
if (hit.getType() == HitResult.Type.BLOCK && hit.getBlockPos().equals(target)) { return clear; }
```

空气格没有碰撞面 ⇒ `clip` 永远命中别的方块 ⇒ `LOS` 恒不清 ⇒
`isValidStandingPoint`（可站 + LOS + 触及）全拒 ⇒ `candidates` 空 ⇒ `no_valid_standing_point`。
（`faceStandable=1/6` 的那 1 个"可站面"是目标正下方的脚位格，但它同样过不了 LOS 这一关。）

### 3.3 为什么把空气格派成了活（`FishboneJob.java:602-604`）—— `1.4j①` 老账

```java
private boolean isAlreadyPassable(ServerLevel level, BlockPos cell) {
    return MovementHelper.bodyPassable(level, cell);   // = canWalkThrough(cell) && canWalkThrough(cell.above())
}
```

- 对**头位格**（y+1）：`bodyPassable` 要求【头位格 **和** 头顶那一格（y+2）】都可穿；
  而 y+2 在 2 格高通道之上**永远是实心**（天花板/岩石）⇒ **任何一个"已经挖通"的头位格都被判成"未通"**
  ⇒ 给它建 `MineTask` ⇒ 挖空气 ⇒ 整条主巷 FAILED。
- 这是台账 `1.4j①`（"`isAlreadyPassable` 用两格谓词问单格"）的**新触发面**：前几轮主巷头位格都是实心的
  （挖进岩体），从不触发；本轮从**已打开的空间**出发（房间/已挖段），第一单元两格都是空气 ⇒ 立即触发。

### 3.4 "要一堵墙"的机理（同一根因的外在表现）

- **有墙（实心岩体）**：脚位格/头位格都实心 ⇒ 正常挖（站位 = 起点格，LOS 斜上命中头位格；后续单元
  站位 = 前一单元的脚位格）⇒ 通道一寸寸往岩体里长。—— 前几轮一直长这样，所以"能启动"。
- **没墙（空气房间）**：第一单元两格都是空气 ⇒ skip 脚位、挖空气头位 ⇒ 5 tick 崩 ⇒ 观感"不让启动"。

## 4 架构问题：**硬形状 + 逐格派活；内核只回答"怎么到"，从不回答"通道该长什么样"**

```
FishboneTemplate（硬形状：start+dir+spur 几何 ⇒ 单元脚位序列 + height=2 剖面；纯几何、不读世界）
  → FishboneJob.excavate() 逐单元、逐 cell（脚位格 → 头位格）：
        isAlreadyPassable(cell) ? skip : new MineTask(cell)
          → MiningPlanner.plan(target, standableOnly=true, cellProfile)
              → CorePathPlanner（A*）→ 内核移动执行器（TRAVERSE/ASCEND/BREAK…）
  单元间的走位（SPUR_RETURN / 返回）= walkRequest = PathRequest.withPlacement（D-440「补一块再走」）
```

- **目标格是谁：模板说了算（硬）。怎么走到、站哪挖：内核说了算（软）。**
- 「自动补上主巷的空位」要拆两半：
  - **"已通格当通道"（skip）** = 作业层 `isAlreadyPassable` 的职责 ⇒ **今天坏的**（§3.3）；
  - **"缺的地板补一块"** = 能力**已经存在**（`cellProfile()` 在 `bridgeBlockBudget` 内给
    `PLACE_STEP_AND_TRAVERSE`，`FishboneJob.java:238-240`；走位也是 `withPlacement`）⇒ 但它
    **走不到那一步**，因为 bot 在上一个 cell 就因"挖空气"判死了。
- ⇒ 结论：**不是内核缺"自动补空位"的能力，是作业层在派活之前用坏谓词把自己判死了。**

## 5 修复方案（**未实施**，待用户拍板）

| # | 修法 | 范围 / 判据 |
|---|---|---|
| **①** ⭐ | **`1.4j①` 落地**：`isAlreadyPassable(cell)` 改单格 `canWalkThrough(level, cell)` | `FishboneJob.java:602-604` 一处。效果：① 已开的脚位/头位格都正确 skip（不管天花板）；② **半成品格**（脚空头实）从"挖空气的脚位格"变成"挖头位那格"（站位 = 上一单元脚位格，LOS 成立）——同时修掉第四轮支巷的 `footPassable=true headPassable=false` 签名 |
| **②**（防御层） | `MiningPlanner.plan` 开头：目标已是空气 ⇒ 按"已通"返回（不再让任何调用点把空气格变成 `no_valid_standing_point` 从而崩整条主巷） | `MiningPlanner.java` 开头一格；防止 ① 之外还有别的误派来源 |
| **③** | 随 ① 天然获得（无需额外逻辑）：空气段连续 skip 到第一个实心格才开始挖 | 即"没有墙也能启动" |

⇒ **`footPassable=true` 的唯一读法：作业正在要求 `MineTask` 去挖一格已经是空气的格子。**

### 2.3 【事实】挖空气为什么必然失败

`MineTask` → `MiningPlanner.planDirect`：先看"当前站位能不能直接挖"（`StandingPointSelector.isValidStandingPoint` 含**视线**判定），否则生成候选站位；候选为空即：

```
[MiningPlanner] standable_only target=… reason=no_valid_standing_point
[MiningPlanner探针] planning failed … reason=no_reachable_standing_point … approach=PLACEMENT_ALLOWED
[Fishbone] main_unreachable:no_reachable_standing_point 主巷单元 N 挖不动 …
```

**空气没有方块形状 ⇒ `LineOfSightChecker` 永远"看不见"它 ⇒ 任何站位都不可能有效 ⇒ 候选恒空**（`faceStandable=1/6` 那次就是"几何上有一个可站面，但视线判定仍然过不了"）。

## 3 根因

### 3.1 【事实】主因：`isAlreadyPassable` 用**两格谓词问单格**（台账 `1.4j①`，未修）

```java
// FishboneJob.java:475-479（跳过分支）
if (isAlreadyPassable(level, cell)) { skipped++; cellInUnit++; return; }
// FishboneJob.java:602-604
private boolean isAlreadyPassable(ServerLevel level, BlockPos cell) {
    return MovementHelper.bodyPassable(level, cell);   // = canWalkThrough(cell) && canWalkThrough(cell.above())
}
```

`cells()` 是**逐格**展开的（`FishboneTemplate:195-203`：每单元 `foot` + `foot.above()`），判据却是"本格 + 上面一格"。真值表：

| 被问的格 | 判据实际在问 | 状态 | 结果 |
|---|---|---|---|
| **脚位格**（cell=1/2） | 脚位 + 头位 | 都实心（新走廊） | false ⇒ `MineTask` ⇒ 👍 正常挖 |
| | | 都空气（已挖通） | true ⇒ 跳过 ⇒ 👍 |
| | | **脚位空 + 头位实（半成品格）** | **false ⇒ 去挖空气 ⇒ 💀** |
| **头位格**（cell=2/2） | **头位 + 天花板** | 头位空气 + 天花板实心 | **false ⇒ 去挖空气 ⇒ 💀** ← **本轮 4/4 全是这一条** |
| | | 头位实心 | false ⇒ `MineTask` ⇒ 👍（这是"挖头位"的正常路径） |

**天花板几乎总是实心** ⇒ 头位格**几乎永远不会**被判成"已通" ⇒ 只要 bot 遇到一段**已经挖通/天然开口**的通道（`cell=1/2` 被跳过），**紧接着的 `cell=2/2` 必死**。

### 3.2 【推断】这正好解释用户的两句话

| 用户的话 | 机理 |
|---|---|
| 「要**起点旁边有一堵墙**才行，不然不让启动」 | 起点 = bot 自己脚位（`D-441`）；**前方第一格是实心** ⇒ 走"正常挖"路径 ⇒ 能开工。**前方已经是空气** ⇒ `cell=1/2` 跳过、`cell=2/2` 去挖空气 ⇒ 5 tick 死。**"需要墙"= "需要第一格是实心"，不是设计，是本判据的下游表现** |
| 「主巷有一格空的，他就放弃了」 | 那一格**已经是空气** ⇒ 本不需要挖 ⇒ 但被判成"要挖" ⇒ 不可能完成 ⇒ `main_unreachable` ⇒ **按 `D-443` §10.2 主巷如实失败**（不是支巷放弃） |

### 3.3 【事实】并存缺陷：地板缺格（`belowSolid=false`）——`I2`

第 4 次失败处 `belowSolid=false` ⇒ `canWalkOn((-75,71,233))` 为假 ⇒ **`(-75,70,233)` 是空气 ⇒ 通道地板缺了一格**。这是**另一件事**（`I2`「行走层支撑格必须存在」），今天**没有任何一方负责补**（见 §3.4）。

### 3.4 【事实】架构回答：**三层分工，第三层是空的**

| 层 | 谁负责 | 现状 | 证据 |
|---|---|---|---|
| **① 形状（硬）** | `FishboneJobItem` → `FishboneTemplate`（纯几何）→ `FishboneJob.units` | ✅ 硬枚举、确定、可复算：`main=20 spacing=3 spur=32 side=BOTH height=2` ⇒ **404 单元 / 808 格** | `[Fishbone] start template=… units=404 cells=808` |
| **② 怎么挖到（全交内核）** | 逐格 `new MineTask(target=cell, MiningBudget.forTarget, MiningProfile(approach=PLACEMENT_ALLOWED))` → `MiningPlanner`（模式 A 现成站位 / 模式 B 隧道 / 进入）+ `StandingPointSelector` + `PathRequest.withPlacement`（只放不拆） | ✅ 站位、路径、补一块支撑、要不要开隧道**全由内核决定** | `profile=standableOnly=true approach=PLACEMENT_ALLOWED` |
| **③ 通道的成品规格（`I1` 连通 / `I2` 地板 / `I3` 不留半成品格）** | **没有人** | ❌ 作业只下发「**挖掉**这一格」，从不下发「**补齐**这一格」，也从不下发「这一格够不够格」 | 全仓无"补通道格"的调用点 |

⇒ **所以答案是"两者都不是"**：
- 形状确实是硬的、直接交给内核**逐格**执行；
- 但内核只回答"**怎么到那一格**"，它**既没有请求、也没有权限**去"补齐一格"；
- **"空位"因此既不被补、也不被跳**，而是变成一次**不可能的挖掘**，最后只能如实分档。

这正是 `D-443` 切片表里 **`P0.5`（I2 补地板）+ `C8` 尾款** 要落的东西；而 §3.1 那个判据是**更前置**的 bug —— 它让 bot **连"跳过"都做不到**。

## 4 修复方案（分批；每条都给判据与红臂）

> 共同纪律：**判据必须先红后绿**（`ALICE_BATTERY_NO_CACHE=1`，并确认日志时间戳是本轮的）；
> **夹具不许写聚合计数式断言**（本轮真机就是被 `descend_precondition` 那种聚合计数坑过一轮）。

### F1【主修，最小】`isAlreadyPassable` → **单格谓词**

- **改**：`FishboneJob.java:602-604`
  ```java
  return MovementHelper.canWalkThrough(level, cell);   // 单格：这一格自己通不通
  ```
- **为什么这样就自洽**（三步同时成立，因为头位格**本来就在 `cells()` 列表里**）：
  1. 脚位格空气 ⇒ 跳；2. 头位格空气 ⇒ 跳 ⇒ 单元完成、**不再产生"挖空气"的请求**；
  3. 半成品格（脚位空 + 头位实）⇒ 脚位跳、**头位格照常被挖** ⇒ 单元补齐。
- **期望**：症状①②同时消失；真机 `[Fishbone] cell … cell=2/2` + `no_reachable_standing_point` 那两行不再出现。
- **判据（新，单元级、确定性、毫秒级）**：造三种单元几何，跑生产 `excavate()` 的单单元推进：
  | 几何 | 期望（修复后） | 期望（红臂：退回 `bodyPassable`） |
  |---|---|---|
  | 全新（两格实心） | 2 次 `MineTask`（脚位、头位） | 同左（**反证：不许把正常挖也禁掉**） |
  | 全空气 | **0 次**、`skipped+2`、单元完成 | 1 次 `MineTask(target=空气)` ⇒ 红 |
  | 脚位空 + 头位实（半成品） | **1 次**，目标 = **头位格** | 1 次，目标 = **脚位格（空气）** ⇒ 红 |
- **红臂**：把 `isAlreadyPassable` 退回 `bodyPassable` ⇒ 第 2、3 行必红。
- **回归面**：`fishbone_slice1`（现 42/0）· `fishbone_slice2`（现 88/0）· **`core`**（真跑；`single:X` 不能当 CORE 的基线）。
- ⚠️ **必须同时写死 `I3` 口径**：单格谓词会把"半成品格"判成"可通行"而**放过**它 —— 上面第 3 行判据就是钉这一条的（"脚位空+头位实"必须**继续挖头位**，不是跳过整个单元）。
- ⚠️ **不许用"到处是空气就全跳过"当修复**：成品验收仍是 `I4`（**纯通行能从起点走到最远端**）。

### F2【并存，需要一次裁定】地板缺格：**补 vs 如实放弃**

- **现状**：`MineTask` 的 `approach=PLACEMENT_ALLOWED`（`MiningProfile:45/116` → `PathRequest.withPlacement`，**只放不拆**）只能补"**去站位点的路**"，**不能给目标格脚下造支撑**；`faceStandable=0/6` 时连站位候选都没有 ⇒ 今天只能落 `no_reachable_standing_point`（**这个码把"地板没了"伪装成"站位找不到"**）。
- **两条路（二选一，必须写死 + 归因）**：
  - **(a) 补**（`I2`）：在缺格处放一块 ⇒ 该列恢复可站；额度沿用 `C8` 的 `max(16, 单元数/10)`，**用尽 ⇒ 如实放弃**（`D-443` 裁定 7b）。
  - **(b) 如实放弃**：由前瞻窗口判 `big_cavern_ahead`（`maxGapLength`，`advanceRefusal:629`）。
- **判据**：造"主巷地板缺 1 格"几何 ⇒ (a) 断言补上且 `advance` 前进；或 (b) 断言归因码 = `big_cavern_ahead`/`bridge_budget_exhausted` **而不是** `no_reachable_standing_point`。
- **红臂**：两个都不做 ⇒ 落回今天的 `no_reachable_standing_point`。

### F3【读数，零风险】`SUMMARY` 的 `spurs=` 标签误导

`FishboneJob.java:1318`（`emitSummary`，参数在 `:1342`）：

```java
template.spurBranches() - spursAbandoned, template.spurBranches(), spursAbandoned
// 打印成 spurs={未放弃}/{总数}
```

⇒ `main=1/20` 与 `spurs=12/12` 并排出现（本轮实际日志），**看起来像"12 条子巷都挖完了"**，其实一条都没开挖。
建议改成 `spursAbandoned=0/12`（含义唯一：只数放弃数）。

### F4【建议不做】入口加"前方是空气"的提示

`FishboneJobItem.originFor:197` 今天只在 **bot 自己站不住** 时拒绝开工（且已有夹具 + 反证：`FishboneSlice2CheckTask:1234-1243`）。
"前方是空气"不该做成入口提示 —— 那是**判据该管的事**（F1）。入口再加一条"靠提示"的规则 = 净增一条没人守的散文规则。

## 1. 问题定义

### 1.1 什么是"上下文管理"

**上下文管理** = 在有限 token 预算内，决定"**此刻模型看到什么**"的全部机制。它同时是**读**（选什么进窗口）与**写**（留下什么给未来的自己）的问题。关键点：**它不等于"把窗口做大"**，也不等于"多记东西"——它是**预算分配 + 保真度管理**。

### 1.2 六个子问题（本报告的拆解轴）

| # | 子问题 | 本质 | "失败"的可观测标志 |
|---|---|---|---|
| 1 | **持久记忆** | 跨会话稳定存在的事实层，与任何单次会话解耦 | 新会话不知道旧决策，重复讨论已定的事 |
| 2 | **压缩保真** | 长历史 → 短表示的有损编码，控制"损失了什么" | 摘要吞掉关键约束/坐标/路径，导致重复犯错 |
| 3 | **检索** | 何时、依据什么把什么拉回窗口 | 召回无关内容挤占预算；或该拉的没拉 |
| 4 | **跨会话延续** | 新会话的起点 = 上次的终点（handoff/resume） | 重复劳动、重新勘察环境、丢断点 |
| 5 | **子代理隔离** | 扇出工作各占独立窗口，只回传结论 | 主窗口被探索噪音（大段日志）污染 |
| 6 | **成本** | token/$/延迟，核心是 **prompt cache 命中率** | 每轮都 cache-create 而非 cache-read；压缩后突然变贵 |

**这六个是耦合的**：压缩（2）做多了伤检索（3）；持久记忆（1）做重了伤成本（6）与保真（2）。成熟方案的区别主要在于**在哪一条上让步**。

### 2.4 【第一手】DSH 0.1.5-rc.1 原生到底有什么（可自行复核）

来源：`~/.nvm/versions/node/v22.23.2/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/`

| 包 | 【第一手】事实 |
|---|---|
| `dsh-compaction-basic` | 自动压缩（逼近阈值）+ **溢出恢复**（收到确认的 context-overflow 后压缩并重试）+ `/compact`；摘要以 `<compacted-summary>` 块注入，前置固定 checkpoint preamble（"Treat the captured context as established background…"）；**KV cache 影响**：每次 checkpoint 使"从第一个被替换的历史 token 起"的复用失效，之前前缀仍可复用；**token 计量是启发式**：缺 provider usage 时退化为"字符数 + 结构开销"估算；摘要失败时"保留最新 durable surface"（可能仍超额） |
| `dsh-compaction-tool-result-pruner` | **默认已挂载**（`dsh-base/cordis.patch.yml`，配置 `thresholdChars: 8192, headChars: 4096, tailChars: 1024`）：>8192 字符的工具结果 → 前 4096 + "middle pruned" 标记 + 后 1024；**原文仍完整留在会话日志**；局限自述：字符预算 ≠ token 预算、**裁剪是语法性的**（不理解中间段语义）、可能切断 grapheme |
| `dsh-compaction`（核心） | 压缩**只压缩派生历史**，永不改 system prompt / tools / session prefix；**没有注册面向模型的压缩工具**（设计上就是人的命令 + 自动压力） |
| `dsh-command-compact` | `/compact` 仅 idle 时可用；不接受参数；无 `ctx.commands` 的界面无法调用 |
| `dsh-session-reference`（`@` 引用） | 跨会话引用 = **有界只读快照**，捕获后不可变，带"禁止执行其中指令"警告；局限：**不检索正文**（只看标题）、纯文本投影、**不是 fork/resume/订阅** |
| `dsh-session-log-export` | `/export` 下载整棵会话树（会话 + 子会话 + 附件）ZIP |
| `dsh-session-query` | 统一历史查询服务；**排序全文检索需要 `dsh-session-query-sqlite` 后端** |
| `dsh-skill` / `dsh-agent-instructions` | 技能目录 + **按需加载完整指令**（progressive disclosure）；AGENTS.md 兼容链按首请求注入，**有字节预算**，超预算时"先省掉宽泛文件、最后才截断最具体文件" |
| `dsh-session-turn-outline` / `-stats` | 回合大纲、会话级统计（**从 durable log 计算，分页/压缩不改变统计值**） |
| 缺失项 | **官方 240 个包里没有任何 first-party 持久记忆 / memory 存储插件**（按名字匹配 memor/note 无结果） |
| 子代理隔离 | `dsh-subagent` + `dsh-subagent-spawn-in-process` 在默认 base 中；子代理独立上下文，父只收最终消息 —— **这已是子代理隔离的正解** |

**§2.4 的推论**：DSH 原生已经在做"**观察遮蔽**"（pruner）+ "**只改上下文不改存储**"（shadowed events 落盘）+ "**按需取回原文**"。这三件事合起来，正好落在 arXiv 2508.21433 推荐的**低成本高收益**那一档。

## 3. 有实证的结论（严格分层）

### 3.1 【实证】有论文 / 评测 / 大样本经验支持

1. **观察遮蔽 ≈ LLM 摘要（效果），且更便宜。** arXiv 2508.21433（JetBrains Research，NeurIPS 2025 DL4Code workshop）。
   → 直接含义：优先遮罩/裁剪大块工具输出，而不是频繁做激进摘要。
2. **长上下文性能非单调下降。** Lost in the Middle (TACL 2024，U 型曲线)；Chroma Context Rot（多模型、随输入增长退化）；llm-effective-context-length（ICLR'25 相关工作）。
   → 直接含义：**"窗口更大"不是上下文管理的解**。
3. **摘要压缩在长程任务上引入执行不稳定。** arXiv 2608.06503：在同一压缩边界恢复同一执行状态、独立重放，轨迹不一致。
   → 直接含义：压缩是**随机变量**；压缩点之后的行为不可复现；**原文必须可回滚**。
4. **上下文文件（CLAUDE.md/AGENTS.md）不是越长越好。** arXiv 2607.27250《Do Context Files Help Coding Agents? A Two-Agent Ablation Study on Real Repositories》；Upsun 博文《The research is in: your AGENTS.md is probably too long》。
   → 具体效应量 **未验证**（只读到标题/摘要片段）。

6. **压缩会影响"能力"本身。** ICML 2025《Can Compressed LLMs Truly Act? An Empirical Evaluation of Agentic Capabilities in LLM Compression》——压缩对 agentic 能力的损伤被单独评测。

   - 【第一手】DSH README：checkpoint 使"从第一个被替换 token 起"的复用失效。

### 3.4 【推断】我的判断（非引文）

1. 我们这个规模（单人 + 一个 AI + 一个仓库，事实体量以万 token 计的 docs），瓶颈**不是记忆容量，而是落盘纪律**。
2. 我们把"压缩"当成本主要矛盾可能定位偏了：**主要矛盾是"什么东西不该进上下文"**（原始日志、长 gradle 输出），而这正是 DSH 默认 pruner + 我们的 `--grep` 纪律在管的。
3. 第三方插件在我们现状下**边际收益 < 维护税**（详见 §4.5）。

## 4. 对本项目的建议

**一句话结论**：我们现在这套（**文档落盘 + 自动压缩 + 遮蔽/取回原文**）**已经落在被实证支持的主流做法上**，不需要引入外部记忆系统；真正值得补的是**两条低成本纪律**，和**一次对压缩保真度的定向加固**。

### 4.1 该做

| # | 做什么 | 成本 | 替代方案 |
|---|---|---|---|
| A1 | **把"遮蔽"当第一手段，把"压缩"当兜底**：对**明知会很大**的输出（gradle 日志、client `latest.log`、长 JSON）先 `--grep`/`head`/落盘再进上下文，而不是整块进窗口后靠自动压缩救 | **~0**（改习惯，已在 AGENTS.md 有雏形） | 调大 pruner 侵略性（把 `thresholdChars` 从 8192 下调、`tailChars` 提高）——配置改动，成本低，但**需实测验证不切掉关键尾部**（pruner 自述是语法性的） |
| A2 | **固定"跨会话长期记忆"的写入口径为三类：可验证事实 / 架构决策 / 断点**，并且**原文一律不进 docs，只放指针**（文件路径、`seq` 区间、commit hash）。理由：实证 §3.1-4（指令文件过长有害）+ 事实体量小、检索无收益 | **低**（已是现状，只需写进 `AGENTS.md` 固化） | 检索式记忆（Mem0 / Zep / MCP memory server 自托管）：成本**高**（新常驻服务 + 嵌入 + 抽取质量不可审计），且与"我们的领域要精确事实"冲突 |
| A3 | **压缩保真度定向加固**：每次 `/compact` 之后，用 `tools/dsh-session-log.mjs --shadowed last` **抽查一次**被遮蔽的 seq 区间是否含"仍需要的约束"，含则 `--seq` 取回并落盘为一行事实 | **低**（每压缩一次多 1 条命令） | 自定义 `dsh-compaction` 后端（模板化摘要，强制保留"路径 + seq + 命令"锚点）——成本**中**（写一个 backend 包），是 A3 的"自动化版"，但引入自维护代码 |

### 4.2 不该做

| # | 不做什么 | 理由 | 反例条件（何时该重估） |
|---|---|---|---|
| N1 | **不装第三方 DSH 插件**（handoff / compact / resume） | DSH 原生已覆盖其核心面（自动压缩 + 溢出恢复 + `/compact` + `/export` + `@` 有界引用 + durable log 统计）；插件带来**版本耦合**（本机已有两个因兼容性被禁用）；其"结构化 handoff"我们用 markdown 已实现。**§4.5 专门评估** | 若进入**无人值守多天**的长任务、且需要自动修剪与自动恢复，重估 |
| N2 | **不引入向量库 / 嵌入检索式记忆**（Mem0 / Zep / MCP memory server 自托管） | 成本高（常驻服务 + 嵌入模型 + 运维）；**抽取/摘要不可审计**（实证 §3.1-3：压缩引入不稳定）；我们的关键事实是**路径物理、方块语义、坐标**这类**要求逐字精确**的内容，抽取式记忆天然与之冲突；事实体量远低于检索收益阈值【推断】 | 文档事实体量增长到**十万 token 量级**且出现"找不到已知事实"的真实失败 |
| N3 | **不调低压缩阈值 / 不更频繁压缩** | 【第一手】每次 checkpoint 打断 KV cache 前缀 → 反复 cache-create；【实证】压缩引入执行不稳定（§3.1-3） | 出现真实的 context-overflow 事故（DSH 已有溢出恢复路径，先依赖它） |
| N4 | **不指望"申请更大窗口"解决** | 实证 §3.1-2：长上下文性能非单调下降 | 无 |

### 4.4 关于"我们现在这套是不是成熟做法"的正面回答

**是。** 三点对上主流：
- "**只改上下文、不改存储**"= 观察遮蔽路线（实证 §3.1-1 推荐档）。
- "**原文可按 seq 取回**"= 对 §3.1-3（压缩不可复现）的正确防御，且比各家产品内置的 `/compact` 更强（Claude Code 的 issue #70459 正说明"没有可靠取回"会变成成本 bug）。
- "**文档 + git 提交做持久记忆**"= 与 CLAUDE.md/AGENTS.md 同族，但把常驻预算压到最小（**优于**把所有记忆塞进常驻指令文件）。

### 4.5 对"倾向不装第三方插件"的评估

**结论：成立，且有一条支持它的独立证据 + 一条需要注意的保留。**

- 支持：DSH 原生覆盖面已经包含这些插件的功能簇（§2.4 逐条列出）；插件是**版本耦合的第三方代码**，而本机已有两个插件因兼容性被禁用（项目已知事实）。
- 支持：社区插件生态的存在（snow-The / zixin947 / mill413、codex #24810）**只能证明需求普遍，不能证明方案有效**（§3.3）。
- **保留（反例方向，需诚实标注）**：这些插件的"主动修剪"若真能减少 summarizer 调用次数，**成本上未必更差**；但我**无网、未安装、无法在本地验证其行为** → 该方向的收益与风险均标 **未验证**。
- **不建议现在做**：可以通过一次**受控试用**（在独立 profile / 非关键会话中挂载，观察是否稳定）来降低不确定性——这比"直接装到主力工作流"风险低得多。是否做，交由用户裁定。

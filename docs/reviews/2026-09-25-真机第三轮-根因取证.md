### 2.3 代码链（每一环都有锚点）

1. `FishboneJob.java:447-452`：`BlockPos cell = unit.foot().above(cellInUnit); if (isAlreadyPassable(level, cell)) { skipped++; … }`

### 4.2 几何（可算）

- 玩家 AABB 半宽 **0.3**（宽 0.6）。
- 例 1：目标列 `z = 175`（格占 `175.0…176.0`，中心 `175.5`）；bot `z = 175.205` ⇒ **离中心 0.295**，AABB 跨 `174.905…175.505` ⇒ **压进邻列 `z = 174` 0.095 格**。

- `delta = (0, −0.0784, 0)` **每 tick 恒定** = 重力 0.08×0.98 被碰撞当场清零的经典签名 ⇒ **它每一 tick 都在"要掉"，每一 tick 都被托住**。
- 被托住的是谁：目标格下方（`to = -74,53,175`）是空气（`toBlock=空气`），但 AABB 的 0.095 那一角压在**邻列**的实心块上（`supportBlock=石头`）⇒ 原版碰撞判定 `onGround=true`。

⇒ **高置信推断（几何+物理一致，但日志不打印"托住它的那一格的坐标"）**：托住 bot 的是**邻列方块的角**。
**可判定预测**：把 bot 居中（离心 0）到目标列，同一条 DESCEND 就会掉下去。

### 4.3 离心是哪来的：**容忍度写在判据里**

- `MovementHelper.java:292-297` `isAtFootColumn`（`CompletionTolerance.COLUMN`）＝ `onGround() && footCell==目标 && y−目标y < 0.5` —— **完全不含居中要求**。
- `MovementHelper.java:270-281` `isSettledAtFootPos(…, maxHorizontal)`（`EXACT`）容忍度**就是 0.3**：`Math.sqrt(dx²+dz²) <= maxHorizontal`，调用处 `DownwardExecution.java:165` 传 `0.3D`。
- **0.3 = AABB 半宽** ⇒ "已到位"所允许的最大离心，正好让 AABB 的一半踩在邻格上。这不是巧合，是同一个数被用在两处、含义不同。

### 4.4 缺的那一支：Baritone 对照（`AGENTS.md` 内核路线要求）

`reference/baritone-1.20.1/.../movements/MovementDownward.java:81-94`：


## 5 「服务端把 bot 校准到方块中心」——怎么用、用到哪里（设计建议）

结论先说：**分两件事，用两种机制，不要用一把锤子。**

### 5.1 机制 A（首选、Baritone 已验证）：**输入驱动的居中**，不是瞬移

- **解决**：§4 的"静止离心 → 压在邻列角上 → 不下落"。
- **落点**：`DownwardExecution` / `FallExecution` 的"等待自然掉落"那一支（`DownwardExecution.java:112-113`），照 `MovementDownward:86-94` 补两支：
  ① 算到目标格中心的水平偏移 `ab`；② `ab ≥ ε`（Baritone 取 **0.2**）⇒ 命令输入朝中心走（Alice 用 `bot.controller()` 的前进/横移，或复用已有的"朝某格走"原语）；③ `ab < ε` ⇒ 才 `stopMovement()` 原地等。
- **为什么不用瞬移**：① Baritone 已经解决了同一个问题，且路线红线要求先对照它；② 输入驱动不产生位置跳变 ⇒ **不会污染 `[Bot] teleported` / `[Events] TELEPORT` 位移检测器**，也不碰 `fallDistance`（掉落伤害诚实性）。

### 5.2 机制 B（用户提议的那个校准）：**"静止 ⇒ 居中"**，只在"结算点"做

- **解决**：§3.2 的模型/实体错位（`inPickupRange` 说够不着，而**模型**按格中心算）。那里 bot 离心可达 **0.49**，比机制 A 的场景更极端，且**不是下落问题**，走过去也无用（要拾取必须进范围）。
- **落到哪里**（这是关键，**只许一处定义**）：
  1. **一个原语、一个 owner**：放在**已经定义"已到位"的同一个地方**（`MovementHelper.isSettledAtFootPos` / `isAtFootColumn` 家族 + R4 session 的 settle 分支 `PathSession.java:145-150`）。
     ⚠️ 理由是本项目已经踩过的坑：`bodyPassable` vs `canWalkThrough`（§2）就是"同一个概念两处定义"；**容忍度 0.3 与居中校正必须写在同一个类里，否则立刻又是一对**。
  2. **触发点只许三个**：
     - (a) **R4 session 停稳时**（`segment_done` / `completed` / 失败清理）——执行器在此**声明"我在 C 格"**；
     - (b) **垂直动作起步前**（`DESCEND` / `FALL` / `DOWNWARD` / `PILLAR` / `PLACE_STEP_AND_TRAVERSE`），且 bot 已在 `from` 格内 ⇒ 保证"落下那一刻是居中的"；
     - (c) 收集类目标**锚点选定之后**（写目标前把 bot 摆正），这是 §3.2 的直接解。
  3. **硬约束**：**绝不每 tick 校准**（会与 `travel()`/连续段 `continuous_advance` 的动量、跳跃弧打架）；**不改 y**；**清空水平 delta**；**不许触发位移/传送事件**；**不许动 `fallDistance`**。
- **代价与风险**（如实）：≤0.3 的瞬移在客户端是"远程实体插值"，理论上平滑，但**必须让用户用眼睛判**（见 §6-Q4）；另外它会让 `EXACT` 容忍度变成"反正会摆正"的遮羞布 ⇒ **必须同时保留"摆正后仍不满足就如实失败"的路径**，否则会把真问题藏起来。

### 5.3 明确**不**该用的地方

| 不要用在 | 为什么 |
|---|---|
| 修 §2 的弃巷 | 目标格已经是**空气**，把 bot 摆得多正都挖不了它。这条只能改**谓词**（单格口径），与校准无关 |
| 规划器里 | 规划是纯函数，不许改实体状态 |
| 当作"万能对齐"每 tick 调用 | 会吃掉移动控制器的语义（离心是移动的**正常中间态**） |
| 替代 `ore_budget_exhausted` / `ore_deferred` 的语义修正 | 那是队列策略，不是位置问题 |

### 5.4 判据（可红可绿，必须在离线夹具里先钉住）

1. **机制 A 夹具**：造"1 格宽地板 + 邻列实心"的几何，把 bot **人为摆在离中心 0.3 处静止**（`setPos`，正是校准的反操作），跑 `DESCEND` ⇒ 断言在 N tick 内到达目标格。
   红臂：去掉居中那一支 ⇒ 必现 `segment_timeout`（复现本轮 145 tick）。
2. **机制 B 夹具**：摆 0.45 离心 + 一个脚边掉落物 ⇒ 断言 `collected=1/1`（而不是 `no_standable_approach`/`retire`）。
   红臂：关掉校准 ⇒ `goal_excluded` + `retire`。
3. 两条都要复算"摆正后离心 = 0"这一读数，**不许只看 PASS**（`silent-measurement-failure`：判据里的数必须是它真读到的那个数）。

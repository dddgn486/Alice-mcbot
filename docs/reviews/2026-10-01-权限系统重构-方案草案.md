## §4 ⭐ 回答你的四问：「谁识别 · 什么时候识别 · 怎么授权 · 怎么不臃肿」

### §4.1 「识别」与「授权」的契约（拆开之后各自的形状）

| | **识别**（意图） | **授权**（权限） |
|---|---|---|
| 问的是 | 这一格**是不是我要办的事** | 这一格**我允不允许动** |
| **谁**回答 | ⭐ **任务**（只有它有目标集） | ⭐ **保护区**（只有它有区域权威） |
| **什么时候** | ⭐ **规划期一次性**（不是逐方块热路径） | ⭐ **写入那一刻，一次** |
| 产物 | **意图集**（我打算动哪些格） | 放行 / 拒绝码 |
| 输入 | 任务自己的目标定义 | ⭐ **位置 ＋ 动作**（⛔ **不看意图**） |
| 载体 | ⭐ **已存在**：`TaskTargetProtection.SCOPES` 的谓词（`isTaskTarget()`） | 今天 = `ZoneAuthority.authorize` |

⭐ **两条互不查询** ⇒ 三个直接收益：
1. ⛔ **"没权限的树被算成少了一棵树"消失**（`A2` §6.2 的病灶：`RegionLumberJob:557-579` 只数 `raw.viable()`）；
2. ⛔ **"识别期过滤、写入期漏"的不对称消失**（今天砍树过滤、补种直写 `setBlock` 绕过，`RegionLumberJob:971`）；
3. ⭐ **`A2` 里"立轴 2 代价高（热路径 + 反向依赖 `job/`）"这个顾虑消失了** ——
   因为**授权不再需要目标集**，识别也**不需要权限** ⇒ 两条都便宜。

### §4.2 「怎么授权」

⭐ **收窄到一条判据**（这是裁定 1 的直接推论）：

> **这一格在保护区内 ∧ bot 在这一格上没有生效的授权 ⇒ 拒。**

⛔ 就这一条。区外 ⇒ `PASS`（不产生授权语义，`D-563` §五）。

⚠️ **但"授权"从哪来，我今天要报一个口径问题**：你说保护区内额度有**两种来源**——
① 默认任务区域修改额度 ② 紧急逃生临时权限+额度。
`A0` §1.9 实测：② 的代码里**自带"信封"前提**（`SurvivalExitTask.withReserve` ＋ `WriteEnvelopes.had(...)`，
`D-241` 逐字：「**只有信封本来就有写授权的任务才准动用准备金**」）
⇒ ⭐ **所以"两种来源"实测是「一种授权来源（任务区域封套）＋ 一种额度调整（逃生准备金）」**。
⚠️ **这条需要你确认口径**：如果逃生**不**是独立授权来源，那么"授权来源"就只有**一个**——
方案会因此更简单（§5 就是按"一个"写的）。

### §4.3 「怎么不臃肿」

⭐ 三个机制，都不是"加分支"：
1. **维度分离**（§2）：权限只占 D/E/F，⛔ 不再和方块语义（C）、自保（G）挤在一个函数里；
2. **弃权链**（§3 第 3 件）：一个维度**只回答自己那一格**，不表态就 `PASS` ⇒
   新增一条规则 = 新增一个谓词，⛔ 不是往 13 步链里插一个 `if`；
3. **顺序显式登记**（§3 第 4 件）：顺序成为**数据**，可打印、可断言、可测试。

## §5 ⭐ 授权面的最小形状（提议）

```
[容器] 按登记顺序问谓词：
  A 幂等   → 是空气 ⇒ ALLOW(already_air)      ← 幂等成功，不是拒绝（D-323 边界）
  B 意图   → ⛔ 不在本链里（识别面已负责；本链不看意图）
  C 方块   → 不可破坏/流体/危险邻接… ⇒ DENY(code)
  G 自保   → 拆了害到 bot 自己 ⇒ DENY(underfoot_block)
  D 权限   → ⛔ 不在保护区 ⇒ PASS
            在保护区 ⇒ 有生效授权 ? ALLOW : DENY(protected_area…)
  E 档位   → 授权存在时，这个动作在这一档允许吗 ⇒ DENY(zone_*_not_allowed)
  F 额度   → 超限 ⇒ DENY(quota_exhausted)
  → 全 PASS ⇒ ALLOW
```
⭐ **每条谓词都可单独断言**（给 pos + act ⇒ 期望的三态），⛔ 不需要构造整条链。

# §10 用户 2026-10-01 第二轮更正（撤回口径 ＋ 目标过滤 ＋ 类名纠正）

## §10.1 ⭐ 撤回与更正：**授权来源 = 保护区封套**（一个）

用户逐字：「**我撤回保护区内额度有两种来源这句话**，应该是**有两种情况拥有修改额度**，
所以**授权来源可以直接保护区封套**（再次说明**任务区是一种保护区的子类**，**只要是保护区，就有权限管理**）」。

| 项 | 原（我写的） | 更正后 |
|---|---|---|
| 额度来源 | 「两种来源」① 任务区域额度 ② 逃生临时权限 | ⭐ **「两种情况拥有修改额度」** —— 逃生是**情况**，⛔ 不是第二种**来源** |
| 授权来源 | 待裁（我荐"一个"） | ⭐ **一个：保护区封套** |
| 任务区 | 「授权封套」（与保护区并列的两个载体） | ⭐ **它是保护区的子类** ⇒ ⛔ 不是并列的第二载体 |
| 权限管理的适用面 | 「在保护区内 ∧ 有生效任务区覆盖」 | ⭐ **只要是保护区，就有权限管理** |

### ⭐ 对方案的三处实质影响（都是简化）

**影响 1 · 两个查询合成一个。** 今天授权面问两次：`isClaimed`（保护区父类，持久）
＋ `zoneOf`（任务区子类，随 scope 生灭）。新口径下这是**一个概念的两层**：
⭐ **「这一格属于哪个保护区实例（父类 or 子类）」——问一次。**

**影响 2 · `protected_area` 的语义要重写。** 它今天的含义是
「在保护区里、**但缺**子类（任务区）覆盖 ⇒ 拒」（`ZoneAuthority:147-151`）。
新口径下这句要变成「**父类保护区自己有权限管理 ⇒ 问父类要授权**」——
⛔ 不再把"缺子类"当成拒绝理由（那是把**实现细节**当成了判据）。

**影响 3 · ⭐「保护区家族有两类生命周期」被显式化。** 父类（持久认领）活在 `SavedData` 里、
子类（任务区）**随 `scopeId` 生灭**。这正是 `A2` §7.4「真源 4 类」里
**A 类（持久）与 B 类（随任务生灭）被混在一条阶梯上**的根源 ⇒ 新方案里**必须分列**。

### ⚠️ 由此产生的一个**精确的待确认点**

> **父类保护区（持久认领）自己的默认封套 = 什么？**

今天它**隐含**是"不给写"（因为 `protected_area` 一律拒）。新方案要把它**显式化**：
⭐ 我的判断 = **父类默认封套 = 只读**（等价于 `L0_READ_ONLY`），子类可以**只能更严或按声明提升**。
⚠️ **这条要你确认**，因为它决定"保护区"是"默认禁止 + 可授"还是"默认允许 + 可禁"。

## §10.2 ⭐ 问题一：「目标」怎么过滤，由谁给过滤单

### §10.2.1 ⭐ 原则**早已写死**（`D-329`，用户 2026-09-20）—— 我只需引用

`job/mine/MineIntent` 的 javadoc 逐字：
> ⚠️⭐ **意图是"搜索偏好"，不是"可挖承诺"**（用户 2026-09-20 点出的陷阱）：一个符合意图的作业区里
> **完全可能有一部分目标实际不可挖**（被保护、不可破、视线不可达）。⇒ 本类的 `refusalFor` 只负责
> 回答"**在不在作业区里**"，**绝不**替授权面/破坏面下结论；区内的候选照样要过
> `ZoneAuthority.candidateRefusal` + `BlockInteraction.breakable`，而且**它们自己的理由码必须保住**
> （不许被 `outside_work_area` 顶替）——否则"不可挖"就会被伪装成"不在计划里"。

`job/JobDeclaration` 同样逐字：
> ⭐ **作业区 / 意图**：…**它只影响候选的取舍与顺序，绝不替授权面/破坏面下结论**。

⇒ ⭐ **"识别不替授权下结论"这条原则，三年前就写死在两个类的 javadoc 里了。**
⛔ **而 `LumberCandidateSource:69-75` 违反的正是它**（用 `candidateRefusal` 把树从 `viable` 踢走）——
⭐ 这是**反方向**的同一个病：**授权替识别下了结论**。

### §10.2.2 ⭐ 载体**也已存在**：`CandidateSet(viable, rejected)`

```java
// job/CandidateSet.java
public record CandidateSet(List<Candidate> viable, List<String> rejected) { … }
```
⭐ **它已经是"两个面并排"的形状** —— `viable` = 意图内可作业；`rejected` = 理由串。
⛔ 问题只在**谁往 `rejected` 里写**：今天**候选源自己既判意图、又判权限**，两件事混在一个 `continue` 里。

### §10.2.3 ⭐ 我的提议：给过滤单**分两个出处**，⛔ 不互相吞并

> **「目标单」（意图）由 `job/` 给；「拒绝单」（权限）由授权面给；两者在 `CandidateSet` 里并列。**

具体 = **`CandidateSet` 加第三栏**（改动极小，一栏 `List`）：

| 栏 | 谁填 | 语义 | ⛔ 不许 |
|---|---|---|---|
| `viable` | ⭐ **job 层**（意图/作业区） | 意图内、未尝试 | 不许被权限过滤掉 |
| `rejected` | ⭐ **job 层** | **作业做不到**（`trunk_too_tall`/`no_stand`/`outside_work_area`…） | 不许放权限码 |
| ⭐ **`denied`**（新） | ⭐ **授权面** | 意图内、**授权面已明确拒绝**（带码） | 不许与 `rejected` 混 |

⭐ **三个直接收益**：
1. ⛔ **`A2` §6.2 的病灶（"没权限被算成少了一棵树"）机械消失** ——
   下游 `standing`/`deficit` 只要 `= viable + denied` 就不会虚高；
2. ✅ **`D-341` 的"如实失败"不再需要下游补丁**（`permissionBlock()` 从 `rejected` 里**猜**哪个是权限码
   + `D-344` 的两条**顺序约束**）—— `denied` 非空且 `viable` 空 ⇒ **直接就是那句话**；
3. ⭐ **决策层能同时看到"我想挖什么"与"我不被允许挖什么"** ⇒ 这是 `O119`（"运行账对 LLM 粒度太小"）要的那种事实。

### §10.2.4 ⚠️ 剩下一个真问题：**`denied` 什么时候算**

- ⛔ **不能在候选生成时算**（那就回到今天的病：授权进识别）；
- ⛔ **也不能只在写入时算**（那决策层会**反复选中挖不动的目标**，`D-323` 附注一记过这个代价：
  一个目标白花 ≈3 秒 × 3 次）；
- ⇒ ⭐ **第三条路：在「选择」那一刻算一次**（`job/SelectionPolicy` 的 pick），结果落进 `denied`。
  ⇒ 这不违反 `D-329`：**意图**仍是 job 自己的；**权限**仍是授权面给的；**两者只在选择处相遇一次**，
  ⛔ 且互不写进对方的栏位。

⚠️ **代价（诚实说）**：`denied` 会让"选择"变贵（每个候选一次授权问）。
⭐ 但可缓存：**授权是区域级的，同一 `scopeId` 内同一格的答案不变**（今天的 `ZONE_PLACES`/`AUDITED` 已是这个形状）。

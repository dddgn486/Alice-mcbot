## 4. 可由日志几何反推的推论（不是猜测，是算出来的）

已知：`[CollectDrops] retire … inRange=false`，`inPickupRange` 的判据是
`bot.getBoundingBox().inflate(1.0, 0.5, 1.0).intersects(item.getBoundingBox())`（`CollectDropsTask:488-490`），
而日志同时给出了 `botBox` 与 `itemPos`/`itemY`：

- 物品占格 `432,87,223` ⇒ 其中心 x ∈ [432.125, 432.875]（`Block.popResource` 的随机偏移），盒半径 0.125，y 底面 87.000。
- 第二次退役时 `botBox.maxX = 431.65` ⇒ 外扩后 432.65；要 `inRange=false` 必须 `item.minX > 432.65`
  ⇒ **物品 x > 432.775**（即落在该格的**东侧 1/8**）。
- 于是 `withinPickupReach(431,87,223, item)`（`CollectDropsTask:477-481`，逐轴 |格中心−物品中心| ≤ **1.2**）
  算得 |431.5 − 432.8| ≈ **1.35 > 1.2** ⇒ **被拒**。
- 而**真实**的原版判据在 bot **站在格中心**时：bot 外扩 maxX = 431.5+0.3+1.0 = **432.8** > item.minX ≈ 432.725 ⇒ **会命中**。

⇒ **`withinPickupReach`（粗判据）比 `inPickupRange`（真实判据）更严**，并且它恰好把"唯一可站的邻格"拒掉了。
另一方面 bot 实际停在 x≈431.19（**没走满到格中心**，外扩 maxX=432.49），此时真实判据也不命中 ⇒ 差 **≈0.08–0.28 格**。
**这与"用户推一下 bot 就捡到了"完全一致**：推一下把 bot 的盒推过阈值即可。

## 9. ⚠️ 同轮日志暴露的**另一处**问题：A1 会把"本 tick 被拒"变成"永久不可达"

**这是上一轮改动（A1）引入的副作用，必须记账。**

事实链（代码直读 + 同轮日志）：

- `MiningPlanner.selectBestApproach`（`MiningPlanner.java:258-283`）对每个候选站位调用 `planPath`，然后
  `planned++;` → `if (!path.reached()) continue;` —— **不区分失败状态**。A1 被拒时返回的是
  `PlanningStatus.SEARCH_LIMIT`（**本 tick 资源**），它和"搜完了确实没有路"在这里**长得一样**。
- 于是 `planned=3` 里可能有 2 次根本没搜（本 tick 被 A1 拒），最终仍打印
  `[MiningPlanner] … planned=3 capped=true reason=no_reachable` ⇒ 文案把"**没搜**"说成了"**没有路**"。
- 上游后果是**永久的**：`MiningPlanner` 返回 `no_reachable_candidate` ⇒ `MineTask` 报
  `found_but_unminable` ⇒ `MineJob.mine()`（`MineJob.java:415`）`attempted.add(mined)` 记入 `attemptFailed`
  ⇒ 该格**本会话再也不会被选中**（`withoutAttempted` → `already_attempted`）。

同轮日志佐证：

| 观测 | 值 |
|---|---|
| `[SearchTick]` 拒绝 | 25 次，**全部 `已发起=1`**（即每 tick 只允许 1 次烧预算搜索） |
| `[MiningPlanner] mode=TUNNEL …` | 每次都是 `candidates=13 planned=3 capped=true reason=no_reachable` |
| `cluster_done`/SKIP | 4 条 `already_attempted` + 1 条 `unbreakable` |
| 目标 `436,82,229` | **从未被挖**（`[WRITE] break` 0 次、`block_break_done` 0 次），却已 `already_attempted` |
| `search_incomplete` | **0 次**（`MineJob.shortfallReason` 已有这个正确词汇，但规划器没把事实传上去） |
| 本轮实际挖掉 | 9 块 |

**为什么这条必须修**：项目红线写的是 `SEARCH_LIMIT ≠ UNREACHABLE`，而这里**在行为上**刚好违反它
（被拒 ⇒ 永久跳过矿石）；同时**日志说谎**——本文档第 6 节的第四轮复算就是照着 `reason=no_reachable`
的字面读的。修法很小：在 `selectBestApproach` 里把 `SEARCH_LIMIT` 视为"**这一格本轮还没被评价**"
（不计入 `MAX_APPROACH_PLANS`、不并入 `no_reachable`、把 `searchLimited` 事实向上传给
`shortfallReason` ⇒ `search_incomplete`），于是矿石下一 tick 还能轮回来。

**结论（事实级）**：bot **尝试了**捡（进了 `[CollectDrops]` 阶段、发了寻路请求、walk 了 1 格），
但**在寻路 `SEARCH_LIMIT` 后立即退役**（`CollectDropsTask` 第 329–342 行：`runner` 非 DONE ⇒ 直接 `retire` + `endCluster(true)`，
**不经过** `reanchor`），随后任务以 `reason=done` 收尾 ⇒ 产物**静默丢失**（外层 `[Job]` 继续挖下一块，
且该格被登记为 `unbreakable` 之类"已了结"）。

## 4. 可由日志几何反推的推论（不是猜测，是算出来的）

已知：`[CollectDrops] retire … inRange=false`，`inPickupRange` 的判据是
`bot.getBoundingBox().inflate(1.0, 0.5, 1.0).intersects(item.getBoundingBox())`（`CollectDropsTask:488-490`），
而日志同时给出了 `botBox` 与 `itemPos`/`itemY`：

- 物品占格 `432,87,223` ⇒ 其中心 x ∈ [432.125, 432.875]（`Block.popResource` 的随机偏移），盒半径 0.125，y 底面 87.000。
- 第二次退役时 `botBox.maxX = 431.65` ⇒ 外扩后 432.65；要 `inRange=false` 必须 `item.minX > 432.65`
  ⇒ **物品 x > 432.775**（即落在该格的**东侧 1/8**）。
- 于是 `withinPickupReach(431,87,223, item)`（`CollectDropsTask:477-481`，逐轴 |格中心−物品中心| ≤ **1.2**）
  算得 |431.5 − 432.8| ≈ **1.35 > 1.2** ⇒ **被拒**。
- 而**真实**的原版判据在 bot **站在格中心**时：bot 外扩 maxX = 431.5+0.3+1.0 = **432.8** > item.minX ≈ 432.725 ⇒ **会命中**。

⇒ **`withinPickupReach`（粗判据）比 `inPickupRange`（真实判据）更严**，并且它恰好把"唯一可站的邻格"拒掉了。
另一方面 bot 实际停在 x≈431.19（**没走满到格中心**，外扩 maxX=432.49），此时真实判据也不命中 ⇒ 差 **≈0.08–0.28 格**。
**这与"用户推一下 bot 就捡到了"完全一致**：推一下把 bot 的盒推过阈值即可。

## 8. 最小修复候选（**待讨论，未实施**）

1. **粗判据对齐真实判据**（`withinPickupReach` 改成像 `inPickupRange` 一样用"站在该格中心时的外扩盒 vs 物品盒"）
   ⇒ `431,87,223` 会被接受为锚点，走位目标变成"能站且够得着"的格。
2. **寻路失败分支允许重试**：`runner` 非 DONE 时，若 `reanchors < MAX_REANCHORS` 且存在**不同的**可站锚点 ⇒ `reanchor` 而不是立即退役（复用既有机制，不新造）。
3. **到位但不在范围内、且锚点就是当前格** ⇒ 朝物品走一小步（用户手动做的就是这件事）。
4. **补日志**：`normalizeAnchor` 在 `best == null` 时也要打一行（现在静默回退，导致 H1 无法从日志判定）。

反向对照（天然具备）：**修复前**三种格级都退役；**修复后**同场景应 `collected=1/1`；
再加一个人工对照：**故意让物品在不可达处**（如悬空/封闭）仍应如实 `unreachable`，不得变成"永远重试"。

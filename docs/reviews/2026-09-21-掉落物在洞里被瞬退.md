## 0. ⭐ 更深一层的根因（2026-09-21 用户三条情景后定位）：**图不完整**

> 用户补充：bot 退役前**站着反复搜索**；**朝东**推的；**夹缝里两件煤看得见，"只挖一格方块就能走过去"**；
> "我严重怀疑算法有累赘，直接寻路到掉落物实际所在格不就行了"。

**用户方向对了一半，而且是关键的一半**：`anchor` **本来就等于掉落物所在格** `432,87,223`
（§1 日志原文），所以不是"没往那格寻路"，而是**"往那格的寻路在图里没有入边"**。

### 缺口（代码直读）

| 边类型 | 准入判据 | 对 `432,87,223`（脚位空气、头位 dirt） |
|---|---|---|
| `TRAVERSE` | `appendPlane:342` → `MovementHelper.canTraverse:334` → **`canStandCentered`** = `canWalkOn && canWalkThrough(foot) && canWalkThrough(foot.above())` | **拒绝**（头位 dirt） |
| `BREAK_AND_TRAVERSE` | 位移 2 格、中间列被挡、**目标须 `canStandCentered`**（`:376`） | 不适用（1 格位移；2 格位移的落点 `433` 是 stone） |
| `BREAK_AND_ENTER` | `appendBreakAndEnter:169`：**`if (canWalkThrough(level, to)) return;`** ← 只查**脚位** | **提前 return**（脚位是 air）⇒ **不生成** |

⇒ **"脚位可通行 + 头位被挡"的格子在整张图里没有任何入边**（三个生成器全落空）。
这正是**一格高夹缝**的形状，也正是用户说"只挖一格方块就能走过去"的**那一格**：

```
432,87,223 = air（脚位）→ 三个生成器都以为这是"能走的"，于是谁都不生成写边
432,88,223 = dirt（头位）→ 真正需要被破掉的**就是这一格**
```

而 `BreakAndEnterExecution.collectBlockers:69-78` **本来就会**把头位收进待破列表：

```java
if (!canWalkThrough(level, toFoot))         result.add(toFoot);
if (!canWalkThrough(level, toFoot.above())) result.add(toFoot.above());   // ← 会收 432,88,223
```

⇒ **唯一拦路的是一行谓词**：早退用脚位判"目的地可通行"，而"可通行"的真正定义（同文件 `canStandCentered`）含头位。

### 对照 Baritone（`D-036` 要求先对照）

- `baritone-1.20.1/.../movements/MovementTraverse.java:57`：
  `super(baritone, from, to, new BetterBlockPos[]{**to.above()**, to}, to.below())`
  —— Baritone 的 Traverse **本身**就把目的地**头位**列为可破方块；
- 同文件 `:109-118`：`hardness1 = …(destX, y, destZ)` 与 **`hardness2 = …(destX, y + 1, destZ)`**，
  两者都进 cost（`return WC + hardness1 + hardness2`）。

⇒ **"脚位空、头位实"在 Baritone 里是一次正常且已计价的 Traverse（顺手把头位挖掉）**；
Alice 既没让 Traverse 覆盖它、又让 BreakAndEnter 提前退出 ⇒ **这是相对 Baritone 的内核缺口，且此前从未登记**（D-036 要求登记偏离）。

### P0 ⭐ 图补全：让"脚位空、头位实"的格有入边（**1 行谓词 + 夹具**）

- 改动：`SurfaceMovementProvider.appendBreakAndEnter:169` 的早退判据
  `canWalkThrough(level, to)` → **`canWalkThrough(level, to) && canWalkThrough(level, to.above())`**
  （即"**整体**可通行才属于 TRAVERSE"）。之后 `collectBlockers` 已会收头位、`canWalkOn(to)` 已有支撑检查、
  `breakable`/成本计算都是现成的 —— **不需要新造机制**。
- 为什么先做它：它是**内核缺口**（相对 Baritone `MovementTraverse:57,109-118`），一处修好同时覆盖
  ① 本次拾取 ② 可能的 `D-373` 88 段绕行 ③ D-366b 抱怨的"绕远/折返"。
- 反向对照（三个）：
  1. **改回脚位判据 ⇒ 夹具必须红**（同一场景 `collected=0/1`）；
  2. **脚位也被挡**（`[BreakEnter] cleared pos=429/430/431` 是天然对照）⇒ 行为**不得**变化；

## 9. ⚠️ 同轮日志暴露的**另一处**问题：A1 会把"本 tick 被拒"变成"永久不可达"

**这是上一轮改动（A1）引入的副作用，必须记账。**

事实链（代码直读 + 同轮日志）：

- `MiningPlanner.selectBestApproach`（`MiningPlanner.java:258-283`）对每个候选站位调用 `planPath`，然后
  `planned++;` → `if (!path.reached()) continue;` —— **不区分失败状态**。A1 被拒时返回的是
  `PlanningStatus.SEARCH_LIMIT`（**本 tick 资源**），它和"搜完了确实没有路"在这里**长得一样**。
- 于是 `planned=3` 里可能有 2 次根本没搜（本 tick 被 A1 拒），最终仍打印
  `[MiningPlanner] … planned=3 capped=true reason=no_reachable` ⇒ 文案把"**没搜**"说成了"**没有路**"。
- 上游后果是**永久的**：`MiningPlanner` 返回 `no_reachable_candidate` ⇒ `MineTask` 报
  `found_but_unminable` ⇒ `MineJob.mine()`（`MineJob.java:415`）`attempted.add(mined)` 记入 `attemptFailed`
  ⇒ 该格**本会话再也不会被选中**（`withoutAttempted` → `already_attempted`）。

同轮日志佐证：

| 观测 | 值 |
|---|---|
| `[SearchTick]` 拒绝 | 25 次，**全部 `已发起=1`**（即每 tick 只允许 1 次烧预算搜索） |
| `[MiningPlanner] mode=TUNNEL …` | 每次都是 `candidates=13 planned=3 capped=true reason=no_reachable` |
| `cluster_done`/SKIP | 4 条 `already_attempted` + 1 条 `unbreakable` |
| 目标 `436,82,229` | **从未被挖**（`[WRITE] break` 0 次、`block_break_done` 0 次），却已 `already_attempted` |
| `search_incomplete` | **0 次**（`MineJob.shortfallReason` 已有这个正确词汇，但规划器没把事实传上去） |
| 本轮实际挖掉 | 9 块 |

**为什么这条必须修**：项目红线写的是 `SEARCH_LIMIT ≠ UNREACHABLE`，而这里**在行为上**刚好违反它
（被拒 ⇒ 永久跳过矿石）；同时**日志说谎**——本文档第 6 节的第四轮复算就是照着 `reason=no_reachable`
的字面读的。修法很小：在 `selectBestApproach` 里把 `SEARCH_LIMIT` 视为"**这一格本轮还没被评价**"
（不计入 `MAX_APPROACH_PLANS`、不并入 `no_reachable`、把 `searchLimited` 事实向上传给
`shortfallReason` ⇒ `search_incomplete`），于是矿石下一 tick 还能轮回来。

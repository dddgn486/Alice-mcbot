# `P4′` 台架与读数（每 tick 搜索预算的 A/B）

**出处**：`docs/OPEN_ITEMS_LEDGER.md §11 C 段 P4′`（由 `P4` 派生）
**台架**：电池步 `tick_budget_bench`（EXTRA，`TickBudgetBenchTask`，2026-09-24 新增）
**验证等级**：`IMPLEMENTED` + `COMPILES` + `SERVER_TESTED`（无头电池实跑；无客户端/真人证据）

## 一、为什么需要这个台架

台账 `P4′` 的原文判据是「**先红后绿**：注入 400 ⇒ CORE 出现/加重 `Can't keep up`；收到 ≤60 ⇒ 消失
（**需客户端或电池可复现的读数**）」。要裁这一条，先得把"可复现的读数"造出来 —— 本台架就是那台仪器：

- `SearchTickBudget` 有**夹具专用口**（`setLimits` / `resetForFixture` / `restoreDefaults`）
  ⇒ **一次运行**就能把三种配置 × 三种负载全量出来，**不用改源码重编译**；
- 每个格子都严格在**一个 tick 内**跑完（`resetForFixture` 把账清零并离开当前 tick ⇒ 下一格是干净的一 tick）。

## 二、九格读数（`run/headless-logs/20260924-140303-single_tick_budget_bench.log`）

三种负载：
**`MINING`** = 13 次搜索、每次受**自己的 50 ms 上限**约束（镜像 `MiningPlanner.planTunnel` 的 13 个站位候选 = **生产形态**）·
**`CHEAP`** = 30 次短搜索（镜像 `mine_menu` 的 20 次 / 161 ms 批处理链）·
**`LEGACY`** = 13 次**无时间上限**的 20000 节点搜索（`D-369` 时代的历史形态 ≈185–229 ms/次）。

| 配置（毫秒/贵搜索/次数） | `MINING`（生产形态） | `CHEAP` | `LEGACY`（历史形态） |
|---|---|---|---|
| **PROD** 400 / 1 / 32 | **402 ms**（放行 8 / 拒 5） | **400 ms**（8 / 拒 22） | 761 ms（放行 1 / 拒 12） |
| **TIGHTENED** 60 / 1 / 32 | **100 ms**（放行 2 / 拒 11） | **100 ms**（2 / 拒 28） | 358 ms（1 / 拒 12） |
| **UNGATED**（三条轴全关） | 650 ms（13 / 拒 0） | 1500 ms（30 / 拒 0） | ⭐ **2578 ms**（13 / 拒 0，183–229 ms/次） |

⭐ **红臂在电池里真的出现了**（这是全日志唯一一条）：

```
Can't keep up! Is the server overloaded? Running 2198ms or 43 ticks behind
```

它就是 `UNGATED/LEGACY` 那格（单 tick wall = **2578 ms**）造成的 —— 与真机那三次
（`2035 / 2632 / 2232 ms or 40 / 52 / 44 ticks behind`）同形。

## 三、判据（16 checks 全绿）

| # | 判据 | 读数 |
|---|---|---|
| ① | 前提：`UNGATED/LEGACY` 每次搜索 ≥ `EXPENSIVE_SEARCH_MILLIS`(100ms) | 183–229 ms ✓ |
| ② | 不变量：闸门开着时 `account ≤ 毫秒上限 + 该格单次最大 ms`（6 格） | 全部成立 ✓ |
| ③ | 红臂前提：`UNGATED/LEGACY` 单 tick ≥ 2000 ms | **2578 ms** ✓ |
| ④ | 效益：收紧后生产形态少烧毫秒（100 < 402）· 廉价链同向（100 < 400）· 代价 = 开始拒绝（11>0 / 28>0） | ✓ |
| ⑤ | 夹具纪律：三条轴还原成生产默认 + 自建基岩壳 125 格逐格还原 | ✓ |

## 四、⭐ 三条结论（都在读数里，不是推断）

1. **收紧的真实收益 = 最坏单 tick 搜索耗时 402 ms → 100 ms**（生产形态与廉价链同向）。
2. **收紧的真实代价 = 同一个 tick 里被拒的搜索数 5 → 11**（廉价链 22 → 28）⇒
   「一个 tick 连做一串搜索」的正常批处理链首当其冲 —— `mine_menu` 的 161 ms 链当初正是为此把
   毫秒轴定在 400（`P4` 评审：第一版用 150 ms ⇒ 该步 1 条既有判据变红）。
3. ⭐⭐ **`P4′` 原判据的后半句（"收到 ≤60 ⇒ `Can't keep up` 消失"）在算术上不成立**：
   闸门开着时，**生产形态**最坏 ~402 ms（连原版告警阈值 2000 ms 的一半都不到）⇒
   400 与 60 **都不会**产生 `Can't keep up`；它只在"闸门全关 + 历史形态"下出现。
   ⇒ 这条判据要成立，必须先承认"红"只能在**闸门关闭**时复现（本台架已把它做成可复现的读数）。
4. ⭐ **真正决定最坏 tick 的不是毫秒轴，而是"第一个搜索永远放行"**：`LEGACY` 那两格
   （PROD 761 ms / TIGHTENED 358 ms，都是**单次**搜索的时长）说明 —— 当**单次搜索本身**很贵时
   （无时间上限的 20000 节点搜索），收毫秒兜底轴几乎不改变结果（两格差 = 搜索耗时波动）。
   ⇒ 若目标是"任何 tick 都别超过 X ms"，杠杆是 **给重消费者自己的预算加时间上限**
   （`SearchBudget` 的 `maxMillis=0` 那一档），而不是收 `DEFAULT_MAX_MILLIS_PER_TICK`。

## 五、诚实边界

- 本台架**不判**"该不该收紧到 60"：它同时是**能力决策**（代价见 §四.2）⇒ 需要用户拍板。
- 读数在同一台机器、同一世界母本、同一次运行内取得（三种配置**同轮对照** ⇒ 不受机器差异影响）；
  但绝对毫秒值随机器/负载变化，**可比的是同一轮内的相对关系**。
- `MINING`/`CHEAP` 两格的 `reached=0`（全部 `PARTIAL`）是**刻意**的：目标不可达 / 每次搜索都被它自己的
  50 ms 上限咬住 ⇒ 每次搜索都烧满预算 = 这正是要量的"贵搜索链"形态。

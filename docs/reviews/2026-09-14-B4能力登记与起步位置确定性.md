## 1. B4：把 `MOD_ADAPTER_PROTOCOL.md` §3 的散文判据变成断言

### 1.1 散文判据原来的两个洞（都是实测出来的，不是推测）

散文判据说"进通用骨架必须满足①上游自述 ②至少两上游共享 ③纯形态学可自校验"，
而给的**取证方式**是"各类里 `mekanism` 字面量出现次数（`grep -c`）"。两个洞：

1. **`grep` 分不出代码与注释**。实测（`tools/machine-map.py` 字节扫描客户端 16 个 jar）：
   `getCraftSlots` 在 **0 个 jar** 里命中、`getItem` 在 **13 个 jar** 里命中 —— 而两者在我们的代码里
   **只出现在注释**（`GridDiscovery` / `CraftMenuIntrospection` 的"这样写只会拿到 null"说明）。
   ⇒ 按字面量计数会把**文档**算成**依赖**。
2. **"0 处 `mekanism`" ≠ 通用**。反例是 `MachineCycle`：**0 处模组字面量**，却**写死 5 个上游访问器名**
   （`getOperatingTicks` / `getActive` / `getRecipeType` / `getRegistryName` / `getEnergy`）。
   "我反射问对象自己"与"我认类名"是**两件事**；字面量计数把前者也算成后者、又把后者漏掉。

### 1.2 现在断言什么（**双向对账 + 上游存在性**）

- **正向**：`CAPABILITY_FILES` 里出现的**访问器形字面量**（`"getXxx"`/`"isXxx"`/`"hasXxx"`，**先剥注释**）
  必须**逐条**声明在 `CAPABILITY_GROUPS` 里 ⇒ "我们依赖了哪些上游名字"不再隐含；
- **反向**：声明的每个名字**必须真的被用** ⇒ 登记不会腐烂成装饰；
- **第三向（有 jar 时）**：名字必须在**该上游 jar 的 class 字节**里找得到
  ⇒ 堵"声明了一个上游根本没有的名字"（改名/笔误/想当然）。缺 jar ⇒ 进 `unverified`
  （沿用 T0-a 口径：**"没复核"绝不等于"复核通过"**）。

**归属不靠猜**：谁属于哪个上游由**字节扫描上游 jar** 反查（2026-09-14）。

### 1.3 读数

```
能力登记（B4）: capabilities=31 组=5 已用=31
                上游已取证=mekanism,thermal,sophisticated,oreexcavation
                共享/基础设施名=['getSlots', 'getStackInSlot']
MACHINE_MAP_CHECK_RESULT PASS: 行=59 未映射=4（Tier A + Tier B 上游双向覆盖 + B4 能力登记双向对账均已执行）
```

**反向对账首跑就精确对齐**：`grep` 数出 32 个 `getXxx` 字面量，其中 2 个是注释 ⇒ 真实依赖 **30** 个，
加上 `isCooking`（`isXxx` 形）= **31** = 声明数。**两组独立方法（人工归属 vs 工具扫描）得出同一个数。**

**组**：`mekanism`(14) / `thermal`(4) / `sophisticated`(10) / `oreexcavation`(1) / `forge`(2，
`IItemHandler`，**不随模组目录分发** ⇒ 结构上不做 jar 取证，已在报告写明)。

### 1.4 负测试（证明它**真能红**）

把一个名字故意改成上游没有的 `getTileEntityRenamedByUpstream` ⇒ **3 条独立报错**：
① 正向"用了但没声明"；② 反向"声明了但没用"；③ 上游字节扫描找不到。`FAIL 问题=3`。
改回 ⇒ `PASS`。

### 1.5 顺带修掉的工具缺口

`find_jar` 原来把 glob **锚定在开头**，而客户端 `mods/` 里有的 jar 带**中文前缀**
（实测 `[矿石挖掘] oreexcavation-1.13.174.jar`）⇒ `oreexcavation-*.jar` **静默匹配不到**，
症状是那句断言进 `unverified`（**容易被读成"环境问题"而不是"我们匹配错了"**）。
现在同时尝试带前缀的写法。⇒ oreexcavation 的能力存在性**从"未复核"变成"已取证"**。

## 2. (甲)：`ASCEND_NO_HEADROOM` 的可判读读数

`ASCEND_NO_HEADROOM` 的产生点是 `AscendExecutionFactory` 里 `!canWalkThrough(from.above(2))`
（起跳需要的头部空间被占）。原来日志只有"码 + 起始脚位"，**分不出**三种可能：
① 场景真在那一格建了墙；② 我们自己的 `PLACE_*` 残留挡路；③ 时序相位（同几何、不同时刻的残留）。

**修法**：把**挡路那一格是什么方块**直接写进失败码 ——
`<稳定码>@<label>=<x,y,z>:<block_id>,…`（`@` 之前是稳定码，grep/比较按前缀用）。
同期给 `ASCEND_INVALID_PRECONDITION` 也加了（`to`/`to.up`/`to.down`）。
这是**终态日志**的一部分，**不是**要回收的临时探针。已核对全仓：**没有任何代码按整串比较**这些码。

⚠️ **诚实边界**：加完之后连跑 **4 轮**，`ASCEND_NO_HEADROOM` **没有再现** ⇒
这条读数**尚未被真实触发过**（`IMPLEMENTED`+`COMPILES`，不是 `SERVER_TESTED`）。
下次见到它时 grep：`ASCEND_NO_HEADROOM@`。

（同一批 9 轮里另 6 轮 30/30。）

⇒ **(A) 修的是电池"步骤"这一层；`pathing` 的"子用例"那一层有同一个缺口。**

根因层次是"**起点没有被声明、也没有被锚定**"，正确的修法是把它变成**契约**，而不是给每个用例加特判。
候选（未实施，需要用户拍）：`Step` 与 `pathing` 子用例都**必须声明起点**（`startFoot`）或**显式声明
"我自带场景/复位"**，**不声明就响亮失败** —— 这样"依赖上一步残留"在构造上不可能。

## 一、⭐⭐⭐ 真缺陷（`D-412`）：`datapacks/` 里的旧副本**盖住**了新场景，而且完全静默

### 1.1 症状（搬迁后第一次跑，看起来像"搬迁把场景弄坏了"）

+32 东移后连跑 3 次，全部：


### 1.2 我做了什么才把因果钉死（**没有靠猜**）

| 步骤 | 观测 | 排除了什么 |
|---|---|---|

⇒ 结论只能是：**执行的函数不是那份文件**。

### 1.3 真因

`datapacks/` 下**每个子目录都是一个活数据包**。而 `sync-windows-artifact.sh:97` 把场景包的备份
放在了 **`datapacks/` 里面**：

```
datapacks/alice_test/                       ← 本轮新复制进去的
datapacks/alice_test.bak.20260920-231028/   ← 备份，同样提供 `alice_test` 命名空间
datapacks/alice_test.bak.20260920-231921/   ← 同上
```

两个 `.bak` **按字典序排在 `alice_test` 之后** ⇒ 同命名空间**后加载者胜** ⇒ 服务端执行的是
**旧副本**（`fill 17 58 203 31 116 231`，已逐字核对）⇒ 它把方块写到**旧坐标**上，
而旧坐标的区块此刻**没被任何人握住**（bot 在新址）⇒ `/setblock` 静默 0 改动 ⇒ **什么都不落地**。

⚠️ 它**能骗过我们所有的现成护栏**：
- `rc=855` 照样是"成功"（命令确实执行了，只是落在没握住的区块上）；
- `D-251`/`D-408` 加的 `scene rc=` 判据**看不见**它（rc 不为 0）；
- `check-scene-connectivity.py` 读的是**仓库里**那份（新的），所以**离线自检全绿**。

### 1.4 影响面（**已核实，比"可能很严重"要窄**）

那两个 `.bak` 是 **2026-09-20 23:19/23:10** 造出来的，而**世界母本正是 2026-09-20 23:51 建/重建的**
⇒ **自那以后每一轮无头电池执行的都是 `.bak` 那份函数**。

⭐ **我核了"到底有没有东西被它吞掉"**（不靠推测）：

| 检查 | 结果 |
|---|---|
| `git log --since="2026-09-20 23:51" --name-only -- tools/test-scenes/ \| grep -c '\.mcfunction'` | **0** ⇒ 母本建成之后，**没有任何已提交的场景函数改动**落在这个窗口里 |
| 客户端存档里的 `.bak`（2026-09-21）与仓库逐文件 `diff -rq` | **0 处不同** ⇒ 那份副本内容与仓库一致（不是"内容陈旧"，是**同名遮蔽**） |
| 本轮 | ✅ 我今天那次 +32 位移（**未提交**）**正是被它吞掉的** —— 这就是它被发现的方式 |

⇒ **诚实结论**：这个缺陷**从 2026-09-20 23:51 起就活着**（真缺陷、会静默吞掉场景改动），
但**历史上没有已提交的场景改动落在该窗口** ⇒ **实际损失 = 0**；它今天的表现形式是
"我改了场景，跑起来却像没改" ⇒ 被三道护栏（离线自检全绿 / `rc=855` / 世界事实与预期不符）**合围**才现形。

## 二、`C6` 搬迁：**试过、否决**（`D-413`）

`datapack` 一修好，搬迁的**真实效果**立刻现形（同一 +32 位移）：

| 观测 | 含义 |
|---|---|
| `premise step=lumber_job 已落地（等了 2 tick）` | ✅ 平台**真的落地了**、bot 站得住（"无认领 + 场景在位"） |
| `rejected=[tree@52,64,208:trunk_too_tall(unreachable=4,hard=2), tree@60,64,208:…(unreachable=4,hard=1), tree@65,64,208:…]` | ❌ **每一棵树都"没有可站立点 + 硬遮挡"** ⇒ `candidates=0` |

⭐ 原因（读场景文件就能看出来）：**这个场景是"连宿主地形一起"抓下来的**，**不是自足的**：
- 清空盒只到 `x17..31`，而树长到 **`x35`**（东边那几棵**站在没被清过的真实地形上**）；
- 文件头自己写着那条"树冠通道红线"：可行走台地 = 建出来的 `x18..30`，**bot 南北穿行靠的是宿主地形**（`x=22..26` 唯一缺口）。

⇒ **纯平移把场景搬进了「未知地形」**：在老家，清空盒外的地形恰好是玩家基地的平整地面（所以成立）；
在新址，盒外是什么没人知道 ⇒ 树被埋/被挡。

⇒ 而且**基地附近没有空位**：我把所有偏移扫了一遍（避开其它 6 个场景 + 2 处认领），
`dx=±32,dz=0` 是**代价最小**的两个，其余可选位都在更远的地方 —— 同样的问题只会更严重。

⇒ **结论：搬迁是错的杠杆。** 场景与宿主地形耦合，改坐标 = 换一个没被验证过的宿主。

## 三、真修法：**把第三方认领从「夹具世界副本」里清掉**（`D-413`）

理由与电池**早已在做**的"清 `alice_*.dat`"**逐字同源**：夹具世界是**给 Alice 的代码用的**，
不是给第三方模组状态用的（母本里的认领只是**玩家存档的副作用**）。

```bash
# tools/headless-battery.sh（只动本轮 $WORLD 副本；ALICE_KEEP_FTB_CLAIMS=1 可保留）
rm -f "$WORLD"/ftbchunks/*.snbt
```

**安全性核对**（不是想当然）：全仓只有两处碰 FTB ——
① 我新加的 `FixtureThirdParty`（只**读**）；
② **`break_refused`（CORE 步）会在运行期自己造一个认领**（`/ftbchunks claim` + 另一队伍的假人）
⇒ **没有任何夹具依赖"预存的认领"** ⇒ 清掉是安全的。

**结果**（场景坐标**已还原**为原始值）：

```
[Regression] lumber_job=PASS ticks=613 idempotent=true
```

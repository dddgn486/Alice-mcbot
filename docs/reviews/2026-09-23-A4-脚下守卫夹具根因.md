## 二、我先后**两次误诊**（留痕，因为它们都被代码注释"支持"过）

| 次 | 我的假设 | 证伪方式 | 结果 |
|---|---|---|---|
| 1 | 注释说"柱形/阶梯几何都 `side_break_failed` ⇒ 守卫在这里无法变红" ⇒ 以为要**重做几何** | 先只加**正向对照**断言（`remaining == 1`）⇒ 立刻**红**（`remaining=3`） | 证明判据能红，但**根因未明** |
| 2 | "**没发镐**，石头靠手挖 ⇒ 太慢 ⇒ `side_break_failed`" | 加 `FixtureToolKit.ensurePickaxe` 后**仍红**（`restored=0`，同一组 note） | **假设被证伪**（镐不是成因；但它仍然必要，见 §五） |

⇒ 按纪律（同一问题两次失败）**停止加猜测**，改上**分层探针**（`MineBlockRunner.tickBreak()` 的失败分支）：

```
[PROBE-A4] target=4001, 100, 2600 breakAllowed=true refusal=protected_area grant=RestoreScope:SCAFFOLD_RESTORE
[PROBE-A4] target=4000, 99, 2600 breakAllowed=true refusal=protected_area grant=RestoreScope:SCAFFOLD_RESTORE
```
（`run/headless-logs/20260923-203355-single_restore_underfoot_safety.log`；探针**验证完已删除**。）

⇒ 不是预算（`breakAllowed=true`），是**区域授权**：`protected_area`。

## 三、根因（代码级）

`protection/ZoneAuthority.authorize` 的第一道门：

```java
TaskZoneRegistry.Zone zone = TaskZoneRegistry.zoneOf(level.getServer(), owner);
if (zone == null || !zone.covers(pos)) {
    return new Decision(Verdict.DENY, "protected_area", …);   // 「保护区里没有生效的任务区」
}
```

而 `TaskZoneRegistry.zoneOf` 是**按"当前作用域"**取任务区的：

```java
String scopeId = WorldModLedger.currentScope(server, owner);
Zone zone = ZONES.get(scopeId);            // ← 只有"当前 scope"上声明的任务区才算生效
```

夹具旧版**顺序写反**：

```java
zone = FixtureZone.protect(...);                 // ① 声明任务区 ⇒ 挂在**外层**电池步作用域 #2:Regression:<step>
String scopeId = WorldModLedger.openScope(..., "c2_underfoot");   // ② 再开**内层**作用域 #3
```

⇒ 回收期的写入都发生在 `#3` 上，而任务区在 `#2` 上 ⇒ `zoneOf` 返回 `null` ⇒ `protected_area`
⇒ `BlockInteraction.breakable=false` ⇒ `MineRunner: TARGET_NOT_BREAKABLE`（`remaining=3`）。

⭐ **顺带解释了旧注释为什么错**：`side_break_failed` 是**下游症状**（拆不动 → 退到侧拆 → 也拆不动），
它被误读成"几何拆不到"。**同一个 `protected_area` 也在替 `Z1` 说话**：`Z1` 要求"恢复只在保护区内"，
而这条夹具恰好证明了**顺序写错时保护区内一次都恢复不了**。

**唯一受害者**：全仓 `FixtureZone.protect` 的四个使用者里，只有一个同时另开了作用域 —— 就是本夹具
（`ScaffoldLifecycleTask` / `CraftStationCheckTask` 不另开作用域；`LedgerZoneScopeCheckTask` **先 `openScope` 后 `protect`**，是正确形状，已在本夹具注释里点名当参照）。

## 四、修法与证据链（**先红后绿 + 双向注入**）

| 步骤 | 改动 | 实测 |
|---|---|---|
| 1 | 只加**正向对照**断言：回收结束后账本只该剩"bot 正踩着的那格"（世界事实，`pendingTemporary(...)==1`） | **红**：`remaining=3`（`20260923-203052`） |
| 2 | 加 `ensurePickaxe` | 仍红（证伪假设 2，见 §二） |
| 3 | 探针分层 | `refusal=protected_area`（`20260923-203355`） |
| 4 | **交换顺序**（先 `openScope` 后 `FixtureZone.protect`）+ 删探针 | **绿**：`restored=2 skipped=1 remaining=1`、真破坏 **2** 次（`20260923-203612`） |
| 5 | 注入 A：把 `D-399` 脚下守卫临时关掉 | **红两条**：`脚下那格必须被守卫点名拒绝`（`skipped=0 terminal=restore_done`）+ 正向对照（`remaining=0`）（`20260923-203854`） |
| 6 | 注入 B：把作用域/任务区顺序**改回旧版** | **红**：正向对照 `remaining=3`（即步骤 1 的那次） |
| 7 | 还原 | **绿**：4 条判据全过（`20260923-203954`） |

## 五、顺带修掉的两处**我自己**的判据缺陷（本会话第 9、10 次"判据太弱"）

1. **旧 check ②** 写的是 `!terminal.contains("restore_partial") || (skipped > 0 && notes != "-")`
   —— **认任何理由**：注入 A 之后 `terminal` 变成 `restore_done`，第一个析取项直接为真 ⇒ **断言空过**。
   改成**无条件点名**：`notes.contains("underfoot_unsafe") && skippedCount >= 1`。
2. **`ensurePickaxe` 仍然保留**，但理由改成真的那个：账本里播种的是 `Blocks.COBBLESTONE`（镐类方块），
   不发镐 ⇒ 回收要靠手挖石头（慢到超预算）。**它不是那条红的成因**，只是让夹具测的是"回收路径"而不是"手挖多慢"。

## 六、诚实边界 / 遗留

1. ⚠️ **`biggestFall <= 1`（"不许摔"）在本几何下不判别**：注入 A（守卫关掉）时 `biggestFall` 仍是 **1**
   ⇒ 那句 javadoc 声称的"守卫不在 ⇒ 摔到地面（≥2 格）⇒ 红"**当前不成立**。要让它成立需要**乱序账本几何**
   （把"支撑 bot 的那格"排在它下面那格**之前**）—— 那是 `§11` 的 **`C2`** 项，未做。
   **本轮没有把它说成"能红"**：能红的是"守卫必须点名拒绝"与"正向对照"这两条。
2. ⚠️ **新发现（登记，未修）**：修好之后 `notes` 里出现 **`drops_left=2`**、`recovered=0`
   ⇒ 拆下来的两块圆石**没有被收回背包**（`RestoreScopeTask` 只在 note 里如实记录，不判红）。
   这是"回收材料闭环"的一个缺口，触发条件 = 出现一次需要材料真的回到背包的场景。见台账 §11-G。
3. 本步是 **EXTRA**（不进 CORE）⇒ 该修**不影响 CORE 判决**；`module:craft`（含本步）实测 **PASS**（78 s）。

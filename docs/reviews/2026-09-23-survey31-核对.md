## §2 我当场补验的那一条：`dsh web` 的绑定与鉴权（报告标「⚠️ 未核实」）

**报告的问题**（§4.4）：「`dsh web` 默认绑 `127.0.0.1` 还是 `0.0.0.0`？**有没有 bind 参数**？」

**实测**（本机）：

```
$ dsh web --help
  --host <host>                  bind host
  --trusted-host <authority...>  extra authority the /api browser-trust fence accepts
                                 (host or host:port; repeatable)
$ ss -ltnp | grep 3081
LISTEN 0 511 127.0.0.1:3081 0.0.0.0:*  users:(("node",pid=1564,fd=25))
```

| 问题 | 答案 |
|---|---|
| 有没有 bind 参数 | ✅ **有**：`--host <host>` |
| 默认绑什么 | ✅ 实测**只绑 `127.0.0.1`**（回环）⇒ §4.5 的「不要直接暴露」是**默认行为**，无需额外加固 |
| 反代要改什么 | 反代与 DSH **同机**时**不用** `--host`（代理连 `127.0.0.1:3081` 即可）；只有「云上还要别的设备直连」才需要 `--host 0.0.0.0` |
| ⭐ **报告没写的坑** | `--trusted-host <authority...>` = **`/api` 的浏览器信任围栏**。用**域名/反代**访问时若不加 `--trusted-host alice.example.com`，很可能出现「**页面能开、功能坏**」（`/api` 被围栏拒）⇒ 这一步应当进 §4.5 的部署清单与 §10 的验收判据 |

⇒ 建议给 §10 补一条判据：**从外部域名访问时，不只是「能打开且要求登录」，还要「能真的发一条消息」**
（后者才会碰到信任围栏）。

## §3 ⚠️ 需要修正的结论：「云上跑 CORE 成本 ≈ 几乎为零」（§14.5-2）

报告的推理链：`D-352` 缓存「只写 PASS」+ 主工作流已重建绿缓存 ⇒ 「同指纹下 `core` 是秒级返回」
⇒ 「全搬之后，**云上跑一轮 CORE 的成本 ≈ 几乎为零**」。

**前半段对**（我复算过：`:406/:413` 只写 PASS；本次 `B3` 那轮就真的命中/重建过）。**结论**要分成两半：

| 场景 | 成本 |
|---|---|
| **没改动源码/工具的重复跑** | ≈ **0**（命中缓存，实测「用时=0s」） |
| ⭐ **每一次真改动之后** | **仍是真跑 ≈ 251 s** —— 因为 `D-352` 指纹 = `src/` + `tools/` + 构建脚本 + `run/world-pristine` + 上游模组 jar + `server.properties` + `unix_args.txt` + `java -version` |

⇒ 而「改一行 → 验一轮」**正是这个项目的主循环** ⇒ **缓存救不了主循环**，它救的是「同一份代码反复验」。
**所以「全搬」在 CORE 上的真实收益不是「便宜」，而是**：
① 云上有**完整的测试面**（上游 jar 齐 ⇒ `check-machine-map` 的 Tier B 由 WARN 变真断言）；
② 云上**随时能跑**（不占用本地 PC、不要求本地开着 WSL）；
③ 机器是 16 G ⇒ 能同时跑 agent 与一轮 CORE。
⚠️ 附带事实（报告没写）：指纹里含 `unix_args.txt` 与 `java -version` ⇒ **缓存不跨机器**（`run/.cache/` 也不进 git）
⇒ 云上**第一次**永远是 251 s 的真跑。

## §4 ⭐ 报告没覆盖的真风险：**世界母本是「输入」，不该是「本地一次性快照」**

**脚本自己给了最有力的措辞**（`headless-battery.sh:167`，逐字）：
> 「世界母本：5 个 CORE 步（`clear_retry`/`write_budget`/`scaffold`/`clear_guard`/`mine_regression`）的
> `START_FOOT` 是绝对坐标，完全依赖它的地形 ⇒ **它是输入，不是环境**」

**今天它是什么**（实测）：

| 事实 | 值 |
|---|---|
| 母本从哪来 | `CLIENT_SAVE` = 客户端存档 `…/worldedit-test/…/saves/新的世界`（`rm -rf` 后 `cp -r`） |
| 什么时候刷新 | **只在不存在时建一次**（`:137` `if [ ! -d "$PRISTINE" ]`）⇒ 想换必须**手动删目录** |
| 客户端存档在动吗 | ✅ **在动**：该世界目录 mtime **9月23 14:08**（今天被打开/玩过）；`Alice/run/world-pristine` 目录 mtime 9月23 12:45 |
| 它在版本控制里吗 | ❌ **不在**（`run/` 是 gitignore 的运行目录）⇒ 它**只在某一台机器上存在** |

⇒ **全搬把「唯一一份母本」搬到云上之后，会出现一个报告没写明的耦合**：
**母本的来源（玩家自己的客户端存档）永远在本地**，而**母本本身只在云上** ⇒ 「唯一母本」这句话
要么意味着「玩家以后不在本地客户端玩那个世界」（不现实：`WINDOWS_CLIENT` 验收永远在本地），
要么意味着「以后每次都要从本地重传存档」⇒ 那时 `D-352` 指纹里的 `run/world-pristine` 变化
⇒ **云上全部缓存失效**（这是**正确**行为，但必须知道）。

**我建议的形状**（与报告 §6.2 的「唯一母本」同向，但补上「版本化」这一步）：
把世界母本从「**本地运行产物**」提升为「**版本化的发布物**」——
`world-pristine` 打成一个 artifact（自己的 Release / 单独仓），带 **sha256 + 该版本期望的 CORE 判决**；
设备（云和本地）都只**下载固定版本**，换版本 = 显式动作 + 复跑一轮 CORE 并对比。
理由：既然脚本自己声明「它是**输入**」，那么输入就该**可寻址、可复现**；
否则「同一份代码在两台机器上跑出不同判决」这件事的**归因**会变得很贵（而 `D-352` 指纹已经把它算进去了）。

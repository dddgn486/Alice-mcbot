# AI Player 设计文档（草案 v0.2）

> 状态：**基础决策已定稿（5 项，见 §5.4/§9）**；架构细节随里程碑推进持续细化
> 配套思考过程见 `AI_PLAYER_NOTES.md`（本文档是其收敛产物，含决策依据与课程记录）

---

## 1. 目标与定位

### 1.1 愿景

为 Minecraft **科技整合包玩家**打造一个真正好用的游戏内 AI 助手：
能像熟练玩家一样理解模组内容、操作机器、完成采集/建造任务，并作为陪伴型 NPC 提供情绪价值。

### 1.2 为什么现有方案做不到（一句话摘要）

| 现有方案 | 致命短板 |
|---|---|
| Voyager / Mindcraft（协议 bot） | 感知走协议（慢）、任务逐格指挥（低效）、看不见模组 GUI |
| mc_aiplayer / numen（游戏内模组） | 执行层漏洞多（站位/搜索/拾取）、任务写死、点不了 GUI |
| Cradle（视觉 GUI） | 慢、脆、无 MC 模组 grounding 数据 |

### 1.3 本项目两大差异化支柱

1. **高效执行层**：LLM 只做目标级决策，确定性执行器负责可靠完成（详见 §4）
2. **服务端接口序列化**：不点 GUI，把 GUI 背后的操作拦截成 AI 可读的语义接口，让 AI 通过"读接口 + 读教程"学会使用任何模组方块（详见 §5）

### 1.4 明确不做的事

- ❌ 不做"视觉点击 GUI"路线
- ❌ 不追求让模型从原始世界数据自主推理一切
- ❌ 不逐格指挥挖掘/建造

## 2. 系统架构总览

```
┌─────────────────────────────────────────────────────┐
│ 决策层（异步）         外部 LLM / 本地小模型           │
│   大模型: 目标规划、异常重规划、人设回复               │
│   小模型/规则: 高频微决策、防呆兜底                   │
│   function calling 工具接口                          │
└──────────────▲──────────────────────┬───────────────┘
               │ 结构化观察/结果        │ 工具调用
┌──────────────┴──────────────────────▼───────────────┐
│ 任务层（游戏内，主线程）                              │
│   GoalPlanner → 任务队列 → TaskManager               │
│   任务作用域缓冲区（事件订阅: 方块变化/实体生成/IO）     │
└──────────────▲──────────────────────┬───────────────┘
               │ 本地事件流            │ 确定性动作
┌──────────────┴──────────────────────▼───────────────┐
│ 执行层（游戏内，主线程 tick 消费）                     │
│   寻路/站位/挖掘/拾取/建造（确定性，绝不交给 LLM）      │
│   验收标准: 可达站位、搜索排序、产物入包、环境检查      │
└─────────────────────────────────────────────────────┘
          ▲                        ▲
          │ 世界读取               │ 接口调用
┌─────────┴──────────┐  ┌──────────┴──────────────────┐
│ 感知层（服务端）     │  │ 服务端接口序列化层（§5）      │
│  World API 直读     │  │ 只读: capability 自动扫描    │
│  差异推送+稀疏化    │  │ 操作: 适配器注册 + gui_hint  │
└────────────────────┘  └─────────────────────────────┘
```

**核心原则**：
- 感知/执行全部在**服务端**（权威数据）；客户端仅作为 GUI 信息展示（可选）
- AI 调用异步，游戏主线程永不等待网络
- 事实由代码验证，不由模型声称

## 3. 感知层设计

### 3.1 数据源

- 服务端 `Level`/`ServerLevel` 直接读取：`getBlockState` / `getEntities` / `getBlockEntity`
- capability 读取：`IItemHandler` / `IEnergyStorage` / `IFluidHandler`

### 3.2 任务作用域缓冲区（Task Scope Buffer）

- 任务启动时注册**局部订阅区域**（BoundingBox）：
  - BlockChange 事件（外部扰动/自挖进度）
  - EntitySpawn 事件（掉落物坐标实时追踪）
  - BlockEntity 数据变化（机器 IO / 完成信号）
- 用途：掉落物精准拾取、垫脚石事后清理、机器完成信号、抗外部扰动
- 全局保持**低频宏观快照**（供 LLM 决策），任务内用**高频事件流**（供执行器微调），避免全量扫描卡 tick

### 3.3 上下文压缩：分类聚合 + 任务视角 Profile

- **只推任务相关局部窗口（N×N×N），符号化压缩**；差异推送：只发变化部分，稳定前缀命中 prompt cache（省钱）
- **分类聚合**（已落地）：把原始方块流按语义归类成四类摘要，而不是逐格列表——
  ① 目标（任务在乎的方块，列坐标）② 危险/障碍（岩浆/水/黑曜石等，列坐标）
  ③ 意外收获（刷怪笼/宝箱/贵重方块，列坐标）④ 普通（仅聚合计数）。
  上千个方块 → 几十行结构化文本
- **任务视角 Profile**（已落地）：换任务 = 换 Profile（目标标签集合 + 范围），
  分类与摘要逻辑不变——这是「按任务自动调整感知权重」的落点。
  当前预置 `MINING`（原版 8 类矿石标签）与 `GENERAL`；建造/探索视角后续补
- **分类规则可扩展**（待做）：危险/收获集合当前硬编码，后续下沉为可注册规则，供模组适配器
  注入本整合包特有的关注方块（如「格雷科技矿脉」「AE2 控制器」）

## 4. 执行层设计

### 4.1 借鉴与教训来源

- mc_aiplayer 精读（已定位 4 类执行缺陷，详见笔记 §3）
- Baritone 的寻路/方块空间分析思路（可参考，不照搬）
- Carpet 假人的"服务端模拟真实玩家"范式

### 4.2 四条验收标准（所有执行器必须满足）

| # | 标准 | 对应缺陷 |
|---|---|---|
| 1 | 任何目标方块先有「可达站位点」才开工，挖掘前做视线无遮挡检查 | 隔空挖、站位卡死 |
| 2 | 目标搜索必有排序（距离/暴露/可达性），暴露方块优先 | 随机乱逛、挖泥开路 |
| 3 | 任务完成 = 产物入包（掉落物追踪到账），非"动作发生过" | 掉落物丢失 |
| 4 | 多 tick 动作前做环境前置检查（流体中/悬空/位移） | 水中沉浮打断 |

### 4.3 动作执行

- 服务端直接发协议包/调世界 API（参考 mc_aiplayer 的 `ActionPack` 模式）
- 动作进队列，主线程按 tick 消费，不阻塞
- 失败回传审计（成功/失败/耗时），失败即重规划，成功沉淀技能

## 5. 服务端接口序列化（核心 spec 草案）

### 5.1 接口来源分两类

| 类型 | 生成方式 | 覆盖能力 |
|---|---|---|
| **只读接口** | 通用拦截器**自动生成**：扫描方块 capability，生成 `read_inventory` / `read_energy` / `read_fluid` 等 | 自动覆盖 90% 科技模组 |
| **操作接口** | **适配器注册**（仿 CC 的 `GenericPeripheralProvider`），模组作者或本项目按需实现 | 提取产物/切换模式等语义操作 |

### 5.2 接口 JSON 格式（v0.1）

```json
{
  "id": "tango_mod:crystal_fusioner/extract_output",
  "display_name": "取出输出产物",
  "gui_hint": "相当于打开晶体融合器界面后,左键点击输出槽取出产物",
  "input_schema": { "type": "object", "properties": { "max_count": { "type": "integer" } } },
  "output_schema": { "items": [ { "id": "tango_mod:intelligent_ingot", "count": 1 } ] },
  "side": "server",
  "permission": "owner"
}
```

- `gui_hint`：**本接口在 GUI 上对应玩家什么操作**——AI 学习的关键语义标注
- `permission`：操作需玩家授权/白名单

### 5.3 ⚠️ 待决策点

1. **拦截层位置**：在 `AbstractContainerMenu` 层做通用代理，还是下沉到 capability 层？（前者覆盖容器操作，后者更通用）
2. **接口发现协议**：AI 如何拉取"这个方块有哪些接口"？（建议：方块旁静态扫描 → 返回 JSON 清单，作为工具 `list_block_interfaces`）
3. **权限模型**：默认只读开放 + 操作需确认？还是玩家可设信任等级？

### 5.4 已定决策（2026-08-16）

1. **拦截层**：以 **capability 层为主**（更通用，覆盖非容器机器；Menu 层代理作为容器类操作的补充拦截点）。
2. **接口发现协议**：方块旁静态扫描 → 返回 JSON 清单，暴露为工具 `list_block_interfaces`。
3. **权限模型**：玩家**信任等级制**——只读接口默认开放；操作接口按等级：owner 自动 / 好友确认 / 其他拒绝。

## 6. 决策层设计（AI 行为）

### 6.1 工具接口（function calling）

- 工具分三组：高层任务（`mine_ore`/`build`）、低层操作（`move_to`/`mine_block`）、查询（`list_interfaces`/`get_task_status`）
- 模型只选工具 + 参数，执行器负责执行（吸收 mc_aiplayer 教训：失败后封锁低层工具防作死）

### 6.2 模型路由（已定：本地高频 + 云端低频；配比后续实测调优）

- 高频微决策（挖哪格/往哪走）：本地小模型或规则引擎，毫秒级
- 目标规划/异常/人设回复：大模型，低频异步
- 候选：Ollama + Qwen 系列本地推理；云端沿用 DeepSeek/中转均可（配置化）
- 参考：Mindcraft 的 Ollama 支持；Roblox 云端异步模式

### 6.3 记忆三层

1. 知识库：合成表/方块属性/接口清单 → 本地结构化库（不进 prompt，检索注入）
2. 技能库：成功动作存成带参宏（Voyager 思路）
3. 情节记忆：任务历史摘要 + 反思

### 6.4 回复风格（两段式）

- 任务完成汇报：**固定词块**（信息准确）
- 语气包装：按人设二次调用模型生成完整回复（情感层）

## 8. 流水线应用：手搓期「模拟 AE」+ AE 期「三件套」

> 功能计划（2026-08-16）：针对科技/魔法整合包的**两大阶段**分别设计 bot 的核心应用。

### 8.1 背景：整合包的两大阶段

1. **手搓阶段**（无 AE 自动化）：半自动流水线、被动生产线，结构不定、复杂多样，AI 难以自动读懂；
2. **AE 自动化阶段**：全套 AE2 网络，机器人可用的操作高度标准化。

### 8.2 手搓阶段：「模拟 AE」（玩家指导，AI 执行）

- **核心原则：玩家严格定义，AI 不思考结构**。与 AE 自动化的原理一致——AE 也不需要"理解"流水线，只需要样板（pattern）定义输入输出。
- **玩家需要定义的内容**：
  | 定义项 | 说明 |
  |---|---|
  | 流水线方块区域 | 玩家圈选/标记，划定 bot 的操作范围 |
  | 输入口 | 材料投放位置（方块+接口） |
  | 输入材料 | 种类与数量 |
  | 输出口 | 产物收取位置 |
  | 输出材料 | 期望产物 |
  | 能源/资源消耗 | 可选，用于判断"是否可开工" |
- **效果**：bot 像一个"模拟 AE"的搬运工——不搭线、不理解线，只按玩家的定义在输入口投放、在输出口收取，帮玩家度过手搓期。
- **落地要点**：这是一套**严谨的功能**（不是让 AI 自由发挥），玩家的标记与定义以结构化数据持久化，形成该世界的「流水线档案」。

### 8.3 AE 阶段：「AE 三件套」内嵌

- **目标**：bot 熟练使用 AE2 网络，把"基础但繁多"的累活交给 AI：
  1. **存取物品**：识别网络、读取网络数据、按需提取/存入（走 IItemHandler，AE2 已暴露）；
  2. **撰写样板**：多选项操作在**本地写规则**——玩家自定义或选择预制规则，AI 按规则写样板（不让 AI 自由发挥选项）；
  3. **管理样板**：样板列表查询、批量替换、回收整理。
- **定位**：这三点直接内嵌进本模组，成为 bot 的高效率"累活"能力，而非依赖外部模组适配。

### 8.4 与「酒狐 agent」的对照

- 酒狐（B站 AI agent，演示机械动力配方自动合成）**无公开开源仓库**，机器结构定位机制不可核实——推测同为"人工标记/蓝图式"路线（机械动力多方块动力网络自动识别难度极高）。
- **本项目结论**：与其赌"自动识别复杂结构"，不如走**玩家标记 + 严格定义**（8.2），把不确定性关进笼子里；识别能力留给"单方块机器 + capability 扫描"（§5）这种可标准化的场景。

### 8.5 扫描效率与记忆存储（回应性能担忧）

**关于"机器密度高、扫描接口慢"**：
- 方块数据读取本身是 O(1) 纳秒级（`getBlockEntity` + capability 是哈希查找），**密度不拖慢单点读取**；
- 慢的是"全区域逐方块扫描 + 逐方块识别"。规避方案：
  1. **按需扫描**：只在任务需要时扫描，绝不全图后台轮询；
  2. **事件失效缓存**：扫描结果进本地缓存，`BlockChange` 事件使相关条目失效，不重复扫；
  3. **玩家标记优先**（8.2）：标记过的机器直接命中，跳过发现环节。

**关于"关键性方块记忆存储"**：
- 分层存储，不塞 prompt：
  | 层 | 内容 | 介质 |
  |---|---|---|
  | 世界常驻知识 | 玩家标记的流水线/机器、接口清单、坐标 | 本地 SQLite（随世界存档） |
  | 扫描缓存 | 近期扫描结果（含失效机制） | 内存 + 磁盘缓存 |
  | 任务上下文 | 当前任务涉及的方块数据 | 任务作用域缓冲区（§3.2） |
- 原则：**关键方块（标记过的）持久化记忆，普通方块按需缓存**；检索注入而非全量塞入。

## 9. 里程碑拆解（提案）

| 里程碑 | 内容 | 验收 |
|---|---|---|
| **M0 技术验证** | 最小可跑 bot：服务端模拟玩家挖 1 个方块 | 隔空挖问题不存在 |
| **M1 感知层** | 世界直读 + 任务作用域缓冲区 | 掉落物实时坐标可得 |
| **M2 只读接口** | capability 自动扫描 + 接口清单工具 | 任意机器能列出物品/能量 |
| **M3 执行层** | 挖掘/寻路/拾取闭环（通过四条验收标准） | 挖矿任务产物入包 |
| **M4 决策层** | function calling + 模型路由 + 两段式回复 | 自然语言指挥挖矿 |
| **M5 知识层** | MC 百科 RAG + 接口学习闭环 | 用教程学会一台新机器 |
| **M6 操作适配器** | 适配器注册机制 + 2 个示例模组适配 | 操作类接口可扩展 |
| **M7 模拟 AE** | 玩家标记流水线（区域/输入输出/材料定义）+ 搬运执行 | 手搓期流水线托管跑通 |
| **M8 AE 三件套** | 网络识别/存取物品/写样板/管样板（规则本地化） | AE 累活交给 bot |

⚠️ 每个里程碑的具体工作量和依赖关系需要进一步细化（M7/M8 依赖 M2 只读接口与 M6 适配器机制）。

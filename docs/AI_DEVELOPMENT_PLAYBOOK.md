# Alice：AI 辅助 Forge 模组开发手册

> 目的：让新的 AI 编码助手在上下文压缩、会话切换和多次交接后，仍能保持项目方向、技术边界、开发习惯和真实验证状态。
>
> 本文是**轻量开发协议**，不是 dsh-agent-bus、active plan 或旧监督工作流的替代品，也不要求每个小改动创建工作包。

## 1. 项目定位

Alice 是 Minecraft Forge 1.20.1 的服务端权威 AI 玩家模组。核心目标不是让 LLM 逐 tick 操作游戏，而是：

```text
用户目标
  -> LLM/规则选择目标、策略和已注册工具
  -> 代码验证权限、资源、风险和参数
  -> 确定性任务编排
  -> 确定性移动/挖掘/交互/搬运执行器
  -> 服务端事实验收
  -> 结构化结果和证据
```

必须长期保持的四条原则：

1. **LLM 只做目标级决策**，不直接决定每 tick 的物理动作、槽位写入或任意网络包。
2. **服务端是唯一真相**，客户端负责显示、输入和测试观察；客户端看到的结果不等于服务端已经成功。
3. **确定性执行器负责安全与完成条件**，必须有前置条件、后置条件、超时、取消和失败码。
4. **能力边界宁可保守失败，也不能用传送、隔空操作、隐式回退或扩大破坏范围伪造成功。**

## 2. 当前应以什么为准

历史文档很多，且工作流已经多次翻新。AI 不应把旧文档中的流程性要求自动当作当前规则。

优先级建议固定为：

```text
用户本轮明确决定 / 实际客户端证据
  > 当前代码和 Git 状态
  > 本文件的稳定原则与当前状态文件
  > 专项设计文档
  > 历史 HANDOVER、旧监督协议、旧实验报告
  > 会话记忆、模型推断
```

如果两个文档冲突，AI 必须指出冲突并询问，而不是自行选择后继续实现。

建议把文档分成三类：

- **稳定规则**：架构边界、服务端权威、Forge 技术原则；不随普通任务频繁改动。
- **当前状态**：正在做什么、什么已验证、什么失败、下一步是什么；每次交接都更新。
- **历史记录**：旧方案、旧结论、已废弃工作流；只用于理解背景，不能直接授权实现。

## 3. 建议新增的最小记忆系统

不要依赖长篇 HANDOVER 作为唯一记忆。建议建立以下四个小文件，每个文件只承担一种职责：

```text
docs/AI_PROJECT_STATE.md       当前唯一工作状态，建议控制在 100~180 行
docs/AI_DECISIONS.md           不可随意推翻的架构决策和理由
docs/AI_TEST_MATRIX.md         功能、入口、预期、证据和当前结果
docs/AI_CHANGELOG.md           按日期记录实际改动、失败和修复
```

### 3.1 `AI_PROJECT_STATE.md` 应包含

```markdown
# Alice 当前状态

更新时间：YYYY-MM-DD
当前分支 / HEAD：
当前目标：一句话
当前阶段：例如 HARD_PATH 稳定 / C1 只读 / 转移实验 / 暂停

## 本轮只允许做
- ...

## 本轮不要做
- ...

## 已验证为真
- [客户端] ...
- [服务端] ...
- [静态/编译] ...

## 未验证或失败
- [客户端待测] ...
- [已知失败] ...
- [证据缺口] ...

## 当前下一步
1. ...

## 如果失败，先收集
- 日志：...
- 截图/视频：...
- 服务端状态：...
- JAR/提交：...
```

它是新会话的第一阅读目标。状态文件中必须区分：`IMPLEMENTED`、`COMPILES`、`SERVER_TESTED`、`CLIENT_TESTED`、`USER_ACCEPTED`，不能用“完成”覆盖这些差异。

### 3.2 `AI_DECISIONS.md` 的记录格式

每条决策只写结论、理由、范围和替代方案：

```markdown
## D-012：普通挖矿保持 HARD_PATH
- 状态：冻结
- 决定：MineTask/DropCollectionTask 不调用 SOFT_SURFACE
- 原因：软移动尚未完成全场景客户端验证
- 影响：曲面不可达时返回 target_requires_tunnel 或保守失败
- 可改条件：独立软移动矩阵通过，并重新讨论任务接入
```

决策不是永远不能变，而是变更必须显式写成“替换旧决策”，不能在修 bug 时悄悄推翻。

### 3.3 `AI_TEST_MATRIX.md` 的核心字段

每个能力至少记录：

| 能力 | 测试入口 | 服务端事实 | 客户端观察 | 结果 | 证据 | 最后验证 |
|---|---|---|---|---|---|---|
| Bot 移动 | `/alice ...` | 位置、碰撞、状态 | 可见移动、无回弹 | CLIENT_TEST_PENDING | log/video | 日期 |

必须把测试入口设计成用户容易执行的命令或测试物品。客户端可见能力不能只靠“代码看起来正确”验收。

### 3.4 `AI_CHANGELOG.md` 记录失败，而不只记录成功

每次记录：

```text
日期 / 提交：
目标：
改动：
验证：compileJava / headless / client
失败现象：
根因是否证实：是/否
未解决风险：
下一步：
```

失败记录非常重要。它能防止新会话重复尝试已失败的补丁，也能防止 AI 把“曾经失败”遗忘后重新引入。

## 4. Skills 使用规则：按风险加载，不把知识库变成审批流程

Skills 是 Alice 的技术记忆层，必须使用；但它们不是工作包审批、提交或交接制度。AI 助手应在**设计和调试前按需读取**，并在回复中说明使用了哪些 skill、采纳了哪条原则。

### 4.1 当前 Skills 清单与触发条件

当前 `.alice-supervision/skills/` 有 18 个 skill：9 个 Forge/调试基础 skill、1 个测试类 skill、3 个 Alice 协作与记忆 skill，以及 5 个 Alice 业务契约 skill，覆盖 Alice 最容易出错的核心领域：

### 4.2 Skill 的正确使用方式

每次任务按以下最小格式使用：

```text
相关 skill：forge-entity-physics-collision + minecraft-client-server-sync
我从 skill 采用的关键原则：设置速度不等于完成移动；服务端状态不等于客户端可见
本任务的定向验证：验证 aiStep/travel/move 链，并在客户端观察同步
```

规则：

1. **先读再设计**：涉及 Forge API 时，在写方案前读取对应 skill；不要等编译失败后才看。
2. **按风险组合读取**：FakePlayer 移动通常同时读取生命周期、物理、实体同步和客户端/服务端同步；GUI 通常同时读取 Menu 和客户端/服务端同步。
3. **只取相关章节**：普通小修改不需要把全部 skill 通读；先看触发条件、核心原则和对应陷阱。
4. **skill 不是最终证据**：skill 只能提供机制和检查项，不能替代当前源码、Forge 版本核对、日志或 Windows 客户端测试。
5. **发现新失败就回写**：若实际失败暴露了 skill 未覆盖的通用陷阱，先在变更日志记录，根因确认后再新增或修订 skill。
6. **禁止机械套用**：skill 中的历史案例是启发，不是对当前代码的事实证明；必须检查当前 Forge 47.x、当前代码和实际工件。

### 4.3 Skills 完整性判断

当前 skills 对 Alice 的“核心执行链”覆盖较好：FakePlayer 生命周期、实体同步、物理碰撞、GUI 协议、客户端/服务端、事件和坐标对象陷阱均有专门文档；调试层也有根因分析和失败模式识别；测试层有 `alice-scene-based-testing`（零参数入口 + 一键场景 + 一键自检 + 证据规范）；新增的 Alice 协作 skill 覆盖会话记忆、Windows 客户端协作和修复前讨论。

但它们**还不算完整的项目知识库**。当前明显缺口是：

- 任务状态机与取消/回收/失败码契约；
- 路径规划与执行器之间的契约、`SEARCH_LIMIT` 语义；
- 物品转移事务、守恒、重启和人工接管；
- capability 只读快照与模组适配器边界；
- 客户端测试矩阵、JAR 工件一致性和证据标准；
- Forge 资源注册、数据生成和打包资源链；
- Server tick 性能、区块加载和主线程阻塞；
- Java/Forge 版本迁移与映射核对。

这些缺口不应通过一次性编写大量文档填满。建议优先级：

1. **`alice-task-lifecycle-and-recovery`**：任务状态、取消、终态、失败码、回收；
2. **`alice-path-planning-execution-contract`**：脚位/支撑坐标、路径结果、执行后置条件和预算；
3. **`alice-inventory-transaction-conservation`**：转移状态机、守恒和中断恢复；
4. **`alice-client-artifact-acceptance`**：源码/JAR/客户端版本、日志、截图和 hash 的证据链；
5. **`forge-capability-adapter-boundary`**：C0-C5 能力分级、只读事实和写操作适配器。

新增 skill 的门槛：问题必须已在项目中真实发生、具有可复用机制、能给出定向测试和明确修复方式；不要为了每个普通 bug 创建 skill。

## 5. 每次 AI 会话的轻量流程

### 5.0 用户唤醒与持续目标规则

Alice 默认采用“用户主动唤醒、单轮明确收口”的协作方式：

1. AI 不主动创建或启用 active goal；普通开发、审计、构建和客户端验证都在当前对话内完成。
2. 只有用户明确要求持续自主推进、多轮无人值守执行，或明确批准创建 active goal 时，才允许使用 active goal；创建前必须说明目标、自动继续范围、轮数上限和停止条件。
3. 一旦任务需要用户在 Windows 客户端操作、提供截图/日志、选择方案、确认扩大范围，或等待外部系统产生证据，AI 必须暂停，不自动轮询、不自动续行，等待用户主动唤醒。
4. “继续”“批准”“开始实施”等明确指令只授权其文字所涵盖的范围；未明确授权的方案选择、正式任务接入、扩大测试范围和破坏性操作仍需再次询问。
5. active goal 的用途是管理真正需要跨轮持续推进的长任务，不用于把客户端等待、用户验收或普通分步开发变成自动唤醒。
6. 如果 active goal 已存在但用户要求暂停，AI 应立即暂停/阻塞该目标，并在回复中说明恢复所需的具体用户动作；不得依靠后续自动轮次等待。

### 阶段 A：恢复上下文（5 分钟内）

AI 开始编码前只做这些动作：

1. `pwd` 确认仓库；
2. 读 `docs/AI_PROJECT_STATE.md`、`docs/AI_DECISIONS.md`、相关专项设计；
3. 查看 `git status`、最近提交和用户上次测试结果；
4. 找到当前任务涉及的 Forge skill；
5. 用一句话向用户复述“我认为当前目标和边界是……”，存在冲突就停下来问。

不要求读取整个历史文档，也不要求运行旧监督脚本。只有用户明确恢复旧监督流程时，才使用旧协议。

### 阶段 B：先定问题，不先改代码

实现前写一个极短的任务卡，放在回复、issue 或状态文件中均可：

```text
目标：修复/实现什么
不改变：哪些稳定能力和边界
涉及层：例如任务状态机 + 服务端同步
成功条件：可观察的具体行为
最小验证：编译、headless 或客户端哪一种
停止条件：出现什么现象时不再继续打补丁
```

小维护可以只有 5 行；跨规划、物理、网络、GUI、FakePlayer 的任务才需要更完整设计。

**寻路与移动系统特殊规则**:

当设计或修复寻路/移动系统时，必须先调查 Baritone 的实现：

1. **不要凭空设计** - Baritone 已经解决了大部分 Minecraft 寻路边界情况
2. **主动搜索 Baritone 源码** - 使用 `web_search` 查找对应的 Movement 类实现
   - 例如：`MovementAscend.java`、`MovementDescend.java`、`MovementDiagonal.java`
   - **本地参考源码**：`/home/fb486/projects/reference/baritone/` 已克隆（2026-01-09）
3. **理解 Baritone 的处理方式** - 关注：
   - 如何检测前置条件（支撑、空间、碰撞）
   - 如何驱动 Bot（跳跃、冲刺、方向控制）
   - 如何判断完成（位置、onGround、settling）
   - 如何处理边缘情况（卡边缘、自动踩台阶、下降触发）
4. **适配到 Alice 架构** - 借鉴 Baritone 的模式，但保持：
   - Alice 的 MovementSpec/MovementExecution 契约
   - Alice 的独立验证链（不接入 MineTask）
   - Alice 的日志前缀和失败码体系
5. **记录参考来源** - 在代码注释或设计文档中注明参考的 Baritone 实现

**ServerPlayer 物理调用链（已实证验证，2026-01-09）**:

⚠️ **关键事实**：`ServerPlayer.tick()` **不会自动调用** `aiStep()`。

- **BotPlayer 必须显式调用** `this.aiStep()` 才会执行物理（第 120 行）
- **调用顺序**：
  1. `controller.onUpdate()` — 读取 forward/strafe/jump，写入 bot.zza/bot.xxa
  2. `super.tick()` — ServerPlayer 的原版 tick（不含物理计算）
  3. `this.aiStep()` — **必须显式调用**，内部调用 `travel()` 执行物理
- **不要删除或注释 `this.aiStep()` 调用** — bot 会完全动不了（实测确认）
- **不要猜测调用链** — ServerPlayer 的继承链与 LivingEntity 不同，必须显式驱动物理

**示例**：
```java
// 参考 Baritone MovementDescend: 检测 Y 坐标下降而不是等待到达目标高度
if (bot.getY() < spec.fromFoot().getY() + 0.5D) {
    phase = Phase.SETTLING;
}
```

这条规则适用于所有 Movement 类型、路径搜索、碰撞检测和物理驱动相关的实现。

### 阶段 C：先做最小闭环，再扩展

推荐顺序：

```text
数据/坐标契约
  -> 单一确定性原语
  -> 独立诊断入口
  -> 服务端事实测试
  -> 客户端冒烟测试
  -> 接入正式任务
  -> 扩展复杂场景
```

不要同时修改规划算法、移动执行器、任务编排、网络协议和客户端入口。若必须同时改多个层，先拆成两个或更多闭环。

### 阶段 D：验证与收口

每次代码修改至少：

1. 查看变更 diff；
2. `./gradlew compileJava`；
3. 运行与风险匹配的 focused 测试；
4. 若涉及客户端行为，构建实际 JAR 并在 Windows 客户端实测；
5. 更新当前状态和变更日志；
6. 明确列出“已证明”和“尚未证明”。

提交和推送是项目协作习惯，而不是每个本地实验的技术验收条件。是否提交、推送由当前协作方式和用户需要决定。

**诊断日志探针规范**:

当客户端测试失败或行为异常时，添加临时诊断日志探针：

1. **在关键检查点添加日志** - 记录可能出错的状态（phase、坐标、条件判断结果）
2. **保持日志前缀一致** - 使用统一的 `[Component Name]` 格式
3. **记录足够的上下文** - 包含 tick 计数、位置、状态、判断条件的实际值
4. **测试验证后立即清理** - 问题确认或修复后，**必须删除所有临时探针日志**
5. **不要永久保留调试日志** - 只保留关键的 started/completed/failed 终态日志

**探针日志示例**:
```java
// ✅ 临时诊断 - 用完必删
com.dddgn.alice.log.BotLog.info("[R2-C Descend] tick={} botY={} fromY={} check={}",
    executionTicks, bot.getY(), spec.fromFoot().getY(), bot.getY() < spec.fromFoot().getY());

// ✅ 永久保留 - 终态日志
BotLog.info("[R2-C Descend] completed session={} from={} to={} actualFoot={} ticks={}",
    sessionId, fromFoot, toFoot, bot.blockPosition(), executionTicks);
```

**物理场景判定规则（强制主动询问）**：

当关键证据需要分辨具体物理场景、而日志无法完整还原客户端物理效果时，**必须主动向用户询问**，不得凭日志或代码推断直接下结论。

出现下列任一情形即视为"必须询问"：

1. **动作/视觉类事实**：bot 是否跳跃、是否贴墙滑动、是否卡在方块边缘、是否抖动或回弹、是否踩上半砖/台阶、是否出现紫黑贴图或橡皮筋；
2. **客户端与服务端不一致**：服务端日志显示已到位，但玩家看到偏移、穿模、悬空或位置不符；
3. **地形与方块状态**：具体方块类型、半砖朝向、流体、蜘蛛网、模组方块行为；
4. **复现条件**：是否可复现、偶发还是必现、是否需要特定朝向/速度/前序动作；
5. **日志盲区**：探针未覆盖的关键分支，或日志被截断/轮转导致证据链断裂。

询问时至少覆盖：用了什么测试入口（游戏内物品/命令 + 具体按键）、预期与实际的差异、复现频率、有无截图或短视频、能否提供 `latest.log` / `debug.log` 片段。得到回答后先复述事实、区分事实与推测，再讨论根因。

**禁止**：用"日志里看起来是…""按代码应该会…"替代用户观察来宣称客户端物理行为已验证。

**测试入口设计规则（零参数优先）**：

> 动手设计测试入口前**必读 skill `alice-scene-based-testing`**（含一键场景模板、夹具契约、反模式清单和完成前自检）。
> 本节是该 skill 的项目侧摘要；冲突时以 skill 为准并同步修订。

新功能的测试入口必须让真人**几乎不用输入**，且**禁止要求用户输入坐标或长参数串**：

1. 首选：**游戏内交互物品**（右键 / Shift+右键），例如 `alice:pathing_planner`（右键方块即规划）；
2. 次选：**一条无坐标的简单命令**，例如 `/alice pathing plan-here`、`/alice pathing chain east 3`（只允许单词方向、小整数这类参数）；
3. 禁止：要求用户计算坐标、记忆长参数串、或手动构造复杂命令；
4. 每个测试入口都必须能在 `docs/TESTING_GUIDE.md` 里用"拿什么物品/打什么命令 + 看什么"三句话写清；
5. 需要视觉判断的结论（是否跳跃、是否回冲、是否卡边缘）必须在测试指南里标为"需要真人确认"，并在测试后主动询问。

**测试夹具设计原则（一次动作覆盖全部信息）**：

从 2026-09-08 的实践总结，后续新功能的测试夹具按以下模式做：

1. **一键场景**：需要特定地形的测试，必须提供数据包函数（`/function alice_test:<scene>`）一键生成，
   禁止让用户手搭地形。场景函数自包含：`reset` → 建造 → `tp @s` → `give` → `tellraw` 说明。
   参考 `tools/test-scenes/alice_test/data/alice_test/functions/pathing_course.mcfunction`。
2. **场景必须孤立**（用户 2026-09-08 设定）：测试场景必须定义为一个**长方体区域**，该区域边界外
   至少一圈（含上方与下方）为**空气**，不得与其他场景或自然地形相连。**不要求封闭房间，
   开阔场景即可**；只有在需要防止 bot 走出/掉落时才加围墙或区域底部隔离地板。
   `reset` 函数必须先把外扩区域整体清空为空气，再建造内部结构。
   判定标准：站在场景内任意位置，四周/上方/下方一圈都不存在非本场景方块。
3. **一键测试**：多个检查项合并为一个自检任务，**一次物品右键跑完**，末尾输出一行
   `SUMMARY key=VALUE key=VALUE ...`，便于 AI 直接读日志判读。
   参考 `PathingBatteryTask`（规划检查 + 全部 Movement + 链）。
4. **各项独立**：每个子项开始前把 bot 复位到统一起点（日志 `reset_to_hub`），避免测试顺序耦合；
   缺地形的项记 `SKIP`，不算失败。
5. **候选同源**：夹具检测"可测什么"时必须复用规划器的 `MovementProvider`，保证
   "可规划即可执行"，避免夹具与内核判定分叉。
6. **场景入库**：数据包与夹具源码必须进仓库（`tools/test-scenes/`），保证可复现，
   不依赖客户端世界里的临时文件。
7. **最小信息量**：能合并的检查项就合并；测试文档按"两次操作"组织（建场景 + 跑自检），
   细查入口降级为附录。

## 5. Forge 1.20.1 的实现规则

### 5.1 客户端/服务端分层

- 世界修改、权限、物理、库存和任务状态必须在服务端。
- 客户端输入只产生请求；服务端必须重新验证 bot、距离、维度、目标、权限和当前任务。
- 集成服务器不等于单线程：单人游戏仍有客户端和服务端两套状态。
- 每个网络包都写清方向、发送者、处理线程和服务端验证条件。

### 5.2 FakePlayer 和实体

涉及 `FakePlayer`/`ServerPlayer` 时，先确认：

- 生命周期、注销、死亡、维度切换和存档恢复；
- 是否加入玩家列表、客户端是否可见、追踪范围是否足够；
- `tick -> aiStep -> travel -> move` 的实际调用链；
- `isEffectiveAi`、输入字段和 `noPhysics` 等状态；
- 不能用 `setPos` 掩盖输入/碰撞执行器问题，除非明确标记为传送/兼容模式。

客户端看不到实体时，优先检查实体注册、广播、追踪和同步，不要先改渲染器。

### 5.3 移动、碰撞和寻路

- 规划坐标必须明确是脚位、支撑方块、目标方块还是实体位置。
- 路径规划结果不能直接等于动作成功；每段都要有进入条件和完成后置条件。
- 完成判断不能只看整数 `blockPosition()`；半砖、台阶和碰撞形状要比较实际脚底与支撑顶面。
- 不要通过不断增加 epsilon、timeout、重试次数来掩盖错误的坐标契约或物理入口。
- `SEARCH_LIMIT` 不等于不可达，更不自动授权挖隧道。
- 普通挖矿、拾取和稳定任务继续使用已验证的 `HARD_PATH`；软移动实验必须保持独立，直到有明确客户端证据。

### 5.4 GUI、容器和网络

GUI 需要同时检查三件事：

1. 服务端如何打开菜单；
2. 客户端构造函数需要什么附加数据；
3. `ContainerData`、按钮和槽位如何回到服务端并同步回来。

`MenuType` 存在、Screen 注册和 JAR 构建成功都不能证明 GUI 可用。必须验证完整协议闭环：

```text
服务端 openScreen
 -> 打开包附加数据
 -> 客户端 Menu 构造
 -> Screen 注册
 -> 客户端请求
 -> 服务端权限/距离/状态校验
 -> 服务端修改
 -> 客户端同步
```

### 5.5 物品转移和机器适配

- 标准 capability 只能证明接口存在，不等于知道槽位业务语义。
- 写操作必须有 `pre -> simulate -> fresh pre -> actual -> post` 或等价的守恒验证。
- 物品事务要能回答“物品现在在哪里”，不能只靠重试。
- 模组适配器应固定 mod id、版本、端点语义、输入输出和失败条件；未知机器优先只读报告。

## 6. 不再“打补丁”的调试规则

根据 `debugging-root-cause-analysis.skill.md` 和 `alice-discussion-before-repair.skill.md`，连续失败时使用：

```text
现象
 -> 可证伪假设
 -> 最小定向测试
 -> 对照组
 -> 证实/排除
 -> 一次性修复
 -> 回归测试
```

### 6.1 什么时候必须停止补丁

出现以下任一情况就停止继续改参数：

- 同一症状两次修复后仍未改善；
- 每次修复后症状变形，已经不知道哪个改动有效；
- 服务端日志说成功但客户端观察失败；
- 当前根因无法解释全部症状；
- 需要连续增加 epsilon、延时、重试或特判；
- 修复会突破既有安全边界或把实验能力接入正式任务。

此时做 5 Whys 或工作/失败对照，而不是再加一个 if。

### 6.2 根因声明的最低标准

AI 只有在能回答以下问题时，才可以说“根因已确认”：

1. 为什么会发生，而不只是哪里报错？
2. 什么时候会发生、什么时候不会发生？
3. 哪个定向测试证明了它？
4. 它能解释全部关键症状吗？
5. 替代解释是否被排除？

否则使用“当前假设”“最可能原因”“证据不足”，禁止把推测写成结论。

## 7. Alice 当前项目的优先建议

### P0：先建立可信的当前状态，而不是继续扩展功能

当前仓库同时存在路线图、历史交接、旧监督协议、实验文档和大量实现记录。建议先创建上述四个轻量状态文件，并明确：

- 哪些能力已被 Windows 客户端验收；
- 哪些只有 compile/headless 证据；
- 哪些仍是实验入口；
- 哪些文档已废弃。

尤其不要让旧 `HANDOVER.md` 的监督流程继续被新 AI 当成强制开发门槛。

### P1：清理“声明已实现”和“源码仍是 TODO”的冲突

当前代码中仍可见类似以下风险信号：

- `MineTask` 中存在“暂时跳过移动直接挖掘”的 TODO；
- 部分 Movement provider 仍是未来实现或占位；
- `BotControllerExample`、道路放置和工具逻辑中存在示例/临时代码；
- 软移动、道路、转移、GUI 和旧实验入口的验证状态并不相同。

建议不要用重写或删除 TODO 的方式“整理完成”，而是逐项标注：

```text
代码状态：ACTIVE / EXPERIMENTAL / DEAD_CODE / PLACEHOLDER
验证状态：NONE / COMPILE / SERVER / CLIENT / ACCEPTED
允许调用者：哪些正式任务可以调用
```

### P2：共享底座优先

短期优先级建议：

1. 任务生命周期、取消、失败码、最终状态和 bot 可回收位置；
2. 统一移动能力契约和 `HARD_PATH` 回归；
3. 统一服务端观察快照和权限边界；
4. 物品转移守恒与重启/中断处理；
5. 独立客户端测试入口与证据记录。

在这些底座稳定前，不建议进入 LLM、AttackTask、复杂 AE 自动化或更多模组写操作。

### P3：每项新能力都先做“诊断版”

例如新做攻击、交互或机器操作时，先提供：

```text
/alice diagnose-xxx
```

或独立测试物品，只完成一个最小动作并输出：输入、服务端状态、动作阶段、后置条件和失败码。诊断入口通过后，再接入正式任务。这样可以避免正式任务同时承担实验、调试和产品功能三种职责。

### P4：把客户端验收提前到最小闭环

不要等整个功能“全部完成”才首次启动客户端。建议：

- 第一个可见实体：先验证生成、追踪、移动同步；
- 第一个 GUI：先验证打开协议和一个只读值；
- 第一个挖掘动作：先验证合法站位、视线和掉落物；
- 第一个转移动作：先验证单种物品的守恒和拒绝路径。

这会比连续数轮 headless + 静态审查后才发现客户端致命问题便宜很多。

## 9. 最终原则

Alice 最需要的不是更厚的流程，而是**更可靠的短记忆和更清晰的证据边界**：

```text
少量稳定规则
+ 一个短的当前状态文件
+ 一份不可悄悄推翻的决策表
+ 一份真实测试矩阵
+ 失败也记录的变更日志
+ 小闭环、早客户端、根因优先
```

AI 助手可以灵活地讨论、实施和修复；但不能灵活地改变项目目标、把猜测当证据，或把实验代码悄悄接入正式能力。

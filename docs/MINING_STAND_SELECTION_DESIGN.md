# 挖掘站位选优 + Baritone 融合：新框架设计（**定稿 v5**）

> 状态：**已定稿**（2026-09-09，用户逐条确认全部同意）。v3/v4/v5 修订记录如下：
> ① 模式 A 候选范围太窄 → **扩到"可挖掘范围内的格子"**，且**上下都要扩展**（要能从下往上挖）；
> ② 评分**必须包含到达站位的路径成本，且权重较大**；评分职责收窄为**只负责挖掘效率**；
> ③ 站位不限于"现成可站的面"——**没有支撑的格子允许自己搭平台**；
> ④ 目标**下方无支撑**时：要么在目标下方放支撑方块，要么只从**正下方站位**挖掘，**按成本选**；
> ⑤ Q1：A 找不到站位**立刻转 B**（哪怕只被挡一层）；⑥ Q4：兜底可用，并**新增正下方 (y−2) 站位**；
> ⑦ Q3 重议：不自造 tunnel 逻辑，**优先沿用已有寻路机制**；
> ⑧ Q5：模式 A 运行期视线失败**计入重试预算，最多两次**（待评估）；
> ⑨ Q6：拾取距离 / 可见面数 / 安全性**都不进评分**；⑩ Q7：确认删除独立清障与 `BotMiner.pickStandCandidates`，夹具重写。
>
> **v4 追加（用户 2026-09-09）**：
> ⑪ 廉价估算**两种方案可切换**（S1 直线下界 / S2 一次 Dijkstra 成本场，默认 S2）；
> ⑫ `MiningBudget` 默认分档 = **普通方块默认成本**，其他分组用**标签/ID 白名单**设定各自上限（不硬编码）；
> ⑬ `BREAK_AND_ENTER` **至少破坏目的地躯干 + 头位两格**；与其它 Movement 衔接出现高低差时**再扩张一格**（防撞头）；
> ⑭ 垂直范围确认：y 与 y−1 全水平展开；y−2…y−4 **只允许正下方**；上方维持原上界（+1 侧面 / +2 `above(2)`）；
> ⑮ 线程模型见 §7（**暂不异步**，前置是快照层）；
> ⑯（v5 定稿）`BREAK_AND_ENTER` 的扩张一格**只在进入时存在高低差时**补挖；
> ⑰（v5 定稿）`MiningBudget` 分档 = 普通方块默认成本 + 标签/ID 白名单分组上限。

## 1. 两个模式的职责

| 模式 | 适用 | 核心 |
|---|---|---|
| **A 直接可挖** | 能从多个角度直接挖到目标 | 保留原站位系统（多角度候选 + 视线前提 + 评分），到达用寻路，到位原地挖 |
| **B 埋藏 / 需通道** | A 找不到任何可用站位（哪怕只被挡一层） | 候选收窄到"目标 4 面 × {同层, 低一层} + 正下方 (y−2)"，到达沿用寻路机制（破坏 + 放置） |

**切换（Q1 已裁定）**：A 无解 → **立刻** B。不再有"清障后重试 A"。

## 2. 模式 A

### 2.1 候选范围（**扩大**）
- 范围 = **眼位可触及目标任一面的格子**（`bot.getBlockReach()` 决定），而不再是"水平最多 1 格"；
- **上下都要扩展**：包括目标上方、下方多层的格子（支持**从下往上挖**）；
- 候选的两种形态：
  1. **现成可站**：`canWalkOn(pos)` + `canWalkThrough(pos)` + `canWalkThrough(pos.above())`；
  2. **可搭建**：该格没有支撑/被方块占用，但可以通过**放置方块搭平台**（`PLACE_STEP_AND_TRAVERSE` 式）变成可站格。
- 排除：目标自身；**是否排除"目标正上方（脚位 y+1）"待定**（挖掉自己支撑）——见 Q1′。

### 2.2 评分（**只负责挖掘效率**）
- **主要项：到达站位的路径成本（权重较大）**——包含破坏/放置成本（用 `withWorldModification` 规划的真实成本）；
- 次要项：挖掘便利性（眼位到目标面的距离/角度等，具体项待定）；
- **不进评分**（用户裁定）：掉落物拾取距离（真人挖矿习惯不在意）、可见面数量（多看到几面与效率无关）、
  安全性单独计分（职责应收窄到挖掘效率）。

**候选成本估算（两方案可切换，默认 S2）**：

| 方案 | 做法 | 精度 | 代价 |
|---|---|---|---|
| **S1 直线下界** | 用 A\* 的 octile 下界排序，取 top-K 精算 | 平坦地形几乎无损；有墙/落差时近邻候选排序会翻转（误差 = 绕行余量 D） | ≈200 次启发式求值，<0.1 ms |
| **S2 Dijkstra 成本场（默认）** | 从 bot 脚位做一次**纯通行** Dijkstra（半径 R≈12），得到每个可达格的**真实纯通行成本**；需搭建的候选估算为 `cost(相邻格)+PLACE_ONE_BLOCK_COST` | **现成可站候选零损失**；仅"需搭建"候选为估算 | 一次搜索 ≈1~3 ms |
| （备选 S3） | 每候选跑有界 A\*（≤200 节点） | 成本可能高估（加权系数导致 ≤1.5× 次优），但口径一致 | ≈2~10 ms |

**top-K**：K=4（保守 6）；精算后若"最优精算成本 > 第 K+1 名估算"，K+=2 重试（有上界）。
切换方式：配置 + 命令（如 `/alice mining estimate lower_bound|dijkstra`），默认 `dijkstra`。

### 2.3 目标下方无支撑的处理（新规则）
若目标下方 (x, y−1, z) 无支撑（悬空目标）→ 挖掉后掉落物会掉进虚空，两种策略**按成本选**：
1. **先在目标下方放支撑方块**（在 (x, y−1, z) 放置），再从侧面/上方站位挖；
2. **只从正下方站位挖**（站位 (x, y−2, z)，向上挖），掉落物落到自己脚边。
> 这两条都要计入路径/动作成本后比较（放置 ≈ `PLACE_ONE_BLOCK_COST`，正下方站位可能路径更长/需搭平台）。

## 3. 模式 B（埋藏 / 需通道）

### 3.1 候选（9 格）
```
(x±1, y,   z)  (x, y,   z±1)      // 同层（目标在躯干/眼位）
(x±1, y−1, z)  (x, y−1, z±1)      // 低一层（目标在头位）
(x,   y−2, z)                     // 正下方（向上挖；掉落物落脚下）
```
排除：目标自身、目标正上方。

### 3.2 到达方式（Q3 重议结论）
- **不自造 tunnel / WALKANDBREAK 语义**，**沿用已有寻路机制**：`PathRequest.withWorldModification`
  （`BREAK_AND_TRAVERSE` / `PLACE_STEP_AND_TRAVERSE` / `DOWNWARD` / `FALL` / `PILLAR`）；
- 但发现一个**能力缺口**：现有 `BREAK_AND_TRAVERSE` 几何是 **dx=2**（破坏中间格），
  **缺 dx=1 的"破坏目的地格并进入"**。Baritone 的 `MovementTraverse.positionsToBreak = {dest, dest.above()}`
  正是这个语义。
  - **用户裁定（v4）**：**新增 `BREAK_AND_ENTER`**（不动 `BREAK_AND_TRAVERSE`），
    **只破坏 1 格语义的扩展**：至少破坏 **目的地躯干格 + 头位格**（`{to, to.above()}`，与 Baritone 一致）；
    若与其它 Movement 衔接导致进入时存在**高低差**（可能撞头），**再扩张一格**（`to.above(2)`）——具体条件见 Q8′。
- **兜底**（Q4 已裁定可用）：9 格全不可用时，允许"以目标格为终点 + 破坏进入"（Baritone `GoalBlock` 式）。

### 3.3 覆盖性目标（用户要求）
除**不可挖掘的方块**与**不可涉及的区域**（熔岩等）外，模式 B **应当保证存在可到达的站位**；
到达方式可能是"挖通道"，也可能是"搭方块"——因此**必须同时允许破坏与放置**（即 `withWorldModification`）。

- 重试是否与 `PathRetryRunner` 的 replans 预算合并——待评估。

## 7. 线程模型（用户提问：能不能像 Baritone 那样单开线程）

**现状（Alice）**：寻路**同步跑在服务端主线程**——`CorePathPlanner` 文档明写"同步主线程执行"，
`MovementContext.live(...)` 直接持有 `ServerLevel` 读实时世界（D-044：R7 异步搜索若立项需接 `BlockStateInterface` 式快照）。

**Baritone 的做法**：`PathingBehavior.findPathInNewThread` → `Baritone.getExecutor()` 线程池，
世界读取全部走 `BlockStateInterface`（`CachedChunk` **快照**），因此可以安全地在工作线程算。

**服务端异步的风险（Forge/原版不替我们兜底）**：
1. `ServerLevel.getBlockState` 在非主线程可能触发区块加载/查询 → "Asking a chunk from a different thread" 类异常、
   或与主线程的区块替换/卸载并发；
2. 任何惰性初始化（形状缓存、capability 查询）都可能写入，非线程安全；
3. Alice 的规划期还读了**主线程独占状态**：bot 快捷栏（`findPlaceableSlot`）、工具栈（`estimateBreakTicks`）、
   静态 `PathingStats`、`ScopeBuffer`；
4. 计划可能基于**跨 tick 不一致**的世界状态（可复现性差）；
5. 收益有限：S2 估算把站位评估压到 1~3 ms，A\* 单次也在毫秒级。

**结论（建议）**：**暂不异步**。若将来确有必要，前置条件是先做**快照层**
（主线程把半径 R 内的方块状态拷进不可变结构 → 工作线程只读快照），
这同时能解决规划期"看不到上一段破坏结果"的投影世界问题（D-055 已登记）。
届时寻路与站位评估可以共用同一份快照。

## 附录：`blockerCount` 是什么

`LineOfSightChecker.LineOfSightResult.blockerCount` 原本表示"沿采样射线遇到的遮挡方块数量"，
用于已删除的视线评分（1 个遮挡 = 50 分 / 多个 = 0 分）。但实现里恒为
`firstBlocker == null ? 0 : 1`（`LineOfSightChecker:44`），**永远是 0 或 1**，因此那个"多遮挡"分支从未生效。
现在视线已改为**前提条件**（D-066），该字段只剩日志里的 `toString` 用途 → 建议直接删除。

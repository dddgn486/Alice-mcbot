# 方块交互三条路线对比：接口直写 vs 菜单协议 vs 视觉识别

> 2026-09-13 用户提问："不同模组菜单信息和交互方式差距非常大。带上那 6 个点，先说清**目前方案**与**仿真方案**的区别：
> ① 兼容性和效率；② 玩家在游戏里能看到的区别。" 本文是回答与留档（**只讨论，未实现**）。

## 0. 先把三条路线分清（用户此前只知道"视觉识别"）

| 路线 | 做法 | 是否本文选项 |
|---|---|---|
| **A 接口直写**（今天是这条） | 拿方块实体的 capability / API：`IItemHandler.insertItem/extractItem`、`IEnergyStorage`、模组自定义 cap（Mek 的 gas/slurry/heat…）、必要时 `instanceof` 直接改字段 | ✅ 现状 |
| **B 菜单协议**（所谓"仿真"） | 走**真实玩家右键的同一条路**：`ServerPlayerGameMode.useItemOn` → 方块 `use()` → `openMenu` 出真菜单 → 用 `AbstractContainerMenu.clicked(slot,button,ClickType)` / `quickMoveStack` 搬物品 → 关闭 | ✅ 待评估 |
| **C 视觉识别** | 截图 + 图像识别 GUI 再模拟鼠标点击 | ❌ 与 B **无关**；B 不渲染、不看画面，走的是协议包 |

**关键澄清**：B 不需要真实客户端、也不需要看屏幕。真实玩家的客户端发的是
`ServerboundUseItemOnPacket`（开箱）与 `ServerboundContainerClickPacket`（点槽位）；
我们在**服务端**直接调用这两个包最终落到的那两个方法，**协议语义完全一致**，只是没有渲染。

## 1. 对比一：兼容性与效率

### 1.1 兼容性（谁能被覆盖、谁来定义"正确")

| 维度 | A 接口直写 | B 菜单协议 |
|---|---|---|
| **通用覆盖面** | Forge capability 只覆盖 **物品/流体/能量**；模组自有机制度（Mek 的气体/浆液/灌注/颜料、热力膨胀的 augments…）**没有统一标准** ⇒ 要么引它的类，要么反射 | **菜单是模组自己暴露给玩家的界面** ⇒ 凡是"人能操作的机器"都在覆盖范围内，**不需要模组作者额外支持任何 API** |
| **槽位/配置语义** | `IItemHandler.getSlots()` 只有**下标，没有语义**；"哪个槽是输入/输出/燃料/升级"必须自己学 ⇒ **每个模组一张表** | 同样是下标；但**菜单里槽位带 GUI 位置/图标**，人可以看懂；语义仍需表，但可以从"玩家怎么看"推出，且**模组必须支持人操作** ⇒ 表更稳定 |
| **配置改动**（面配置/升级/安全/红石） | 只能靠模组专属接口（`ISideConfiguration`/`ITileUpgradable`/`ISecurityTile`…）⇒ **强耦合、易随版本失效** | 走菜单里的按钮/页签（点击语义）⇒ **同一条通用机制**，不需要专属接口 |
| **模组策略与钩子** | ⚠️ **可能被绕过**：安全终端/领地/统计/成就/"谁插入了"的钩子通常挂在 **GUI 打开与点击**上；capability 直写常不触发 ⇒ 我们可能**做了模组不允许的事**（今天没有任何机制能发现） | ✅ **走的就是模组自己的入口**：打开/点击会如实触发它的钩子、权限与提示 ⇒ "兼容"不只是"能改"，而是"**按模组意图改**" |
| **版本稳定性** | 模组内部类/字段一变就崩（我们刚吃过：硬引用 Mek 在无 Mek 客户端**必崩**）⇒ 必须反射 + absence-safe | 菜单协议是**长期稳定的公共面**（原版 + Forge 都保证），模组更新几乎不影响 |
| **能力边界（谁能做/谁做不到）** | 能做 B 做不到的：**跨距离/瞬时的批量搬运**（只要自己定义范围规则）、机器内部状态读写 | 做不到"玩家做不到的事"：**受原版触及（use ≈4.5 格）与菜单校验（箱子 `stillValid` 8 格）约束**；菜单没暴露的东西碰不到 |

### 1.2 效率

| 维度 | A 接口直写 | B 菜单协议 |
|---|---|---|
| 单次开销 | 一次方法调用（+可能的 NBT/字段写）⇒ **微秒级** | 开菜单 + 若干次点击 + `broadcastChanges` + 关菜单 ⇒ **毫秒级**，且受槽位/堆叠规则限制 |
| 大批量 | 可一次插入上千件（只受我们自己的 `WriteBudget` 约束） | 逐槽/逐堆操作；一次点击只能搬一堆 ⇒ **慢**（但"慢"正是玩家的真实速度） |
| 需要的物理条件 | 今天**没有**（我们最近才把"站到箱子上"改成 L1 的范围内操作）；可以任意放宽 | **必须**站在够得着的可站点、朝向方块、菜单有效（离太远自动关） |
| 可见副作用成本 | 几乎为零（也正因此**不可见**） | 有声音/开盖动画/`ContainerOpenersCounter` 计数等真实副作用 |

**一句话**：**A 更快、更通用（对"自己的机制"）、但语义靠我们自学且可能绕过模组意图；
B 慢一些、受限更多，但它是模组**自己保证**的接口，且天然不会做"玩家做不到的事"。**

## 2. 对比二：玩家在游戏里能看到的区别

| 观察点 | A 接口直写 | B 菜单协议 |
|---|---|---|
| **动作可读性** | 几乎**不可读**：bot 站定后箱子里的东西**凭空变化**（没有开盖、没有声音、没有朝向要求）；玩家看到现象但看不到"因" | 与真人一致：bot **转向方块 → 右键 → 开盖动画 + 开箱音 → 物品逐堆移动 → 关盖**；因果关系肉眼可跟 |
| **箱子开盖动画/音效** | ❌ 不触发（`ChestBlock` 的开合是通过 `ContainerOpenersCounter`/方块事件驱动的） | ✅ 触发（真人同款） |
| **玩家自己也开着这个箱子时** | 物品会经由 `broadcastChanges` **突然出现/消失**在他的界面里（"隔空被搬走"的观感） | 同左（服务端内容变化一样会同步），但玩家更容易理解"是有个 bot 在操作" |
| **模组侧的可见反馈**（安全提示、访问日志、机器音效/粒子） | ❌ 一般不触发 | ✅ 触发（模组把反馈挂在菜单打开/点击上） |
| **被保护/被拒绝时的表现** | ⚠️ 可能**无声地成功**（绕过保护）—— 最危险的一种"看不到" | ✅ 会像玩家一样**被拒绝**（打不开/提示"无权限"），行为可预期 |
| **"像不像人"** | 像管道/料斗（自动化基建） | 像人（这通常正是"AI 玩家"这个项目想要的观感） |

## 3. 那 6 个讨论点，在两条路线下各自是什么形态

| # | 议题 | A 接口直写 | B 菜单协议 |
|---|---|---|---|
| 1 | **驱动器形态** | 每模组一张"能力/字段"适配表（强耦合） | **一个通用菜单驱动器** + 数据驱动的"槽位语义表"（弱耦合，且这张表人也看得懂） |
| 2 | **槽位语义** | 必须有（下标→含义），否则不知道往哪插 | 同样必须有（点击哪个槽），但可复用同一张表 ⇒ **两条路都逃不掉适配表**，B 的表更稳定 |
| 3 | **生命周期与超时** | 无新增状态（一次调用即完成） | **新增"菜单开着"这个状态**：中断/生存打断/下线必须能安全关闭，否则会变成新的死状态。✅ **2026-09-13 实测踩到并已修**：用户发现"任务终止时箱子还开着" ⇒ 见 `bot/MenuLifecycle`（收尾收敛点强制关闭 + 看门狗告警） |
| 4 | **授权与账本** | 今天 = A11 容器写入 + 预算（刚接上） | 同 A11；另需回答"**打开菜单算不算读取**"（可能触发模组权限记录 ⇒ 也应入账本） |
| 5 | **客户端/服务端边界** | 无客户端参与 | 需验证：**没有真实客户端**时服务端菜单状态自洽（`openMenu` → `clicked` → `broadcastChanges` 不依赖客户端回包）——**L2 的第一技术风险点** |
| 6 | **失败码词表** | `adapter_missing` / `capability_absent` / `slot_semantics_unknown` | `menu_open_failed` / `menu_slot_mismatch` / `menu_closed_early` / `container_full` |

## 4. 结论与建议（待用户裁定）

1. **不建议二选一**，建议**分层**：
   - **B 作为默认**（"能开菜单就用菜单"）—— 因为它是模组自己的契约，**不会绕过权限/统计/保护**，
     且玩家能看懂 bot 在干什么；
   - **A 作为显式优化**，仅在**适配表明确声明"该机器支持能力直写且语义等价"**时启用
     （例如纯物流箱、料斗），并**仍然要求 L1 的站位/触及**，避免"隔空搬运"的观感。
2. **"玩家能看见"应当成为一条产品要求**（写进决策）：无论走哪条路，bot 的操作都应**可被旁观者理解**
   ——这条比"用哪种协议"更重要。
3. **第 5 项验证已完成（2026-09-13，用户实测"符合预期"）**：`alice:menu_probe` 真的开出 `ChestMenu`、
   真的用菜单点击搬动物品、干净收尾 ⇒ **B 路线可行**；同时暴露并修掉了"终止时菜单不收尾"的生命周期漏洞。
4. **下一步最该做的是第 5 项的技术验证**（1 个最小实验，代价小、结论硬）：
   让 bot 在无真实客户端的情况下**真的打开一次箱子菜单**，读回槽位内容、点一下、关闭，
   确认服务端状态自洽。它成立 ⇒ L2 可行；不成立 ⇒ 整条 B 路线要重新评估（而不是先写一堆适配器）。
4. 需要你定的：
   - 是否同意"**B 默认 + A 显式优化**"的分层；
   - 是否先做第 5 项验证；
   - 若 L2 成立，**槽位语义表**由谁产出（人工登记 / 从 JEI 类别抓 / 运行时试探 + 人工确认）。

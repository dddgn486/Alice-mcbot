## 1. Baritone 对照：它的水中移动到底有多自由（`D-036` 内核路线要求）

来源：`/home/fb486/projects/reference/baritone-1.20.1`（路径相对该仓库根）。

### 1.1 结论先行

> **Baritone 没有自由 3D 游泳。** 水平方向"浸没也能走"（成本 ~2× 陆地），向上只有"水柱专用上升"，
> 向下只有"掉进水里"，**没有下潜**；而且**水中放置/破坏默认几乎全被拦**。

### 1.2 逐条事实

| 能力 | Baritone 的做法 | 位置 |
|---|---|---|
| **浸没时水平移动** | **允许**：闸门只查 `canWalkOn(目的地下一格)`，**不要求有地面**；执行 = `MOVE_FORWARD` + **常态 JUMP** | `MovementTraverse.java:84`、`:269-270`；`Movement.java:126-128` |
| 水平移动成本 | `WALK_ONE_IN_WATER_COST ≈ 9.09` vs 陆地 `≈ 4.63`（**~2×**）；`waterWalkSpeed` 按 Depth Strider 插值 | `ActionCosts.java:25-26`；`CalculationContext.java:120-124` |
| 水中冲刺 | **抑制**（`sprintInWater` 才放行） | `MovementTraverse.java:89,112`；`Settings.java:816` |
| **向上** | 水柱专用上升（`LADDER_UP_ONE_COST`）；其余上升靠 JUMP | `MovementPillar.java:77-81,150-155` |
| **向下** | **只能"掉进水里"**（要求非流水 + 下方有可走方块） | `MovementDescend.java:160-179`；`MovementFall.java:102-103` |
| 下潜（dive） | **不存在**（无 pitch/dive 输入；grep 无） | —— |
| **可站语义（关键差异）** | **浸没层可站、水面层不可站**（jesus off 时 `isWater(above) ^ assumeWalkOnWater`）；镜像规则：浸没的水**不可穿过** | `MovementHelper.java:451`、`:226-230` |
| 桥接进水里 | **COST_INF**（浸没时禁止） | `MovementTraverse.java:130-134` |
| 游泳时回填 | **不可能**（backplace 禁） | `MovementTraverse.java:160-161` |
| 液体中搭柱 | 没有"可倚靠面"就 **COST_INF** | `MovementPillar.java:94-98` |
| 向流体里放置 | **被闸门挡住**（`allowPlaceInFluidsSource/Flow`，**默认关**） | `CalculationContext.java:166-170`；`Settings.java:83,88` |
| 液体正上方破坏 | **总是允许**；相邻液体的破坏**回避** | `MovementHelper.java:87,98-109`；`Settings.java:148` |
| 水桶下落技巧 | 放水桶 → 落地 → 收回 | `MovementFall.java:102-103,128-141` |

### 1.3 对 Alice 的三条直接含义

1. **用户 ② 想要的机制在 Baritone 里是被禁的**（向流体里放置默认关、桥接进水里 COST_INF）
   ⇒ Alice 做「**用水位放置覆盖、再站上去**」是一次**主动偏离**。
   `D-036` 要求：登记 `Baritone 文件:行` + **Alice 特有约束**（下文 §4 给约束）。
2. **可站语义两边相反**（Baritone：浸没层可站；Alice `D-251`：**水面层**可站、浸没层不可站）
   ⇒ 这条差异**正好决定**用户考量 ⑤ 的答案（见 §3.0）。
3. 成本可抄的部分：**水中移动 = 陆地 ~2×**（`ActionCosts.java:25-26`）。Alice 现在有没有这一项，
   待 §2 审计确认。

## 3. 分层计划（顺序待用户裁定）

### 3.0 先回答用户考量 ⑤（**我的分析，待 §2 事实确认**）

> **「一进水就浮」是**利**，不是弊** —— 它很可能是**唯一**能让规划器动起来的前置。

理由（基于 Alice 的 `D-251` 语义，待审计确认）：
- 若**完全浸没**的格子不是合法落点（`canWalkOn` 为假），那么搜索在该状态下的**水平边一条也生成不出来**
  （`TRAVERSE`/`DIAGONAL` 都要求目的地可站）⇒ bot 在**不可规划状态**里，任何"去找无水站位"都无从谈起；
- 浮到**水面**后，水面格**变成**合法落点 ⇒ 才可能生成"沿水面水平移动 → 靠近岸边 → 上岸/放置出水"的路径。
- 因此顺序应当是 **先浮（已有，`D-380`）→ 再水平**，而不是"为了水平而拒绝上浮"。
- ⚠️ 唯一会互相打架的情形是"目标在水下"（水下通道/水下矿洞入口）：但用户口径 ③ 已把范围限定在
  **已有的无液体站位** ⇒ 不冲突。
- ⚠️ **必须实测的一条**（第 0 阶段）：浮到水面后能否**真的**沿水面水平移动
  （执行期是否持续按住跳跃保持浮面 —— `D-243`/`D-251` 的 `shouldHoldJumpInWater` 是否覆盖 `TRAVERSE` 段）。

### 3.1 分层（每层都要有"能红的判据 + 零参数客户端入口"）

| 层 | 做什么 | 依赖 | 判据（夹具/电池步） | 客户端入口 |
|---|---|---|---|---|
| **0 观察** | 量清"浮起来之后能不能水平走到岸边"：水面格算不算可站、能不能规划、执行期会不会掉下去 | 无（只观察） | 新夹具：水面平台 + 岸边高 1 格，断言"能规划到岸边站位的路径"（`status/movements`） | 现有：把 bot 放进水里看它是否**朝岸边移动** |
| **1 现成无水站位 + 纯通行可达** | 直接走过去（也许**大部分能力已存在**，先确认缺什么） | 层 0 | 同上夹具的"成功"分支 | 同上 |
| **2 有站位但纯通行不可达 ⇒ 世界修改** | 明确**偏向放置**：把水**覆盖**成落脚点再上去；挖掘作为最后手段 | 层 1 + 定义"水可被放置覆盖" + 成本模型修正（§2 待查） | 新夹具：岸边无水站位在 2 格外、纯通行规划失败 ⇒ 必须用**放置**类边到达；断言"用了放置、没挖" | 新物品/命令：进水后应"搭一块再上来" |
| **3 没有现成站位 ⇒ 如实失败** | **不做**（只做判据）：不许挖/放来**自己造**落脚点 | 层 2 的授权面 | 夹具负例：四周全无无水站位 ⇒ 必须**如实失败**且**零世界改动** | 无（看日志失败码） |

### 3.2 成本模型（用户考量 ⑥）

- **放置**成本 = `CostModel.PLACE_ONE_BLOCK_COST` = 20/6 ≈ **3.33** 走路格；
- **挖掘**成本 = `(estimateBreakTicks + BREAK_PENALTY_TICKS) / WALK_ONE_BLOCK_TICKS`；
- 若 `estimateBreakTicks` **没有**水中惩罚项 ⇒ 水中挖石头被算成"陆地速度" ⇒ **规划器会过度挖**。
  修正方向：把"眼在水里 ⇒ ×5（除 Aqua Affinity/潮涌能量）"写进 `estimateBreakTicks`
  （**唯一来源**，规划与执行共用 ⇒ 不产生第二份口径），然后让 **规划器自然偏向放置**，
  而不是在规划器里塞"水里优先放置"的特判。
- ⚠️ 这条修正会**改变既有路线选择**（水中挖掘变贵）⇒ 必须配反证夹具 + CORE 回归。

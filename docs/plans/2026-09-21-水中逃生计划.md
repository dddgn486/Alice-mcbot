## 1. Baritone 对照：它的水中移动到底有多自由（`D-036` 内核路线要求）

来源：`/home/fb486/projects/reference/baritone-1.20.1`（路径相对该仓库根）。

### 1.1 结论先行

> **Baritone 没有自由 3D 游泳。** 水平方向"浸没也能走"（成本 ~2× 陆地），向上只有"水柱专用上升"，
> 向下只有"掉进水里"，**没有下潜**；而且**水中放置/破坏默认几乎全被拦**。

### 1.2 逐条事实

| 能力 | Baritone 的做法 | 位置 |
|---|---|---|
| **浸没时水平移动** | **允许**：闸门只查 `canWalkOn(目的地下一格)`，**不要求有地面**；执行 = `MOVE_FORWARD` + **常态 JUMP** | `MovementTraverse.java:84`、`:269-270`；`Movement.java:126-128` |
| 水平移动成本 | `WALK_ONE_IN_WATER_COST ≈ 9.09` vs 陆地 `≈ 4.63`（**~2×**）；`waterWalkSpeed` 按 Depth Strider 插值 | `ActionCosts.java:25-26`；`CalculationContext.java:120-124` |
| 水中冲刺 | **抑制**（`sprintInWater` 才放行） | `MovementTraverse.java:89,112`；`Settings.java:816` |
| **向上** | 水柱专用上升（`LADDER_UP_ONE_COST`）；其余上升靠 JUMP | `MovementPillar.java:77-81,150-155` |
| **向下** | **只能"掉进水里"**（要求非流水 + 下方有可走方块） | `MovementDescend.java:160-179`；`MovementFall.java:102-103` |
| 下潜（dive） | **不存在**（无 pitch/dive 输入；grep 无） | —— |
| **可站语义（关键差异）** | **浸没层可站、水面层不可站**（jesus off 时 `isWater(above) ^ assumeWalkOnWater`）；镜像规则：浸没的水**不可穿过** | `MovementHelper.java:451`、`:226-230` |
| 桥接进水里 | **COST_INF**（浸没时禁止） | `MovementTraverse.java:130-134` |
| 游泳时回填 | **不可能**（backplace 禁） | `MovementTraverse.java:160-161` |
| 液体中搭柱 | 没有"可倚靠面"就 **COST_INF** | `MovementPillar.java:94-98` |
| 向流体里放置 | **被闸门挡住**（`allowPlaceInFluidsSource/Flow`，**默认关**） | `CalculationContext.java:166-170`；`Settings.java:83,88` |
| 液体正上方破坏 | **总是允许**；相邻液体的破坏**回避** | `MovementHelper.java:87,98-109`；`Settings.java:148` |
| 水桶下落技巧 | 放水桶 → 落地 → 收回 | `MovementFall.java:102-103,128-141` |

### 1.3 对 Alice 的三条直接含义

1. **用户 ② 想要的机制在 Baritone 里是被禁的**（向流体里放置默认关、桥接进水里 COST_INF）

   `D-036` 要求：登记 `Baritone 文件:行` + **Alice 特有约束**（下文 §4 给约束）。
2. **可站语义两边相反**（Baritone：浸没层可站；Alice `D-251`：**水面层**可站、浸没层不可站）

3. 成本可抄的部分：**水中移动 = 陆地 ~2×**（`ActionCosts.java:25-26`）。Alice 现在有没有这一项，

### 2.2 逐条事实（审计原文，位置略）

- **`canWalkOn` 水位例外（`D-251`）精确语义**（`MovementHelper.java:55-57`）：
  `if (below 是水) return isWater(foot) && !isWater(foot.above())`
  ⇒ (a) **完全浸没**（脚+头都是水）= **假**，无支撑；(b) **水面格**（脚是水、上面是空气）= **真**；
  (c) 干燥格：below 是空气/水源/`avoid` ⇒ 假，固体 ⇒ 真，无碰撞 ⇒ 再往下探一层（`:58-72`）。
- **完全浸没时十种 Movement 的成边能力**：`TRAVERSE`/`DIAGONAL`/`ASCEND`/`DESCEND` 全都要目的地
  `canWalkOn` ⇒ 只有"顶层水格"目的地可行；`DOWNWARD` 不行（`canWalkOn(from.below())` 假、流体 tick +∞）；
  `FALL` 不行（要求无流体的可站落点）；`PILLAR`/`PLACE_STEP_AND_TRAVERSE` **取决于**几何（需要
  `hasPlacementFace`：脚旁/目的地下方要有固体邻居）；`BREAK_AND_ENTER`（水本身可穿 ⇒ 提前返回）、
  `BREAK_AND_TRAVERSE`（要 `canStandCentered` + `mid` 可站）**不成**。
  ⇒ **开阔水面里一条边都生成不出来** ⇒ **完全浸没的 bot 今天规划不出任何移动**（`SurfaceMovementProvider.java:51,95,136-138,179-187,244-249,299-304,326,350,384,399,449-482`）
  ⇒ **这正好证成 §3.0 的结论：先浮是前置，不是妨碍**。
- **庇护所搜索**：`isRefuge` = 区块已载入 + 脚/头无液体可穿 + `canWalkOn`；`nearestSafeRefuge` =
  脚下 17³ 盒内最近者、`REFUGE_RADIUS=8`、找不到返回 `null`；`hasRefuge` **排除 bot 自己那格**；
  `plannableRefuge` 先做 `PathRequest.of` 预检（只有 `UNREACHABLE` 算无出口），再套 8/8 逃生准备金
  （带写权），按 `hazard+foot+writes` 缓存（`SurvivalSystem.java:234-235,268-287,430,451-474,477-489`）。
- **`SurvivalFloatTask` 语义**：成功 = `!眼在水里 && air ≥ 100`（`AIR_SAFE`）；失败 = `ticks > 240`
  （`MAX_TICKS`）⇒ `markFloatFailed` + 封 1200 tick；**只在头还在水里时按跳跃**；**头出水但 air<100 时
  既不按跳跃也不移动**；结束时清跳跃与移动、任务即终了（`SurvivalFloatTask.java:66-74,86-87`；
  `SurvivalSystem.java:403-407`；`BotManager.java:2290-2292`）；无任务时再沉下去会**重新**起一次上浮
  （`BotManager.java:2346-2359`）。
- ⚠️ **与用户观察的差异（以用户观察为准，记账不改）**：审计读代码说"头出水但空气没缓过来时不按跳跃 ⇒
  **可能缓沉**"，而用户第十一轮实测**没有缓沉**。两条并不矛盾（无任务再沉会立刻重起上浮 ⇒ 观感是浮面维持），
  但**"浮面维持"这件事本身没有专门判据**（既没有夹具断言"浮起后 N tick 内不出水"，也没有"持续踩水"的实现）
  ⇒ 登记为**未验证**，别当成已实现的能力。

## 3. 分层计划（顺序待用户裁定）

### 3.0 先回答用户考量 ⑤（**我的分析，待 §2 事实确认**）

> **「一进水就浮」是**利**，不是弊** —— 它很可能是**唯一**能让规划器动起来的前置。

理由（~~基于 Alice 的 `D-251` 语义，待审计确认~~ **✅ 已由 §2.2 审计证实**）：
- 若**完全浸没**的格子不是合法落点（`canWalkOn` 为假），那么搜索在该状态下的**水平边一条也生成不出来**
  （`TRAVERSE`/`DIAGONAL` 都要求目的地可站）⇒ bot 在**不可规划状态**里，任何"去找无水站位"都无从谈起；
- 浮到**水面**后，水面格**变成**合法落点 ⇒ 才可能生成"沿水面水平移动 → 靠近岸边 → 上岸/放置出水"的路径。
- 因此顺序应当是 **先浮（已有，`D-380`）→ 再水平**，而不是"为了水平而拒绝上浮"。
- ⚠️ 唯一会互相打架的情形是"目标在水下"（水下通道/水下矿洞入口）：但用户口径 ③ 已把范围限定在
  **已有的无液体站位** ⇒ 不冲突。
- ⚠️ **必须实测的一条**（第 0 阶段）：浮到水面后能否**真的**沿水面水平移动
  （执行期是否持续按住跳跃保持浮面 —— `D-243`/`D-251` 的 `shouldHoldJumpInWater` 是否覆盖 `TRAVERSE` 段）。

### 3.1 分层（每层都要有"能红的判据 + 零参数客户端入口"）

| 层 | 做什么 | 依赖 | 判据（夹具/电池步） | 客户端入口 |
|---|---|---|---|---|
| **0 观察** | 量清"浮起来之后能不能水平走到岸边"：水面格算不算可站、能不能规划、执行期会不会掉下去 | 无（只观察） | 新夹具：水面平台 + 岸边高 1 格，断言"能规划到岸边站位的路径"（`status/movements`） | 现有：把 bot 放进水里看它是否**朝岸边移动** |
| **1 现成无水站位 + 纯通行可达** | 直接走过去（也许**大部分能力已存在**，先确认缺什么） | 层 0 | 同上夹具的"成功"分支 | 同上 |
| **2 有站位但纯通行不可达 ⇒ 世界修改** | 明确**偏向放置**：把水**覆盖**成落脚点再上去；挖掘作为最后手段 | 层 1 + 定义"水可被放置覆盖" + 成本模型修正（§2 待查） | 新夹具：岸边无水站位在 2 格外、纯通行规划失败 ⇒ 必须用**放置**类边到达；断言"用了放置、没挖" | 新物品/命令：进水后应"搭一块再上来" |
| **3 没有现成站位 ⇒ 如实失败** | **不做**（只做判据）：不许挖/放来**自己造**落脚点 | 层 2 的授权面 | 夹具负例：四周全无无水站位 ⇒ 必须**如实失败**且**零世界改动** | 无（看日志失败码） |

### 3.2 成本模型（用户考量 ⑥）

- **放置**成本 = `CostModel.PLACE_ONE_BLOCK_COST` = 20/6 ≈ **3.33** 走路格；
- **挖掘**成本 = `(estimateBreakTicks + BREAK_PENALTY_TICKS) / WALK_ONE_BLOCK_TICKS`；
- ✅ **已证实（§2.1 发现①）**：`estimateBreakTicks` **没有**水中惩罚项 ⇒ 水中挖石头被算成"陆地速度"
  （差 5×，眼在水里+离地则 25×）⇒ **规划器会过度挖**。
  修正方向：把"眼在水里 ⇒ ×5（除 Aqua Affinity/潮涌能量）"写进 `estimateBreakTicks`
  （**唯一来源**，规划与执行共用 ⇒ 不产生第二份口径），然后让 **规划器自然偏向放置**，
  而不是在规划器里塞"水里优先放置"的特判。
- ⚠️ 这条修正会**改变既有路线选择**（水中挖掘变贵）⇒ 必须配反证夹具 + CORE 回归。

## 6. 「上岸（纯通行）」设计（用户第十二轮追加 = **要做**，层 0/1 的切片）

### 6.1 先回答："他在水里窒息受伤时会逃到岸边，为啥不套给一般状态？"

**事实（代码级，全部可核）**：

1. 用户看到的那次"逃到岸边"走的是：`classify` 空气归零 ⇒ `LOW_AIR`（`SurvivalSystem.java:543-545`）
   ⇒ 它是**软危险**（`:130-131`）⇒ 过 10 tick 宽限（`SOFT_HAZARD_GRACE_TICKS=10`，`:87`）
   ⇒ `plannableRefuge(bot, type, allowWrites)` 找到**无液体 + 纯通行可达**的落点（`:210-216`）
   ⇒ 判决 `INTERRUPT` ⇒ `BotManager.startSurvivalExit()`（`:2263`、`:2375`）
   ⇒ 起 `SurvivalExitTask(bot, refuge, reserve=false)`（`:2405-2439`，纯通行请求）。
2. **它其实已经接在"无任务"档里了**（`tickHazardWithoutTask` 的 `case INTERRUPT -> startSurvivalExit()`）。
   一般状态够不着它，是两个**设计选择叠加**：
   - **① `WATER_CONTACT` 不是软危险** ⇒ `decide` 恒 `IGNORE`（`:154-156` 记着真机实测
     `hazard=WATER_CONTACT duration=241 air=300→62` 零反应）。这是**故意**的：在水里本身不是危险
     —— 水下挖矿、蹚河、钓鱼都不该被打断；而且电池步 `survival_exit` 的相位就靠"眼在水里 + air=5"。
     ⇒ 一般状态（只要没快淹死）**根本不产生判决**，`startSurvivalExit` 那一格进不去。
   - **② `D-380` 的浮面档在 `decide` 之前 `return`**（`BotManager.java:2346-2359`）⇒ 眼睛还在水里时
     **只会浮**；浮上来之后眼睛出水 ⇒ 危险又回到 `WATER_CONTACT` ⇒ 还是 `IGNORE`
     ⇒ **bot 浮在水面不动，没人叫它上岸**。这就是用户看到的缺口。
3. **顺序不能颠倒（技术原因，§2.2 审计）**：完全浸没时十种 Movement **一条边都生成不出来**
   ⇒ 从水下起逃生任务**注定失败** ⇒ **必须先浮、再走**。所以修法不是"把逃生套过去"，
   而是**在浮面之后接一次"找岸"**。
   ⚠️ **2026-09-21 落地时修正了一句过度自信的话**（红对照实测抓到）：原来写的是
   "`plannableRefuge` 的纯通行预检**必然** `UNREACHABLE`" —— **不对**：预检内部的 `isPlannable`
   用的是**时间预算**（`PRECHECK_MAX_MILLIS`），口径是「`SEARCH_LIMIT` 也算可尝试」
   ⇒ **同一格、同一代码、两次跑会给出不同答案**（实测 `true`/`false`）。
   ⇒ 落地做法改成**结构闸门**：找岸档要求 `眼已出水`（`!isEyeInFluid(WATER)`）
   —— 顺序写进代码，不依赖那条不稳的经验（详见 `D-382` §四）。

### 6.2 最小改法（复用现成机制，不造新 Movement、不碰写入）

在 `BotManager.tickHazardWithoutTask` 的浮面档**之后**加一条（顺序：**先浮 → 再找岸**）：

1. `无任务` 且 `bot 在水里`（脚位或眼位有水，复用 `SurvivalSystem` 的 `containsWater` 口径）⇒
   `refuge = SurvivalSystem.plannableRefuge(bot, hazard.type(), false)`（**第三个参数 = false = 纯通行**）：
   - **有** ⇒ `startSurvivalExit()`（现成方法 ⇒ 自动带 `exit=<refuge>` 日志与 `SurvivalExitTask`）；
   - **无** 且**眼在水里** ⇒ 保持 `D-380` 的上浮（浮完下一 tick 再评估）。
2. **半径沿用 `REFUGE_RADIUS=8`**（不新造阈值）；8 格外 = 用户口径③的**如实失败**
   （`exit=none` / `exit=unreachable` 两个键都已存在）。
3. **只对无任务生效**（有任务时"在水里"照旧不打断；危险升级仍走原 `decide` 三条分支）。
4. ⚠️ **落地前先验的一条（已查到大部分事实，见下）**："沿水面走到岸"在执行侧靠的是
   `MovementHelper.shouldHoldJumpInWater` = **脚位是水 且 脚位 Y < 目标 Y**（`MovementHelper.java:158-161`；
   对照 Baritone `MovementTraverse:243-248`），执行器 `TraverseExecution.java:155`、`AscendExecution.java:89`
   与**段间 settle** `PathSession.java:133-139` 都在用这个唯一定义。
   ⇒ 水面**同高**横渡时**起手不按跳跃**（先被重力压下去一点）⇒ 脚位掉到目标格以下才按 ⇒ **自纠回浮面**
   —— 这大概率就是用户"**没有缓沉**"观感的来源（跌一点点就被按回去），也说明**不需要**新写"浮面维持"。
   ⚠️ 仍未验证的是**眼睛短暂没入水面**那一瞬的观感，以及 `escapeTask=true` 时三条救援分支
   **全被 `!escapeTask` 排除**（`BotManager.java:2207-2290`）⇒ 逃生途中没有第二道兜底
   ⇒ 需要一轮客户端确认（零参数入口：把 bot 放进浅水/池边，看它走上岸）。
5. **判据（每层都要能红）**：新无头夹具 = 水池 + **8 格内**的干岸 ⇒
   断言"无任务落水 ⇒ 先浮 ⇒ **随后规划出到干落点的纯通行路径**"，并断言 `WriteEnvelopes` **零写**；
   反例夹具 = 8 格内无干落点 ⇒ **如实失败**（`exit=none`）且**零位移、零世界改动**。
   客户端零参数入口：把 bot 传送进浅水/池边（现成做法），看它是否**走上岸**。
6. **不做什么**（防越界）：不放方块、不挖方块、不扩大搜索半径、不给自己造站位
   （层 2/3 仍在延后区，重开触发见文件头）。

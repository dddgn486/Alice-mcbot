## §3 ⭐⭐ 一处关键结构事实：**写授权的载体就藏在这里**

`action/MineBlockRunner.java:207-213`（逐字）：

```java
PathRequest request = plan.mode() == MiningPlan.Mode.TUNNEL
        || plan.mode() == MiningPlan.Mode.ENTER_TARGET
        ? PathRequest.miningApproach(...)   // ← 允许破坏/放置
        : PathRequest.of(...);              // ← 纯通行
```

### 5.2 ⭐⭐ 决定性证据：**Baritone 的 Goal 里没有世界**

GoalAxis · GoalComposite · GoalInverted · GoalNear · GoalRunAway · GoalXZ · GoalYLevel …

⇒ **`Goal` 层结构上"表达不了"「能站」**（它压根看不见方块）。

### 5.3 挖矿侧的 Goal 形态（全部实读）

### 7.4 Baritone 的实际做法（✅ 实读）

- `ThreadPoolExecutor(4, Integer.MAX_VALUE, 60s, SynchronousQueue)` —— **4 核心线程**、无队列
- `PathingBehavior` **把整个搜索提交**：`Baritone.getExecutor().execute(() -> { … pathfinder.calculate(primaryTimeout, failureTimeout); … })`
- **结果回来时**在 `synchronized (pathPlanLock)` 里挂成 `current` / `next`；⛔ 逐字还有 **`discarding orphan path segment with incorrect start`** 这类丢弃逻辑
- 主线程**从不等**：只**发起**，然后每 tick 轮询"算完没有 / 要不要重发起"
- 超时也异步：`primaryTimeoutMS` / `failureTimeoutMS` / `planAheadPrimaryTimeoutMS` …
- ⭐ 关键配套 = **`BlockStateInterface`（chunk 缓存 + `isLoaded`）** ⇒ 搜索线程**读世界不碰主线程**
⇒ **模式 = 「发起/轮询 + 世界视图快照 + 结果原子换入」**

### 7.5 我的判断（⚠️ 勘测侧观点，供裁）

**赞成做，但次序上排在 `K2`/顺序颠倒/解体之后**，理由与代价各四条：

**赞成（都有本仓实证）**
1. **它治的是"症状的根"**：§7.3 四层补丁里至少两层（1、2）可退化成"兜底"而不是"唯一防线"。
2. ⭐ **它解开的是"设计被 tick 预算扭曲"这一类问题**。最硬的证据 = `MiningPlanner:56` 逐字：截断的"届时正确做法是**把穷举摊到多个 tick**（记住进度、下 tick 继续），而不是把上限调大" ⇒ ⭐ **线程化正好让"摊 tick"这个正解变得不必要**。
3. **它让两类账分开**：今天 `SearchTickBudget` 是**一个共享账**，于是"选择期成本场 Dijkstra"（`recordExternal`，真机 `ms=69`）与"到位搜索"**抢同一个 50 ms**（`SearchTickBudget` javadoc 自己写下了这个坑）。
4. ⭐ **它是"重做簇连续挖掘"的前置之一**（`OS-4`）：簇挖掘的本质是"高频重扫 + 高频重算 Goal"（Baritone `rescan` 5 tick），而**在 tick 线程上做高频重扫不可行**（`P6` 搜索线程化 = 3+ 轮未做）。

**代价/风险**
1. ⚠️⚠️ **最大：世界视图**。Alice 的搜索**直接读实时 `ServerLevel`**，且有红线「**内核从不加载区块**」（`GOAL_NOT_LOADED` 守卫 + `skipped_unloaded`）。⇒ **必须有线程安全快照**（Baritone `BlockStateInterface`），否则从非 tick 线程读世界会踩 `ChunkMap` 的线程安全。⇒ **`D-036` 第 8 条的"前置条件 = 快照层"是真的前置，不是顺序偏好。**
2. ⚠️ **`SearchTickBudget` / `PathingStats` 必须改形状**（通知 javadoc 自己写了：非同步字段 ⇒ **每 tick 快照交换**）。
3. ⚠️ **会引入"天然竞态"**：Baritone 那句 `discarding orphan path segment with incorrect start` 就是代价。⚠️ 而 Alice **刚吃过这个坑**（`D-474` 的 `exec_replan_race`）⇒ **竞态会从"夹具造出来的"变成"天然的"**。
4. ⚠️ **它不省总量，只省"卡 tick"**（CPU 总花费不变，可能更高）。⇒ **它不改善"搜索太贵"** —— 那是 `4.2` 顺序颠倒 + `K2` 的事。**两件事治不同的病，不许互相冒充**（`survey/35 §9.4`）。

**同时序建议（三档）**

| 选项 | 内容 |
|---|---|
| **甲** ⭐ | **不独立排期**，把它**挂在簇挖掘的立项条件里**：先定簇挖掘形态（是否要 5-tick 级重扫）—— **要 ⇒ 快照层 + 线程化是簇挖掘的第一前置**；不要 ⇒ 降级为"长尾优化"，排 `4.2`/`K2` 之后按实测决定 |
| **乙** | **单独排，排在 `K2` 之后、批 3（结构大件）之内**，理由 = "四层补丁该换根治" |
| **丙** | **先只验证硬前置**（0.5 轮级、不承诺线程化）：把 `CorePathPlanner.plan` 的"读世界"部分用一个**只读快照**包起来（**不改线程**），实测"快照层能否与实时读**逐字同结论**" ⇒ 这是线程化的**唯一硬前置**，可单独做最小可验证闭环 |

⚠️ **为什么我倾向"排在 `4.2`/`K2` 之后"**：`4.2` 的顺序颠倒会让"贵的那条腿"在**大多数情况下不再被走到** ⇒ 先做线程化**会用工程手段掩盖"顺序错了"这个真问题**（`method-vs-goal-drift` 的同族风险）；`K2` + 顺序颠倒之后，需要在 tick 线程上烧 50 ms 的搜索次数**结构性下降** ⇒ 那时再评估"还剩多少长尾值得为它引入快照层"，**决策依据更好**。
⭐ **唯一的例外（可能提前）**：若簇挖掘要做成 Baritone 式高频重扫，则**线程化是它的前置而非可选项**。

### 9.2 「加高」实测（回应 §1.3 与 `DS-18`）

**Alice 今天怎么解决**（✅ 实读 `GainStepRunner`）：

- 对内核发一个 **`PathRequest.climbApproach(foot → foot.above())`**，然后**硬要求 `pillars == 1`**（`:52` 逐字 `pillars != 1 || pillars > profile.gainBlockBudget()` ⇒ `FAILED`）⇒ ⚠️ **一次调用只能抬 1 格**；
- 要抬 N 格 ⇒ **由编排器（`MineTask` 的 `GAIN` 相位）循环调用 N 次**（每次一次独立规划 + 一次独立 `PathRetryRunner` 会话）；
- 预算 = `MiningProfile.maxGainSteps` + `gainBlockBudget`（默认 **12**，「用户 2026-09-11 裁定：12，砍树够用；**模组超高树不在范围**」）；`sweepGain(trunkHeight)` 按树干高**几何推导**步数。

**Baritone 怎么解决**（✅ 实读 `MovementPillar`）：

- ⭐ `MovementPillar` 是**搜索里的一种移动**（与 `Traverse`/`Ascend`/`Descend`/`Diagonal`/`Fall`/`Parkour` 并列，**共 8 种，且 `Baritone` 全树无 `MovementBreak`**）；
- 它的 `cost()` 里含：`costOfPlacingAt(...)`（放置成本，无一次性方块 ⇒ `COST_INF`）+ **破坏头顶那格**（`y+2`）的 `getMiningDurationTicks` + 一串否决（梯子 / 底部半砖 / 水 / 栅栏门 / 头顶落砂 / 睡莲地毯）；
- ⇒ **"搭几格"由搜索一次算出**，且与其他移动**在同一份成本模型里权衡**；上限 = **搜索预算** + `allowPlace` + 库存。

**够好吗 —— ⚠️ 我的判断：不够好，且缺口是结构性的（三条）**

| # | 缺口 | 证据 |
|---|---|---|
| 1 | ⚠️ **它只能抬 1 格**，N 格 = 外部循环 N 次 ⇒ 成本 ×N 且失败面累积（每次都有 `PathRetryRunner` 的失败面） | `GainStepRunner:52` `pillars != 1 ⇒ FAILED` |
| 2 | ⚠️ **预算挂在"放置块数"而不是时间** ⇒ 与 `DS-19` 同病（**用收紧手段代替统一时间/重试限制**） | `gainBlockBudget` / `DEFAULT_GAIN_BLOCK_BUDGET = 12` |
| 3 | ⚠️ **"搭几格才够得到"不是搜索算出来的，是几何推导**（`sweepGain(trunkHeight)`）；推导错了就够不到（模组超高树**如实停在 12**） | `maxGainSteps` / `MiningProfile.sweepGain` |

⇒ ⭐ **三条合起来 = "加高"是一个被外挂的能力，而不是搜索的一个维度。**

### 9.4 ⭐ `DS-11`/`DS-12` 命名与语义：三个集合的序实测

| 载体 | 装什么 | **序是什么** |
|---|---|---|
| `LumberJob.queue = Tree.logsBottomUp()` | ⭐ **几何相连簇**（`Tree.logs`） | ⭐ **挖掘顺序（自下而上）** —— `Tree.logsBottomUp()` 逐字 `return logs;`，javadoc「砍伐顺序：自下而上（与旧 `getLogsInCutOrder()` 一致）」⇒ **成员集合与挖掘顺序是同一个 `List`** |

| `MineJob` 的"簇消费队列" | 选中点所在**几何相连簇**的成员 | **"选中的排第一"** + 其余几何顺序 |

⇒ ⭐ **三条结论**：

1. **`LumberJob.queue` 确实是"带挖掘顺序的簇"** —— 用户猜测**成立**，而且**两者根本没分离**（`Tree.logs` 一个 `List` 兼两职）。
2. ⚠️ **`oreQueue` 更糟：它连簇都不是** —— 它是一个**工作队列**（消费即出队），必须与 **`oreSettled`（已结案）** + **`chasePending`（够不着、未结案）** **三个集合合起来**才表达"待办 / 已办 / 延后"。⇒ **`queue` 这个名字掩盖了"这是一个三集状态机"**（`DS-14` 的"混乱"正是指这个）。
3. ⇒ **正解不是"给簇换名字"，而是把「簇」（集合）与「序」（策略）拆成两个东西**，让 `queue` 只表示"待办序列"，**簇作为它的构造输入**。
   ⇒ ⭐ 这直接回答"硬编码挖掘顺序和簇放一起是否合适"：**不合适** —— "自下而上"是**策略**（可按需改：自上而下 / 按暴露度 / 按距离），簇是**事实**（几何相连）。今天 `Tree.logs` **把策略焊进了事实里**。
   ⇒ **顺序应该是消费方的一个策略参数，不是簇自带的字段。**

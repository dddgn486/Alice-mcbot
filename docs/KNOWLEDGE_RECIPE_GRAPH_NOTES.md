# 参考材料：LLM 的知识面 / 配方图 / 整合包复杂度（2026-09-12 讨论纪要）

> 状态：**参考材料，不是实现授权**。用途是把"整合包里做一件复杂物品"这类问题的**判断与取舍**留下来，
> 避免以后重新发明或重复调查。任何落地都要走 `DECISION_LAYER_DESIGN.md` 的分步框架与既有决策
> （D-076 授权红线、D-106 预算、D-119 工具语义、D-130 区域语义、D-134/D-135 决策层契约）。

## 0. 触发这次讨论的真实问题

目标：让 bot 自己做一把**青铜镐**（整合包 ATM 环境）。
- 材料齐 ⇒ 简单；**材料全无 ⇒ 支线爆炸**：做木棍要砍树、找砍树的地方；青铜镐本身可能是**模组配方**
  （需要配方记忆或 JEI 查询）；极端情况工具**不能用工作台做**，要用格雷的复杂装配 / 精英工作台等
  **非原版工作站**（匠魂那类 DIY 工具不在设计范围内）。
- 青铜怎么来：铜锭 + 锡锭"融合"；而整合包里**青铜的获取路径一大堆**（不同模组机器、单模组内嵌套：
  铜锭→铜粉→烧制→铜锭 的环）；再往上是**矿处**（格雷赤铁矿→铁锭）——整合包玩家在不同阶段有
  **默认处理流程**（前期统统烧锭、中后期走流水线吃副产物），而"每种物品在不同阶段换默认获取入口"
  若靠人力维护，操作成本极大。
- 用户曾设想：让 AI 学教程/wiki，把**获取方式的分支链 + 玩家经验**蒸馏成 skill/知识库，再按阶段与
  自然语言切换策略。担忧：蒸馏成本高、模组分支/版本变化（尤其格雷）与整合包魔改让人无从下手。

## 1. 核心判断：**配方是数据，不是知识**

- Minecraft 配方在**运行时**机器可读：vanilla `RecipeManager`；JEI/EMI 插件 API 是统一的**只读面**。
- 整合包魔改（KubeJS / CraftTweaker / GT recipe map）**最终都体现在运行时配方表** ⇒ **运行时 > wiki**。
- wiki/教程讲的是"**流程**"（机器怎么用、流水线怎么摆），不是"材料是什么"。
- ⇒ "青铜有哪些获取路径""铜粉能不能磨"这类问题**不需要任何训练/蒸馏**，只需要**图查询**。

## 2. 知识分四类，四种机制（**别把 A 类当 B 类处理**）

| 类别 | 例子 | 机制 | 训练 | 联网 |
|---|---|---|---|---|
| **A 事实/配方** | 青铜=铜+锡；铜粉→铜锭；哪台机器能做什么 | **运行时图查询**（RecipeManager + JEI 类别）→ 离线导出成本地索引 | ❌ | ❌ |
| **B 程序/流程** | 某机器怎么投料、流水线怎么摆 | **本地文档库 + 检索（RAG）**；蒸馏"skill"仅在必要时 | ❌（检索优于蒸馏） | 仅"缺数据 + 玩家同意"，**带来源、标未验证** |
| **C 偏好/策略** | 前期烧锭 / 中后期流水线；"别砍云杉" | **可编辑规则库**（自然语言 → LLM 起草 → 请示确认 → 落库） | ❌ | ❌ |
| **D 措辞** | 汇报、解释、对话 | LLM 原生能力（prompt） | 可选：后期 LoRA 只调**格式遵从**，不是知识 | ❌ |

**反模式（明确不做）**：
1. ❌ 为了知识去**训练**模型 —— 版本/魔改一变知识全废，分支爆炸训练不完；
2. ❌ 把 wiki **蒸馏**成 static 知识库 —— 检索不会过期，蒸馏会冻结；
3. ❌ 让 LLM **记住配方** —— 配方永远从运行时查；
4. ❌ 让 LLM **编造坐标/机器/能力** —— 选项一律由确定性层生成（见 §4）。

## 3. "默认获取入口随阶段变化" = **策略层**（最头疼、也最容易解）

做成**规则数据**，而不是"每次问 LLM"：

```
RoutePreference {
  targetMatcher : "#forge:ingots/iron" | "minecraft:iron_ingot" | 具体 id
  stage         : early | mid | late（或玩家自定义阶段名）
  order         : ["minecraft:blasting", "gt:macerator→gt:ore_washer→…"]
  avoid         : ["gt:fusion*"]
  goal          : "speed" | "byproduct" | "energy"
  updatedBy     : "player:dddgn" | "llm:draft#42" | "default"
  updatedAt     : tick/时间
}
```
- 规划器（确定性）在图上搜索时**按偏好排序**候选；无偏好 ⇒ 退回"最短/最便宜"默认；
- 玩家一句话 ⇒ LLM **只起草一条规则** ⇒ 请示确认 ⇒ 落库；
- **批量改入口 = 批量编辑规则**（可导入/导出/分享），**不需要重新训练任何东西**；
- 模组/整合包变了 ⇒ 规则里的 id 失效时**如实标记"规则过期"**，玩家一键修（不静默失效）。

## 4. 复杂度收敛：**三个可重建的产物**（这替代"蒸馏知识"）

1. **配方索引**：`item → recipes(输入/机器/数量/条件/JEI类别)`，落本地 SQLite/JSON。
   **游戏内导出 + 离线 Python 分析**（对齐已有离线自检文化：`check-scene-connectivity.py`、
   `analyze-lumber-scene.py`）⇒ 换包**重导**（几分钟），不维护知识。
2. **机器适配器**：每个工作站/机器一个小适配器（投料/配置/取料）；**未适配 ⇒ 降级为只读提示 + 请示**。
3. **偏好规则库**：见 §3。

⇒ 应对"格雷/分支模组/版本变化"的答案是 **重建 + 降级 + 改规则**，而不是"无从下手"。

## 5. 分阶段（P1 是地图，必须先做）

| 阶段 | 内容 | 判据 |
|---|---|---|
| **P1 只读规划** | 目标物品 → 图上逆推（BFS，深度/分支有界）⇒ 材料树 + 所需机器 + top-N 路线（按偏好排序）。**不执行** | 对 vanilla（木镐/石镐）与 1 个模组物品，材料树/机器需求与 JEI 人工核对一致；对"铜锭↔铜粉"这类**环**给出有界不循环路线 |
| **P2 获取材料执行** | 复用伐木/挖掘；新增 `CraftTask`（工作台/背包 3×3）、`SmeltTask`（熔炉） | 库存 0 ⇒ 做出木镐/石镐（砍树→木棍→合成），全程可复盘 |
| **P3 机器链** | `ProcessTask` + JEI 类别适配器（先 1–2 种）；未适配机器 ⇒ 只读提示 + 请示 | 用已适配机器跑通一条真实链；未适配机器给出"需要 X 机器，未适配"的请示而非瞎试 |
| **P4 偏好规则 + 阶段** | 规则库 + 自然语言编辑 + 批量改入口 | 一句"从现在起矿石先磨粉再烧" ⇒ 后续计划改道；规则可导出/分享 |
| **P5 文档检索/联网** | 只补程序性知识，带来源与确认 | 检索到的流程能引导一次真实操作（且标注来源） |

## 6. 与决策层三条通道的关系

- **汇报通道**：任务树里带**缺料树**（"要做青铜镐：缺 3 铜锭 + 1 锡锭"）；
- **决策通道**：候选菜单新增一类 —— **"目标物品 → 规划出的 top-N 路线"**（服务端算好，各带代价/缺料/所需机器），**LLM 只选路线**；
- **请示通道**：① 路线要用**未适配机器**；② 要动**玩家资源/结构**；③ **规则变更**（是否改默认获取入口）。

## 7. mc_aiplayer 对照（本机源码 + 配置，2026-09-12 读）

它已经把"LLM 只调工具、不要细节"这套做出来了，可直接借鉴：

| 项 | 值 | 含义 |
|---|---|---|
| `tools` + `tool_choice: "auto"` | 原生 **function calling** | 我们是"文本里回严格 JSON"（provider 无关，已验证） |
| `exposeLowLevelTools` | `false` | **低层工具默认不暴露** |
| `maxToolCallsPerTurn` / `maxTurnsPerRequest` | `6` / `12` | 工具循环**有界** |
| `perception` | `radius 16, maxBlocks 20, maxEntities 10, maxItems 10, includeRawLists: false` | **感知有界、不给原始列表** |
| `maxHistoryMessages` | `36` | 上下文有界 |
| `stuckWindowTicks` | `200` | 卡住看门狗 |
| `verboseReports` | `true` | **详细汇报是开关**（按需，不是每轮推） |
| `thinking / reasoningEffort` | `true / low` | 显式控制推理预算（与我们 `maxTokens` 教训一致） |
| HTTP 栈 | `java.net.http.HttpClient` + `connectTimeout(10s)` + 阻塞 `send()`，**不设自定义 executor** | 与我们相同；不共用 executor ⇒ 天然没有我们踩过的死锁 |

**可借鉴**：原生 tool calling、低层工具不暴露、感知/上下文/轮次全部有界、详细汇报按需。
**不照抄**：它的知识面同样依赖运行时查询；"低层工具隐藏"我们已有等价物（动作词汇表 + 白名单）。

# Alice 产品架构与整合包适配路线

> 状态：长期方向文档 v1，2026-08-21
> 本文定义产品目标、兼容层级、确定性执行边界和阶段路线。具体移动/道路/挖矿约束仍以对应专项设计和 R# 决策为准。

## 1. 产品目标

Alice 最终服务三个彼此关联但验收方式不同的产品域。

### 1.1 通用玩家助手

面向大多数原版和整合包环境，提供接近普通玩家的确定性任务：

- 挖矿、收集木材、采集作物或野生食物；
- 攻击明确目标动物并收集目标产物；
- 跟随和保护玩家；
- 在安全区停留、返航、巡逻和保护基地；
- 后续可加入钓鱼及其他可明确建模的通用活动。

这些任务可以通过物品/方块/实体标签和玩家参数复用到许多模组内容，但“ID 可识别”不等于“行为已兼容”。模组矿物通常可复用挖矿链；模组作物、树木、动物、钓鱼机制若改变成熟判定、掉落、交互或工具规则，仍需要数据规则或代码适配器。

最大共享前置是移动与站位可靠性。跟随、战斗、采集、巡逻和搬运都不能各自复制一套寻路补丁；它们应消费同一组经场景验证的移动能力，并显式声明可用能力，例如平地、上阶、下降、开门、游泳或危险逃生。未验证能力必须拒绝，不可由 LLM 指令绕过。

### 1.2 无 AE 自动合成阶段：玩家定义的“模拟 AE”

目标不是让 bot 自动理解或搭建任意流水线，而是让玩家把现有半自动流水线登记成可执行生产单元，Alice 负责按订单搬运、投料、等待、收产物和处理可预见异常。

玩家定义的 `PipelineProfile` 至少包含：

- 流水线 ID、版本和允许操作区域；
- 输入端点、输出端点、缓存端点，以及每个端点的具体语义接口；
- 一次批次的必需输入、催化剂、工具、容器和能源前置条件；
- 期望主产物、允许副产物、概率产物和残留物；
- 消耗模型：固定消耗、概率消耗、耐久消耗、可返还催化剂；
- 启动条件、完成判据、超时、卡机检测、重试上限和人工接管条件；
- 并发、容量、最小批量、禁止混料和清空要求；
- 端点权限及物品丢失/多出时的恢复策略。

Alice 不从方块布局猜测这些语义。LLM 可以根据本地指导手册和当前订单选择一个已登记的流水线、批量和路线；确定性执行器必须在每次物品转移前后核对库存差值、端点版本、权限和完成判据。

多配方路线由 `ProductionPlanner` 在已登记、可执行的工艺边之间选择。路线评分可考虑库存、时间、能源、稀缺催化剂、成功概率和玩家偏好，但选中路线后，每一步都必须落到已验证的 recipe/pipeline contract，不能让模型临时发明槽位或机器操作。

### 1.3 AE 自动合成阶段：AE 网络助理

目标是通过 AE2 的服务端数据和适配器完成大量重复操作，而不是模拟视觉点击终端。

分为三个能力族：

1. **网络存取与任务观察**：识别明确网络，查询可见库存、CPU/合成任务和存储状态，按权限执行可验证的存取。
2. **样板编写**：根据确定的 recipe、替代品规则、数量、容器/副产物处理和玩家选择，生成可预览、可审计的 crafting/processing pattern。
3. **样板管理与放置**：读取现有样板及实际供应器/接口拓扑，按机器连接、频道、锁槽、输入输出能力和玩家定义的角色选择放置位置；支持查重、版本迁移、回收和冲突报告。

JEI 导入只能作为候选来源，不能作为真值。样板编写必须区分：

- 精确物品与可替代输入；
- crafting pattern 与 processing pattern；
- 容器返回、催化剂、工具耐久、概率消耗和概率产出；
- 不同机器/配方提供方对数量和 NBT/组件的要求；
- 玩家或整合包定义的优先路线。

样板放置不能只按供应器名字猜测。必须读取实际网络拓扑和机器端点语义，或由玩家在 `NetworkProfile` 中标记角色。任何无法证明匹配的放置只生成建议/预览，不直接执行。

## 2. 修订后的系统架构

```text
玩家自然语言 / 参数面板 / 预设方案
                |
                v
GoalRequest + TaskPolicy + WorldProfile
                |
     LLM 目标规划与异常重规划
                |
      受约束的 ToolCall / PlanDraft
                |
       Policy Gate + Plan Validator
                |
      Task / Production / AE Orchestrator
                |
   确定性动作与模组语义适配器
                |
 Server World / Capability / Mod API / Events
                |
 Observation + TaskExecutionRecord + Inventory Delta
                +--------------------> 决策反馈
```

### 2.1 决策层

LLM 负责：

- 解析用户目标和省略条件；
- 从候选目标、候选生产路线和已注册工具中选择；
- 在确定性失败后根据结构化原因换目标、换路线或请求用户信息；
- 生成解释和自然语言回复。

LLM 不负责：

- 每 tick 移动、碰撞和攻击时机；
- 猜槽位、直接写 NBT、任意发模组网络包；
- 自行扩大破坏/搬运区域、权限、预算或重试次数；
- 宣告任务成功、物品到账、机器完成或样板正确。

### 2.2 策略与计划验证层

这是现有设计需要显式补出的层。它将 LLM 工具调用转换为可执行计划，并完成：

- schema、权限、任务预算和参数完整性校验；
- 目标、端点、配方、适配器和世界档案版本解析；
- 库存守恒、材料预留、容量和危险检查；
- 将不确定性变成拒绝、候选列表或用户确认，而不是自由文本猜测；
- 对重复失败、无进展和世界变化触发熔断。

### 2.3 编排层

编排层维护长任务的事务状态：步骤、资源预留、作用域订阅、补偿动作和恢复点。它可以组合挖矿、搬运、机器处理和 AE 操作，但不能跳过每个动作自己的确定性验收。

### 2.4 执行层

执行层由小而明确的状态机组成：移动、站位、挖掘、攻击、拾取、交互、物品传输、机器配置、等待完成、样板写入等。每个原语声明：

- 输入 schema 与能力前置；
- 每 tick 或每事务的服务端事实检查；
- 成功后的可验证后置条件；
- 失败码、超时、取消和可回收状态；
- 是否修改世界或消耗资源。

规则引擎可以做高频小决策，但必须属于原语/编排器的批准策略，不是第二个不受约束的 LLM。

## 3. 任务参数化

参数不是简单附加到 prompt 的文字，而是跨层使用的结构化策略。

### 3.1 四类参数

| 类别 | 示例 | 谁解释 | 谁强制 |
|---|---|---|---|
| 目标参数 | 物品/方块/实体标签、数量、质量或 NBT | LLM/GUI | 计划验证器 |
| 世界参数 | 区域、端点、网络、机器、库存来源 | WorldProfile | 服务端解析器 |
| 策略参数 | 工具来源、路线偏好、危险容忍、催化剂保护 | LLM/预设 | Policy Gate |
| 终止参数 | 数量、时间、背包阈值、失败预算、人工确认 | 用户/预设 | 编排器 |

### 3.2 预设与覆盖

- 项目提供保守预设，例如“只采暴露目标”“不自动开隧道”“稀有催化剂不消耗”“概率工艺仅在实际产物达到目标且投入未超预算时结束”。
- 整合包作者可发布 `PackProfile`，补充标签、机器适配器、危险规则、推荐路线和知识手册。
- 世界/服务器保存 `WorldProfile`，记录玩家标记的区域、端点、流水线和 AE 网络角色。
- 单次任务 `TaskPolicy` 只能在权限允许范围内覆盖默认值；LLM 不能持久修改 PackProfile 或安全策略。

这些结构化参数会生成紧凑的模型上下文，但其主要价值是让执行层和计划验证器可强制执行，而不只是“给模型更多提示词”。

## 4. 模组与整合包兼容分级

“兼容一个模组”必须标明达到哪一级，不能笼统宣称通用兼容。

| 等级 | 能力 | 主要机制 | 典型范围 |
|---|---|---|---|
| C0 识别 | ID、标签、方块/实体/物品存在 | Registry/Tag | 大部分模组内容 |
| C1 只读观察 | 库存、能量、流体、状态摘要 | Forge/模组 capability、BlockEntity | 暴露稳定接口的机器 |
| C2 通用受限操作 | 经模拟校验的插入/提取、普通实体交互 | 标准 capability/原版 API | 语义明确的简单端点 |
| C3 配置驱动语义 | 玩家/整合包定义槽位、端点、配方、完成条件 | PackProfile/WorldProfile | 手搓期流水线 |
| C4 模组原生适配 | 工作模式、专有化学品、AE 样板/网络拓扑等 | 版本化代码适配器 | Mekanism、AE2 等目标模组 |
| C5 端到端技能 | 经客户端/服务器验收的完整任务 | 编排器 + 适配器 + 知识包 | 指定版本和场景 |

重要修正：标准 capability 能提高 C1 覆盖率，但不能自动提供 C3/C4 的语义。教程/RAG 可以帮助 LLM 选择工具，却不能替代执行层适配器。

### 4.1 适配包结构

一个可发布的 `ModAdapterPack` 应包含：

- 目标 mod id、版本范围和依赖；
- 方块/实体/物品分类规则；
- 只读 snapshot provider；
- 操作 descriptor 与确定性 handler；
- recipe/processing 归一化器；
- 完成判据、库存差值和异常码；
- 迁移/失效规则及测试矩阵；
- 对应本地指导手册条目。

适配器不能通过反射或内部 API 静默跨版本运行。版本不匹配时应降级到已证明的兼容级别，通常是 C0/C1，只读报告而不是尝试写操作。

## 5. 本地知识与“指导手册”

知识系统的目标不是让每次任务联网，而是建立版本化、可追溯、按需检索的本地知识层。

### 5.1 三种知识资产

1. **事实库**：注册表、标签、配方、接口 schema、玩家标记和当前版本；由代码读取，可验证。
2. **指导手册**：从官方文档、目标站点教程、整合包说明和已验实践提炼出的短章节，记录适用版本、来源、前置条件、风险和可调用工具。
3. **运行经验**：特定世界中成功/失败的任务记录、耗时和玩家修正；只能作为路线评分证据，不能自动变成执行权限。

指导手册类似“知识 skill”，但与可执行 skill 分离：

- 手册告诉模型何时选择哪个已注册工具；
- executable skill 是版本化编排模板，只能调用确定性 handler；
- 任何手册文本都不能直接生成任意代码或绕过适配器。

### 5.2 构建流程

```text
受信来源抓取 -> 版本/来源标注 -> 文本清洗 -> 原子事实与步骤提取
-> 与游戏注册表/API 交叉校验 -> 人工或测试审核 -> 本地发布包
```

联网检索是知识缺失或版本冲突时的后备。检索结果默认是 `UNVERIFIED_KNOWLEDGE`，经引用、版本核对和适配器/客户端验证后才能进入稳定指导手册。

## 6. 不确定工艺与库存事务

科技整合包的机器任务不能只比较“输入消失、输出出现”。需要统一的 `ProcessContract`：

- 固定输入、可替代输入、催化剂、概率消耗、容器返回；
- 主产物、固定副产物、概率产物和废料；
- 单次/批次边界、机器容量、进度或外部完成信号；
- 允许的库存差值区间和置信条件；
- 超时、卡机、混料、能源不足、输出堵塞和外部玩家干预。

确定性并不意味着结果无随机性，而是对随机结果有明确的观察、记账和停止策略。例如“获得 64 个目标产物”可以重复批次直至库存事实达到目标，但必须受最大输入、最大批次、时间和稀有资源预算约束。

物品搬运按事务记录：`planned -> reserved -> extracted -> carried/in_transit -> inserted -> verified`。任一步失败都必须知道物品当前在哪，并进入可恢复或人工接管状态，不能仅重试导致复制、吞物或混料。

## 7. 可实现性判断

### 7.1 确切可实现

- 基于服务端事实的标签化采集、攻击、拾取、安全区和有限任务参数；
- 标准 capability 的结构化只读快照；
- 对明确端点执行模拟插入/提取后的物品搬运；
- 玩家定义流水线后按确定性 contract 投料、等待、收产物；
- 针对固定 AE2/Mekanism 版本编写、测试专用适配器；
- 本地版本化指导手册和按需外部检索；
- LLM 选择目标/路线，执行层验收并反馈结构化错误。

### 7.2 可实现但成本高

- 在复杂地形长期跟随、战斗保护和巡逻：依赖完整移动原语、目标优先级、友军/领地规则和应急恢复；
- 通用树木/作物/食物采集：不同模组的结构、成熟、重种和掉落规则需要数据或适配器；
- 任意机器工艺归一化：需要逐模组处理专有资源、模式和 API；
- AE 样板自动编写与正确放置：需要深入 AE2 API、网络拓扑、配方规范和大量场景测试；
- 多路线生产规划：算法本身可做，困难在可靠的 recipe/process 数据和事务执行。

### 7.3 不应承诺为通用自动能力

- 仅靠 capability 自动理解任意复杂机器的所有槽位和模式；
- 仅靠教程文本生成安全的机器写操作；
- 自动理解并搭建任意玩家流水线；
- 不经玩家规则就正确处理所有魔改配方、随机工艺和样板放置；
- 让 LLM 逐步控制移动/战斗/库存来弥补执行器缺失；
- “接入一个新模组无需代码或配置即可端到端工作”。

## 8. 产品驱动的阶段路线

### 阶段 A：可靠执行内核

产出：统一任务请求/策略/结果、移动能力边界、站位、挖掘、拾取、攻击基础、物品库存事务、安全区和失败回收。

审核点：原版式任务必须用服务端事实验收；复杂地形能力逐原语进入客户端矩阵。

### 阶段 B：通用助手闭环

按独立工作包完成：挖矿/木材、动物食物、作物/野生食物、跟随、停留/返航、巡逻、保护和钓鱼。优先做复用广且移动前置明确的任务，不把所有功能塞入一个“生存助手”。

### 阶段 C：语义接口与事务搬运

产出：版本化只读 snapshot、接口 descriptor、权限、模拟插入/提取、库存预留和搬运事务。先用原版容器与一个简单科技机器端点验收。

### 阶段 D：玩家定义流水线

产出：WorldProfile 标记工具、PipelineProfile/ProcessContract、固定路线生产订单、异常与人工接管。先做固定输入输出、确定消耗和单机器/双端点；随后增加催化剂、副产物和概率工艺。

### 阶段 E：目标模组适配包

选择项目实际整合包中优先级最高的模组逐个达到 C4/C5。每个适配包单独版本化、测试和降级，不追求一次覆盖所有科技模组。

### 阶段 F：AE 网络助理

依次实现只读网络观察、受限存取、样板解析/预览、规则化写入、拓扑感知放置和批量管理。每一步都要能独立使用和验收。

### 阶段 G：LLM 与本地知识闭环

在稳定工具之上接入异步 LLM、参数面板、本地指导手册和按需 RAG。可以较早做只读规划原型，但任何写操作必须等对应 handler/Policy Gate 成熟。

阶段并非严格串行：知识手册、适配器调研和独立通用任务可以并行；共享移动、库存事务、权限与结果契约必须作为主线先稳定。

## 9. 下一阶段建议

当前不应直接从可观测性跳到 LLM 或 AE 样板。建议顺序：

1. 修正 HANDOVER 当前 revision 事实并冻结本文为长期路线入口；
2. `interface-readonly-snapshot-v1`：建立 C1 结构化事实，不声称机器语义已兼容；
3. `inventory-transfer-transaction-design-v1`：先做浅调研；涉及 Forge capability 模拟插入/提取、物品守恒与失败恢复，若版本语义不清则派深度调查；
4. 并行准备通用助手的 `AttackTask` 最小闭环，但必须以 HARD_PATH 和明确实体目标为边界；
5. 在实际目标整合包确定后，由用户给出优先模组列表，再排 `ModAdapterPack` 顺序；
6. AE2 样板与拓扑属于专项高风险模块，实施前必须深度调查固定版本 API 和成熟开源实现。

## 10. 需要用户逐步拍板的问题

- 首个目标整合包及优先模组/版本是什么；Mekanism、AE2 之外还有哪些必须首发支持？
- 通用助手的保护行为允许攻击哪些实体，如何处理玩家、宠物、中立生物、领地和误伤？
- 玩家定义流水线采用世界内标记工具、配置 GUI，还是两者并存？
- 物品搬运强调真实背包运输，还是允许经服务端语义接口直接端点到端点转移；两种模式的沉浸感和可靠性不同。
- 概率工艺的默认停止策略是目标数量、最大投入、置信阈值还是玩家选择？
- 本地指导手册由项目发布、整合包作者发布还是允许服务器管理员编辑；签名、来源和版本冲突如何处理？

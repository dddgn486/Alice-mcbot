# AI Player 设计笔记

> 来源：mc_aiplayer 精读期间的思考整理（2026-08）
> 目标企划：游戏内 AI 助手——优化 AI 行为模式 + 模组 GUI 通用操作入口

---

## 一、指令参数化：给简单任务做「指令模板」

### 1.1 问题

- mc_aiplayer 的 system prompt 规则 3 让高层工具（如 `mine_ore`）自动准备所需工具。
- 但「准备工具」本身有难易之分：AI player 身上不一定马上做得出来，世界也可能**不是常规生存**
  （空岛生存、高难度整合包），自动准备的路径可能走不通或很绕。
- 现状缺陷：简单任务（收集、挖掘）完全靠自然语言让 AI 自己整理任务步骤、判断前置条件，
  低效且容易出错。

### 1.2 想法

- 与其让 AI 从自然语言自由发挥，不如「像发指令一样」提供**预制参数 / 建议补充参数**。
- 一个**环境参数完备的指令**能让长任务效率大幅提高——几句话的补充说明，换掉 AI 大量试错。

### 1.3 挖掘任务参数模板（示例）

| 参数 | 选项举例 | 作用 |
|---|---|---|
| 工具策略 | 用现成工具 / 让 AI 自行收集 / 指定来源 | 绕开「自动准备工具」的不确定性 |
| 挖掘地点 | 指定坐标 / 指定生物群系 / 让 AI 自选 | 免去 AI 盲目找矿 |
| 终止条件 | 挖到 N 个 / 挖满 X 分钟 / 背包满即回 | 明确"任务何时算完成" |
| 行动范围 | 半径限制 / 禁止进入某区域 | 防止跑丢、误入危险区 |

### 1.4 GUI 承载

- 在 GUI 上为简单任务指令提供**预制参数**：玩家点选或自定义条件。
- 目标体验：像"下命令"一样填几个选项，而不是写一大段 prompt。

### 1.5 非原版适配（重要）

- 自定义参数让「非原版物品/方块、但玩法贴近原版」的内容能直接适配基础指令。
- 例：挖**模组矿物**、熔炼**模组物品**——参数里直接填物品 id 即可复用同一套任务逻辑。
- 深层价值：玩家（整合包作者/宿主）最懂自己世界的规则，
  参数化 = 让人类把世界知识**一次性注入任务**，而不是让 AI 反复试错去猜。

## 二、回复风格：关键词汇报 + 人设二次生成

### 2.1 问题

- 现状：作者的回复是**设定好的固定词块**（工作汇报式）。
- 承认其优点：短期效率高、信息准确。
- 但期望：AI player 能给予玩家**精神价值**（陪伴感），而不是僵化的汇报。

### 2.2 想法（两段式回复）

1. **任务完成时仍汇报固定关键词** —— 保留效率与准确性（信息层）；
2. **根据人设，二次交给 AI 生成完整回复** —— 语气个性化（情感层）。

即：**结构/事实由词块保证，语气由模型生成**。两者拆开，不牺牲可靠性，换取陪伴感。

## 三、实测问题记录（mc_aiplayer 实机观察，2026-08-16）

> 来源：本人进游戏实测。归因部分为**待验证推测**（尚未通读 action/ 源码），标注 ★待验证★。

### 3.1 寻路到目标方块「正上方」的别扭行为

- **现象**：挖掘坐标 (x,y,z) 的方块时，bot 总尝试先走到该方块**正上方**（采集/寻路任务都如此）；
  目标上方经常有方块阻挡 → 反复卡住；若侥幸走到上方 2-3 格，甚至**隔着方块直接挖掘**。
- **✅ 已定位（代码证据）**：
  - 站位设计：`OreDigTask.java:1189` 注释自曝「approach 目标=矿正下方」，站位点选目标下方/附近，无「视线无遮挡」检查；
  - 隔空挖根因：`MiningController.java:43-47` 只做距离检查（`BLOCK_INTERACTION_RANGE + 0.5 = 5.0` 格），
    服务端模拟没有原版客户端的 raycast 视线检查 → 站上方 2-3 格、隔一层方块仍可挖。
- **改进方向**（未来项目）：
  1. 站位点改为「目标方块的**相邻可达面**」：六个面中选最近的可站立空位，而非固定上方；
  2. 挖掘前做**视线无遮挡检查**（raycast），对齐原版行为；收紧 reach，**禁止隔空挖**。

### 3.2 目标搜索随机性强、不会简化任务

- **现象**：简单挖石头任务到处闲逛；识别地形慢、寻路慢；
  不采几格外**暴露**的石头，反而先挖开脚下好几块泥土再挖到石头。
- **✅ 已定位（代码证据）**：
  - 「挖泥开路」是设计行为：`DigNav.java` 在 A* 走不通时直线朝目标「挖一格走一格」，
    `stepToward`+`firstSolid` 路上有方块就挖；
  - 「不采远处暴露石头」是**目标选择**问题：OreDigTask 的目标评分逻辑（rich-zone 选择），与执行层无关。
- **改进方向**：
  1. 目标选择：以 bot 为中心扫描范围内全部目标方块，按「距离 + 暴露程度 + 可达性」排序，取最优；
  2. **暴露方块优先**：视距内可直接够到的，直接采，不先开路；
  3. 寻路**绕行而非破坏**：路径上的方块不是任务目标时绝不挖。

### 3.3 掉落物获取率低

- **现象**：挖完方块 / 杀完生物后，掉落物没自动吸到身上，就**不再管**。
- **⚠️ 部分定位（代码证据）**：拾取是「分任务」的——`GatherQuotaTask`（采集作物）有完整
  PICKUP 状态机（掉落物统计、连续未拾取才判超时，见 77-82 行）；**挖矿类任务（MineTask/OreDigTask）没有**。
  需实测按任务类型分别验证。
- **改进方向**：
  1. 任务完成条件包含「掉落物入包」（监听拾取事件 / 收尾时扫描周围 ItemEntity）；
  2. 把 GatherQuotaTask 的拾取状态机提取成通用原语，所有「产物型」任务共用；
  3. 可选：范围自动收集（需作为开关，避免改变原版体验）。

### 3.4 环境细节考虑不足（水中挖掘沉浮打断）

- **现象**：在水表面挖掘时不断沉浮，挖掘进度被反复打断。
- **✅ 已定位（代码证据）**：`MiningController` 每 tick 依赖「眼睛位置稳定」
  （`lookAtBlock` + 5 格距离检查）；bot 被流体推动漂移 → 漂出判定 → `out_of_reach` 失败
  → BlockMiner 归零 → 任务重来，循环。**挖掘循环无任何「站位稳定性」检查**。
- **改进方向**：
  1. 动作前置检查：多 tick 动作开始前，确认站位稳定（不在流体中漂移、不悬空坠落）；
  2. 流体中的站位策略：贴底 / 找稳定立足点，或先出水；
  3. 感知快照加入「是否在水中」等环境字段，让模型/执行器据此决策。

### 3.5 四条问题的共同启示

- 这些都不是「模型不够聪明」，而是**执行层的确定性逻辑有漏洞**（站位、搜索、拾取、环境检查）。
- 印证此前的架构结论：**别把细节交给模型**，把细节写进执行器；
  模型只做「目标级」决策，执行器负责把每个目标可靠地完成。
- 未来项目的「执行层验收标准」雏形：
  1. 任何目标方块都要有「可达站位点」才开工；
  2. 搜索必有排序（距离/暴露/可达性）；
  3. 任务完成 = 产物入包，而非动作发生过；
  4. 多 tick 动作前做环境前置检查。

## 四、动态感知与任务作用域：从「静态快照」走向「上下文敏感监听」

> 来源：对实机缺陷（掉落物丢失、站位卡死、中间变数丢失）的深层解法思考（2026-08-16）

### 4.1 实体级动态追踪：解耦「挖掘」与「拾取」

- **核心想法**：
  任务不应在动作触发后就撒手不管，而应**直接监听/追踪动作引发的衍生实体变化**。
  以挖矿为例：方块破裂时，实时捕获生成的 `ItemEntity`（坐标、运动矢量、存活状态）。
- **带来的架构解耦**：
  - **站位更自由**：AI 不必强行走到方块正下方/贴脸处才敢挖，可以在任何合法视线与距离内挖掘；
  - **精准拾取**：挖掘完成后，直接向掉落物实际落点（或弹飞后的静止坐标）发起移动拾取，
    避免掉落物滚落悬崖、飘散未入包，或被熔岩烧毁前抢救；
  - **异常早感知**：若掉落物入岩浆（实体消失），任务能立刻感知并上报「矿物烧毁」，
    而非盲目去原处摸空。

### 4.2 任务作用域缓冲区（Task Scope Buffer / 事务上下文）

- **核心想法**：
  为每个长任务划定一个**局部的时空监控缓冲区（Bounding Box / Tracking Scope）**，
  在任务生命周期内实时记录并响应范围内的状态流转，而非仅依赖任务开始前的一张静态世界快照。

- **三大关键应用场景**：

| 场景 | 机制与收益 |
|---|---|
| **建造与修筑** | 实时记录脚手架/垫脚石的放置坐标。任务完工时，自动回溯「临时方块列表」并逐一拆除清理，恢复现场。 |
| **变数对抗（抗干扰）** | 任务执行期间，若作用域内发生外部扰动（如流水冲刷、苦力怕爆炸破坏已建结构、重力方块塌落），局部监听器立即产生反馈，触发任务内修补或重规划，避免 AI 凭旧记忆一条道走到黑。 |
| **科技整合包机器追踪** | 锁定目标机器的 `BlockEntity` 数据（能量、流体储量、工作进度、报错状态）。无需 AI 频繁调工具跑过去「肉眼检查」，在作用域内即可实时拉取机器完成信号（如：晶体融合完成、ME 终端请求就绪）。 |

### 4.3 架构沉淀：从「轮询世界」到「事件驱动 + 局部订阅」

- **现状缺陷（mc_aiplayer 等方案）**：
  世界感知全靠大模型发起一次 `PerceptionCollector.collect()` 拍全量快照，
  中间过程是盲盒；高频全量扫描又会严重消耗主线程算力（卡 tick）。
- **未来架构雏形**：
  1. **全局层**：维持低频宏观快照（用于大模型高层决策）；
  2. **任务层（Scope）**：任务启动时向游戏引擎注册一个**局部订阅区域**（监听 BlockChange、EntitySpawn、BlockEntityData）；
  3. **确定性执行器**：直接消费局部事件流做微调（捡掉落、拆垫脚、看机器），有重大意外才向上打断唤醒大模型。

## 五、知识获取机制：实时外部知识检索（RAG / 搜索工具化）

> 来源：针对模组时效性、科技整合包复杂配方与玩法的知识供给思考（2026-08-16）

### 5.1 现状与痛点

- **现有开源项目（mc_aiplayer / numen / Mindcraft 等）均未内置联网搜索**：
  - 依赖模型预训练参数内的通用原版知识，或本地硬编码的原版数据（如 `RecipeRegistry`）；
  - 面对**非原版模组（科技包、格雷科技、AE2等）**、私有魔改配方或版本更新时，模型完全处于「盲人」状态，极易产生逻辑幻觉。

### 5.2 解决方案倾向：做法 A（模型工具化实时搜索 / 动态 RAG）

- **核心路线选择**：
  不将搜索逻辑写死在外部控制流，而是将**网络知识检索作为标准 Agent Tool 暴露给大模型**（如 `search_mcmod_wiki` / `search_web`），由模型在遭遇未知机制或配方时自主发起调用。

- **高价值数据源与玩家检索习惯对齐**：

| 数据源 | 解决的痛点 | 落地形式 |
|---|---|---|
| **MC百科（MCMOD.cn）** | 中文整合包与模组玩法教程、流程指引、多模组联动技巧。最符合国内科技包玩家习惯。 | 针对性搜索接口 / 网页解析器，提取条目正文与教程小节。 |
| **模组项目更新日志（Changelog / Release Notes）** | 模组版本迭代带来的特性变动、配方移除、机制重做等**时效性陷阱**，避免 AI 照搬旧版过时攻略。 | GitHub Releases / CurseForge / Modrinth 动态更新日志拉取。 |
| **官方 Wiki / 开发者文档** | 复杂机制细节（如格雷科技电压等级、超导线缆衰减公式、AE2 空间频道规划）。 | 外部特定域名定向检索。 |

### 5.3 机制设计要点（防呆与防卡死）

1. **按需触发，非默认全量塞入**：
   - 只有在模型判定「当前任务涉及未知模组内容」或「配方/机器无法从本地数据解析」时才调用搜索工具；
   - 避免每轮交互都联网引入数百毫秒至数秒的网络延迟与额外 Token 开销。
2. **清洗与精炼（文本降噪）**：
   - 网页 HTML 不直接喂给模型，提取纯文本/Markdown 结构，剔除广告与无关导航，提取核心配方/机制段落。
3. **本地缓存（搜索记忆）**：
   - 同一模组条目或机制的查询结果持久化到本地（如 SQLite/JSON 知识库），形成该世界的专属知识库，第二次遭遇同类问题无需重复联网。

## 七、结构理解：从「方块集合」到「流水线语义」

### 7.1 世界读取的分层能力（科技整合包关键）

| 层 | 能读到什么 | 用什么 |
|---|---|---|
| 方块状态 | 朝向、含水、点燃等属性 | `world.getBlockState(pos)`（原版通用） |
| 方块实体数据 | 箱子内容、熔炉进度、机器内部数值 | `world.getBlockEntity(pos)` + NBT |
| IO 情况 | 物品/能量/流体接口的存量与速率 | Forge capability（`IItemHandler`/`IEnergyStorage`/`IFluidHandler`） |
| 结构语义 | 「这是一台高速熔炉组」 | **无现成方案**，需模式匹配或外挂知识 |

### 7.2 结论：数据可读，语义不可推断

- **数据层完全可行**：任何模组方块的状态/数据/IO 都能通过原版 + capability API 读取——未来项目「感知层」该做的就是这个；
- **语义层现有框架全做不到**：Baritone 只有空间可达性；模型从原始方块数据自主推断「流水线设计」不可靠；
- **案例**：原版「自动矿车高速熔炉组」——AI 能读出每个熔炉进度、每台矿车位置，但**看不出「这是统一结构」**；
- **出路**：结构模式匹配（代码规则）+ 外挂知识（玩家说明 / MC百科 / 更新日志），把「语义」作为可注入的知识层。

## 八、服务端 vs 客户端开发（对 AI bot 的影响）

| 维度 | 服务端（dedicated server） | 客户端 |
|---|---|---|
| 世界数据/方块/实体/BlockEntity | ✅ 权威真实 | ⚠️ 仅「可见部分」 |
| 渲染 / GUI / 声音 | ❌ 无 | ✅ 全部 |
| 输入模拟（点击 GUI） | ❌ 做不到 | ✅ 可以 |
| 物理（重力/流体） | ✅ 真实物理 | 同步服务端结果 |

**对 AI bot 架构的映射**：
- **感知** → 服务端拿权威数据（方块/实体/BlockEntity/capability）；
- **行动执行** → 服务端直接发协议包/改世界（mc_aiplayer 的 `interactionManager.processBlockBreakingAction` 即此路）；
- **GUI 操作** → 只能在客户端实现（GUI 是客户端概念），需「客户端操作 + 服务端验证」桥接——正是「GUI 通用主入口」的架构落点；
- mc_aiplayer 是**纯服务端模组** → 天生点不了 GUI（架构宿命，非疏忽）。

## 九、服务端接口序列化：GUI 语义化 API（核心决策）

> 2026-08-16 架构决策：**放弃「bot 点击 GUI」路线**，改为服务端拦截 + 序列化语义接口。
> 理由：GUI 视觉点击兼容性极低、训练成本大、慢且脆弱。

### 9.1 拦截层：GUI 操作在服务端的真实落点

| 交互类型 | 服务端可拦截? | 拦截点 |
|---|---|---|
| 物品传输（AE 终端取物、机器塞料） | ✅ | `AbstractContainerMenu.clicked()` + `IItemHandler.insert/extract`（AE2 已将网络暴露为 IItemHandler） |
| 机器配置/模式切换 | ⚠️ 部分 | 走 capability / 服务端网络包则能拦；纯客户端视觉效果拦不到（不影响逻辑） |
| 读取方块数据（内容物/能量/魔力） | ✅ 完全 | `BlockEntity` + Forge capability（本就是服务端权威概念） |

**结论**：值钱的操作（物品流动/能量/机器状态）90% 在服务端能力层，天然可拦截；
只需在能力层之上做一层「语义化代理」，无需触碰客户端渲染。

### 9.2 序列化接口格式（骨架）

```json
{
  "id": "tango_mod:crystal_fusioner/extract_output",
  "display_name": "取出输出产物",
  "gui_hint": "相当于打开晶体融合器界面后,左键点击输出槽取出产物",
  "input_schema": { "type": "object", "properties": { "max_count": { "type": "integer" } } },
  "output_schema": { "items": [ { "id": "tango_mod:intelligent_ingot", "count": 1 } ] },
  "side": "server",
  "permission": "owner"
}
```

- `gui_hint` = 「这个调用在 GUI 上对应玩家什么操作」的语义描述——AI 学习的关键；
- `permission` = 操作需玩家授权/白名单（安全性基线）。

### 9.3 三层价值

1. **兼容性**：不做视觉点击，任何暴露 capability 的模组自动可用（科技包 90% 机器均暴露）；
2. **可学习性**：接口自带语义描述 = 游戏内文档，AI 拉取接口清单即可自学未知模组；
3. **自洽性**：拦截器产生的数据流正好喂给「任务作用域缓冲区」（第四章）做机器 IO 实时追踪。

### 9.4 学习路径（AI 如何学会用新方块）

1. AI 遇到未知机器 → 拉取该方块的服务端接口清单；
2. 逐条读 `gui_hint`（= 玩家教程的机器语言版）理解用途；
3. 需要细节时触发联网检索（第五章：MC百科 / 更新日志 RAG）；
4. 尝试调用 → 观察 `output_schema` 结果 → 沉淀进本地知识库（缓存）。

## 附：mc_aiplayer 精读课程要点速查

- **DeepSeekApiClient = 普通 HTTP 客户端**：寄 JSON（messages/tools/max_tokens…）、收 JSON（content/tool_calls/usage）。没有魔法。
- **function calling 闭环**：模型只"说"要调哪个工具 → 游戏执行 → 结果塞回历史 → 再问模型，循环。
- **感知 = 文本**：世界状态 JSON 拼进 user 消息（`Current state:\n{json}`）。
- **异步 + lease**：模型调用不阻塞游戏线程；旧请求回信用 lease 作废。
- **system prompt 是防呆工程**：每条规则对应一个实测失败场景（乱调工具打断任务、边干活边唠嗑、摆烂求人…）。
